Terraform and Infrastructure-as-Code

Learn to manage infrastructure the way software is managed — declared in code, reviewed in pull requests, and converged by machines, from first resource to GitOps pipeline.

Overview

What this sequence is.

This sequence teaches infrastructure as code as an engineering discipline: the declarative mental model that makes it work, the HCL language you write it in, the state file that makes it possible (and dangerous), the provider and module ecosystem you build on, the environment strategies that keep prod safe, the plan/apply discipline that keeps changes reviewable, the GitOps flow that makes git the source of truth, and the testing and safety practices that keep it all from burning down. It is organized around the public Terraform documentation from HashiCorp, with the GitOps modules drawing on the Argo CD project's public docs — but it teaches the engineering underneath, the mental models that transfer to OpenTofu and every other declarative tool.

The core idea is simple to state and deep to operate: describe the infrastructure you want, let a machine compute the difference from reality, and converge the two — repeatably, reviewably, reversibly. Every module here turns one part of that loop into working skill, and the labs build a real pipeline piece by piece.

Who this is for

  • DevOps and platform engineers who provision and operate cloud infrastructure.
  • Backend engineers who want their environments reproducible instead of hand-built.
  • System administrators moving from click-ops and shell scripts to declarative management.

Prerequisites

  • Comfort on the command line and with a text editor; basic Git (clone, commit, push, pull request).
  • Basic cloud concepts: what a VM, a network, and object storage are (any provider).
  • A cloud account with a free tier or a local lab — the early modules run entirely on local providers with zero cloud cost.

How to use this sequence

  • Work the modules in order; the mental model in Module 0 is the lens for everything after.
  • Do the labs with real state files and real plans — IaC is learned by converging, not by reading.
  • Start every lab with local providers (local, random, null) before spending cloud money; the mechanics are identical.
  • Keep every lab configuration in git from the first module — the habit is part of the curriculum.

The curriculum

Eight modules, from mental model to production pipeline.

Module 1

The IaC Mental Model: Declarative State vs. Imperative Steps

Declarative vs imperative configuration

Declarative configuration describes the desired end state ("there is a bucket named X with versioning on"); imperative configuration describes the steps to get there ("create the bucket, then enable versioning"). The difference that matters is what happens on the second run and after a failure: declarative tools converge toward the description regardless of starting point, while imperative scripts replay steps that may fail, duplicate, or conflict. The lab's shell-script-versus-Terraform comparison makes this physical — run each twice, kill each mid-way, and observe which one recovers gracefully. IaC is the declarative bet: describe the what, let the tool figure out the how.

Desired state, actual state, and the diff (delta) between them

Every IaC tool reasons about three things: the desired state (your code), the actual state (what exists in the world), and the diff — the delta between them that the tool plans to execute. Terraform's plan is literally this diff rendered for human review: additions, changes, destructions. The convergence loop is plan (compute the diff), apply (execute it), reconcile (verify reality matches). Understanding that the tool never "remembers what you did" — it only compares desired against actual — explains everything from drift detection to why deleting code deletes infrastructure.

Idempotency: applying the same definition twice produces no further changes

Idempotency means applying the same definition twice produces no further changes — the second apply is a no-op. terraform apply is idempotent because it converges toward declared state: if reality already matches, the diff is empty. An imperative aws s3 mb is not: run it twice and the second run errors (or worse, with scripts that append or duplicate). The checkpoint's one-sentence definition is the interview answer, but the operational meaning is deeper: idempotency is what makes automation safe to retry, safe to schedule, and safe to run after partial failures. Non-idempotent automation is a loaded gun pointed at your infrastructure.

Configuration drift and drift detection

Configuration drift is the gap between what your code declares and what actually exists — born from click-ops changes, manual hotfixes, out-of-band automation, or provider-side defaults changing under you. Three concrete ways it appears in a team AWS account: someone tweaks a security group in the console during an incident, an auto-scaling event changes a count your code pins, a teammate applies from a stale branch. Drift detection is the plan showing changes you didn't author — and the discipline is making code the source of truth: either import the change into code or revert the manual edit, never let the two disagree silently. Refresh-only plans exist precisely for drift review without the intent to change anything.

Convergence loop: plan, apply, reconcile

The convergence loop — plan, apply, reconcile — is the heartbeat of declarative infrastructure. Plan computes the diff and presents it for review; apply executes the diff against real APIs; reconcile (the next plan, or continuous reconciliation in GitOps tools) confirms reality converged. Each phase has its failure mode: plans can be stale (reality changed since), applies can partially fail (leaving half-converged state), reconciliation can flap (something keeps un-converging). The professional habit is treating the loop as a cycle, not a one-shot: after every apply, plan again and expect empty. An empty plan is the system's way of saying "we agree."

Mutable vs immutable infrastructure patterns

Mutable infrastructure changes in place (patch the server, update the config); immutable infrastructure replaces wholesale (build a new image, swap it in, destroy the old). Terraform leans immutable for resources it can replace — changing an AMI means a new instance, not a patched one — because replacement is more predictable than surgery. But some resources are inherently mutable (a database's storage size, a DNS record), and the plan tells you which you're getting: -/+ means replacement, ~ means in-place. The checkpoint's risk ranking falls out here: the destroy-and-recreate change carries the highest risk because replacement means downtime or data movement, while in-place updates are usually non-disruptive. Read the symbols; they encode the blast radius.

IaC benefits: versioning, peer review, repeatable environments

IaC's benefits are why teams adopt it: versioning (every change is a commit with an author and a reason), peer review (infrastructure changes get the same scrutiny as code), and repeatable environments (dev, staging, and prod built from the same definitions). The problems it creates are the price: state management (the mapping between code and reality must be stored, locked, and protected), and blast radius (one apply can touch everything the code describes — which is the point, and the danger). The honest framing this module ends on: IaC doesn't eliminate infrastructure risk, it converts operational risk into code-review risk — which is a trade worth making, because code review scales and heroics don't.

Learning objectives

  • Contrast declarative desired-state definitions with imperative step-by-step scripts in terms of idempotency and failure recovery.
  • Explain configuration drift: how it forms, why it matters, and how a reconciling engine detects it.
  • Describe the core loop of modern IaC: declare desired state, compute a diff, converge reality.
  • Identify which problems IaC solves (repeatability, auditability, review) and which it creates (state management, blast radius).

    2. Run terraform plan and read the drift detection output: the tool names exactly what differs and what it will do about it.
    3. Apply to reconcile, and write down the rule: code is the source of truth, manual changes get absorbed or reverted.

  3. Lab: Create two environments with identical intent but different tooling (one with shell scripts, one with Terraform); document which one survives a partial-failure rerun.

  4. Lab: Simulate a click-ops change and a code change to the same resource, then practice resolving them by making code the source of truth.

Self-check questions

Define idempotency in one sentence and explain why `terraform apply` is idempotent but `aws s3 mb` is not.
Answer: Idempotency: repeated application produces the same end state without extra effects. terraform apply converges to the declared state (second run changes nothing); aws s3 mb is imperative — running it twice errors because the bucket already exists.
List three concrete ways drift can appear in a team-managed AWS account.
Answer: 1) Console click-ops changing a resource Terraform manages. 2) Another team's automation (or a teammate's script) mutating tags, rules, or sizes. 3) AWS-side changes (e.g. default updates, or a resource replaced outside Terraform). The next plan surfaces all three as diffs.
Task: given a plan that shows `~ update in-place` on three resources and `-/+ destroy and recreate` on one, identify which change carries the highest risk.
Answer: Read the -/+ first — destruction is the risk. Identify WHY it forces replacement (usually a ForceNew attribute like AMI or subnet change), confirm the resource is safe to recreate (stateless? data backed up?), and only then approve. Updates in place are routine; replacements need justification.

Module 2

HCL: Resources, Variables, Outputs, Data Sources, Expressions

Block types: terraform, provider, resource, variable, output, data, locals, module

HCL (HashiCorp Configuration Language) organizes infrastructure into block types, each with a job: terraform (version and backend requirements), provider (which APIs to talk to), resource (the managed objects), variable (inputs), output (exposed values), data (read-only queries), locals (named expressions), and module (reusable groups). The file layout convention — main.tf for resources, variables.tf for inputs, outputs.tf for outputs, versions.tf for requirements — isn't enforced by the tool but is enforced by every team you'll join. Learning the block types is learning the vocabulary; the layout convention is learning the grammar teams actually speak.

Resource addressing and implicit/explicit dependency graph (`depends_on`)

Every resource has an address (type.name, like aws_instance.web) and Terraform builds a dependency graph from how addresses reference each other: if one resource's attribute feeds another's argument, the dependency is implicit and ordering is automatic. Explicit depends_on exists for dependencies the graph can't see (a provisioner side effect, an API eventual-consistency gap) — and it's a code smell when overused, because it papers over relationships that should be expressed as references. The rule: references first (they carry data and ordering), depends_on only for the invisible. A clean graph is a correct apply order; a tangled one is where "it worked when I ran it twice" comes from.

Variable types, defaults, validation blocks, and sensitive flags

Variables are typed inputs with optional defaults, validation rules, and a sensitive flag: type list(string) with a default and a validation block (the checkpoint's from-memory exercise) is the shape of every well-designed input. Validation runs before any API calls, failing fast on bad input instead of halfway through an apply. The sensitive flag redacts values from console output — but (Module 7's lesson, previewed) it does not encrypt them in state. Locals, by contrast, are derived values computed from variables and resources — use them when the value is an internal convenience, variables when it's an interface someone else provides.

Data sources as read-only queries against provider APIs

Data sources are read-only queries against provider APIs: the latest AMI matching a filter, the availability zones in a region, an existing VPC's attributes. They let configuration adapt to the world instead of hardcoding it — the checkpoint's "value known only after another resource is created" is either a resource reference (implicit dependency, preferred) or a data source reading what Terraform doesn't manage. The discipline: data sources describe the world's current state at plan time, so a data source that changes between plan and apply is a plan-time bomb — prefer references for anything Terraform itself creates.

Expressions: `for`, ternary, `merge`, `lookup`, splat `[*]`, dynamic blocks

HCL expressions are a small functional language: for expressions transform collections, ternaries branch, merge and lookup combine and query maps, the splat operator [*] projects attributes across a list of resources, and dynamic blocks generate repeated nested blocks from a map. The dynamic-block refactor lab is the canonical use: N security-group rules from one map variable instead of N copied blocks. Built-in functions cover strings, collections, encoding (jsonencode, base64encode), and more — enough that most "I need a script for this" impulses dissolve into an expression. Expressiveness here is what keeps configurations DRY without leaving the declarative model.

Built-in functions for string, collection, and encoding operations

The locals-vs-variables question is about interface versus implementation: variables are the module's public contract (typed, documented, validated), locals are its private computations. The checkpoint's answer: prefer locals when the value is derived from other inputs and never provided directly — a computed naming prefix, a merged tag map. Putting derived values in variable defaults instead scatters logic into the interface and invites callers to override what they shouldn't. Clean modules read like functions: variables in, locals computed, resources declared, outputs out.

File layout conventions: main.tf, variables.tf, outputs.tf, versions.tf

File layout is team communication: versions.tf pins the Terraform and provider versions, variables.tf declares the interface, main.tf holds the resources, outputs.tf exposes the results. Root modules are what you apply; child modules are what's reused — and the layout convention applies inside child modules too, so every module reads the same way. The consistency pays off in review: a reviewer who knows where to look for the interface versus the implementation reviews faster and catches more. Adopt the convention on day one; it's the cheapest professionalism in the ecosystem.

Learning objectives

  • Author `resource` blocks with correct addressing (`type.name`) and attribute references.
  • Distinguish input variables, local values, outputs, and data sources by purpose and data flow.
  • Write HCL expressions: conditionals, for-expressions, splat operators, and type conversions.
  • Structure a configuration directory: provider blocks, version files, and root vs child module layout.

Self-check questions

Write from memory: a variable block with type `list(string)`, a default, and a validation rule.
Answer: variable "subnets" { type = list(string) default = ["10.0.1.0/24"] validation { condition = length(var.subnets) > 0 error_message = "At least one subnet required." } } — type, default, and a condition that fails fast with a clear message.
Explain when `locals` are preferable to `variable` defaults.
Answer: When the value is derived from other values (computed names, transformed lists) rather than an external input. Variables are the module's inputs; locals are internal derived values — putting derived logic in locals keeps the interface clean.

Answer: Reference the attribute directly: subnet_id = aws_subnet.main.id. Terraform builds the dependency graph from references automatically — no explicit depends_on needed for data flow. Never hardcode a value that another resource produces.

Module 3

State: The File, Locking, Remote Backends, and Import

State file as the mapping of resource addresses to provider-side object IDs

The state file is Terraform's memory: it maps each resource address in your configuration to the real object ID the provider created, and it caches the object's attributes. Three things live in state that aren't in your .tf files (the checkpoint's answer): the provider-assigned IDs, the cached attribute values from the last apply, and the dependency graph metadata Terraform needs for ordering. Without state, Terraform can't plan — it wouldn't know which real objects correspond to which configuration blocks. This is why "delete the state file" is never a fix: it's amnesia, and the next plan will try to recreate everything (or worse, adopt nothing and collide).

State locking (e.g., DynamoDB, native backend locks) and why concurrent writes corrupt state

State is a shared, mutable file, so concurrent writes corrupt it — state locking exists to serialize access. Backends implement locking differently (DynamoDB conditional writes for the S3 backend, native locks in Terraform Cloud, lease mechanisms elsewhere), but the principle is universal: one writer at a time, and a crashed run can leave a stale lock that must be force-unlocked with the lock ID. The lab's kill-mid-apply exercise teaches the recovery: identify the stale lock, verify no run is actually active, force-unlock with the recorded ID, and re-plan. Locking makes team workflows safe; knowing the unlock procedure makes them resilient.

Remote backends: S3/GCS/Azure with versioning and encryption

Remote backends store state outside your laptop — S3, GCS, Azure Blob, Terraform Cloud — with versioning and encryption, turning the state file from a local artifact into team infrastructure. Versioning means every state change is recoverable (the backend keeps history); encryption at rest protects the secrets state inevitably contains (Module 7's lesson). The migrate-state lab moves a local state to remote with init -migrate-state, which copies the state and rewrites the backend config — the promotion from solo to team workflow in one command. Backend choice is organizational: whoever can read the backend can read your secrets, so access control on the backend is access control on everything.

State versioning, backups (`terraform.tfstate.backup`), and manual inspection

terraform import brings existing infrastructure under management: you give it the resource address and the provider ID, and it writes the binding into state — but it writes no configuration, so the mandatory follow-up is writing the matching .tf block until plan is empty. The checkpoint's rename scenario resolves here too: when a teammate renames a resource in code, the plan shows destroy-and-recreate (new address, no state binding); terraform state mv rebinds the old address to the new one, and the plan goes quiet. Import and mv are the two state-surgeries every practitioner needs: one adopts the unmanaged, the other renames without recreation.

`terraform import` addressing and the follow-up of writing matching configuration

The state surgery toolkit — mv (rename addresses), rm (forget a resource without destroying it — it becomes unmanaged, not deleted), pull/push (download/upload state for inspection or repair), replace-provider (migrate resource bindings across provider renames) — is powerful precisely because it edits the mapping without touching reality. rm is the subtle one: the resource still exists in the cloud, Terraform just stops managing it, which is either exactly what you wanted (handing off to another configuration) or a drift time-bomb. Every surgery ends the same way: run plan and confirm it shows what you intended — the state is too important for unverified edits.

State surgery commands: `mv`, `rm`, `pull`, `push`, `replace-provider`

State versioning and backups are the safety net under the surgeries: terraform.tfstate.backup is written before destructive operations, remote backends keep version history, and manual inspection (terraform state show, terraform state list) lets you read the mapping before you edit it. The recovery hierarchy for state problems is: re-run the failed command (transient), restore from backup/version history (corruption), and only then hand-editing — in that order, because each step down is more dangerous. The lab's stale-lock recovery plus a backup-restore drill covers the two failures you'll actually meet. State is the one file whose loss is unrecoverable by re-running code — treat it accordingly.

Workspaces as named state partitions within one backend

Workspaces are named state partitions sharing one configuration and one backend key prefix: terraform workspace new staging gives you a second state file for the same code. They're convenient for ephemeral environments (feature branches, personal sandboxes) and dangerous for strong isolation — the checkpoint's risk: same backend, same credentials, same code path, so a wrong-workspace apply hits the wrong environment with nothing but a name to stop you. The environment module's verdict (next) stands: workspaces for the ephemeral, directories with separate backends and credentials for anything that matters. Know which you're in at all times — the workspace name in the prompt is load-bearing.

Learning objectives

  • Explain what the state file records (bindings between configuration and real objects) and why Terraform cannot function without it.
  • Configure a remote backend with state locking to make team workflows safe.
  • Execute `terraform import` to bring pre-existing infrastructure under management, and `terraform state mv` to refactor without recreation.
  • Recover from common state failures: lock held by a crashed run, and state/backend mismatch.

Self-check questions

Name three things stored in the state file that are NOT in your .tf files.
Answer: 1) Real-world resource IDs assigned by the provider. 2) Current attribute values read from the API (the "actual" side of the diff). 3) Sensitive values (passwords, keys) in plaintext — plus dependency mappings and the serial/lineage metadata.
Explain why committing terraform.tfstate to git is an anti-pattern.
Answer: The state contains secrets in plaintext (leaked to every repo clone), it changes on every apply (merge-conflict magnet), and concurrent applies corrupt it without locking. State belongs in a remote backend with locking and encryption.
Task: plan shows a resource will be recreated after a teammate renamed it in code — which state command avoids the recreation?
Answer: terraform state mv (or a moved block) renames the resource in state without destroying it — the rename is then a no-op instead of a destroy/create. The lesson: renames are state operations, not code edits alone.

Module 4

Providers and Modules: Registry, Version Constraints, Authoring

Provider as a plugin bridging Terraform core to an API surface

A provider is the plugin bridging Terraform core to an API surface — AWS, Azure, GCP, and hundreds of others — translating resource blocks into API calls. Terraform core itself knows nothing about clouds; every create/read/update/delete goes through the provider's schema. This architecture is why provider upgrades can change plans: a new provider version may rename attributes, change defaults, or alter diff behavior, and your configuration hasn't changed at all. The provider is a dependency with the same upgrade discipline as any library — pin it, read its changelog, test the upgrade.

`required_providers` and `required_version` constraint syntax

Version constraints live in required_providers (per-provider source and version) and required_version (Terraform core itself), using operators with precise semantics: >= is a floor, ~> is the pessimistic operator that allows only the rightmost-version-component to increment. The checkpoint's constraint — patch updates within 5.31.x but nothing newer — is ~> 5.31.0 (allows >= 5.31.0, < 5.32.0), while ~> 5.31 would allow up to 6.0. The lock file (.terraform.lock.hcl) records the exact provider builds selected, so init is reproducible across machines. Constraints declare intent, the lock file records reality — and production pins both, upgrading on a cadence, not by surprise.

Public vs private module registries; module source addresses

Modules are reusable Terraform packages addressed by source: the public Registry (versioned, e.g., source with a version pin), private registries, git URLs, or local paths. A module's interface is its variables.tf (the contract: typed, documented inputs) and outputs.tf (what it exposes), plus a README with examples — the interface design determines whether the module is a joy or a trap. The authoring lab's logging-bucket module practices the discipline: naming convention, encryption, lifecycle, all parameterized, no hardcoded account specifics. Good modules are opinionated about the right things (security defaults) and parameterized about the variable things (names, sizes) — and minimal in side effects.

Module interface design: variables.tf contract, outputs.tf, README with examples

Version pinning for modules is stricter than for providers: pin Registry modules to exact versions in production, because a minor version bump can change a default (the checkpoint's scenario — the new default you didn't ask for, arriving via a loose pin). The pin lives in the module block's version argument; upgrading is a deliberate version-bump commit with a reviewed plan. The lab's loosen-the-pin-then-init-upgrade exercise shows the alternative: what changes when you let the resolver pick newest. Registry modules are someone else's code running with your credentials — treat version selection with the seriousness that implies.

Version pinning strategy for production: exact pins, lock file, upgrade cadence

Provider schema changes are the hidden upgrade risk: a major provider version may rename arguments, require new ones, or change resource behavior, and the plan will show you the consequences — if you read it. The scratch-workspace upgrade lab practices the procedure: read the changelog first, adjust configuration, then review the plan diff before applying. Minor provider upgrades are usually safe; major ones are projects. The discipline that saves you: never upgrade providers in the same change as infrastructure changes — the plan should show exactly one kind of news at a time.

Provider schema changes and why upgrades can alter plans

terraform init resolves and installs the dependency tree: provider plugins per the lock file (or the newest allowed on first init), and modules per their source addresses. The plugin cache (a shared directory across configurations) speeds this up and insulates you from registry outages. Understanding init matters when it fails: network issues, an unsatisfiable constraint, a moved module source — each has a distinct error, and "just delete .terraform and re-init" is the correct fix more often than it should be. Init is deterministic given the lock file; if it's not, the lock file is the first suspect.

`terraform init` dependency resolution and the plugin cache

Module interface design is API design: variables.tf is the contract (every input typed, described, validated, with sane defaults only where safe), outputs.tf is what callers may depend on (stable, documented), and the README with examples is the documentation no one reads until they need it — which is exactly when it must exist. The terraform-docs lab enforces the documentation mechanically: generated input/output tables in the README, checked by a pre-commit hook, so docs can't drift from code. A module without documented inputs is a guessing game; a module whose docs are generated from the code is a contract you can trust.

Module 5

Workspaces and Environments: Isolation Strategies and tfvars Layering

Workspaces as alternate state files sharing one configuration and backend key prefix

Workspaces give you alternate state files for one configuration: terraform workspace new feature-x, and your applies land in a separate state under the same backend key prefix. The use case is ephemeral environments — a developer's sandbox, a short-lived feature test — where spinning up full backend infrastructure per environment is overkill. The mechanism is simple and the danger is proportional: it's just a name, and names are easy to get wrong. Workspace-aware configurations often interpolate the workspace name into resource names to avoid collisions — which works until two workspaces need genuinely different shapes, at which point the single-codebase constraint chafes.

Directory-per-environment as the stronger isolation boundary (separate state, separate credentials)

Directory-per-environment is the stronger isolation boundary: envs/dev and envs/prod as separate root configurations (sharing child modules), each with its own backend, its own state, and — critically — its own credentials. The isolation is structural, not nominal: a prod apply requires prod credentials and the prod directory, so accidents need multiple simultaneous mistakes. The promotion lab (dev applied, module version bumped to prod) practices the workflow the model enables. When the question is "how do we make sure dev experiments can't touch prod," directories are the answer workspaces can't give.

tfvars layering: `terraform.tfvars`, `*.auto.tfvars`, `-var-file` precedence order

Variable values layer with a defined precedence, lowest to highest: environment variables (TF_VAR_name), then terraform.tfvars, then terraform.tfvars.json, then *.auto.tfvars (alphabetical), then -var-file flags, then -var flags. The checkpoint's ranking resolves: TF_VAR_x < terraform.tfvars < x.auto.tfvars < -var. The layering strategy this enables: common defaults in terraform.tfvars, environment specifics in prod.auto.tfvars, secrets via environment or -var (never committed), one-off overrides with -var. The precedence lab demonstrates each override winning in turn — know the order cold, because "why did my value lose" is always a precedence question.

Environment promotion: same module version, environment-scoped inputs

Environment promotion means the same module version flows dev → staging → prod with environment-scoped inputs differing: promotion bumps the module version pin in the next environment's configuration, and the apply there is reviewed like any other change. The runbook lab writes the exact command sequence — plan in staging, approve, apply, bump prod pin, plan in prod, approve, apply — because promotion performed from memory is promotion performed wrong eventually. The principle: artifacts (module versions) promote, environments don't drift apart, and every promotion is a reviewed plan. "It worked in dev" becomes evidence, not hope, when the artifact is identical.

Backend key naming schemes per environment

Backend key naming schemes make the isolation visible: one state file per environment per region, with keys like env:/prod/network/terraform.tfstate or s3://bucket/prod/us-east-1/app.tfstate. The design task in the checkpoints — three environments, two regions — resolves to six state files under a predictable key tree, each with its own lock. Predictable keys are operational tooling: on-call can find any environment's state without asking, automation can iterate the tree, and access policies can scope per prefix. Name the keys like you'll be reading them at 3 AM, because you will be.

When workspaces are acceptable (ephemeral feature environments) vs when they are not

The workspaces-vs-directories verdict: workspaces are acceptable for ephemeral, low-stakes environments where the cost of full isolation exceeds the risk — feature sandboxes, personal experiments. They are not acceptable for prod/staging separation, where the risks (one shared backend, one credential set, one typo away from the wrong environment) dwarf the convenience. The concrete risk the checkpoint asks for: applying while in the wrong workspace hits the wrong environment's state with no structural barrier — directories with separate credentials make that mistake require deliberate credential misuse. Choose the isolation model by the blast radius, not by the typing effort.

Module 6

Planning Workflows: plan/apply Discipline, Targeted Changes, Destroy Hygiene

`terraform plan -out` artifact as the reviewed unit of change

The plan file (terraform plan -out=tfplan) is the reviewed unit of change: a saved, inspectable artifact describing exactly what apply will do. The discipline is plan → review → apply the saved file, never re-planning at apply time — because the world may have changed between your review and the apply, and the saved plan is what you actually approved. In CI, the plan file (or its JSON rendering) is the artifact the pipeline carries from the plan job to the apply job, often as a pull-request comment. "Apply what you reviewed" is the whole rule; the saved plan file is how you enforce it.

Plan output notation: `+`, `~`, `-`, `-/+` and what triggers replacement

Plan output notation is a compact language: + creates, ~ updates in place, - destroys, -/+ destroys and recreates (replacement), <= reads a data source. Replacement (-/+) deserves special attention: it means downtime or data movement for that resource, and unexpected replacements in a plan are the number-one thing reviewers hunt for. The investigation habit for a surprise -/+ on a stateful resource (the checkpoint's task): identify which argument change forced replacement (the plan says), decide whether the change is intended, and if it is, plan the data migration before approving. Read every symbol; the plan is telling you the blast radius in shorthand.

`-target` / `-replace` semantics and the partial-state risk they introduce

-target restricts the apply to specific resources and their dependencies; -replace (the modern successor to taint) forces replacement of specific resources. Both are surgical tools with a partial-state risk: targeting skips the rest of the graph, so the resulting state may not match the full configuration — the next full plan will show the outstanding diff, which is fine if you follow through and dangerous if you forget. Justified uses: recovering a single broken resource, or replacing one instance without touching the fleet. The anti-pattern is routine targeting as a workflow — if you always -target, your configuration has stopped describing your infrastructure, and the plan has stopped being trustworthy.

`lifecycle` meta-arguments: `prevent_destroy`, `create_before_destroy`, `ignore_changes`

Lifecycle meta-arguments tune resource behavior: prevent_destroy makes the plan fail rather than destroy the resource (the lab's database exercise — attempt removal, handle the deliberate error, then decide consciously); create_before_destroy reverses the replacement order (new resource up before old goes down — zero-downtime replacement where the provider supports it); ignore_changes tells Terraform to stop managing specific attributes (for values an external system owns, like an autoscaler's desired count). Each is a deliberate exception to the declarative model, and each should carry a comment explaining why — future reviewers need to know the exception is load-bearing, not accidental.

Refresh-only plans and their role in drift review

Refresh-only mode (plan -refresh-only / apply -refresh-only) updates the state to match reality without changing anything — the drift-review tool. It answers "what changed out-of-band?" as a plan that proposes no infrastructure changes, only state updates. The workflow: refresh-only plan to see the drift, decide per drift whether to import it into code or revert it in the world, then run the normal plan/apply to converge. Scheduled refresh-only runs (nightly, in CI) turn drift detection from an incident response into a routine — the dashboard that says "reality and code agree" (or names exactly where they don't).

`terraform destroy` vs removing configuration then applying

Destroy hygiene treats teardown as seriously as setup: terraform plan -destroy renders the teardown for review (the lab's walk-the-order exercise — read what goes away in what order), staged teardown handles dependencies (data layers after the apps that use them, or however your graph demands), and prevent_destroy on the truly irreplaceable (production databases, state buckets) makes "oops" structurally impossible. terraform destroy versus removing configuration and applying differ in intent signaling: destroy says "this whole configuration goes away," config-removal says "these resources are no longer described" (and without prevent_destroy, they get destroyed either way). Teardown deserves the same review discipline as construction — the plan -destroy output gets read, not skimmed.

Applying the saved plan file (not re-planning) in automation

Automation must apply the saved plan file, not re-plan at apply time — the checkpoint's "why": the plan you reviewed is a point-in-time diff, and re-planning substitutes a new diff you didn't review. The CI shape is: plan job saves the plan file and posts its human-readable rendering as a PR comment; approval gates on human review; the apply job (on merge, or manual trigger) applies the saved file. If the plan file is stale (its recorded state no longer matches), apply fails rather than applying something unreviewed — which is the safety property you want. The pipeline's contract with the reviewer is simple: what you read is what runs, bit for bit.

  • Diagnose plan output: additions, changes, destroys, replacements, and data-source reads.

Module 7

GitOps Flow: Git as Source of Truth, Argo CD Sync, PR Workflows for Infra

Git as the single source of truth; declarative manifests and drift reconciliation

The GitOps contract is simple: git holds the desired state, and an agent running in the cluster continuously reconciles reality toward it. No one applies from a laptop to production — changes flow through commits, and the cluster converges itself. This inverts the Terraform workflow's human-driven apply: the actor converging state is the in-cluster agent (Argo CD, Flux), not the engineer. The payoff is auditability (every change is a commit), self-healing (manual edits get reverted), and a single source of truth that survives laptop loss. The checkpoint's contrast is the mental model: terraform apply from a laptop means you are the reconciler; Argo CD auto-sync means the cluster reconciles itself, and you're the author of intent.

Argo CD Application CRD: source repo/path, destination cluster/namespace

Argo CD's Application custom resource is the unit of GitOps: it names a source (repo, path, target revision) and a destination (cluster, namespace), and the controller does the rest. Sync status reports whether the cluster matches git (Synced vs OutOfSync); health status reports whether the resources themselves are healthy (Healthy, Degraded, Progressing) — and the two are independent: an app can be Synced but Degraded (git's desired state is itself broken) or OutOfSync but Healthy (someone hand-edited a working deployment). Reading both statuses is the GitOps equivalent of reading plan output: sync says "do we match intent," health says "is intent any good."

Sync status vs health status; out-of-sync detection and diff view

Auto-sync, prune, and self-heal are the automation dials, each with blast-radius tradeoffs. Auto-sync applies git changes without human approval — fast, and exactly as dangerous as your review process. Prune deletes cluster resources that git no longer describes — the garbage collector that prevents orphan sprawl, and the feature that deletes production when someone force-pushes a bad commit. Self-heal reverts manual cluster edits back to git's state — the drift-killer that also reverts your emergency hotfix. The lab's bad-commit-then-git-revert exercise teaches the recovery shape: with auto-sync on, the fix is a revert commit, not a kubectl command — the GitOps way, even under pressure.

Auto-sync, prune, self-heal: power and blast-radius tradeoffs

Sync waves and hooks order multi-resource rollouts: CRDs before the custom resources that use them, namespaces before the workloads in them, database migrations before the app version that needs them. Waves assign phases (negative waves run first), hooks run jobs at sync lifecycle points (pre-sync, post-sync) — the machinery for "this must happen before that" inside a declarative world. Without ordering, a sync that creates a CR and its CRD simultaneously races — and races are just bugs with timing. Design your Applications' wave structure deliberately for anything with cross-resource dependencies; the default (everything at once) is correct only for independent resources.

Sync waves and hooks for ordered rollouts (CRDs before workloads)

PR-driven infrastructure workflows bring code review to operations: CI runs fmt, validate, and plan on every pull request, posts the plan as a PR comment, and merge is blocked until approved (the atlantis-style flow, with CODEOWNERS routing reviews to the right humans and protected branches enforcing the gates). The plan-on-PR is the reviewable unit — reviewers read infrastructure diffs the way they read code diffs. The security-group-0.0.0.0/0 checkpoint resolves here: it's caught in the PR plan review (human) and by policy-as-code gates (automated, next module) — defense in depth at the change's front door, before it ever reaches an apply.

PR-driven infra: atlantis-style plan comments, CODEOWNERS, protected branches

Secrets in GitOps can't live in git as plaintext, so the ecosystem offers three patterns: Sealed Secrets (encrypt with the cluster's public key; only the in-cluster controller can decrypt), External Secrets Operator (git holds references; the operator fetches actual values from a vault at sync time), and SOPS-encrypted values (age/PGP-encrypted files decrypted by the sync pipeline). The lab's SOPS-or-Sealed-Secrets exercise practices one end to end: commit the encrypted form, watch the cluster materialize the real Secret. The rule is absolute — plaintext secrets in git are a breach, not a shortcut — and the pattern choice is organizational: who holds the decryption keys determines your trust model.

Secret strategies: Sealed Secrets, External Secrets Operator, SOPS-encrypted values

The full GitOps loop closes when Terraform-style planning meets GitOps-style reconciliation: PR proposes (plan as comment), humans and policy gates approve, merge applies (for Terraform via apply-on-merge; for cluster state via Argo CD sync). Drift has two handlers now: Terraform's refresh-only plans for the cloud resources, Argo CD's self-heal for the cluster resources — both reporting "reality vs. intent" continuously. The operating principle: every change to production is a git commit, every git commit is reviewed, and the machines do the converging. Teams that reach this state stop asking "who changed prod?" — the answer is always in the log.

Module 8

Testing and Safety: Plan Review, Policy-as-Code, Secrets Handling

Plan review checklist: replacements, permission changes, data exfiltration surface

The plan review checklist is the human gate: scan for replacements (-/+ on anything stateful gets investigated, never rubber-stamped), permission changes (IAM, security groups — the 0.0.0.0/0 hunt), and data exfiltration surface (new public endpoints, logging destinations, cross-account access). The ordered gates from commit to apply (the checkpoint's task): fmt and validate (syntax), plan rendering (human review), policy-as-code evaluation (automated guardrails), approval (human sign-off), then apply of the saved plan. Each gate catches a different failure class; skipping one is betting that class doesn't apply to your change. The checklist isn't bureaucracy — it's the accumulated scar tissue of the industry, and it works.

Policy-as-code engines: Sentinel/OPA/Conftest evaluating plan JSON

Policy-as-code engines evaluate the plan's JSON against written rules: Sentinel, OPA, and Conftest all consume the planned changes and pass or fail the build. The guardrails are the organization's non-negotiables expressed as code — mandatory tags, encryption-at-rest required, region allowlists, no 0.0.0.0/0 ingress. The lab's Conftest/OPA rule (fail on unencrypted storage or missing tags) is the template: write the rule in pseudocode first, then in the engine's language, then watch it catch a violating plan. Policy-as-code scales review: humans judge intent, machines enforce invariants — and the machines never get tired or rushed.

Common guardrails: mandatory tags, encryption-at-rest, region allowlists, no `0.0.0.0/0` ingress

The common guardrails encode hard-won lessons: mandatory tags (cost allocation and ownership — untagged resources are unowned resources), encryption at rest (no unencrypted storage, ever), region allowlists (data residency and cost control), and no public ingress except through reviewed exceptions. Each guardrail should map to a real incident class the organization has seen or plausibly fears — guardrails without rationale become ritual, and ritual gets bypassed. Start with the four in the lab, add yours from your incident history, and review the set annually: the threat model evolves, and the guardrails must follow.

`sensitive = true` markings and why state still contains the values

sensitive = true does not encrypt the value in the state file — it only redacts it from console output and logs. The checkpoint's answer is the critical understanding: the value sits in state in plaintext, readable by anyone with backend access, which is why the lab has you prove it by inspecting the state after apply. Real secret handling means secrets never enter state as plaintext: vault data sources (read at apply time, still landing in state — know this), environment-backed credentials for providers, and short-lived tokens that expire before they can be abused. The rule: state is a secrets-bearing artifact; encrypt the backend, restrict its readers, and minimize what flows through it.

Secrets injection: vault providers, environment-backed credentials, short-lived tokens

Secrets injection patterns keep credentials out of code: provider credentials from environment variables or identity federation (never hardcoded), application secrets from vault data sources or external secret operators, and short-lived tokens (cloud IAM roles, dynamic vault credentials) instead of long-lived keys wherever the provider supports them. Rotation strategy is part of the design: how often, how automated, what breaks if a rotation fails — a secret you can't rotate is a secret you don't control. Least-privilege provider credentials complete the picture: the CI role that applies staging can't touch prod, because it was never granted access. Credentials are infrastructure too; manage them with the same rigor.

State encryption at rest and access control on the backend

State encryption at rest and backend access control are the last line for the secrets state inevitably holds: enable the backend's server-side encryption (with a customer-managed key where compliance demands it), version the state for recovery, and scope IAM so only the automation roles and break-glass humans can read it. Audit who accessed the backend — state reads are sensitive operations, and the access logs are the evidence. The tabletop incident lab (bad apply deleted a queue — recover via state history and git revert) practices the recovery that encryption and versioning enable: the blast happened, the state history shows exactly what was there, and the revert restores it. Backups you can't restore from are theater; rehearse the restore.

Blast radius: module granularity, environment staging, canary applies

Blast-radius reduction is architecture: small modules (a change touches one concern, not the platform), environment staging (dev first, prod last, with the promotion discipline from Module 4), and canary applies (roll the change to a slice before the fleet). Each limits how much one bad change can break — and "how much can one apply break" should be a question you can answer for every configuration you own. The rollback plan is part of every change: git revert plus apply for Terraform-managed resources, with state history as the backstop. Design so that the worst case is bounded and recoverable, because the worst case is a matter of when, not if.

Learning objectives

  • Build a layered review process: human plan review, automated lint/validate, and policy gates before apply.
  • Express infrastructure guardrails as policy-as-code (allowed regions, required tags, no public buckets).
  • Handle secrets correctly: never in state-visible plaintext, rotation strategy, least-privilege provider credentials.
  • Design a blast-radius reduction strategy: small modules, staged rollouts, and rollback plans.

Self-check questions

Does `sensitive = true` encrypt the value in the state file? Explain the real protection it provides.
Answer: No. sensitive = true only suppresses the value from CLI output and logs — the state file still holds it in plaintext. Real protection: remote backend encryption, minimal state access, and keeping secrets out of Terraform where possible (use vault data sources with short-lived values).
Write one OPA/Conftest-style rule in pseudocode that blocks public S3 buckets.
Answer: deny[msg] { some r in input.resource.aws_s3_bucket_acl; r.acl == "public-read"; msg := sprintf("public ACL on %s", [r.name]) } — iterate the planned resources, deny any public ACL with a message naming the offender.
Task: list the ordered gates a production apply pipeline should enforce from commit to apply.
Answer: 1) fmt/validate + lint. 2) plan on PR (visible diff). 3) Policy-as-code gate (OPA/conftest). 4) Human approval of the plan. 5) Apply the SAVED plan file from CI. 6) Post-apply drift check. Each gate's output is evidence the next gate trusts.

Concept glossary

The words this sequence uses.

  • Declarative vs imperative — declarative says what the infrastructure should be; imperative says the steps to get there. IaC is declarative: you describe desired state, the tool converges to it.
  • Desired state, actual state, drift — desired state is your configuration, actual state is what the provider reports, and drift is the delta between them; drift detection is how you find changes made outside your code.
  • Idempotency — applying the same definition twice produces no further changes; the property that makes plan/apply safe to re-run.
  • Convergence loop — plan, apply, reconcile: preview the diff, apply it, and reconcile reality back to the declared state.
  • HCL — HashiCorp Configuration Language: the block types are terraform, provider, resource, variable, output, data, and locals; file layout conventions (main.tf, variables.tf, outputs.tf, versions.tf) keep modules readable.
  • State file — the mapping of resource addresses to provider-side objects; locking (DynamoDB, native backend locks) prevents concurrent writes, and remote backends (S3/GCS/Azure with versioning and encryption) keep it safe and shared.
  • terraform import — brings an existing resource under management; it only addresses the state — you still write the matching configuration afterward.
  • Workspaces — named state partitions within one backend; one configuration, several isolated state files.
  • Provider / module — a provider is the plugin bridging Terraform core to an API surface; a module is a packaged, version-pinned unit of configuration from the registry or your own repo.

Worked procedure

Ship one reviewed module, end to end.

  1. Write the resource blocks. Declare resources with variables (typed, validated, sensitive where needed), outputs, and data sources as read-only queries — keep main.tf, variables.tf, outputs.tf, and versions.tf separated.
  2. Pin and init. Set provider version constraints in versions.tf, then terraform init — unpinned providers are how a Tuesday becomes an incident.
  3. Read the plan. Run terraform plan and read the diff like a code review: every create, update, and destroy should be expected before it happens.
  4. Apply, then plan again. Apply, then immediately re-plan — a clean second plan (no changes) proves idempotency and catches drift early.
  5. Move state to a remote backend. Backend with versioning and encryption plus locking; keep terraform.tfstate.backup semantics in mind and never hand-edit state you can manage with mv/rm/import.
  6. Write the plan/apply runbook. Document who runs what, in which workspace, with which approvals — the runbook is the portfolio artifact.
