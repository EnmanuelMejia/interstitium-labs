The Local AI Lab

Run capable AI models on your own hardware: quantization and the GGUF format, the runtime layer, desktop apps, web interfaces, honest production serving — and a lab track from first install to your own API.

Start the sequence All sequences

SCIENTIA OMNIA VINCIT

The sequence

Your machine is the cloud.

Most people experience AI as an API endpoint: prompts travel to someone else's datacenter, and answers come back. But the open-weight era changed the equation — capable models can now run on ordinary hardware, fully offline, with no account, no per-token bill, and no third party reading your prompts. The machinery that makes this possible — quantization formats, cross-platform inference runtimes, desktop apps, self-hosted interfaces, and production serving stacks — is what this sequence teaches.

The field is layered, and the tools sit at different layers. An inference runtime (llama.cpp, Ollama, LocalAI) executes model weights on your hardware. A desktop app (LM Studio, Jan, GPT4All, TextGen) wraps a runtime in a friendly interface. A web UI (Open WebUI, koboldcpp) puts a chat surface in your browser. A serving stack (vLLM) is a different animal entirely — production-grade throughput for many concurrent users, not a desktop tool. This sequence is honest about which layer each tool occupies, because picking the wrong layer is the most common beginner mistake.

You will learn why local inference matters (privacy, latency, cost, sovereignty), how quantization and the GGUF format shrink models onto real hardware, how the runtimes differ, how to size hardware for a model, how to read a model license before using weights commercially, and — in the final lab track — how to go from a fresh install to a model you can both chat with and call as an API from your own code.

Who this sequence is for

  • Engineers and technical users who want AI capability without sending data to third parties.
  • Developers building features on local models who need to understand runtimes, APIs, and hardware trade-offs.
  • Homelab and self-hosting practitioners extending their stack into local inference.

Prerequisites

  • Comfortable with the command line on Windows, macOS, or Linux.
  • A machine with enough memory to hold a small model (see Module 7's qualitative tiers — ordinary laptops qualify for small models).
  • No GPU required to start; a GPU accelerates everything later. No machine-learning background needed — the sequence explains the ideas it uses.

How to use it

  • Work the modules in order: the why (privacy, quantization) is the vocabulary the tooling chapters assume.
  • Install one runtime and run one model in Module 8's lab track — reading about inference is abstract; watching tokens stream from your own machine is concrete.
  • Every project linked below is the authority on itself. This guide teaches the mental models; the project's own docs are the reference for exact flags and versions.
  • Keep the honesty discipline this sequence models: categorize every tool by its layer, and check what each layer actually promises before adopting it.

The curriculum

10 modules, in order.

Module 1

Why Local: Privacy, Latency, Cost, Sovereignty

Learning objectives

  • State the privacy, latency, cost, and sovereignty arguments for local inference
  • Distinguish what local inference protects against and what it does not
  • Recognize when a cloud API remains the rational choice

Key concepts, explained

The API model and its data trail

In the cloud-API model, every prompt leaves your machine: it is logged by the provider's infrastructure, subject to the provider's retention and training policies, billed per token, and unavailable when the network or the provider is down. For casual use that is a fine trade. For sensitive documents, proprietary code, or regulated data, it is a data trail you chose to create.

Local inference inverts the model: the weights live on your disk, the computation happens in your RAM, and prompts never leave the building. The attack surface shrinks from "every system your provider operates" to "the machine in front of you."

Privacy: prompts that never leave

The privacy argument is the strongest one. A locally running model cannot phone home your documents, because there is no home to phone — assuming the application itself is honest, which is why this sequence favors open-source runtimes whose behavior is auditable. No terms-of-service change can retroactively expose prompts that were never transmitted.

This is not absolute: apps can bundle telemetry, plugins can call out, and anything you paste into a browser-based UI lives in that browser's context. Local is a necessary condition for prompt privacy, not a sufficient one — verify each application's network behavior rather than assuming "local" means "silent."

Latency: inference at memory speed

Cloud inference adds round-trip latency to every interaction; local inference is bounded only by your hardware's memory bandwidth and compute. Small models on a modern laptop stream tokens with no network hop at all, which makes local models feel snappier than their size suggests for interactive work.

The honest qualifier: absolute throughput on consumer hardware is lower than a datacenter cluster's. Local wins on latency and responsiveness for single-user interactive use; it does not win on raw tokens-per-second against industrial infrastructure.

Cost: hardware once, inference free

Cloud inference is metered: every token costs money, forever. Local inference is capitalized: you pay for the hardware once (or you already own it), and then each additional prompt costs electricity. Heavy, sustained usage flips the economics decisively toward local.

The honest qualifier: the hardware has to be capable enough for the model you want, and capable hardware is not free. The cost argument holds when you already own the machine or when usage volume would otherwise generate a large API bill.

Sovereignty: the open-weight era

Open-weight models — weights published for download, as opposed to models available only behind an API — made local inference possible at all. A growing ecosystem of openly distributed models means you can choose, inspect, fine-tune, and keep running a model even if its publisher pivots, deprecates it, or changes its behavior. You hold the artifact, not a lease on someone else's.

Sovereignty is also about continuity: a local model works on a plane, in an outage, or after a vendor shuts down. The model on your disk does not get a deprecation email.

When the cloud still wins

Intellectual honesty requires the other side. Frontier-scale models do not fit on consumer hardware — if you need the largest models' capabilities, you rent them. Rapidly changing tasks benefit from providers' constant model updates; your local model is frozen at download. And if you have no hardware at all, the cloud is the only option. Choose the layer that fits the job.

Hands-on labs

  1. Write your threat model before installing anything
    List what you want local AI for, what data you would feed it, and what "private" must mean for your use case. The list becomes the yardstick every tool choice is measured against.
  2. Audit one application's network behavior while running locally
    Run a local model, then watch your machine's outbound connections while you chat with it. The exercise teaches the difference between "runs locally" and "never transmits" — a distinction marketing copy likes to blur.
  3. Price one month of your heaviest imagined usage as API tokens versus hardware you own
    Estimate tokens per day, multiply by a provider's published per-token price, and compare against the sunk cost of your machine. The crossover point is usually lower than people expect.

Self-check

  • What data trail does a cloud API prompt create that a local prompt does not?
  • Give one way a nominally "local" app could still leak your prompts.
  • When is paying for a cloud API the rational choice despite owning hardware?

Module 2

Quantization and GGUF: Fitting Models on Real Hardware

Learning objectives

  • Explain quantization as a precision-for-memory trade
  • Describe what the GGUF container format carries and why it exists
  • Read a model card and license before downloading weights
  • Navigate the Hugging Face GGUF ecosystem as a model source

Key concepts, explained

Quantization: fewer bits per weight

A model's weights are numbers, and numbers cost memory per bit of precision. Quantization stores those weights at reduced precision — commonly 8, 6, 5, 4, 3, or 2 bits per weight instead of 16 — trading a measured amount of output quality for a large reduction in memory and a speedup in inference. It is the single technique that moved capable models from datacenters onto laptops.

The trade is graceful, not cliff-like: moderate quantization preserves most capability, and the quality loss concentrates in the deepest cuts. This is why the ecosystem standardizes on a ladder of precision levels rather than one format — you pick the rung your hardware can afford.

GGUF: the container format

GGUF is the file format the llama.cpp ecosystem standardized on for distributing quantized models: one file carrying the model architecture metadata, the tokenizer, and the quantized weights together. It succeeded the older GGML format and is documented in the format specification the ggml project maintains. A "GGUF model" is a self-describing artifact any GGUF-capable runtime can load.

The practical consequence: model distribution converged on single downloadable files. You fetch one GGUF file and you have everything the runtime needs — no separate tokenizer downloads, no conversion step, no framework-specific packaging.

The Hugging Face GGUF ecosystem

Hugging Face hosts the distribution layer: model publishers and community members upload GGUF builds of open-weight models, often in several quantization levels per model so you can choose your trade-off. Community quantizers — including contributors who maintain the runtimes themselves — publish widely used quantized builds, and the original model publishers increasingly ship official GGUF variants.

Treat the model page as the source of truth: the quantization level, the base model it was built from, and the license all live on the model card. Download from publishers and quantizers with a track record, and verify checksums when provided.

Model weight licensing, in general terms

Model weights are intellectual property, and each model family ships its own license. Some families use permissive open-source licenses (Apache 2.0, MIT). Others — including well-known families like Llama, Gemma, Qwen, and Mistral releases — use custom licenses with their own terms around commercial use, redistribution, and attribution. Terms differ between families and between versions within a family.

The rule is procedural, not legal advice: read the model card's license before using weights in anything commercial, and treat "open weights" and "open source" as different claims. This guide states no legal conclusions; the license text on the model page is authoritative.

Choosing a quantization level for your hardware

The choice is a three-way negotiation between your available memory, your tolerance for quality loss, and your patience. More bits per weight means more memory and slower loading but closer-to-original quality; fewer bits means the opposite. Start at a middle rung, try your actual workload, and move down only if memory forces you or up only if quality disappoints you.

Context length interacts with the choice: longer contexts consume additional memory at runtime regardless of quantization, so a model that fits for short chats may strain under long documents. Size the whole workload, not just the weights.

Hands-on labs

  1. Compare three quantization levels of one model family on Hugging Face
    Find a model published in multiple GGUF quantizations, read the model cards, and note file sizes, stated base model, and license. The cards are the ecosystem's paperwork — learn to read them before downloading.
  2. Read the GGUF format specification's overview
    Skim the ggml project's GGUF documentation to see what the container carries: metadata, tensor info, quantization types. Understanding the container demystifies every "which file do I download" question.
  3. Write a one-paragraph license summary for three model families
    Pick three well-known open-weight families, read each model card's license section, and summarize in your own words what each permits. The differences between them are the point.

Self-check

  • What does a GGUF file contain besides the weights?
  • Why does quantization trade quality for memory rather than breaking the model outright?
  • What must you check on a model card before commercial use?

Module 3

The Runtime Layer: llama.cpp, Ollama, LocalAI

Learning objectives

  • Explain what an inference runtime does: load weights, run the model, stream tokens
  • Contrast llama.cpp (engine), Ollama (runtime + model library), and LocalAI (drop-in API engine)
  • Choose a runtime for a given use case

Key concepts, explained

What a runtime actually does

An inference runtime performs three jobs: it loads quantized weights from disk into memory, it executes the model's math layer by layer against your prompt (the "forward pass"), and it streams the generated tokens back as they are produced. Everything else — model downloading, chat interfaces, API compatibility — is convenience layered on top of these three jobs. When you compare runtimes, you are comparing how well they do the core three and how much convenience they add.

Keep this separation in mind and the ecosystem stops looking like a pile of competing apps and starts looking like what it is: a small number of engines with many interfaces.

llama.cpp: the engine underneath

llama.cpp is the foundational inference engine of the local-AI ecosystem: LLM inference written in plain C/C++ with no heavy framework dependencies, built on the ggml tensor library. It defined the GGUF format, pioneered the quantization ladder, and ships backends for the hardware people actually own — custom CUDA kernels for NVIDIA GPUs, HIP for AMD, Vulkan and SYCL for cross-vendor acceleration, and first-class Apple Silicon support via ARM NEON, Accelerate, and Metal. Many of the tools in this sequence build on llama.cpp or its ideas.

It also ships its own server: llama-server exposes an OpenAI-compatible REST API, so the same engine that runs on the command line can serve HTTP requests to your own code. Learn llama.cpp and you understand the substrate everything else stands on.

Ollama: the runtime with a model library

Ollama packages local inference as a product: a background service, a simple command line (ollama pull to fetch, ollama run to chat), a curated model library at ollama.com/library, and an OpenAI-compatible chat API on localhost. A Modelfile lets you customize a model's system prompt and parameters declaratively. It is the fastest path from "nothing installed" to "chatting with a model," and its API makes it a natural backend for other tools.

Think of Ollama as the runtime for people who want the engine to behave like a service: install it, pull named models, and talk to a stable local endpoint instead of managing files and flags.

LocalAI: the drop-in API engine

LocalAI takes a different position: it is an open-source AI engine designed as a drop-in replacement for commercial APIs, offering OpenAI-, Anthropic-, and ElevenLabs-compatible endpoints across backends that cover not just text models but vision, voice, image, and video generation — on any hardware, with no GPU required. It adds the operational features an API deployment needs: API-key authentication, user quotas, and role-based access.

Choose LocalAI when your goal is "my own private API that speaks the protocols my code already speaks" — particularly if you want to point existing OpenAI-targeted code at a local endpoint without rewriting it.

Choosing between them

The choice follows the use case. Want to understand and control the engine, run on exotic hardware, or build on the reference implementation? Start with llama.cpp. Want the shortest path to a working local model with a model library and a chat API? Start with Ollama. Want a self-hosted, multi-user API endpoint that existing code can target unchanged, across modalities? Start with LocalAI. These are complementary positions on a spectrum, not rival factions — many practitioners run more than one.

Hands-on labs

  1. Install one runtime and run your first local model
    Pick the runtime that matches your use case from the guidance above, install it per its own docs, and get a small model generating text. The first locally generated token is the moment the whole sequence becomes real.
  2. Call the runtime's API from a script
    Send an HTTP request to the local endpoint (Ollama's localhost API, llama-server, or LocalAI) from a short script in your language of choice. A runtime you can only chat with is a toy; a runtime you can call from code is infrastructure.
  3. Compare the same prompt across two runtimes
    Run an equivalent model through two different runtimes and compare the experience: setup friction, speed, API shape. The comparison teaches you what each runtime's convenience layer actually buys.

Self-check

  • What three jobs does every inference runtime perform?
  • Which runtime would you pick for multi-user API-keyed access, and why?
  • What does llama.cpp's backend list tell you about its hardware philosophy?

Module 4

The Desktop Layer: LM Studio, Jan, GPT4All, TextGen

Learning objectives

  • Describe what a desktop app adds over a raw runtime: discovery, GUI, local server mode
  • Contrast the four desktop apps' positions: discovery-first, offline-first, simplicity-first, power-user
  • Enable a desktop app's local server and point another tool at it

Key concepts, explained

What the desktop layer adds

A desktop app wraps an inference runtime in a human interface: a window instead of a terminal, visual model discovery and download instead of URLs and checksums, chat with history and settings instead of flags, and — critically — a local server mode that exposes the running model as an OpenAI-compatible endpoint other tools can consume. The runtime does the math; the app does the hospitality.

The honest framing: you are trading some control and transparency for convenience. A desktop app is the right choice when the user is a person who wants to chat, not an engineer who wants to tune; it is the wrong choice when you need scriptability, multi-user access, or to know exactly which binary is executing your weights.

LM Studio: discovery-first (proprietary app, open tooling)

LM Studio is a popular desktop application for discovering, downloading, and chatting with local models, with in-app search across Hugging Face's model catalog and a local server mode exposing an OpenAI-compatible API. An honest note on provenance: the desktop application itself is proprietary software distributed by the lmstudio-ai organization — it is not one of the organization's GitHub repositories. The org does publish open-source tooling alongside it (SDKs, engine components, and utilities), but the flagship app is a closed-source download. Evaluate it on its merits, and know what "open" does and does not cover.

Jan: the offline-first desktop app

Jan positions itself as the open-source ChatGPT replacement that runs fully offline on your computer — a desktop application whose headline feature is the absence of a network dependency. (Repository note: the project moved from the menloresearch organization to janhq; the old path redirects to the current one.) It is the choice to examine when the requirement is stated as "works with the network cable unplugged."

GPT4All: simplicity-first

GPT4All's pitch is the shortest in the field: run capable models privately on everyday desktops and laptops, no GPU and no API calls required — download the application and start. It is explicitly open-source and available for commercial use, which matters for the licensing-conscious. When the audience is non-technical users who need local AI without a setup project, this is the app shaped for them.

TextGen: the power-user desktop app

TextGen (the current name of the project long known as oobabooga's text-generation-webui — the old repository path redirects to the new one) is the desktop app for people who outgrow simple chat: text, vision, tool-calling, and web search behind one interface, with an OpenAI/Anthropic-compatible API, portable builds for CUDA, Vulkan, ROCm, and CPU-only systems, and an extension system for deeper customization. Open source, no telemetry, and aimed squarely at tinkerers.

The pattern across all four: each app answers "who is sitting in front of the machine?" differently — the explorer (LM Studio), the offline purist (Jan), the casual user (GPT4All), the tinkerer (TextGen). Match the app to the human.

Hands-on labs

  1. Install a desktop app, download a model through its UI, and chat
    Use the app's own discovery flow rather than the command line. Notice what the UI hides from you — and ask whether anything it hides is something you needed to know.
  2. Enable local server mode and call it from another tool
    Turn on the app's OpenAI-compatible server and point a second client at it — a script, or Open WebUI from the next module. The moment one tool consumes another's endpoint, the layered architecture of the ecosystem clicks into place.
  3. Compare model discovery across two apps
    Search for the same model family in two different apps' discovery flows and compare what metadata each shows: quantization options, licenses, download sizes. Discovery UX is where apps differ most.

Self-check

  • What does a desktop app add over the runtime it wraps?
  • Which app would you recommend to a non-technical user, and which to a tinkerer?
  • What is not open about LM Studio, and why does the distinction matter?

Module 5

The Web-UI Layer: Open WebUI and koboldcpp

Learning objectives

  • Explain why a browser-based interface is a separate layer from the runtime
  • Describe Open WebUI's provider-agnostic position, RAG, and Pipelines/Functions extensibility
  • Describe koboldcpp as a single-file runtime-plus-UI with a broad API surface

Key concepts, explained

Why the interface is its own layer

A web UI does not run the model — it talks to something that does. This separation is the ecosystem's superpower: any chat interface that speaks the OpenAI-compatible protocol can sit in front of any runtime that serves it. You can swap the model, the runtime, or the interface independently, like changing the tires without rebuilding the engine. Understanding the interface as a client, not an engine, is what makes the whole stack composable.

Open WebUI: the provider-agnostic home for AI

Open WebUI is a self-hosted, extensible web platform for interacting with models — designed to run entirely offline and to connect to anything: local Ollama, any OpenAI-compatible API (LM Studio, vLLM, and others), or cloud providers, mixed freely. Its two most consequential features are local RAG — retrieval-augmented generation over your own documents, with vector-database backing, hybrid search, and reranking — and its extensibility model: Pipelines and Functions, a plugin system for injecting custom logic into the chat flow.

Think of Open WebUI as the interface you graduate to when one model in one window stops being enough: multiple backends, your documents searchable inside chat, and custom behavior you write yourself. The project's own documentation is the reference for the plugin system; this guide's job is to tell you the system exists and what it is for.

koboldcpp: one file, zero install

koboldcpp takes minimalism to the extreme: a single self-contained executable — no installation, no dependencies — that runs GGML and GGUF models on CPU or GPU with full or partial offloading, built on llama.cpp with the KoboldAI interface bundled in. Its API surface is unusually broad: KoboldAI, OpenAI-compatible, and Ollama-compatible endpoints, plus image-generation and speech endpoints, so one binary can serve many client types.

It even inverts the usual direction: launched without a model, its interface can act as a pure front end for cloud providers. The lesson of koboldcpp is architectural — the file you download can be the entire stack, runtime and interface fused, when the design prioritizes portability above all else.

Composing the stack yourself

The canonical composition this module teaches: a runtime serving an OpenAI-compatible endpoint (Ollama, llama-server, LocalAI, or a desktop app in server mode) with a web UI pointed at it (Open WebUI, or koboldcpp's interface). Each piece is replaceable; the protocol between them is the contract. Build this once and you will never again confuse "the app I chat in" with "the thing running the model."

Hands-on labs

  1. Point Open WebUI at your runtime's endpoint
    Run Open WebUI (via its documented install methods) connected to the runtime you installed in Module 3. Chat through the web UI while the model runs elsewhere on your machine — the split is the lesson.
  2. Load a document into Open WebUI's RAG and question it
    Add a PDF or text file to the RAG system and ask questions answerable only from that document. Watching the model cite your own file makes retrieval-augmented generation concrete.
  3. Run koboldcpp as a single-file server and hit two different APIs on it
    Launch koboldcpp with a GGUF model, then call both its OpenAI-compatible endpoint and its native API from scripts. One binary, multiple protocols — the API surface is the feature.

Self-check

  • What protocol lets any web UI talk to any runtime?
  • What do Open WebUI Pipelines and Functions let you customize?
  • Why is koboldcpp's single-file design a meaningful architectural choice, not just convenience?

Module 6

The Serving Tier, Honestly Separated: vLLM

Learning objectives

  • Distinguish production serving from desktop inference by audience and requirements
  • Describe what vLLM optimizes for: throughput and memory efficiency at serving scale
  • State when vLLM is the wrong tool for a single user

Key concepts, explained

A different audience

This module exists because listicles keep filing vLLM next to desktop apps, and the filing is wrong. vLLM is a high-throughput, memory-efficient inference and serving engine for large language models — infrastructure for serving many concurrent requests efficiently, the kind of system you run when your model is a service with users. A desktop app answers "how do I chat with a model on my laptop"; vLLM answers "how do I serve thousands of requests per GPU-hour." Different question, different tool, different operator.

The honest categorization matters because the failure mode is real: a beginner who installs a serving stack expecting a chat window finds configuration surface built for throughput engineering. Respect the layering and everyone is happier.

What vLLM optimizes

vLLM's documented design goals are serving throughput and efficient management of the attention key-value memory — the memory that grows with every concurrent request — via its PagedAttention technique, alongside high-throughput decoding strategies like parallel sampling and beam search. It exposes an OpenAI-compatible API server (plus Anthropic Messages and gRPC support), so applications written against those protocols can target it.

In plain terms: where a desktop runtime optimizes for "one user, one model, now," vLLM optimizes for "many users, sustained load, minimal waste." The techniques are about packing concurrent work onto expensive hardware efficiently.

When vLLM is the right call

You reach for vLLM when you have outgrown single-user inference: an internal service for a team, a product backend, a research setup running batched evaluations, a homelab serving a household. Its natural habitat is a machine with serious GPU memory and an operator comfortable with server software — the profile this sequence's earlier modules deliberately did not assume.

When it is the wrong call

If you are one person wanting to chat with a model on your own machine, vLLM is overkill — the desktop and runtime layers of Modules 3–5 are simpler, better documented for that job, and designed for your hardware. Adopting a serving stack for single-user chat is like renting a datacenter rack to host a personal blog: it works, and it misses the point.

Hands-on labs

  1. Write the decision memo: serving stack vs desktop runtime
    Describe a hypothetical deployment (users, concurrency, hardware, operator skill) and argue in writing which layer fits. The deliverable is judgment, not a working install — knowing when not to use a tool is the skill.
  2. Read vLLM's architecture documentation at the level of its design goals
    Skim the project's docs for what it promises (throughput, memory efficiency, API compatibility) and what it assumes (hardware, operator expertise). Compare those assumptions against Modules 3–5's tools.
  3. (Optional, hardware permitting) Serve one model via vLLM and compare the API surface to Ollama's
    If you have a capable GPU, stand up vLLM's OpenAI-compatible server and call it with the same script you used against Ollama. Note how similar the client side looks — protocol compatibility hiding radically different machinery.

Self-check

  • What question does vLLM answer that a desktop app does not?
  • Why is listing vLLM among "desktop AI tools" a category error?
  • What does PagedAttention manage, and why does it matter at serving scale?

Module 7

Hardware Sizing: Qualitative Tiers, Honest Trade-offs

Learning objectives

  • Explain why memory — not raw compute — is the binding constraint for local inference
  • Describe the four hardware tiers and what each unlocks
  • Explain GPU offloading, unified memory, and backend choice (CUDA, ROCm/HIP, Vulkan, Metal)

Key concepts, explained

Memory is the binding constraint

Local inference is a memory problem first and a compute problem second. The model's weights must live in memory (VRAM, system RAM, or unified memory) before a single token is generated, and the working memory for the current conversation grows on top. If the model does not fit in memory, it does not run — no amount of CPU speed compensates. This one fact governs every hardware decision in the sequence: size memory to the model, then worry about speed.

The corollary is hopeful: because the constraint is memory rather than exotic compute, ordinary machines with generous RAM run genuinely capable models. You do not need a datacenter; you need enough memory.

Tier 1 — the CPU-only laptop

The machine you already own. Modern runtimes run small quantized models entirely on CPU, and for short interactive chats the experience is usable — slower per token than GPU inference, but private, free, and available everywhere. This tier is where everyone should start: it proves the concept before any hardware decision, and it is sufficient for learning the entire software stack in this sequence.

Tier 2 — unified memory (Apple Silicon and similar)

Systems where CPU and GPU share one memory pool change the arithmetic: the "VRAM vs RAM" split disappears, and the whole pool is available to the model. Runtimes with first-class support for these architectures (llama.cpp's Metal/Accelerate path, for example) turn a laptop into a surprisingly capable inference machine for mid-size models. The tier's limit is the total pool size — generous, but fixed at purchase.

Tier 3 — the consumer discrete GPU

A gaming-class NVIDIA (or AMD) GPU dedicates its own fast VRAM to the model, with the CPU holding whatever does not fit — the standard "partial offload" arrangement, where some model layers run on the GPU and the rest on the CPU. GPU acceleration is where token speeds become genuinely comfortable for larger models. Backend choice follows the vendor: CUDA for NVIDIA, ROCm/HIP for AMD, Vulkan as the cross-vendor fallback.

Tier 4 — the workstation and beyond

Multiple GPUs, very large memory pools, server-class hardware — the tier where the biggest open-weight models become runnable and where serving stacks like vLLM earn their keep. This is enthusiast, professional, or organizational territory: the hardware is a deliberate investment, and the operator is expected to understand what they bought. Nothing in this sequence requires this tier; it is included so you can recognize it when your ambitions arrive there.

Offloading and backend choice, in practice

Partial offload is the pragmatic middle: the runtime places as many model layers as fit into GPU memory and runs the remainder on the CPU. More offloaded layers means faster inference, up to the limit of your VRAM; the setting is tunable per run, so you experiment rather than calculate. For backends, the rule is simple: use the vendor-native path your hardware offers (CUDA on NVIDIA, the Metal path on Apple Silicon, ROCm/HIP on AMD) and fall back to Vulkan or CPU when no native path exists.

Hands-on labs

  1. Inventory your own hardware against the four tiers
    Record your machine's RAM, GPU (if any), and VRAM/unified pool, and place yourself on the tier ladder. The placement tells you which model sizes are realistic before you download anything.
  2. Run one model at two offload settings and feel the difference
    If you have a GPU, run the same model with full CPU inference and then with GPU offload enabled, and compare the subjective speed. The gap is the reason backends exist.
  3. Deliberately try a model that does not fit
    Attempt to load a model larger than your memory and observe the failure mode (slow swap thrash or an out-of-memory error). Knowing what "too big" looks like is cheaper learned once, intentionally, than discovered mid-project.

Self-check

  • Why is memory, not compute, the binding constraint?
  • What does partial offload do, and what limits it?
  • Which backend would you choose on NVIDIA, Apple Silicon, and AMD hardware respectively?

Module 8

The Lab Track: Install → Pull → Serve → Chat → API

Learning objectives

  • Execute the full local-inference pipeline end to end on your own machine
  • Serve a model over HTTP and consume it from both a UI and your own code
  • Document your stack so it is reproducible

Key concepts, explained

The pipeline as one motion

Everything this sequence taught converges on five verbs: install a runtime, pull (download) a model, serve it over HTTP, chat with it through an interface, and call it as an API from your own code. Each verb exercises a different layer — runtime, distribution, networking, interface, programmability — and the complete motion is the difference between "I read about local AI" and "I operate local AI." This module is the capstone: do all five, in order, on your machine.

Step 1 — Install: one runtime, your choice

Pick the runtime that matched your use case in Module 3 — Ollama for the shortest path, llama.cpp for engine-level control, LocalAI for a private multi-user API — and install it following the project's own documentation for your operating system. Verify the install with the project's own hello-world equivalent before proceeding. A verified install is the foundation; everything downstream assumes it.

Step 2 — Pull: one small model, deliberately

Fetch a small model suited to your hardware tier from Module 7 — small enough to leave headroom, from a publisher you trust, in a quantization level your memory affords. Read its model card first: base model, quantization, license. Note the file size and where it lands on disk. Deliberate selection now prevents the "downloaded something enormous, machine unhappy" failure mode later.

Step 3 — Serve: the model as an HTTP endpoint

Start the runtime's server mode — Ollama's background service, llama-server, LocalAI's API, or a desktop app's local server — and confirm the endpoint responds. The model is now a network service on your own machine: the same architectural shape as a cloud API, with the datacenter replaced by your desk. Record the host, port, and protocol; every later step addresses the model through this endpoint.

Step 4 — Chat: an interface on the endpoint

Point a chat interface at your endpoint — Open WebUI for the full-featured option, koboldcpp's bundled UI for the single-file option, or the runtime's own chat — and hold a real conversation. Load a document into RAG if your interface supports it. This is the user-facing proof that the stack works: a person, a browser, a model, no cloud.

Step 5 — API: your code calls your model

Write a short program in your preferred language that sends a prompt to your local endpoint and prints the response — using the OpenAI-compatible chat format most of these runtimes speak. Then change one parameter (temperature, system prompt, max tokens) and observe the effect. A model you can call from code is infrastructure you own; this step is where the sequence's knowledge becomes a capability you can build on.

Document the stack

Write down what you built: runtime and version, model name and quantization, endpoint address, interface used, hardware tier, and anything you had to troubleshoot. A local AI setup you cannot reproduce is a demo; a documented one is a lab. Keep the document — it is the starting point for every future experiment.

Hands-on labs

  1. Complete the five-verb pipeline and record each step's output
    Install, pull, serve, chat, API — in order, capturing the commands and responses. The record is both proof of completion and your personal runbook.
  2. Swap one layer and keep the rest working
    Change exactly one component — a different model, a different interface, a different runtime serving the same protocol — and confirm the stack still works. The swap succeeding is the composability thesis of Module 5, demonstrated.
  3. Take the stack offline and verify it still works
    Disconnect from the network and repeat the chat and API steps. Whatever keeps working is genuinely local; whatever breaks was secretly depending on the cloud. Note the difference.
  4. Write the one-page operator's guide for your stack
    Startup order, endpoint addresses, model location, troubleshooting notes, shutdown procedure. Hand it to your future self — or to anyone you want to onboard.

Self-check

  • Which layer does each of the five verbs exercise?
  • Why does the offline test distinguish genuinely local stacks from nominally local ones?
  • What would you change first if you needed to serve a second user?

Module 9

Local RAG: Retrieval That Runs on Your Machine

Learning objectives

  • Explain the RAG pipeline's verbs: chunk, embed, store, retrieve, rerank, ground
  • Choose between Open WebUI Functions and Pipelines for extending retrieval
  • Compare the five local vector stores and pick one for an embedded use case
  • Explain hybrid search and reranking as the two-stage relevance discipline

Key concepts, explained

Chunk, embed, store, retrieve, rerank, ground

A model cannot read your whole archive: its context window is finite, and pasting everything into every prompt is the most expensive way to be unhelpful. Retrieval-augmented generation reverses the problem: keep your documents in a store, fetch only the passages that matter for the current question, and let the model answer from those. Six verbs: chunk the documents into retrievable pieces, embed each piece as a vector (a list of numbers capturing its meaning), store the vectors in an index, retrieve the pieces nearest the question, rerank the candidates with a heavier model, and ground the answer in what came back. The retrieval is the skill; the model is just the writer.

The honest framing: retrieval does not make the model truthful. It makes the model traceable — an answer that cites passages can be checked, and one that cannot should not be trusted. The failure modes move upstream: bad chunking, stale documents, poisoned sources. (The agent-stack-ops sequence covers what poisoned retrieval costs an agent.)

Open WebUI's two extension rails: Functions and Pipelines

Open WebUI already speaks RAG out of the box — you can load documents and query them. When you need custom behavior, the project offers two extension rails with an explicit pecking order. Functions are built in: Python plugins stored in the database and auto-loaded by the server, in four types — Pipe (custom models in the sidebar), Filter (middleware with hooks before the model, per provider call, on the live stream, and after the model), Action (toolbar buttons), and Event (background logic). Pipelines is the heavier route: a separate Python plugin server (its own process, OpenAI-compatible endpoints) for computationally heavy work you want offloaded from the main instance. The project's own README says plainly: for simple additions and basic filters, use Functions, not Pipelines.

Both rails execute arbitrary Python, and the documentation carries critical security warnings — do not install functions or pipelines from untrusted sources. An extension that can see every prompt is a plugin with total access; treat it like one.

The five local vector stores

Five open projects cover the local vector-database landscape, and all five run on your own hardware:

  • Qdrant (Apache-2.0) — a Rust search engine with dense, sparse, and multi-vector search plus payload filtering; runs as a single binary or container, with an in-process Edge mode.
  • Chroma (Apache-2.0) — the Python-first store with a minimal API; genuinely embedded (a persistent client on a local directory) for the simplest setups, with server and paid cloud tiers above it.
  • LanceDB (Apache-2.0) — an embedded retrieval library on the Lance columnar format: vector, full-text, and SQL queries from a local directory, no server process at all.
  • Milvus (Apache-2.0) — the distributed, billion-scale engine; on a single machine, Milvus Lite runs embedded as a local file database, which is the sane starting point — the full cluster is operationally heavy.
  • Weaviate (community edition BSD-3-Clause) — cloud-native with built-in vectorizers and hybrid search; honest caveat: the repository ships enterprise-edition code alongside the community code, so know what you are actually running.

Picking one is a weight-class decision, not a loyalty decision: an embedded library for a single app (LanceDB, Chroma, Milvus Lite), a single binary for a small service (Qdrant), a distributed engine when you have genuinely outgrown one machine.

Hybrid search and reranking: the two-stage relevance discipline

Dense vectors capture meaning; keyword search captures exact terms. A query for "provisioning error 0x8007" needs the exact code, not a semantic paraphrase — so serious retrieval runs hybrid search: dense and BM25-style keyword search together, fused into one ranking. Qdrant, Weaviate, Milvus, and LanceDB all document native hybrid search, with fusion strategies like Reciprocal Rank Fusion. Chroma is the honest exception: its hybrid search is documented as a paid-cloud feature, not for the self-hosted build — do not assume parity.

Then comes the second stage: reranking. A fast retriever fetches a broad candidate set (say, the top 100), and a heavier model scores each query–passage pair to order the final few. Rerankers are cross-encoders — query and passage go in together, a score comes out, no embeddings involved — which makes them more accurate and more expensive than the first stage. The BGE reranker family (BAAI) is the common open example, runnable locally; the toolkit code is MIT, but each model checkpoint carries its own license, so check the model page before commercial use. The discipline: spend cheap retrieval on breadth, expensive scoring on the shortlist.

Chunking: where retrieval quality is actually decided

Retrieval fails most often at the chunk boundary — the answer lived in a paragraph that got split in half. The standard tool is the recursive splitter: try to split on paragraph breaks first, then sentences, then words, keeping each chunk under a size limit, with a small overlap between consecutive chunks so context survives the boundary. Overlap is the cheap insurance; chunk size is the dial. Semantic chunking goes further — grouping sentences by topic using embeddings instead of fixed sizes — and the parent-document pattern retrieves small chunks but returns their larger parents to the model. Measure retrieval quality before you tune anything else: the embedding model rarely matters as much as the chunking does.

Hands-on labs

  1. Index a real folder and ask it questions
    Point Open WebUI's built-in RAG at a folder of your own documents. Ask questions whose answers live in specific passages. Note which answers cite their sources and which hallucinate — the difference is the ground in "ground."
  2. Break retrieval with bad chunking, then fix it
    Index the same documents with very large and very small chunk sizes. Compare which questions get answered correctly. This is the chunk-size dial, learned empirically rather than guessed.
  3. Run a hybrid query and a dense-only query side by side
    Ask a question containing an exact identifier (an error code, a function name, a proper noun). Compare pure vector retrieval against a hybrid search. The gap is why keyword search refuses to die.
  4. Add a reranker to the loop
    Retrieve the top 20 candidates for a question, then rerank them with a local cross-encoder. Compare the top 3 before and after. Decide where in your pipeline the latency budget for reranking belongs.

Self-check

  • What do the verbs of RAG each do, and which one usually decides quality?
  • When would you use a Pipeline instead of a Function in Open WebUI?
  • Why does hybrid search exist — what does keyword search catch that vectors miss?
  • What is a reranker, and why does it run second instead of first?

Module 10

Fine-tuning on Your Hardware: LoRA, QLoRA, and the Adapter Discipline

Learning objectives

  • Explain why LoRA and QLoRA make fine-tuning possible on consumer hardware
  • Name the three QLoRA innovations and what each one buys you
  • Follow the PEFT adapter path from 4-bit config to merged weights
  • Distinguish fine-tuning from preference optimization (DPO, ORPO) — and when each applies
  • Check model licenses honestly: the tool is not the licensor

Key concepts, explained

Full fine-tuning is the expensive reference point

Updating every weight in a model means holding the weights, their gradients, and the optimizer's bookkeeping — roughly four times the weight memory for Adam-style optimizers (simple arithmetic, not a vendor claim). That is why full fine-tuning of large models is datacenter work: the memory bill scales with every parameter. Parameter-efficient methods exist to break that scaling.

LoRA: freeze the giant, train the small

Low-Rank Adaptation freezes the pretrained weights and injects two small trainable matrices — a rank-r decomposition of the weight update — into the model's layers. At inference time the adapters merge back into the weights, so the served model costs nothing extra per token. The original paper's comparison is specific and worth quoting honestly: against full Adam fine-tuning of GPT-3 175B, LoRA trains on the order of 10,000x fewer parameters with about 3x lower GPU memory — that is a comparison at 175B scale with Adam, not a universal constant. The principle travels; the exact ratios do not.

QLoRA: three ideas that fit big models on small cards

QLoRA (Dettmers et al., May 2023) stacks three innovations on LoRA: NF4, a 4-bit float format information-theoretically optimal for normally distributed weights; double quantization, which quantizes the quantization constants themselves to save more memory; and paged optimizers, which page memory spikes to avoid the out-of-memory failures that kill long runs. The paper's headline result — fine-tuning a 65B model on a single 48GB GPU while preserving full 16-bit fine-tuning task performance — is a real 2023 result, and it is the reason consumer fine-tuning exists as a practice.

The honest consumer translation: the 65B figure needs a 48GB card. On 16–24GB hardware, QLoRA is a 7B/8B-class technique — the weights at 4-bit are ~3.5GB for 7B parameters, leaving room for adapters, optimizer states, and the KV cache. "Fine-tune on a laptop" is marketing shorthand; the discipline version is "fine-tune 7B-class models on real consumer GPUs, and read the memory budget first." The paper's own quality claims (e.g., its chatbot-benchmark numbers) are 2023 paper-specific results — and the paper itself warns that current chatbot benchmarks are not trustworthy. Never present them as current evidence.

The PEFT path: config, train, merge

Hugging Face's PEFT library is the canonical implementation. The QLoRA workflow is three objects: a BitsAndBytesConfig (4-bit, NF4, double quantization, bfloat16 compute), prepare_model_for_kbit_training() to ready the frozen model, and a LoraConfig (rank, alpha, target modules, task type) wrapped by get_peft_model(). Setting target_modules="all-linear" matches the paper's all-linear-layers recipe. When training is done, merge_adapter() or merge_and_unload() folds the adapter into the base weights — and PEFT documents one sharp caveat: merging is only guaranteed correct for LoRA with int8-weight-only; other method/dtype combinations can error or silently misbehave.

PEFT is a family, not a single trick. The low-rank relatives include AdaLoRA (adaptive rank via importance scoring), LoHa and LoKr (Hadamard and Kronecker products of low-rank updates); IA3 scales activations with learned vectors instead of touching weights; OFT and BOFT constrain updates to orthogonal matrices; prompt tuning, prefix tuning, and P-tuning leave the weights alone entirely and train input-side vectors. Know the taxonomy as vocabulary — you do not need to run all of them.

Beyond supervised fine-tuning: preference optimization

SFT teaches the model to imitate; preference optimization teaches it which imitations you prefer. The TRL library is the standard harness: SFTTrainer, DPOTrainer, ORPOTrainer, and reward-modeling trainers, all taking a peft_config so the two stacks compose. DPO needs a reference model; ORPO is reference-model-free — an odds-ratio term on top of the SFT loss, so preference tuning happens in one phase instead of two. The discipline: alignment methods inherit whatever your data's preferences actually encode. A preference dataset full of your own biases produces a model full of your biases — the math is honest, the data may not be.

The tooling layer: Axolotl, Unsloth, MLX

Three tools cover the practical paths. Axolotl is config-driven: one YAML file covers dataset prep, training, evaluation, quantization, and inference — its llama-3 example configs (e.g., lora-8b.yml with adapter: lora, lora_r: 32, gradient checkpointing, cosine schedule) are the honest reference for what a complete recipe looks like. Unsloth provides fast training kernels and exports to GGUF — but keep two honesty notes on record: its "2x faster, 70% less VRAM" framing is the vendor's own marketing claim, never an established fact, and its Hugging Face checkpoints are unofficial mirrors that carry the base model's license (verified on one upload: llama3.1). Unsloth is a tool, not a model licensor. MLX brings LoRA/QLoRA to Apple Silicon: convert.py -q builds a 4-bit model, lora.py trains, adapters land in adapters.npz, fuse.py merges — with documented memory tips (QLoRA, smaller batches, fewer LoRA layers, shorter sequences).

The license discipline

The single most skipped step in local fine-tuning: the adapter is yours, but the base weights are not. Fine-tuning a model whose license forbids redistribution does not wash the license — the fine-tuned artifact inherits the base license. Check the model card before you train, not after you publish. The merge step does not change the legal facts; it only changes the file layout.

Hands-on labs

  1. Budget a fine-tuning run on paper
    Pick a 7B model and 16GB VRAM. Work the memory arithmetic: 4-bit weights (~3.5GB) + adapters (rank 16 vs 64 — count the parameters) + optimizer states + KV cache for your sequence length. Decide whether it fits before you download anything.
  2. Walk an Axolotl config line by line
    Read the example lora-8b.yml end to end: adapter settings, quantization, gradient checkpointing, schedule. For each line, state what it controls and what breaks if you change it. Config literacy is the transferable skill.
  3. License-check a checkpoint you might use
    Pick a fine-tuned checkpoint from a hub, read its license field, and trace which base model's license it inherits. Practice the discipline: the tool that made it is not the licensor.

  • When does ORPO apply and when does DPO — and what does each need in the data?
  • You downloaded a "fine-tuned" 4-bit checkpoint. Whose license governs it?
