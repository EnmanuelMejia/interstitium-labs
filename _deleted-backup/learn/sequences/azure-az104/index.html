Azure Administrator (AZ-104)

Identity, governance, storage, compute, networking, monitoring, and recovery — the working administrator's map of Microsoft Azure.

Start the sequence All sequences

SCIENTIA OMNIA VINCIT

The sequence

What you will learn, and how.

Microsoft Azure is a public cloud platform: compute, storage, networking, and identity delivered as services you provision through the portal, the command line, or infrastructure-as-code. The administrator's job is to make those services correct, secure, observable, and recoverable — and to do it repeatedly, at scale, without click-ops heroics.

This sequence follows the AZ-104 administrator domain in a practitioner's order. You begin with identity, because everything in Azure is gated by Microsoft Entra ID: users, groups, licenses, Conditional Access, MFA. Then governance — the management-group, subscription, and resource-group hierarchy plus RBAC, policy, locks, and tags — the guardrails that keep a tenant sane. Storage and compute come next: choosing the right account kinds, replication, VM families, scale sets, and App Service. Virtual networking follows, then monitoring and alerting with Azure Monitor and KQL, then backup and disaster recovery, and finally the tooling craft: CLI, PowerShell, Bicep, cost management, and an exam-day strategy.

Everything here is keyed to Microsoft Learn, which is authoritative for exact portal behavior, CLI syntax, and current service details. This page teaches the concepts and the judgment; Learn supplies the canonical reference.

Who this sequence is for

  • System administrators moving on-premises Windows or hybrid workloads to Azure.
  • IT professionals preparing for the AZ-104 certification as working administrators, not just exam-takers.
  • Engineers who already understand networking and OS fundamentals and need the Azure-specific control plane.

Prerequisites

  • Familiarity with core IT concepts: virtual machines, DNS, TCP/IP subnets, and Active Directory basics.
  • An Azure free account for the labs — nearly every lab here can run on free-tier or low-cost resources; set a budget alert before you start.
  • Comfort with either Bash or PowerShell for the CLI labs.

How to use it

  • Work the modules in order; identity and governance underpin everything after them.
  • Do the labs in a dedicated lab subscription you can tear down. Azure bills by the meter — the budget-alert lab exists for a reason.
  • For each module, write the "on paper" artifacts (policy statements, DR plans, KQL queries) before touching the portal. Design first, click second.
  • Verify every CLI command and portal flow against current Microsoft Learn documentation; the cloud moves and this guide teaches concepts, not click paths.

Module 1

Entra Identity Foundation

Learning objectives

  • Create and manage users, groups, and external guest accounts in Microsoft Entra ID.
  • Explain how licenses gate features like Conditional Access and Privileged Identity Management.
  • Describe hybrid identity concepts: password hash sync, pass-through auth, federation, and Seamless SSO.
  • Configure multifactor authentication enforcement for administrator accounts.

Key concepts, explained

Tenant, directory, and administrative units

A Microsoft Entra tenant is the dedicated instance of the identity service for your organization — the security boundary that holds your users, groups, and applications. The directory is the store itself; the tenant is your organization's isolated instance of it.

Administrative units let you delegate administration over a subset of users, groups, or devices without granting tenant-wide roles. They are how large organizations give a regional IT team control over their own people while keeping the global administrator role scarce.

User types: member vs guest, and B2B invitations

Member users are your organization's own identities; guest users are external collaborators invited through B2B. Guests get limited default permissions and are visibly marked, which keeps the trust boundary explicit.

A guest invitation alone grants no resource access — the invitation creates the identity, but access comes only from subsequent group memberships or role assignments. Identity and authorization are separate steps by design.

Groups: security, Microsoft 365, dynamic membership rules

Security groups exist for access control: assign a role or grant resource access to the group once, and membership changes propagate automatically. Microsoft 365 groups add a collaboration bundle (mailbox, SharePoint site, Teams) on top of the group.

Dynamic groups define membership with a rule — "all users with department = Engineering" — evaluated continuously. They eliminate the stale-membership problem for attributes the directory already knows, like department, job title, or user type.

License tiers: Entra ID Free, P1, P2 and feature gates

Entra ID comes in tiers, and the tier gates the features: Free covers basic user and group management; P1 unlocks Conditional Access, hybrid identity features, and dynamic groups; P2 adds Privileged Identity Management and Identity Protection risk-based policies.

This matters operationally because designs that assume Conditional Access or PIM simply do not work on a Free tenant. Know which features your tenant's licenses entitle you to before you promise them in a design.

Conditional Access policy structure (signals, conditions, grant controls)

Conditional Access is the policy engine that decides, per sign-in, whether access is granted, requires MFA, or is blocked. Each policy combines signals (who the user is, what device, what network, what risk level), conditions (which apps and users the policy applies to), and grant controls (require MFA, require compliant device, block).

The power — and the danger — is that policies compose: multiple policies apply to one sign-in, and the strictest grant control wins. Design policies as a small, reviewed set with a break-glass exclusion, and test in report-only mode before enforcing.

MFA enforcement and SSPR concepts

Multifactor authentication requires a second factor beyond the password — an authenticator app approval, a hardware key, a phone call — and administrator accounts should always require it, enforced by Conditional Access rather than by per-user settings.

Self-service password reset (SSPR) lets users recover their own accounts using registered authentication methods, which cuts help-desk load. Both MFA and SSPR depend on users having registered their methods in advance — enrollment is the part organizations always underestimate.

Microsoft Entra Connect Sync object model basics

Hybrid identity joins an on-premises Active Directory to Entra ID. Entra Connect Sync replicates user and group objects upward, joining them to cloud identities so one credential works in both worlds.

The sync engine maps on-premises attributes to cloud attributes according to sync rules, and the choice of authentication method — password hash sync, pass-through authentication, or federation — determines where the actual credential verification happens. Understand the object flow before troubleshooting sync errors, because most of them are attribute-mapping problems.

Hands-on labs

  1. Create a free tenant; add two users and one guest, assign them to a security group.
    Building the tenant yourself makes the member/guest distinction tangible. Invite a real external address as the guest so you see the B2B redemption flow end to end.
  2. Build a dynamic group with a rule based on department and verify membership updates.
    Set the department attribute on your test users, write the rule, and watch membership resolve. Then change an attribute and confirm the group updates — the rule engine working visibly.
  3. Write a Conditional Access-style policy statement (on paper) requiring MFA for admins on risky sign-ins.
    Writing the policy as sentences — "when an administrator signs in from an unfamiliar location, require MFA" — forces you to name the signals, conditions, and grant control explicitly before any portal clicking.
  4. Export users and group memberships with Azure PowerShell or az ad commands.
    Scripted exports are the administrator's audit trail. Compare the CLI output against what the portal shows; the CLI teaches you the underlying object model the portal hides.

Self-check

Why does a guest invitation alone not grant resource access?
Answer: The invitation only creates the identity object. Authorization is a separate step — group memberships or role assignments granted afterwards. Entra separates authentication (who) from authorization (what) by design.
Which identity sync option leaves the password in Microsoft Entra ID vs on-premises?
Answer: Password hash sync leaves a hash in Entra ID (cloud verifies). Pass-through authentication and federation keep verification on-premises — the password never lives in the cloud.
Name two features gated behind Entra ID P1/P2 licenses.
Answer: P1: Conditional Access, hybrid identity features, dynamic groups. P2 adds: Privileged Identity Management and Identity Protection risk-based policies.

Module 2

Governance: Subscriptions, RBAC, and Policy

Learning objectives

  • Organize tenants into management groups, subscriptions, and resource groups with a naming scheme.
  • Assign role-based access control using least-privilege built-in roles and custom roles.
  • Author and assign Azure Policy definitions and initiatives to enforce organizational standards.
  • Apply resource locks and tagging to protect and classify production resources.

Key concepts, explained

Hierarchy: management group > subscription > resource group > resource

Azure organizes everything in a four-level hierarchy. Management groups sit at the top and let you apply policy and RBAC across many subscriptions at once. Subscriptions are the billing and quota boundary. Resource groups are the deployment and lifecycle boundary — you deploy, manage, and eventually delete resources as a group. Resources are the actual services.

Design the hierarchy before creating anything: management groups by organizational division, subscriptions by workload or environment, resource groups by application lifecycle. A hierarchy designed up front prevents the "one subscription with 400 unrelated resources" sprawl that is painful to untangle.

RBAC model: security principal, role definition, scope, assignment; allow-model only

Role-based access control has four parts: a security principal (user, group, or service identity), a role definition (the set of permitted actions), a scope (where it applies — management group, subscription, resource group, or resource), and the assignment tying them together.

RBAC is an allow model: there are no deny assignments, only the absence of permission — plus explicit Deny used internally by features like locks and blueprints. Effective permission is the union of all assignments across scopes, which is why auditing effective access means enumerating every assignment, not reading one.

Built-in roles: Owner, Contributor, Reader, User Access Administrator

The four foundational roles: Owner can manage everything including access; Contributor can manage everything except access; Reader can view everything but change nothing; User Access Administrator can manage access but not resources.

Default to the least of these that gets the job done, and prefer group assignments over individual ones. Owner is almost never the right answer for a human's day-to-day work — it exists for the rare cases where access management and resource management must coincide.

Custom roles: actions, notActions, assignable scopes, JSON structure

When no built-in role fits — "this team may restart VMs but not resize them" — you write a custom role as JSON: actions lists the permitted operations as provider/action strings, notActions carves out exceptions, and assignableScopes bounds where the role may be granted.

Custom roles are powerful and therefore review-worthy: an overly broad actions list with a wildcard quietly recreates Contributor. Keep custom roles narrow, name them for the job they enable, and re-certify them periodically.

Azure Policy: definition, assignment, initiative, compliance vs remediation, deny/audit/deployIfNotExists effects

Azure Policy is the guardrail engine: a policy definition states a rule ("resource groups must carry a cost-center tag"); an assignment applies it at a scope; an initiative bundles definitions into one assignable set, like a compliance standard.

Effects determine teeth: audit flags violations, deny blocks non-compliant deployments, deployIfNotExists remediates by deploying the missing configuration. Compliance is the dashboard — what fraction of resources conform; remediation is the action. Start new policies in audit mode, review the compliance picture, then escalate to deny.

Locks: CanNotDelete vs ReadOnly, inheritance behavior

Resource locks protect against accidents: CanNotDelete blocks deletion while allowing modification; ReadOnly blocks both modification and deletion. Locks inherit down the hierarchy — a lock on a resource group protects every resource inside it.

Locks are the last line of defense for production, and they apply to everyone including Owners, which is exactly the point. The classic failure they prevent is the 2 AM "wrong resource group deleted" incident.

Tags: key-value metadata, tag policies, inheritance limits

Tags are free-form key-value metadata on resources — environment, cost-center, owner — that power cost reporting, automation targeting, and policy. A tagging standard enforced by policy is what makes chargeback and lifecycle automation possible.

Tags do not inherit: a tag on a resource group does not flow to its resources, which surprises everyone once. Enforce tagging at creation time with policy, because retroactive tagging of a large estate is a project nobody wants.

Hands-on labs

  1. Create a resource group; assign Reader at subscription scope to a test user and Contributor at RG scope.
    Sign in as the test user and confirm: read-only outside the resource group, full control inside it. Feeling the scope boundary as the user is worth more than reading about it.
  2. Write a custom role JSON granting VM restart-only rights; assign it and verify denied actions fail.
    Craft the actions list narrowly, assign the role, then attempt a forbidden action — like resizing the VM — and watch it fail. The failure is the proof the role is least-privilege.
  3. Assign a built-in policy requiring tags on resource groups; deploy a resource and check compliance.
    Assign the policy in audit mode first, deploy an untagged resource, and read the compliance result. Then switch to deny and watch the same deployment get blocked.
  4. Place a CanNotDelete lock on a resource group and attempt deletion to observe the block.
    Try to delete the locked resource group and read the denial. Then remove the lock and delete successfully — the lock is a guardrail, not a vault.

Self-check

A user is Reader at subscription scope and Contributor at RG scope — what is the effective permission in that RG?
Answer: Contributor inside that resource group — RBAC is an allow model and effective permission is the union of all assignments. Reader elsewhere grants nothing extra.
What happens to resources when a lock is placed on their parent resource group?
Answer: Locks inherit: every resource in the group is protected. CanNotDelete blocks deletion (allows modification); ReadOnly blocks both. They apply even to Owners.
Distinguish a policy definition from an initiative and an assignment.
Answer: Definition = the rule itself. Initiative = a bundled set of definitions (e.g. a compliance standard). Assignment = applying a definition or initiative at a scope. Effects (audit/deny/deployIfNotExists) set the teeth.

Module 3

Storage Engineering

Learning objectives

  • Choose storage account kind, performance tier, and replication for a workload's SLA and cost profile.
  • Manage blob access tiers and lifecycle policies to control cost and retention.
  • Secure data with shared access signatures, stored access policies, and network rules.
  • Configure Azure Files shares with identity-based access for lift-and-shift scenarios.

Key concepts, explained

Account kinds: StorageV2, BlobStorage, FileStorage, Premium tiers

The general-purpose v2 (StorageV2) account is the default choice — it supports blobs, files, queues, and tables with tiering. BlobStorage accounts are blob-optimized legacy kinds; FileStorage provides premium file shares; premium tiers trade cost for consistent low latency.

Choose the kind by workload: object storage with lifecycle needs wants StorageV2; latency-sensitive file shares want premium. The account kind is set at creation and constrains what the account can do, so decide deliberately.

Replication: LRS, ZRS, GRS, GZRS, RA variants; RPO/RTO implications

Replication is the durability dial. LRS keeps three copies in one datacenter — cheap, vulnerable to facility loss. ZRS spreads copies across availability zones in a region — resilient to datacenter failure. GRS replicates to a paired region — resilient to regional disaster. GZRS combines both. Read-access variants (RA-GRS) add a readable secondary endpoint.

Each step up the ladder costs more and changes your recovery story: RPO (how much data you can lose) and RTO (how long recovery takes) follow from the replication choice. Match the replication to the data's actual value, not to your anxiety.

Blob tiers: Hot, Cool, Cold, Archive; rehydration behavior

Blob access tiers price storage against retrieval: Hot for frequently accessed data, Cool for infrequently accessed, Cold for rarely accessed, Archive for data that can sit offline for hours. Moving down the tiers cuts storage cost and raises access cost and latency.

Archive is the extreme: data is offline and must be rehydrated — copied back to an online tier — before it can be read, which takes hours and costs. Lifecycle policies automate the descent; rehydration is always a deliberate, planned operation.

Lifecycle management rules: filters, actions, tier-to-archive automation

Lifecycle management applies rules to blobs by prefix, age, and type: after N days move to Cool, after M days to Archive, after Y days delete. The rules run daily and turn a cost policy into an automatic behavior.

Write the rules from your retention requirements, not from guesswork: compliance retention sets the delete floor, access patterns set the tiering thresholds. Test rules against a sample container before pointing them at production data.

SAS types: service, account, user-delegation; least-privilege scoping

A shared access signature is a time-boxed, permission-scoped token appended to a URL — it grants delegated access without sharing the account key. Service SAS delegates access to one service; account SAS to the whole account; user-delegation SAS is bound to a Microsoft Entra identity via OAuth instead of the account key.

Prefer user-delegation SAS: it inherits Entra identity, supports revocation by disabling the identity, and never exposes the account keys. Scope every SAS to the minimum permissions, resource, IP range, and expiry the task needs — a SAS is a bearer token, and bearer tokens leak.

Storage firewall, private endpoints, service endpoints

By default a storage account is reachable from the public internet with the key. The storage firewall restricts access to selected virtual networks and IP ranges; service endpoints extend the VNet identity to the storage service; private endpoints give the account a private IP inside your VNet so traffic never crosses the public internet.

Defense in depth here means: firewall on, private endpoint for sensitive data, and keys rotated — with Entra-based access (RBAC, user-delegation SAS) preferred over key-based access wherever possible.

Azure Files: SMB/NFS shares, AD/Entra DS authentication, share snapshots

Azure Files exposes SMB and NFS shares in the cloud — the lift-and-shift answer for applications that expect a file share. Shares can authenticate with storage keys or, properly, with identity: on-premises AD or Entra Domain Services, so access follows the user, not a shared key.

Share snapshots capture point-in-time copies for recovery without a full backup product. For traditional file-server workloads, the combination of identity-based access plus snapshots covers the essentials.

Hands-on labs

  1. Create a StorageV2 account with GRS; upload blobs via AzCopy and verify redundancy setting.
    AzCopy is the workhorse for bulk transfer; the portal confirms the redundancy you configured. Do both so you learn the tool and the verification.
  2. Set a lifecycle rule moving blobs to Cool after 30 days; dry-run evaluation logic on sample data.
    Apply the rule to a test container with old and new blobs and confirm only the old ones are candidates. Lifecycle mistakes on production data are expensive; the test container is cheap.
  3. Generate a time-boxed, IP-restricted SAS for one container and test read vs write denial.
    Create the SAS with read-only permission, then attempt a write with it and watch it fail. Then let it expire and watch reads fail too — the token lifecycle made visible.
  4. Mount an Azure Files share from a VM and from a workstation over SMB with a stored key.
    Mounting from both places demonstrates the share is network-attached storage, not VM-local. Note where the key is stored and consider how you would replace it with identity-based access.

Self-check

When is ZRS preferable to GRS, and what does RA-GRS add?
Answer: ZRS when the threat model is datacenter failure within a region and you want lower latency/cost than cross-region replication. GRS protects against losing the whole region. RA-GRS adds a readable secondary endpoint in the paired region.
What minimum privilege and expiry should a SAS carry, and why prefer user-delegation SAS?
Answer: Minimum permissions, narrowest resource, shortest expiry, IP restriction where possible. User-delegation SAS is bound to an Entra identity (revocable, no account keys exposed) instead of the storage account key.
How does Archive tier rehydration affect read latency and cost?
Answer: Archive blobs are offline: reads require rehydration to an online tier first, taking hours and incurring retrieval costs. Plan rehydration deliberately; never archive data you might need urgently.

Module 4

Compute: VMs, Scale Sets, and App Service

Learning objectives

  • Size, deploy, and harden Azure VMs including disks, availability options, and extensions.
  • Configure Virtual Machine Scale Sets with autoscale rules for elastic workloads.
  • Deploy web workloads to App Service plans with deployment slots and scaling rules.
  • Run simple containerized workloads on Azure Container Instances.

Key concepts, explained

VM series families, vCPU/RAM ratios, and generation 1 vs 2 images

Azure VM sizes are grouped in series by workload profile: B-series for burstable low-cost workloads, D-series for general compute, E-series for memory-heavy, F-series for compute-heavy, and specialized families for GPU, HPC, and storage. The series letter encodes the vCPU-to-RAM ratio and the price curve.

Generation 2 images add UEFI boot, larger disks, and security features like secure boot over generation 1's BIOS boot. Default to generation 2 for new deployments; generation 1 remains for legacy images that require it.

Availability sets (fault/update domains) vs availability zones vs SLA math

Availability is engineered in layers. Availability sets spread VMs across fault domains (separate racks/power) and update domains (separate maintenance groups) within one datacenter. Availability zones spread VMs across physically separate datacenters in a region — protection against datacenter-level failure.

Zones beat sets for fault tolerance, and the SLA reflects it: Azure's published SLAs require the prescribed deployment pattern (two or more instances across zones, for example) — a single VM carries no high-availability SLA regardless of how carefully you built it.

Managed disks: SSD/HDD tiers, disk encryption, snapshots

Managed disks abstract the storage accounts away: you pick a tier — Standard HDD, Standard SSD, Premium SSD, Ultra — and Azure handles the rest. The tier sets the IOPS and throughput ceiling, so disk performance is a sizing decision, not a tuning exercise.

Encrypt disks (Azure Disk Encryption or encryption at host), and use snapshots for point-in-time copies before risky changes. A snapshot before a major upgrade is the cheapest insurance in the cloud.

VM extensions: Custom Script, Azure Monitor agent, Desired State Configuration

Extensions are small agents installed on the VM by the Azure fabric: Custom Script runs your script at provisioning time, the Azure Monitor agent ships telemetry, and Desired State Configuration enforces configuration. They install without you logging into the VM.

Extensions are the bootstrap path: a VM can go from bare image to configured, monitored member of the fleet with no interactive session. But every extension is also attack surface and failure surface — install only what the workload needs.

VMSS: uniform vs flexible orchestration, instance protection, rolling upgrades

Virtual Machine Scale Sets manage a fleet of identical VMs as one resource: autoscale rules add and remove instances by metric, and upgrades roll across the set. Uniform orchestration treats instances as identical and interchangeable; flexible orchestration allows mixed VM types and standalone-VM behaviors within the set.

Instance protection pins specific instances against scale-in, and rolling upgrades update the set in batches with health gates. Choose flexible when the fleet is heterogeneous or when you are migrating from standalone VMs; uniform when the workload is truly cattle.

App Service plans: tier capabilities, scale-out rules, slots and slot swapping

App Service is the managed web platform: you deploy code, Azure runs the servers. The App Service plan defines the VM size, count, and feature tier — Free/Shared for experiments, Basic/Standard for production workloads, Premium and Isolated for scale and network isolation.

Deployment slots give you staging environments that swap with production — including sticky "slot settings" for connection strings that must not swap. Scale-out rules add instances by metric. The platform handles patching and load balancing; you own the code and the configuration.

ACI: container groups, restart policies, volume mounts

Azure Container Instances run containers without managing any orchestrator: you describe a container group — image, CPU, memory, ports, environment — and it runs, billed per second. Restart policies (always, on failure, never) control what happens when the container exits.

ACI is the right answer for burst workloads, CI agents, and simple single-container jobs. It is not a Kubernetes replacement: no service discovery, no rolling updates, no complex networking — just containers, fast.

Hands-on labs

  1. Deploy a B-series VM from the portal and the CLI; attach a data disk and enable disk encryption concepts review.
    Doing the same deployment twice — once by clicking, once by scripting — teaches the mapping between portal concepts and CLI parameters. The CLI version is the one you keep.
  2. Create a 2-instance VMSS with a CPU-based autoscale rule; generate load and watch instance count change.
    Generate synthetic load, watch the metric cross the threshold, and observe a new instance join the set. Autoscale is only real once you have watched it fire.
  3. Publish a static site to App Service; add a staging slot and perform a swap with slot settings.
    Deploy to the staging slot, verify it, then swap — and confirm the sticky setting stayed with the slot. The swap is the zero-downtime deployment in its simplest form.
  4. Run a container group in ACI with an environment variable and a mounted Azure Files volume.
    Pass configuration via environment and persistent data via the file share. The container stays stateless; the state lives in the volume — the pattern that makes containers safe.

Self-check

Why do availability zones beat availability sets for datacenter-level fault tolerance?
Answer: Sets spread VMs across racks inside one datacenter (fault/update domains); zones spread them across physically separate datacenters. Zones survive datacenter-level failure; sets do not.
What must be true of app settings for them to be 'sticky' to a deployment slot?
Answer: The app setting must be marked as a slot setting. Sticky settings stay with the slot during a swap (e.g. a staging connection string); non-sticky settings travel with the swap to production.
When would VMSS flexible orchestration be chosen over uniform?
Answer: Flexible when the fleet is heterogeneous (mixed VM types) or you are migrating standalone VMs into a set. Uniform when instances are truly identical and interchangeable — the classic elastic web tier.

Module 5

Virtual Networking

Learning objectives

  • Design VNet address space, subnets, and delegation for multi-tier applications.
  • Control traffic with NSGs, ASGs, and route tables including forced tunneling concepts.
  • Connect networks via peering, VPN gateways, and understand ExpressRoute circuit concepts.
  • Provide name resolution with Azure DNS private zones and choose a load-balancing solution.

Key concepts, explained

VNet CIDR planning, subnet sizing, reserved addresses, delegated subnets

A virtual network is your private address space in Azure, defined by CIDR blocks you choose. Plan it like real estate: large enough for growth, non-overlapping with on-premises ranges you will connect to, and subdivided into subnets per tier — web, app, data — sized with headroom.

Azure reserves a few addresses in each subnet (network, gateway, DNS, broadcast equivalents), and delegated subnets hand control of a subnet to a specific Azure service. The common failure is sizing subnets too tightly and discovering the service you need requires delegation space you did not leave.

NSG rule evaluation: priority order, 5-tuple, default rules, service tags

Network security groups filter traffic by rules evaluated in priority order — lower number wins — each matching on the 5-tuple: source, source port, destination, destination port, protocol. The first matching rule decides: allow or deny.

Default rules sit at the bottom: allow VNet-internal traffic and Azure load balancer probes, deny everything inbound from the internet. Service tags (like VirtualNetwork or AzureLoadBalancer) name Azure-defined address groups so rules survive IP changes. Design rule sets top-down: specific allows first, broad denies last, defaults as the backstop.

Application Security Groups for workload-based grouping

Application security groups let you tag VM network interfaces by workload role — "web-servers," "db-servers" — and write NSG rules against those labels instead of IP ranges. When a new web server joins, it inherits the right rules by joining the group.

This decouples security policy from addressing: the rule "web-servers may reach db-servers on 1433" stays correct as instances come and go. Use ASGs wherever NSG rules would otherwise hardcode IPs that autoscale will invalidate.

VNet peering: transitive routing limits, gateway transit, cross-region peering

VNet peering connects two virtual networks with low-latency private connectivity, as if they were one network. Peering is explicitly non-transitive: if A peers with B and B peers with C, A cannot reach C through B — each relationship must be peered directly.

Gateway transit is the controlled exception: a peered VNet can use the other VNet's VPN or ExpressRoute gateway to reach on-premises, when configured. Cross-region peering extends the same model across regions. Design hub-and-spoke topologies with these rules in mind: the hub peers with every spoke, and transit is granted deliberately.

VPN gateway SKUs, site-to-site vs point-to-site, BGP basics

A VPN gateway connects your VNet to on-premises over encrypted IPsec tunnels. Site-to-site connects whole networks (branch office to Azure); point-to-site connects individual clients (remote workers to Azure). Gateway SKUs set the throughput and feature ceiling — size by expected traffic, not by optimism.

BGP (Border Gateway Protocol) exchanges routes dynamically between Azure and on-premises, so new subnets propagate automatically instead of requiring static route updates on both sides. For anything beyond a single static tunnel, BGP is worth the small configuration cost.

ExpressRoute: circuits, peering types (private, Microsoft), FastPath

ExpressRoute is a private, dedicated connection from your network to Azure through a connectivity provider — not over the public internet, with more predictable latency and throughput than VPN. A circuit is the provisioned connection; peering types define what it carries: private peering reaches your VNets, Microsoft peering reaches Microsoft 365 and other public services.

FastPath sends traffic directly to VMs in the VNet, bypassing the gateway for lower latency. ExpressRoute costs significantly more than VPN and takes weeks to provision — choose it for sustained high-throughput or compliance-driven private connectivity, not for convenience.

DNS: Azure-provided vs private DNS zones, split-horizon concepts

Every VNet gets Azure-provided DNS for internal name resolution, but private DNS zones give you authoritative control: define your own zone (corp.internal) whose records resolve only inside linked VNets. This is how private endpoints and internal services get stable names.

Split-horizon DNS serves different answers inside and outside: the same name resolves to a private IP internally and a public IP externally. It is the standard pattern for services reachable from both the office/VNet and the internet.

Load Balancer (L4) vs Application Gateway (L7/WAF) vs Front Door vs Traffic Manager

Azure has four load-balancing answers at different layers. Load Balancer is layer 4 — TCP/UDP distribution within a region, with inbound NAT and outbound rules. Application Gateway is layer 7 — HTTP routing, TLS termination, and an optional web application firewall. Front Door is the global layer-7 front end with edge caching and instant failover across regions. Traffic Manager is DNS-based global routing.

Choose by need: regional TCP spreading wants Load Balancer; HTTP routing and WAF want Application Gateway; multi-region web with fast failover wants Front Door; non-HTTP global distribution wants Traffic Manager. Matching the scenario to the layer is the whole decision.

Hands-on labs

  1. Build two peered VNets with a web tier and DB tier; enforce DB access with an NSG allowing only the web subnet.
    This is the classic three-tier network in miniature: peering for connectivity, NSG for segmentation. Test that the web tier reaches the database and that a jump host in a third subnet does not.
  2. Add a route table sending internet egress through a virtual appliance hop to observe UDR behavior.
    User-defined routes override Azure's default system routes. Forcing egress through an appliance demonstrates how traffic steering works — and how a misconfigured route blackholes everything.
  3. Create a private DNS zone resolving a private endpoint hostname inside the VNet.
    Link the zone to the VNet, add the record, and resolve it from a VM inside. The private name resolving to a private IP is the moment private DNS clicks.
  4. Stand up an internal Load Balancer across two VMs and verify session distribution.
    Send traffic through the load balancer and confirm both backends serve requests. Then stop one backend and watch health probes pull it from rotation.

Self-check

In what order are NSG rules evaluated, and which default rule denies inbound internet traffic?
Answer: Priority order, lowest number first; the first matching rule wins (allow or deny). The built-in default rule DenyAllInBound (priority 65000) denies inbound internet traffic that no custom rule allowed.
Why is VNet peering non-transitive, and how does gateway transit change the design?
Answer: A↔B and B↔C peering does not give A a path to C — each pair must peer directly. Gateway transit is the controlled exception: a spoke can use the hub's VPN/ExpressRoute gateway to reach on-premises when configured.
Match four scenarios to Load Balancer, Application Gateway, Front Door, and Traffic Manager.
Answer: Regional TCP spreading → Load Balancer (L4). HTTP routing + WAF → Application Gateway (L7). Multi-region web with fast failover → Front Door. Non-HTTP global distribution → Traffic Manager (DNS).

Module 6

Monitoring and Alerting

Learning objectives

  • Build an Azure Monitor observability baseline: metrics, logs, and the Activity log.
  • Write KQL queries in Log Analytics to answer operational questions.
  • Configure alert rules with action groups and sensible thresholds to avoid alert fatigue.
  • Use Network Watcher tools to diagnose connectivity and packet flow.

Key concepts, explained

Data platform: metrics (time-series) vs logs (Log Analytics workspaces)

Azure Monitor collects two fundamentally different telemetry types. Metrics are numeric time series — CPU percent, request count, disk queue depth — cheap to store, fast to query, ideal for alerting on thresholds. Logs are rich semi-structured records — every request, every sign-in, every deployment event — stored in Log Analytics workspaces and queried with KQL.

The discipline: alert on metrics, investigate with logs. Metrics tell you something is wrong within seconds; logs tell you why within minutes. Sending everything to logs is expensive; sending nothing to logs leaves you blind during incidents.

KQL essentials: where, project, summarize, joins, timechart

The Kusto Query Language is the read path for all Azure logs. Its core verbs compose like a pipeline: where filters rows, project selects columns, summarize aggregates (count, avg, percentiles) by groups, join correlates tables, and render timechart turns a time-bucketed aggregation into a graph.

Learn KQL by answering real questions — "which users failed sign-in most this week?" — not by memorizing verbs. A working analyst's KQL is twenty verbs used fluently, and every investigation sharpens it.

Alert anatomy: signal, condition, evaluation frequency, action groups, alert processing rules

An alert rule names a signal (a metric or log query), a condition (threshold, operator, aggregation window), and an evaluation frequency (how often to check). When the condition holds, the rule fires into action groups — the notification and webhook targets — optionally shaped by alert processing rules that suppress or schedule notifications.

The failure modes are all here: thresholds without aggregation windows flap, evaluation frequencies slower than the incident miss it, and action groups that page everyone for everything train everyone to ignore pages. Design alerts like you design code: deliberately, and with tests.

Diagnostic settings: routing platform logs to workspaces, storage, or event hubs

Azure resources do not log verbosely by default; diagnostic settings decide where each resource's platform logs and metrics go — a Log Analytics workspace for analysis, a storage account for cheap long-term retention, an event hub for streaming to external SIEMs.

Enable diagnostics as part of provisioning, not after the first incident. The logs you need during an outage are the ones you configured last quarter.

Activity log vs resource logs vs Entra sign-in logs

Three log streams answer three questions. The Activity log records control-plane operations — who created, deleted, or modified what, and when. Resource logs (diagnostic logs) record data-plane behavior — what the service itself did. Entra sign-in logs record authentication events — who signed in, from where, with what result.

Incident triage starts by picking the right stream: "who deleted the resource?" is the Activity log; "why is the app returning 500s?" is resource logs; "was this account compromised?" is sign-in logs.

Network Watcher: IP flow verify, connection troubleshoot, packet capture, NSG diagnostics

Network Watcher is the packet-level truth for Azure networking. IP flow verify answers "would this NSG rule allow this packet?" without sending traffic. Connection troubleshoot tests end-to-end TCP connectivity and names the blocking hop. Packet capture grabs real packets from a VM for Wireshark-level analysis.

When connectivity fails, work this toolkit in order: verify the NSG decision, test the connection, capture the packets. Guessing at routing tables before checking the NSG verdict wastes the most time.

Azure Service Health vs Resource Health

Service Health reports Azure-wide issues — region outages, planned maintenance — that affect your services from the outside. Resource Health reports the health of your specific resources as Azure sees them — is this VM actually running, or has the platform flagged it?

During an incident, check both: Service Health tells you whether to wait for Microsoft, Resource Health tells you whether the problem is yours. Conflating them sends you debugging your configuration during a platform outage.

Hands-on labs

  1. Enable diagnostics on a VM sending metrics to a Log Analytics workspace; write KQL for top CPU processes.
    Wire the diagnostics, generate load, then write the query that ranks processes by CPU. The full loop — configure, generate, query — is the observability muscle.
  2. Create a metric alert on VM CPU > 80% for 5 minutes wired to an email action group.
    Set the threshold, the aggregation window, and the action group, then trigger it with load. Receiving the actual alert email closes the loop between configuration and reality.
  3. Query the Activity log in KQL for all write operations in the last 24 hours.
    The Activity log answers "what changed?" — the first question in any configuration-drift investigation. Practice reading it before you need it.
  4. Use IP flow verify to confirm an NSG rule blocks a test flow, then fix the rule and re-verify.
    Verify the block, edit the rule, verify the allow. The before-and-after proves both the tool and your understanding of rule evaluation.

Self-check

Write a KQL query returning failed sign-in attempts grouped by user in the last 7 days.
Answer: SigninLogs | where TimeGenerated > ago(7d) | where ResultType != 0 | summarize failures = count() by UserPrincipalName | sort by failures desc — ResultType 0 means success; anything else is a failure.
What three components must an alert rule define to fire reliably without noise?
Answer: A signal (metric or log query), a condition (threshold, operator, aggregation window), and an evaluation frequency. Miss any one and you get silence or noise.
Which Network Watcher tool proves whether an NSG allowed or denied a specific packet?
Answer: IP flow verify — it evaluates the effective NSG rules against a hypothetical packet (source, destination, port, protocol) and reports allow/deny without sending traffic.

Module 7

Backup and Disaster Recovery

Learning objectives

  • Design backup policies in a Recovery Services vault for VMs, file shares, and SQL workloads.
  • Perform file-level and full-VM restores and validate recovery points.
  • Explain Azure Site Recovery replication, failover, and failback concepts.
  • Harden vaults against ransomware: soft delete, immutable vaults, and private endpoints.

Key concepts, explained

Recovery Services vault vs Backup vault; MARS agent vs VM extension approaches

Backup configuration lives in vaults: the Recovery Services vault is the classic vault for Azure VMs, on-premises servers via the MARS agent, and file shares; the newer Backup vault serves newer workload types. The vault holds the policies, the recovery points, and the access controls.

For Azure VMs, backup runs through the VM backup extension — no agent to install. For on-premises machines, the MARS (Microsoft Azure Recovery Services) agent does the job. Know which path your workload takes, because troubleshooting starts there.

Backup policy: frequency, retention ranges (daily/weekly/monthly/yearly), GFS rotation

A backup policy states how often to back up and how long to keep each recovery point. The GFS (grandfather-father-son) rotation keeps daily points for days, weekly points for weeks, monthly points for months, and yearly points for years — recent granularity where you need it, long history where compliance demands it.

Design retention from requirements: RPO sets the frequency, compliance sets the long tail. The policy is a cost decision as much as a safety decision — every retained point has a storage bill.

Recovery points: crash-consistent vs application-consistent (VSS)

A crash-consistent recovery point captures the disks as if the power had been cut — the data is there, but in-flight application state may not be. An application-consistent point uses VSS (Volume Shadow Copy Service) to quiesce applications first, so databases and transaction logs are in a clean state.

For databases and transactional workloads, application-consistent points are what make restores trustworthy. Crash-consistent is fine for stateless tiers; never assume it is fine for a database.

Restore options: original location, alternate location, file-level recovery

Recovery is not one operation: full-VM restore to the original location rebuilds the machine in place; alternate-location restore builds a copy beside production for validation; file-level recovery mounts the recovery point and extracts individual files without restoring the whole VM.

Practice all three before you need them. The restore you have rehearsed is the restore that works at 3 AM; the restore you are reading about for the first time is a gamble.

Site Recovery: replication policy, RPO thresholds, test failover vs planned failover

Azure Site Recovery replicates VMs to a second region continuously, with a replication policy defining the recovery-point frequency and retention. When disaster strikes, failover brings the replicated VMs up in the secondary region; failback reverses the direction when the primary recovers.

A test failover spins up the replicated VMs in an isolated network to prove the plan works — without touching production. A planned failover is the real thing, with an expected brief downtime. Test failovers are how DR plans stay honest; run them on a schedule.

Soft delete, security PIN, immutability, cross-region restore

Backups are a ransomware target, so vaults harden themselves: soft delete retains deleted backup data for a retention period so malicious deletion is recoverable; immutability locks recovery points against any deletion or modification; cross-region restore keeps a usable copy outside the primary region's fate.

Enable all three for production vaults. A backup that an attacker can delete is not a backup — it is a false sense of security with a storage bill.

Backup storage redundancy: LRS vs GRS vault storage

The vault's own storage can be locally redundant (LRS — three copies in one datacenter) or geo-redundant (GRS — replicated to a paired region). GRS costs more and protects against regional disaster; LRS is cheaper and sufficient when the vault's region is not your disaster scenario.

Match the vault redundancy to the disaster you are planning for. If the plan is "survive losing this region," the backups must live somewhere that survives it too.

Hands-on labs

  1. Enable VM backup with a custom policy (daily + weekly retention); trigger an on-demand backup.
    Configure the policy from your retention requirements, then trigger an immediate backup to prove the pipeline works before the first scheduled run.
  2. Delete a test file inside the VM, then perform a file-level restore from the recovery point.
    The delete-then-restore loop is the smallest complete backup test. If file-level recovery works, the chain from policy to recovery point to restore is proven.
  3. Walk through a Site Recovery test failover plan for a single VM on paper, listing rollback steps.
    Write the plan as a runbook: prerequisites, failover steps, validation checks, and the rollback path. Paper plans reveal gaps that clicking through a wizard hides.
  4. Enable soft delete on the vault and attempt to delete a backup item to observe protection.
    Try to destroy a backup and watch the vault refuse or retain it. The protection is only real if you have tested the attack it defends against.

Self-check

What distinguishes a crash-consistent recovery point from an application-consistent one?
Answer: Crash-consistent captures disks as if power were cut — in-flight app state may be lost. Application-consistent uses VSS to quiesce applications first, so databases restore cleanly. Never trust crash-consistent for a database.
Why run a test failover instead of a planned failover when validating a DR plan?
Answer: Test failover spins up replicated VMs in an isolated network — it proves the plan works without touching production or committing to the failover. Planned failover is the real thing, with real downtime.
Which vault settings protect backups from malicious deletion?
Answer: Soft delete (deleted backup data retained for a period), immutability (recovery points locked against deletion/modification), and cross-region restore (a usable copy outside the primary region's fate).

Module 8

Administration Tooling and Exam Execution

Learning objectives

  • Work fluently in Azure CLI, Azure PowerShell, and Cloud Shell for day-to-day administration.
  • Read and parameterize ARM templates and Bicep files for repeatable deployments.
  • Manage subscriptions, quotas, cost alerts, and support requests as an administrator.
  • Apply an exam-day strategy: lab-first pacing, process of elimination, and flag-and-return discipline.

Key concepts, explained

az vs Az modules: subscription context, --query JMESPath, idempotent scripting

The Azure CLI (az) and Azure PowerShell (Az modules) are the two scripting interfaces, and fluency in at least one is non-negotiable. Both operate in a subscription context — set it explicitly per command or per session, because running against the wrong subscription is a classic and expensive mistake.

The CLI's --query flag filters JSON output with JMESPath, turning verbose responses into scriptable values. Write scripts idempotently — create-if-missing rather than blind create — so re-runs converge instead of erroring.

Cloud Shell: storage persistence, environment variables, editor integration

Cloud Shell is a browser-based shell with the CLI, PowerShell, and common tools preinstalled and pre-authenticated to your tenant. It persists files in an attached storage account across sessions, so scripts and history survive.

It is the fastest path to a working Azure shell from any machine — but it is also a shared, ephemeral-feeling environment, so treat anything important as code stored in a repo, not as files in the shell.

ARM template structure: parameters, variables, resources, outputs; deployment modes

ARM templates declare Azure infrastructure as JSON: parameters are the inputs, variables the computed values, resources the things to create, outputs the values to return. The template is the deployment's source of truth, reviewed and versioned like code.

Deployment modes matter: complete mode makes the resource group match the template exactly (deleting anything not declared — powerful and dangerous), while incremental mode only adds or updates. Know which mode you are in before you deploy.

Bicep: modules, symbolic names, what-if deployments, decompiling ARM

Bicep is the modern infrastructure-as-code language for Azure: cleaner syntax than ARM JSON, compiling down to ARM templates. Modules compose deployments from reusable files, symbolic names replace fragile string references between resources, and existing ARM JSON can be decompiled into Bicep as a migration path.

The what-if operation previews exactly what a deployment would create, modify, or delete — the mandatory review step before any production deployment. Bicep plus what-if is the professional deployment workflow.

Cost Management: budgets, alerts, cost analysis scopes, tagging for chargeback

Cost Management turns the metered bill into actionable data: budgets set spending thresholds with alert actions at percentages of the budget, cost analysis breaks spend down by scope — subscription, resource group, tag — and tagging makes chargeback to teams possible.

Set budget alerts on every subscription on day one, including lab subscriptions. The tagging standard from the governance module is what makes cost analysis meaningful — untagged resources are unattributable spend.

Quotas, support plans, and service limit requests

Every subscription has quotas — caps on vCPUs per region, public IPs, storage accounts — that gate how much you can deploy. Hitting a quota looks like a deployment failure, so check quotas before diagnosing anything else when provisioning fails at scale.

Quotas can be raised through support requests, and support plans define how fast Microsoft responds. Know your plan's response times before an incident, not during one.

Exam mechanics: case studies, labs, review screens; time budgeting per question

The AZ-104 exam mixes multiple-choice questions with case studies — multi-question scenarios built on a shared business background — and hands-on lab tasks in a live Azure environment. The review screen lets you flag questions and return to them, which is a strategic tool, not an afterthought.

The exam-day discipline: answer confidently-known questions first, flag the uncertain ones, and return with remaining time — never leave a question blank, since there is no penalty for wrong answers. Budget your time per question up front and check the clock at the halfway mark.

Hands-on labs

  1. Write a 10-line bash script using az CLI that creates an RG, VNet, and VM idempotently.
    Guard each creation step with an existence check so the script converges on re-run. Ten lines of idempotent scripting beats fifty lines of click-ops documentation.
  2. Author a Bicep file deploying a storage account and App Service plan; run what-if before deploying.
    Write the Bicep, run what-if, read the preview carefully, then deploy. The what-if output is the change review — treat discrepancies as findings, not noise.
  3. Create a budget alert at 80% of a $50 monthly cap scoped to your lab subscription.
    The alert is your financial circuit breaker. Scope it to the lab subscription so experiments cannot surprise you, and confirm the notification arrives.
  4. Do a timed 20-question drill: answer, flag uncertain items, return once — measure accuracy vs speed.
    Simulate the exam rhythm on practice questions: first pass for confident answers, flagged items on return, clock awareness throughout. The drill trains pacing, which is half the exam.

Self-check

What does a Bicep what-if run tell you that a plain deployment does not?
Answer: Exactly what the deployment would create, modify, or delete — the change preview — without touching anything. A plain deployment just executes; what-if is the mandatory review step before production changes.
How do you scope an az command to a specific subscription without changing global context?
Answer: Pass --subscription <id-or-name> on the command, or run az account set --subscription for the session. Per-command scoping is safer in scripts.
What is your personal time budget per question for a 45-question exam session?
Answer: No universal number — compute it on exam day: total minutes ÷ question count, minus a buffer for case studies and review. Write it down before starting, check the clock at the halfway mark, and never leave a question blank.
