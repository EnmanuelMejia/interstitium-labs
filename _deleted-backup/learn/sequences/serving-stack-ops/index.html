Serving Stack Ops: Production Inference with vLLM

One model, many users, bounded hardware: the throughput engineering that separates a demo from a service — paged memory, batched scheduling, honest deployment, and observability you can actually page on.

Start the sequence All sequences

SCIENTIA OMNIA VINCIT

The premise

Serving is not inference-plus-one-user.

A desktop runtime optimizes one user's latency: get the next token out fast. A serving stack optimizes throughput under contention: fifty engineers asking questions at once, each expecting an answer, on hardware that does not grow. That is a different engineering problem — memory layout, scheduling, queueing, and observability — and it has different tools. This sequence teaches the stack around vLLM, the open-source serving engine that has become the reference implementation of modern inference serving.

The honesty contract of this sequence: we teach mechanisms, not throughput numbers. Vendors and papers quote 2–4x figures from specific evaluations on specific hardware in specific years; none of that transfers to your hardware. Every time this page dates a claim (2026-10-07), it is because the serving landscape moves fast — text-generation-inference is archived, docs paths get restructured, projects reposition. Re-verify before you build.

Your progress: 0/5 modules complete — saved in this browser.

5 modules plus a build lab, in order.

Mechanisms first, deployment second, gateways and observability last. Each module ends with a self-check; the build lab asks you to write a real production serving plan.

Module 1

Throughput fundamentals: where the memory goes

Learning objectives

  • Explain the prefill/decode split and why decode is memory-bandwidth-bound
  • Explain PagedAttention as an operating-system idea applied to the KV cache
  • Distinguish continuous batching, chunked prefill, and prefix caching as three scheduling decisions
  • Refuse throughput numbers as facts — mechanisms transfer, measurements do not

Key concepts, explained

Prefill and decode: two workloads wearing one trench coat

Every request has two phases. Prefill reads the whole prompt at once and builds the key-value cache — a compute-heavy, parallel-friendly burst. Decode emits one token at a time, each step re-reading the cache — sequential, and bottlenecked by memory bandwidth, not by the GPU's arithmetic units. Any serving story that ignores this split is fiction: prefill wants batching to amortize, decode wants memory efficiency. The whole serving stack exists to serve both masters at once.

PagedAttention: virtual memory for the KV cache

The naive implementation reserves one contiguous block of memory per request — and since request lengths vary, most of that reservation sits empty while still counting against the budget. PagedAttention (Kwon et al., September 2023, presented at SOSP 2023) treats the KV cache like an operating system treats RAM: fixed-size blocks allocated on demand, mapped like virtual-memory pages. The paper's own evaluation reports near-zero KV-cache memory waste and block sharing within and across requests — and that "within and across requests" matters: shared system prompts and parallel sampling reuse the same blocks instead of duplicating them.

Two honesty notes, both load-bearing. First: vLLM's own design doc for PagedAttention carries a warning that it is historical and no longer describes the code — ground your understanding in the paper and the current README, not the design doc. Second: the paper's 2–4x throughput figures are a 2023 evaluation against the baselines of that era on the hardware of that era. They are not your numbers. The transferable lesson is the mechanism — paged blocks, shared across requests — not the measurement.

The scheduling trio

Continuous batching keeps the batch full at the iteration level: as one request finishes, another starts — no waiting for the whole batch to complete like the old static-batching days. Chunked prefill splits a long prompt into chunks so one huge prefill cannot stall everyone else's decoding. Prefix caching reuses the cached key-value blocks of shared prefixes (a system prompt thousands of requests share) instead of recomputing them. These are three scheduling decisions with three separate names because they solve three separate contention problems.

Self-check

  • Why is decode memory-bandwidth-bound while prefill is compute-bound?
  • What did PagedAttention borrow from operating systems, and what does block sharing buy?
  • A vendor quotes a 3x throughput number for a serving engine. What do you ask before believing it?

Module 2

vLLM: the library and the server are different machines

Learning objectives

  • Choose between the LLM class and vllm serve by ops posture, not habit
  • Name what the server adds: endpoints, health, metrics, queue policy
  • Recognize that EngineArgs are the same vocabulary in both paths

Key concepts, explained

One engine, two postures

vLLM is both a Python library and an HTTP server, and the discipline is knowing which one you are operating. The library path (LLM class) is for offline and batch inference: your process owns the model, runs the prompts, and exits. The server path (vllm serve <model>) is a long-lived OpenAI-compatible HTTP service. Same engine, same EngineArgs vocabulary in both — the difference is everything the server has to be while it stays up.

What the server adds

The server's documented endpoints are the interface contract: /v1/chat/completions and /v1/completions for generation, /v1/embeddings, /tokenize, plus the ops surface — /health, /ping, and /metrics. Those last three are the whole point of the server posture: /health is what load balancers and Kubernetes probes check, /metrics is the Prometheus stream your dashboards read (module 5), and queue policy decides what happens when demand exceeds capacity — queued requests can be rejected with HTTP 503 once the queue limit is hit. A batch script needs none of this; a production service needs all of it. Do not pick the posture by habit — pick it by whether anyone will be paging you.

Self-check

  • A nightly batch job scores a million support tickets. Library or server?
  • Which three endpoints make the server posture operationally different from the library?
  • Where do queue limits surface to the caller?

Module 3

Deploying the server: Docker, engine args, Kubernetes

Learning objectives

  • Launch the official container with the shared-memory configuration it actually needs
  • Set the five engine arguments that decide whether your server fits your hardware
  • Describe the Kubernetes shape: probes, model-cache PVC, shared memory, secrets

Key concepts, explained

Docker: the official images and the shm gotcha

The project publishes official images — vllm/vllm-openai for CUDA, plus -rocm and -xpu variants — and the deployment docs carry one configuration that trips up nearly every first deployment: tensor-parallel inference needs shared memory, so the container must run with --ipc=host or an explicit --shm-size. Without it, multi-GPU serving fails in ways that look like driver bugs but are really just a small /dev/shm. The images can also run as the non-root vllm user — least privilege applies to inference servers too.

The five engine arguments that matter first

Open the engine-argument reference (the canonical path as of 2026-10-07 — the docs were restructured, and older serving/ paths are stale) and the five arguments that decide fit:

  • --gpu-memory-utilization (default 0.92) — the fraction of GPU memory the engine claims; the rest is headroom for the runtime itself.
  • --max-model-len — the context window (prompt + output), auto-derived to fit by default; this is where the KV cache competes with the weights.
  • --max-num-seqs / --max-num-queued-reqs — concurrency and queue depth; exceed the queue and the caller gets HTTP 503, which is the load-shedding contract your gateway must handle.
  • --kv-cache-memory-bytes — an explicit per-GPU KV-cache size that overrides the utilization fraction; the manual lever when you know your workload.
  • --block-size — tokens per KV-cache block: the page size of the PagedAttention system from module 1.

The scheduling policy (fcfs default, or priority) and the watermark (fraction of KV blocks kept free) complete the picture: these are the knobs between "fast" and "alive."

Kubernetes: the production shape

The documented K8s deployment is a Deployment plus a Service: /health backing liveness and readiness probes, a persistent volume claim for the Hugging Face model cache (models are large; re-downloading per pod restart is a rookie tax), an emptyDir volume for the shared memory the tensor-parallel path needs, and a Secret for the Hugging Face token. gRPC serving is available via a flag for services that speak gRPC. The community alternatives — Helm charts, KServe, the vllm-project/production-stack, llm-d, AIBrix, NVIDIA Dynamo — exist, but start from the native manifests: understanding the primitives makes every higher-level stack legible.

Self-check

  • Why does a multi-GPU vLLM container need --ipc=host or --shm-size?
  • Your queue depth is exceeded. What HTTP status do callers see, and whose problem is it?
  • Why does the K8s deployment put the model cache on a persistent volume?

Module 4

Scaling out: parallelism and quantized serving

Learning objectives

  • Choose between tensor, pipeline, and data parallelism by what you are constrained on
  • Name the documented quantization formats and read the per-architecture compatibility table
  • Explain why quantized serving is a deployment choice, not a quality claim

Key concepts, explained

The parallelism vocabulary

One GPU stops being enough along exactly three axes, and each axis has a flag: tensor parallelism (--tensor-parallel-size) splits each layer's matrices across the GPUs in one node — for when the model does not fit one card; pipeline parallelism (--pipeline-parallel-size) stages layers across devices — for when you want to pipeline stages of the network; data parallelism (--data-parallel-size) replicates the model and splits the requests — for when the model fits but the request rate does not. Mixture-of-experts models get their own --enable-expert-parallel, and prefill/decode context parallelism handles long contexts. Multi-node setups add --nnodes, --node-rank, and the master address/port. The discipline: name your constraint first (fit? throughput? latency?), then pick the flag that addresses it — never "turn them all on and see."

Quantized serving, honestly

vLLM documents a wide set of quantization formats — AutoAWQ, BitsAndBytes, GPTQModel, LLM Compressor (FP8 W8A8, INT4 W4A16, INT8 W4A8/W8A8), NVIDIA Model Optimizer, AMD Quark, GGUF, TorchAO, FP8 generally — plus quantized KV cache and online quantization, with a compatibility table spanning GPU generations from Volta through Hopper, plus AMD, Intel GPU, and CPU. Two honesty notes. First, these are formats the engine can serve, not endorsements of each format's quality — the page that documents a format is not claiming it is the right choice for your model. Second, check the architecture row for your hardware before you plan around a format: a quantized-serving plan that ignores the compatibility table is a plan to discover the table at 2 AM. Continuous batching's siblings from the README — speculative decoding and prefix caching — are listed as first-class throughput features; treat them as mechanisms to learn, not numbers to quote.

Self-check

  • The model fits one GPU but request volume tripled. Which parallelism flag, and why?
  • A teammate says "we'll serve GPTQ because it's the fastest." What is wrong with that sentence?
  • Before planning a quantized-serving deployment, which two pages do you read?

Module 5

Gateways and observability: the ops half of serving

Learning objectives

  • Explain why a gateway sits in front of serving engines in production
  • Route a client through LiteLLM to a hosted vLLM server using the current documented pattern
  • Read a vLLM Prometheus metric set and name the three latency signals that matter
  • State the 2026-10-07 landscape accurately — and why it will change

Key concepts, explained

The gateway layer: LiteLLM

In production, clients rarely talk to one serving engine directly. A gateway presents a single OpenAI-compatible interface and routes behind it — across providers, across engine instances, with virtual keys, load balancing, guardrails, and spend tracking. LiteLLM is the reference open example: its documented vLLM provider pattern routes through model="hosted_vllm/<model-name>" with an api_base pointing at your server. One deprecation to respect: the older vllm/ prefix is deprecated in favor of hosted_vllm/ — copy the current pattern from the provider docs, not from a 2024 blog post. The gateway is also where the 503s from module 3's queue policy get handled gracefully: retries, failover, and backoff live here, not in every client.

Observability: metrics you can page on

vLLM's server exposes a Prometheus-compatible /metrics endpoint with vllm:-prefixed metrics, and the metrics design page ships a Grafana reference dashboard. The three latency signals every serving deployment needs are vllm:time_to_first_token_seconds (TTFT — time to first token), vllm:inter_token_latency_seconds (per-token pace), and vllm:e2e_request_latency_seconds, alongside server-level signals: running request count, queue length, and vllm:kv_cache_usage_perc. Learn to read these three together: TTFT spiking with stable inter-token latency means prefill contention; both rising means the whole system is saturated; KV cache at 100% means your --max-num-seqs math from module 3 was optimistic. Observability is what turns "the model is slow" from a complaint into a diagnosis.

The landscape, dated 2026-10-07

Three facts about the serving landscape, all dated because all three will change. Text-generation-inference (TGI) is archived/in maintenance mode — its own README now recommends vLLM and SGLang going forward, which makes it a dependency-risk lesson, not a deployment option. SGLang (hosted by LMSYS) is the live alternative whose project acknowledges learning design and reusing code from vLLM. And vLLM's own docs restructure frequently — engine args moved from serving/ to configuration/, metrics from serving/ to design/, deployment docs to deployment/ — so any URL you memorized may be stale. The discipline this module exists to teach: date every infrastructure claim, and re-verify the landscape quarterly before you commit a deployment to it.

Self-check

  • Why does the gateway own retries and backoff rather than each client?
  • TTFT spikes but inter-token latency is stable. Where is the contention?
  • What is the correct LiteLLM model prefix for a hosted vLLM server, and why does it matter that you check?

Build lab

Write the production serving plan.

The capstone is a document, not a deployment: a one-page production serving plan for a 13B-class model on two GPUs serving an internal team of fifty engineers. Write it before you touch a cluster.

The plan must answer, in order

  1. Posture: library or server — and the one sentence that justifies it.
  2. Engine args: --tensor-parallel-size, --gpu-memory-utilization, --max-model-len, --max-num-seqs, --max-num-queued-reqs — each with the reasoning, not just the value. What happens at queue overflow?
  3. Container: which official image, how shared memory is configured, and which user the process runs as.
  4. Kubernetes: probes against which endpoint, where the model cache lives, where shared memory comes from, where the HF token lives.
  5. Gateway: where LiteLLM (or your gateway of choice) sits, how clients route, and how 503s are retried.
  6. Observability: the three latency signals and one alert threshold each — with the failure mode each threshold detects.
  7. Landscape date: the date on the plan, and which claims you re-verified that day (TGI status, the engine-args path, the LiteLLM prefix).

The exit discipline: your plan must name one dependency that could be archived next quarter and how you would migrate. TGI's archival is the worked example on this page — your plan's dependency could be anything. Serving stacks are chosen, monitored, and exited; they are never married.
