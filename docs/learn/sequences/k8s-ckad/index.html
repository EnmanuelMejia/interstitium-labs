Overview

What this sequence is.

This sequence teaches Kubernetes from the application developer's side of the glass: how to package your code as pods, externalize its configuration, run batch and scheduled work, roll out new versions safely, observe what your app is doing, expose it to the world, lock down its network, and give it durable storage. It is organized around the public Certified Kubernetes Application Developer curriculum published by the Linux Foundation and CNCF, but it teaches the engineering underneath — the design patterns and failure modes that make the difference between an app that merely runs on Kubernetes and one that belongs there.

The developer's contract with Kubernetes is simple to state and deep to master: declare what your application needs, let the platform provide it, and build your app to survive the platform's decisions — rescheduling, restarts, scaling, and network partitions. Every module here turns one clause of that contract into working skill.

Who this is for

  • Application developers deploying services, APIs, and workers onto Kubernetes clusters.
  • Backend engineers who want their apps to be good citizens of the platform: observable, configurable, and resilient.
  • DevOps-adjacent developers who write the manifests, Helm charts, or operators their teams run.

Prerequisites

  • You can write and run an application in at least one language (any will do).
  • Basic container literacy: images, containers, and running something with Docker or Podman.
  • Comfort editing YAML and using a command line; kubectl installed and a cluster to practice on (a local one is fine).

How to use this sequence

  • Work the modules in order; later modules assume you can already write a correct pod spec in your sleep.
  • Type every manifest by hand at least once — the exam this curriculum mirrors is hands-on, and so is the job.
  • For each lab, break the working setup afterward and repair it; debugging speed is the skill being trained.
  • Keep a personal cheatsheet of the kubectl one-liners you reach for most; it becomes your runbook.

Module 1

Pod Anatomy and Multi-Container Composition

Pod as the atomic deployable unit: shared network and storage context.

The pod is Kubernetes' atomic unit: the smallest thing you can deploy, and the boundary inside which containers share a network namespace, an IP address, and storage volumes. Containers in the same pod communicate over localhost as if they were processes on one machine, which is what makes the multi-container patterns in this module possible. The pod is also the unit of scheduling and fate — it is placed on one node, and if that node dies, the pod dies with it (controllers recreate it elsewhere, but the pod object itself is mortal). Designing at pod granularity, not container granularity, is the first mental shift Kubernetes asks of developers.

Init containers: sequential setup gates that run to completion before app containers start.

Init containers run to completion, in order, before any application container starts — they are the pod's setup phase. Use them for things the app needs but shouldn't do itself: waiting for a dependency to be reachable, generating configuration files, or running database migrations. If an init container fails, the pod restarts it according to the pod's restart policy and the app containers never start, which makes a failing init container a loud, obvious gate rather than a subtle runtime bug. The rule of thumb: if it must happen before the app starts and must succeed, it's an init container.

Sidecar vs adapter vs ambassador patterns and when each earns its overhead.

Multi-container pods come in three named patterns, each earning its extra container differently. A sidecar runs alongside the main container for its whole life — the log shipper that tails the app's log files is the canonical example. An adapter normalizes the main container's output for the outside world, like a metrics exporter translating app-specific stats into Prometheus format. An ambassador proxies the main container's connections outward, handling concerns like TLS or connection pooling that the app shouldn't know about. The overhead test is real: every extra container costs resources and complexity, so reach for these patterns only when the concern genuinely doesn't belong inside the application container.

Resource requests versus limits: scheduling guarantees vs runtime enforcement and OOM risk.

Requests tell the scheduler how much CPU and memory your container needs to be placed; limits tell the kernel how much it's allowed to actually consume. The gap between them is your burst headroom — and your risk: a container that regularly exceeds its requests can be evicted under pressure, and one that exceeds its memory limit is OOM-killed, no appeal. Setting requests too low gets your pod evicted when the node fills up; setting limits too low gets it killed when it does real work. Production discipline is to measure actual usage, set requests near the steady state, set limits at the tolerable peak, and revisit both as the app evolves.

QoS classes (Guaranteed, Burstable, BestEffort) derived from request/limit pairing.

Kubernetes assigns every pod a Quality of Service class derived purely from its requests and limits: Guaranteed when every container's requests equal its limits, BestEffort when nothing is set, Burstable for everything in between. Under node memory pressure, the kubelet evicts in QoS order — BestEffort pods die first, Guaranteed last — so the class is effectively your pod's priority in a resource crunch. The checkpoint answer falls out of the definition: requests equal to limits on every container is Guaranteed. Choosing your class deliberately, rather than inheriting it by accident, is one of the cheapest reliability wins in the platform.

Namespaces: scoping, resource quotas, and context switching with kubectl config.

Namespaces partition a cluster into virtual clusters: separate name scopes, separate resource quotas, separate RBAC boundaries, all sharing the same control plane. They are how teams, environments, and applications coexist without colliding — the same manifest deploys cleanly into dev and prod namespaces because names only need to be unique within a namespace. kubectl config lets you switch your current context's default namespace, which is both a convenience and a loaded gun: always verify your namespace before applying, especially with destructive commands. Resource quotas per namespace turn "don't hog the cluster" from a social norm into an enforced limit.

Ephemeral container debugging and kubectl exec/attach/cp workflows.

Debugging a running pod has a dedicated toolkit beyond logs: kubectl exec runs a command inside a container, kubectl attach connects to the main process's streams, and kubectl cp moves files in and out. Ephemeral containers — added to a running pod with kubectl debug — are the modern answer to "my production image has no shell": they share the pod's namespaces so you can inspect a distressed container with proper tooling without rebuilding the image. The one-liner the checkpoint asks for is kubectl debug with a target pod and a debug image, which attaches a troubleshooting container to the pod's process namespace. Learn these before you need them; at 3 AM you want reflexes, not documentation.

Learning objectives

  • Declare pod specs imperatively and declaratively with correct container fields.
  • Compose sidecar, adapter, and ambassador multi-container pods for a single primary workload.
  • Control pod scheduling with node selectors, affinity hints, and resource requests/limits.
  • Manage pods across namespaces with context switching and default-namespace discipline.

Hands-on labs

  1. Lab: Build a pod with an init container that writes a config file to an emptyDir before the app starts.

    1. Write a pod manifest with an init container (busybox) that writes a config file into an emptyDir volume, and an app container that reads that file on startup.
    2. Apply it and watch the pod phases: Init:0/1 while setup runs, then the app container starting only after the init completes.
    3. Break the init container's command on purpose and observe the pod never reaching Running — the setup gate working as designed.

  2. Lab: Add a log-shipping sidecar to a busy app container and verify shared-volume visibility.

    1. Take a pod running a chatty application and add a sidecar container that tails the shared log volume and forwards lines (even just to its own stdout).
    2. Verify from the sidecar's logs that it sees the app container's output via the shared volume — the sidecar pattern made visible.
    3. Discuss with yourself what the app would have to do without the sidecar, and why the separation is worth the extra container.

  3. Lab: Set requests/limits on a workload, then trigger OOMKill and observe the pod event trail.

    1. Deploy a workload with a memory limit deliberately set below what a small memory-hungry program needs, and run the program.
    2. Watch kubectl describe report OOMKilled and the pod's event trail narrate the kill; note the exit code 137.
    3. Raise the limit to a sane value, redeploy, and confirm the workload completes — you have now seen both sides of the limit contract.

  4. Lab: Create two namespaces, deploy identical manifests into each, and switch contexts to operate both.

    1. Create two namespaces (for example lab-a and lab-b) and deploy the identical manifest into each.
    2. Use kubectl config to switch your default namespace back and forth, operating each copy independently.
    3. Delete one namespace and confirm the other is untouched — the isolation boundary made tangible.

Self-check questions

When does an init container restart, and how does a failing one affect pod phase?
Answer: Init containers run to completion in order before app containers start; if one fails, it restarts (per the pod restartPolicy) and the pod stays in Pending/Init phase — app containers never start until all init containers succeed.
Write a one-line kubectl command to run a temporary debug container inside an existing pod.
Answer: kubectl debug -it <pod> --image=busybox --target=<container> — attaches an ephemeral container sharing the target's process namespace. No manifest editing, removed when the pod is deleted.
Which QoS class does a pod get when requests equal limits on every container?
Answer: Guaranteed — the highest QoS class, evicted last under pressure. (All containers must set both requests and limits, equal, for every resource.)

Module 2

Configuration: ConfigMaps, Secrets, and Injection Paths

ConfigMap data sources: literal, file, and directory imports and their tradeoffs.

A ConfigMap is Kubernetes' answer to "where does configuration live": a named object holding key-value pairs or whole files, decoupled from the container image. You can build one from literals on the command line, from individual files, or from an entire directory — each with tradeoffs: literals are quick but opaque, files preserve structure, directories scale to real config trees. The point is always the same: the image holds code, the ConfigMap holds environment, and the same image runs in dev, staging, and prod with different ConfigMaps. Hardcoding config into an image is the anti-pattern this whole module exists to kill.

Secret types: Opaque, tls, dockerconfigjson, and base64 encoding is not encryption.

Secrets hold sensitive values — passwords, tokens, TLS keys — with the same shape as ConfigMaps but a different contract: values are base64-encoded (not encrypted, merely encoded — anyone who can read the Secret can decode it), and the API server can encrypt them at rest if configured. The typed variants (tls, dockerconfigjson, basic-auth) add validation for their specific formats, catching malformed credentials at creation time. The security truth to internalize: base64 is transport packaging, not a control — real protection comes from etcd encryption at rest, RBAC restricting who can read Secrets, and not logging them. Treat a Secret you can read as plaintext, because it is.

envFrom versus per-key env: bulk injection versus explicit, auditable wiring.

Configuration reaches containers through two injection paths with different ergonomics. Environment variables (individual env entries or bulk envFrom) are simple and familiar, but they are frozen at container start — changing the ConfigMap doesn't change a running process's environment. Volume mounts project config as files, which the kubelet refreshes when the source changes, so file-reading apps can pick up new config without a restart. envFrom is convenient for wholesale injection; per-key env is explicit and auditable — which you choose depends on whether you value brevity or traceability. The twelve-factor discipline underneath: config varies between deploys, code doesn't, so keep them in different objects.

Volume-mounted config: live file updates on kubelet sync versus stale env vars.

Volume-mounted ConfigMaps and Secrets update on the kubelet's sync loop — typically within a minute or two — while environment variables never update for a running container. This asymmetry is the source of real production bugs: "I updated the Secret, why is the app still using the old password?" Because it read it once from the environment at startup. The checkpoint answers: a volume consumer picks up the change automatically (after the sync delay); an env consumer needs a pod restart. Design accordingly — either mount as files and watch for changes, or make config changes part of your rollout (which also gives you rollback).

immutable ConfigMaps/Secrets: performance and consistency wins for static config.

Marking a ConfigMap or Secret immutable freezes its data forever: no updates, which lets the kubelet cache it aggressively instead of watching it, reducing API server load at scale. The tradeoff is that every config change becomes a create-new-object-plus-rollout operation — which is arguably the correct discipline anyway, since it makes config changes versioned and reviewable. The lab's attempted edit demonstrates the guard: the API rejects the update with a clear error, proving immutability is enforced server-side, not a client convention. Use immutable for config that genuinely never changes at runtime; the performance win is real on large clusters.

SubPath mounts: isolating single files without shadowing whole directories.

Mounting a single file from a ConfigMap with subPath isolates just that file into the container without shadowing the rest of the target directory — the alternative (mounting the whole volume at a path) hides everything else that was there. The protection it buys is precise: your app's existing directory tree survives, with one config file overlaid. The cost is that subPath mounts don't receive the automatic updates that whole-volume mounts do — the file is a snapshot from mount time. So subPath is the right tool for surgical single-file injection into a populated directory, with the documented caveat that updates require a remount (i.e., a pod restart).

Learning objectives

  • Externalize configuration into ConfigMaps and sensitive values into Secrets.
  • Inject config as environment variables and as mounted files via volumes.
  • Rotate secrets safely and reason about when pods actually pick up new values.
  • Apply the twelve-factor split: image holds code, config holds environment.

Hands-on labs

  1. Lab: Create a ConfigMap from a directory, inject it as env vars, then remount it as files and diff behavior.

    1. Create a ConfigMap from a directory containing two or three config files, then inject it into a pod first as environment variables (envFrom) and then as a mounted volume.
    2. From inside the pod, compare: env shows the keys as variables, the mount shows them as files — same source, two consumption shapes.
    3. Update the ConfigMap and observe which consumption path reflects the change without a restart, and which doesn't.

  2. Lab: Mount a Secret as a volume, update it, and measure how long the file reflects the change.

    1. Create a Secret, mount it as a volume in a pod, and read the file from inside the container.
    2. Update the Secret's value and time how long until the mounted file reflects the change — this is the kubelet sync delay made measurable.
    3. Repeat with env injection and confirm the env value is frozen until the pod restarts: the checkpoint answer, demonstrated.

  3. Lab: Mark a ConfigMap immutable and attempt an edit; read the API error and explain the guard.

    1. Create a ConfigMap with immutable: true, then attempt to edit it with kubectl edit.
    2. Read the API server's rejection error and explain in your own words what invariant the guard protects.
    3. Create a new immutable ConfigMap with the corrected data and roll your deployment to it — the immutable-config workflow.

  4. Lab: Build an app image with zero baked config and fully parameterize it from ConfigMap plus Secret.

    1. Build a minimal app image that reads all of its configuration (port, greeting message, feature flags) from environment and files, with zero config baked in.
    2. Parameterize it fully from one ConfigMap and one Secret, deploy it, and verify it behaves per the injected values.
    3. Swap the ConfigMap for a different environment's values and redeploy — same image, different behavior: the twelve-factor split, proven.

Self-check questions

After updating a mounted Secret, must you restart the pod for a volume consumer? For an env consumer?
Answer: Volume consumer: no restart needed — kubelet syncs the mounted files (eventually consistent, ~a minute). Env consumer: YES, restart required — env vars are snapshotted at container start. (Exception: subPath mounts never update.)
What does subPath protect you from when mounting a single config file?
Answer: Mounting a whole ConfigMap as a directory would hide the container's existing files at that path; subPath mounts just one file to one path. Trade-off: subPath volumes do NOT receive updates — the file is frozen at mount time.
Why is base64 in Secrets not a security control, and where should real encryption live?
Answer: base64 is an encoding, not encryption — anyone who can read the Secret decodes it trivially. Real protection lives in etcd encryption at rest, RBAC restricting Secret reads, and external secret managers; treat Secret values as sensitive but not encrypted by the encoding.

Module 3

Batch Workloads: Jobs and CronJobs

Job completion semantics: completions count, parallelism, and the success contract.

A Job models finite work: run these pods until N completions succeed, with up to P running in parallel. completions is the success contract (how many pods must finish successfully), parallelism is the fan-out (how many may run at once), and the controller keeps creating pods until the contract is met. This is the shape of batch processing, data migrations, and one-off computations — work with an end, unlike Deployments' endless "keep N running." The mental model that prevents misuse: Deployments maintain a steady state, Jobs drive toward a terminal state.

Restart policies for jobs: OnFailure/Never and why Always is rejected.

Job pods must use restartPolicy Never or OnFailure — Always is rejected, because a Job that "always restarts" could never be observed as complete. OnFailure retries the pod in place (same pod object, container restarted); Never creates a fresh pod for each attempt, which keeps each attempt's logs separately inspectable. The choice is about debuggability versus speed: Never gives you a clean corpse per attempt, OnFailure is cheaper. Either way, the Job's completion accounting only counts successful pod completions, so retries don't corrupt the contract.

BackoffLimit and activeDeadlineSeconds: bounding retries and runaway jobs.

Two knobs bound a Job's misbehavior: backoffLimit caps how many times failed pods are retried before the whole Job is marked failed, and activeDeadlineSeconds caps the total wall-clock time the Job may run before it's killed. Without backoffLimit, a deterministically-failing Job retries forever, burning cluster resources on work that can never succeed. Without activeDeadlineSeconds, a hung Job holds its parallelism slots indefinitely. Setting both is the difference between a batch system and a batch hope — every Job you write in production should carry both.

CronJob schedule syntax and startingDeadlineSeconds for missed schedules.

A CronJob is a Job with a schedule: cron syntax defines when, and the controller creates a Job object at each firing. startingDeadlineSeconds handles missed schedules — if the controller was down longer than this window when a firing time passes, that run is skipped rather than piled up. The schedule uses the controller's timezone context, so "every day at 2 AM" means what the cluster thinks 2 AM is — a classic source of off-by-hours surprises. CronJobs are for recurring batch work: backups, reports, cleanup sweeps — anything where "run this periodically until told otherwise" is the requirement.

ConcurrencyPolicy: Allow, Forbid, Replace for overlapping cron invocations.

concurrencyPolicy decides what happens when a CronJob's schedule fires while the previous run is still going: Allow starts another (overlapping runs), Forbid skips the new firing, Replace kills the old run and starts fresh. Forbid is the safe default for work that must not overlap (backups writing to the same destination); Allow fits idempotent, partitionable work; Replace fits "latest state wins" refresh jobs. Choosing wrong is how you get either corrupted outputs from overlapping writers or silently skipped runs you assumed happened — the policy is part of the job's correctness, not a tuning detail.

TTL-after-finished and manual cleanup of completed job objects.

Finished Jobs accumulate — every CronJob firing leaves a Job object and its pods behind — so Kubernetes offers two cleanup paths: manual deletion and ttlSecondsAfterFinished, which garbage-collects finished Jobs after the given delay. Without one of these, a busy CronJob slowly fills etcd with history, which is both clutter and real storage pressure on the cluster's brain. The production pattern is a short TTL (hours, not days) plus log shipping, so history lives in your logging system rather than in etcd. "Who cleans up the Jobs" should never be an unanswered question in a cluster you operate.

Learning objectives

  • Model one-shot and parallel batch work with Jobs, completions, and parallelism.
  • Schedule recurring work with CronJobs and reason about missed and overlapping runs.
  • Design idempotent job logic so retries and restarts are safe.
  • Inspect and clean up job history with backoff limits and TTL policies.

Hands-on labs

  1. Lab: Run a parallel Job with completions=8, parallelism=4 and watch pod fan-out in real time.

    1. Write a Job with completions: 8 and parallelism: 4 where each pod sleeps a random few seconds then exits 0.
    2. Apply it and watch kubectl get pods in real time: at most 4 running at once, new ones starting as others complete, until 8 successes.
    3. Delete the Job and confirm its pods are cleaned up with it — Job-owned pods have the Job as their owner.

  2. Lab: Make a Job fail on attempt one, then verify backoffLimit stops retries after the configured count.

    1. Write a Job whose container always exits 1, with backoffLimit: 3.
    2. Apply it and count the pod attempts: the Job is marked Failed after the configured retries, not before.
    3. Raise backoffLimit and observe the difference — the retry budget is explicit and visible.

  3. Lab: Deploy a CronJob every minute with concurrencyPolicy Forbid and observe skipped schedules.

    1. Create a CronJob scheduled every minute, with concurrencyPolicy: Forbid, whose job sleeps 90 seconds.
    2. Watch two schedule firings: the second is skipped because the first is still running — check the CronJob's status for the evidence.
    3. Change the policy to Allow and observe overlapping runs; then to Replace and observe the kill-and-restart behavior.

  4. Lab: Write a job whose work is idempotent, kill it mid-run, and confirm a retry produces no duplicate effects.

    1. Write a job that appends a line to a shared file (or increments a counter in a ConfigMap-backed volume) — deliberately non-idempotent at first.
    2. Kill it mid-run, let it retry, and observe the duplicate effect: the corruption idempotency prevents.
    3. Rewrite the work to be idempotent (write-if-absent, or deterministic output names), repeat the kill, and confirm the retry is harmless.

Self-check questions

A CronJob pod is still running when the next schedule fires under each concurrencyPolicy — what happens?
Answer: Allow: start another (overlapping runs). Forbid: skip the new run. Replace: kill the running pod and start fresh. Choose by whether overlapping work is safe.
How do completions and parallelism interact to bound total pod count?
Answer: completions = total successful pods needed; parallelism = max running at once. Total pods created is bounded by completions (+ retries); concurrency never exceeds parallelism.
Why does a Job require restartPolicy OnFailure or Never?
Answer: Jobs track pod completions — Always would restart finished pods forever, breaking the completion accounting. The Job controller needs pods to stay finished so it can count them.

Module 4

Deployments: Rollouts, Rollbacks, and Release Strategies

ReplicaSet ownership: Deployments manage ReplicaSets, which manage pods — never hand-edit replicas.

The ownership chain is strict: a Deployment manages ReplicaSets, and each ReplicaSet manages pods — you never touch the lower layers directly. Every change to the Deployment's pod template spawns a new ReplicaSet and scales the old one down, which is why rollout history is literally the sequence of ReplicaSets the Deployment has owned. Hand-editing a ReplicaSet's replica count is fighting your own controller: the Deployment will "correct" your change on its next reconciliation. The discipline is to treat the Deployment as the only write interface and the ReplicaSet as its implementation detail.

RollingUpdate strategy math: how maxSurge and maxUnavailable set the pod count envelope.

The RollingUpdate strategy is governed by two numbers: maxSurge (how many extra pods above the replica count may exist during the update) and maxUnavailable (how many pods below the replica count the update may tolerate). With replicas=4, maxSurge=1, maxUnavailable=0, the update can run 5 pods at once but never fewer than 4 — the checkpoint's answer, and the shape of a zero-downtime rollout that needs spare capacity. Setting maxSurge=0 and maxUnavailable=1 inverts the tradeoff: no extra capacity needed, but one pod is down at a time. These two integers are the capacity-vs-availability dial for every release you ship.

Revision history via change-cause annotations; rollout pause, resume, and undo.

Every rollout writes revision history, annotated with the change-cause if you record it, which is what makes rollbacks possible: kubectl rollout undo returns the Deployment to a previous ReplicaSet revision. kubectl rollout pause freezes a rollout mid-flight — both the old and new ReplicaSets stay at their current sizes — so you can inspect, test, and then resume or undo. The production habit is to set meaningful change records on every rollout, so history reads like a changelog instead of a sequence of anonymous revisions. A rollout without recorded history is still reversible, but good luck knowing what you're reverting to.

Readiness gates as the rollout safety valve: unready pods block progression.

Readiness probes are the rollout's safety valve: a pod that isn't ready is excluded from Service endpoints, and a rolling update won't proceed past a pod that never becomes ready. This is what prevents a bad release from taking down the fleet — the new ReplicaSet's pods fail readiness, the rollout stalls, and the old version keeps serving. The failure mode to respect is the rollout that stalls forever on a broken readiness probe while maxUnavailable pods are already down: capacity planning and probe correctness are release-safety work, not afterthoughts. Never ship a rollout strategy without knowing exactly what your readiness probe proves.

Blue-green: full parallel stack with a service selector flip; canary: fractional traffic to the new revision.

Blue-green and canary are the two classic release shapes beyond plain rolling updates. Blue-green runs the full new stack (green) alongside the old (blue) and flips the Service selector in one atomic switch — instant rollback by flipping back, but double the capacity during the transition. Canary routes a small fraction of traffic to the new version (two Deployments behind one Service, split by pod labels and replica counts) and watches it before widening — smaller blast radius, but real users hit the new code during evaluation. The blast-radius distinction is the point: blue-green risks the flip moment, canary risks the canary cohort. Choose by which risk your system tolerates better.

Image update semantics: tag changes versus imagePullPolicy Always for :latest.

Updating an image is not just changing a tag: the kubelet's decision to actually pull is governed by imagePullPolicy. With the default policy, a changed tag triggers a fresh pull; but the :latest tag (or any tag reused across builds) with a cached image can silently run the old code — the classic "I pushed a new image and nothing changed" bug. imagePullPolicy: Always eliminates the ambiguity for mutable tags, at the cost of a registry round-trip on every pod start. The production-grade answer is immutable tags (a digest or build ID per release) plus explicit rollout records, so "which code is running" is always answerable from the Deployment spec alone.

Learning objectives

  • Declare Deployments with correct label selectors and replica management.
  • Drive rolling updates with maxSurge/maxUnavailable tuned to capacity constraints.
  • Execute rollbacks with revision history and diagnose failed rollouts.
  • Sketch canary and blue-green release flows on top of Deployments and Services.

Hands-on labs

  1. Lab: Roll a Deployment through three image revisions, then roll back to revision one by number.

    1. Deploy an app at image v1, then roll through v2 and v3 with kubectl set image, recording each change.
    2. Run kubectl rollout history and identify the three revisions; then roll back to revision 1 by number with kubectl rollout undo --to-revision.
    3. Verify the running image tag reverted, and note that the rollback itself created a new revision — history only moves forward.

  2. Lab: Pause a rollout mid-update, inspect the two live ReplicaSets, then resume.

    1. Start a rollout to a new image, then immediately kubectl rollout pause; confirm with get replicasets that old and new coexist at partial sizes.
    2. Inspect both ReplicaSets' pod counts and labels, then kubectl rollout resume and watch the update complete.
    3. Reflect on when you'd use this: pausing a deploy to run smoke tests against the partially-rolled fleet before committing.

  3. Lab: Set maxSurge=0 and maxUnavailable=1 on a 3-replica Deployment and trace the pod replacement order.

    1. On a 3-replica Deployment, set maxSurge: 0 and maxUnavailable: 1, then trigger a rollout while watching pod events in real time.
    2. Trace the replacement order: one pod terminates before its replacement starts — the capacity-conservative extreme.
    3. Contrast with the default (25% surge/unavailable) and articulate which you'd choose for a capacity-constrained cluster versus a latency-sensitive service.

  4. Lab: Implement a manual canary: split traffic 90/10 with two Deployments behind one Service via pod labels.

    1. Deploy v1 of an app with 9 replicas and v2 with 1 replica, both behind a single Service selected by a shared label — a manual 90/10 canary.
    2. Send traffic and confirm roughly one in ten requests hits v2 (check via a version header or log line).
    3. Shift the ratio by scaling the Deployments, then complete or abort the canary: the full canary lifecycle, operated by hand.

Self-check questions

Which kubectl command lists rollout revision history, and how do you target a specific revision for rollback?
Answer: kubectl rollout history deployment/<name>; roll back to a specific revision with kubectl rollout undo deployment/<name> --to-revision=N. Revisions are recorded only when the pod template changes.
With replicas=4, maxSurge=1, maxUnavailable=0, what is the max pod count during the update?
Answer: 5. maxSurge=1 allows one extra above desired (4+1); maxUnavailable=0 means all 4 desired must stay available during the update.
What distinguishes a canary from blue-green in terms of blast radius?
Answer: Canary routes a small fraction of live traffic to the new version (tiny blast radius, real production signal). Blue-green runs two full environments and flips all traffic at once (blast radius is the whole fleet at flip time, but instant rollback).

Module 5

Observability: Probes, Logging, and Monitoring Primitives

Startup probe: shields slow-boot apps from premature liveness kills; disables others until success.

The startup probe exists for slow-booting applications: while it hasn't succeeded, the kubelet disables the liveness and readiness probes, giving the app as long as it needs to initialize without being killed for "failing" health checks it was never ready to pass. Without a startup probe, teams inflate liveness delays to cover the slowest boot, which then delays detection of genuine deadlocks for every pod. The correct division of labor: startup probe covers "are you up yet," liveness covers "are you still alive," readiness covers "should you get traffic." A slow-starting app without a startup probe is a crash-loop waiting for a cold node.

Liveness probe: restarts a stuck container — never wire it to external dependencies.

The liveness probe answers one question — "is this container deadlocked?" — and its only action is restarting the container. That makes it dangerous when pointed at external dependencies: a liveness probe that checks the database restarts your app every time the database hiccups, turning a downstream blip into a self-inflicted outage — the classic amplifier the checkpoint warns about. Liveness should test the process itself (is the event loop responsive? is the HTTP handler answering?), never the health of something else. If the probe's failure says more about a dependency than about your container, it's a readiness concern or an alert, not a liveness probe.

Readiness probe: removes the pod from service endpoints without restarting it.

The readiness probe controls Service membership without restarting anything: a failing readiness probe removes the pod from endpoints, a passing one adds it back. "Passes liveness but gets no traffic" is therefore the signature of a failing readiness probe — the container is alive, but the platform has decided it shouldn't serve. This is the mechanism behind graceful startup (don't take traffic until warmed up), graceful degradation (stop taking traffic while overloaded), and safe rollouts (the previous concept's safety valve). Readiness is the pod's way of voting itself in and out of the load balancer, and getting the vote right is core application-platform design.

Probe failure accounting: failureThreshold × periodSeconds as the real reaction latency.

Probe timing is arithmetic, not vibes: worst-case detection delay is roughly failureThreshold multiplied by periodSeconds (plus the timeout), so periodSeconds=10 with failureThreshold=3 means up to ~30 seconds before the kubelet acts on a failure. Shorten the period and you detect faster but risk flapping on transient blips; lengthen it and you ride out noise but react slowly to real death. The checkpoint's computation is the skill: read any probe spec and immediately know its reaction latency. Tune probes against your app's real failure modes — fast detection for deadlock-prone workers, patient thresholds for apps with occasional slow responses.

kubectl logs -p and multi-container -c: post-crash forensics from terminated containers.

Container logs are the application's voice, and kubectl logs is how you hear it — with -p to read the previous (crashed) container's final words before the evidence rotates away, and -c to select among multi-container pods. The forensics habit is: crash first, logs -p immediately, because kubelet log rotation and pod deletion destroy evidence on a schedule that doesn't care about your incident. Structure your app's logs for this workflow — timestamps, request IDs, one event per line — and the difference between a ten-minute diagnosis and a two-hour one is usually decided here. Logs are also why the sidecar pattern from Module 0 exists: some teams need every log line shipped off-node before it can disappear.

Metrics Server and kubectl top: the minimum viable monitoring loop for CPU/memory pressure.

The Metrics Server is the minimum viable monitoring loop: it scrapes CPU and memory from kubelets and serves kubectl top, which shows live resource usage per node and per pod. It's not a monitoring system — no history, no alerts — but it's the fastest way to answer "is this pod actually using what it requested?" and to correlate a memory leak with the OOMKill in the events. The lab's leak simulation makes the loop concrete: watch top climb, watch the limit approach, watch the kill. When top shows usage far above requests, you've found either a misconfigured workload or a genuine capacity problem — either way, it's the cheapest signal in the cluster.

Learning objectives

  • Configure liveness, readiness, and startup probes with correct failure semantics.
  • Choose probe handlers (HTTP, TCP, exec) and tune periods, thresholds, and timeouts.
  • Extract application logs with kubectl logs, multi-container selection, and previous-container retrieval.
  • Read pod events and resource metrics to localize failures before guessing.

Hands-on labs

  1. Lab: Give a slow-starting app a startup probe and show that the liveness probe stays dormant until it passes.

    1. Deploy an app that sleeps 60 seconds before listening, with a liveness probe that would fail during the sleep and a startup probe covering the boot window.
    2. Observe that the liveness probe stays dormant until the startup probe succeeds — then remove the startup probe and watch the app get killed mid-boot.
    3. Write down the rule: startup probe duration should cover your p99 cold-start time, not your average.

  2. Lab: Misconfigure a readiness probe and demonstrate endpoints draining while the pod keeps running.

    1. Point a readiness probe at an endpoint you can toggle (a file's existence, a flag), and toggle it while watching the Service's endpoints.
    2. Confirm the pod keeps running (liveness unaffected) while endpoints drain and refill — readiness as a traffic valve, demonstrated.
    3. Now misconfigure the probe to always fail and observe a rollout stall: the safety valve holding the line against a bad release.

  3. Lab: Crash a container, then retrieve its final log lines with logs -p before the evidence rotates away.

    1. Crash a container (exit 1 after printing a distinctive final log line), then immediately run kubectl logs -p to retrieve its last words.
    2. In a multi-container pod, practice selecting containers with -c and comparing their logs side by side.
    3. Time-box yourself: the forensics drill is only useful if it's reflexive, so repeat until the flags are muscle memory.

  4. Lab: Simulate a memory leak, watch kubectl top climb, and correlate with the OOMKill event.

    1. Run a program with a slow memory leak inside a pod with a modest memory limit, and watch kubectl top in one terminal and events in another.
    2. Correlate the climbing usage with the eventual OOMKilled event and the restart — the full leak-to-kill arc.
    3. Set requests/limits from what you measured, and note how the numbers you chose map to the QoS class from Module 0.

Self-check questions

Why is a liveness probe pointed at a database a classic outage amplifier?
Answer: When the DB slows, every pod's liveness fails simultaneously → mass restarts → thundering herd on the recovering DB → prolonged outage. Liveness should test the container itself; readiness should gate traffic during dependency trouble.
A pod passes liveness but never receives traffic — which probe is failing and why?
Answer: Readiness. Liveness only restarts dead containers; readiness controls Service endpoint membership. Failing readiness = alive but removed from traffic — exactly this symptom.
Compute worst-case detection delay for periodSeconds=10, failureThreshold=3.
Answer: ~30 seconds (3 consecutive failures × 10s period), plus initialDelaySeconds/startup allowance. Worst case adds nearly a full extra period of skew — budget ~30-40s before the failure is acted on.

Module 6

Services, DNS Discovery, and Ingress

Service selector to Endpoints: the label contract that actually routes traffic.

Traffic routing starts with a label contract: the Service's selector must match the pods' labels, and the resulting Endpoints object is the actual list of destinations kube-proxy load-balances across. Zero addresses in Endpoints means the contract is broken — wrong labels, unready pods, or wrong namespace — and no amount of network debugging will help until the contract is fixed. The debugging order is therefore always contract first, network second: describe the Service, check the selector, list candidate pods with their labels. Three distinct root causes for empty endpoints: selector/label mismatch, all matching pods failing readiness, and pods living in a different namespace than the Service.

ClusterIP as stable virtual IP with kube-proxy load balancing across endpoints.

ClusterIP gives the Service a stable virtual IP for in-cluster traffic — the default and the right choice for backend-to-backend calls. NodePort additionally opens a high port on every node for external access without any cloud integration; LoadBalancer goes further and provisions a cloud load balancer. The exposure tier you choose should match the consumer: ClusterIP for internal, NodePort or LoadBalancer for external, and Ingress (below) when the external traffic is HTTP and needs routing rules. Over-exposing (LoadBalancer for something only the cluster needs) wastes cloud resources and widens attack surface for nothing.

NodePort range and LoadBalancer provisioning: when each exposure tier is warranted.

A headless Service (clusterIP: None) skips the virtual IP and kube-proxy load balancing entirely: DNS returns the individual pod IPs as A records instead. This is what stateful systems need when the client must pick a specific replica — databases with leader/follower roles, or any custom discovery logic. Pod DNS records follow a predictable pattern under the headless service name, which clients can enumerate. The rule: reach for headless when the application needs to address pods individually; use ClusterIP when it just needs "a healthy instance, any instance."

Headless services (clusterIP: None): direct pod DNS records for stateful or custom discovery.

Ingress is the HTTP-aware routing layer: rules map hosts and paths to Services, and the IngressClass selects which installed controller implements them. TLS termination happens at the controller, using the certificate stored in the Secret the Ingress references — so "HTTPS is broken" is a controller-and-Secret problem, not an Ingress-object problem. The most common Ingress failure remains the missing or mismatched controller: rules that no controller watches are valid objects that do nothing. When you write an Ingress, your first verification should always be that a controller is actually reconciling it (check the controller's logs, not just the Ingress's status).

Ingress anatomy: IngressClass, rules, hosts, paths, and TLS secret termination.

Cluster DNS gives every Service three usable names: the short name (web), the namespace-qualified name (web.shop), and the fully qualified web.shop.svc.cluster.local — with search domains making the short forms work from inside pods. Headless services extend this to pods: each pod gets its own DNS A record, which is how stateful clients discover individual replicas. The FQDN form matters when a pod needs to be unambiguous about which namespace's service it means, or when search-domain behavior differs (some runtimes and musl-based images handle search domains idiosyncratically). Knowing all three forms — and when each is required — prevents an entire class of "works from here, fails from there" mysteries.

DNS naming: svc, svc.namespace, svc.namespace.svc.cluster.local — and pod DNS for headless.

End-to-end connectivity debugging follows the packet's path: does the Service have endpoints (the label contract), does DNS resolve the name (CoreDNS and the client's config), and does kube-proxy route to the endpoints (the node's forwarding rules)? Each layer has its own signature when broken — empty endpoints, NXDOMAIN or timeouts, resolution without routing — and checking them in path order converges fast. kubectl describe, nslookup from a debug pod, and the node's proxy rules are the three tools; the skill is knowing which layer each tool interrogates. Debug the path, not the symptom.

Learning objectives

  • Expose pods through ClusterIP, NodePort, and LoadBalancer services with correct selectors.
  • Use cluster DNS names for service discovery: short, namespace-qualified, and FQDN forms.
  • Route external HTTP traffic with Ingress rules, hosts, and path matching.
  • Debug connectivity end-to-end: endpoints, DNS, and kube-proxy behavior.

Hands-on labs

  1. Lab: Expose a Deployment three ways and curl each from inside and outside the cluster.

    1. Expose one Deployment three ways: ClusterIP, NodePort, and (if your lab cloud supports it) LoadBalancer.
    2. From inside the cluster, curl the ClusterIP service; from outside, curl the NodePort and the load balancer address.
    3. Write down which consumer each tier serves — the exposure decision matrix you'll reuse on every service you ship.

  2. Lab: Break a Service selector label, then diagnose empty Endpoints with kubectl describe.

    1. Deliberately break a Service's selector (change one label character), then run kubectl describe on the Service and the Endpoints.
    2. Diagnose the empty Endpoints from the evidence alone, repair the selector, and confirm traffic flows again.
    3. Repeat until the diagnosis takes under a minute — this is the highest-frequency service bug in existence.

  3. Lab: Write an Ingress with two hosts and path prefixes routing to two different services.

    1. Write an Ingress with two hosts (for example store.test and api.test) and path prefixes routing to two different Services.
    2. Point the hostnames at your cluster (hosts file or test DNS) and curl each, confirming host- and path-based routing both work.
    3. Add TLS with a self-signed cert in a Secret and confirm HTTPS terminates at the controller.

  4. Lab: Deploy a headless Service and resolve individual pod A-records with nslookup from a debug pod.

    1. Create a headless Service for a small StatefulSet-like set of pods and, from a debug pod, nslookup the service name.
    2. Confirm you get individual pod A records rather than one virtual IP, and resolve one pod's full DNS name directly.
    3. Explain in your own words why a database client would prefer this over a ClusterIP service.

Self-check questions

Endpoints show zero addresses — list three distinct root causes and how to confirm each.
Answer: 1) Selector matches no pods — verify with kubectl get pods -l. 2) Pods exist but are not ready — check readiness probes. 3) Pods in terminating state or the Service targets the wrong port — check describe. Confirm each by comparing selector labels against pod labels directly.
When would you choose a headless Service over a ClusterIP one?
Answer: When clients need the individual pod IPs — stateful apps doing their own discovery/replication (databases, clustered caches). Headless (clusterIP: None) returns pod IPs via DNS instead of a single virtual IP.
Where does TLS termination happen in an Ingress flow, and what object holds the certificate?
Answer: At the Ingress controller (the L7 proxy). The certificate lives in a TLS-type Secret referenced by the Ingress tls section — the controller loads it and terminates TLS before proxying plain HTTP to the Service.

Module 7

Network Policies from the Application Side

Default open networking: all pods can reach all pods until a policy selects them.

Kubernetes networking starts open: with no policies, every pod can reach every other pod on any port. This default surprises developers coming from cloud security groups, but it's deliberate — connectivity first, restriction as an explicit act. The consequence is that "the network is secure" is never true by default in Kubernetes; it's true only after you've written the policies that make it so. Every NetworkPolicy you write is a move away from this default toward least-privilege, and the first one (usually a default-deny) is the most important.

Policy types ingress/egress: selecting a pod in either direction flips it to deny-by-default for that direction.

The pivotal semantic: when a NetworkPolicy selects a pod, that pod's traffic becomes deny-by-default in each direction the policy's types list (ingress, egress, or both). A policy with an empty ingress rule list but type ingress doesn't "allow nothing explicitly" — it selects pods and allows nothing, which is the default-deny posture. This is why applying your first policy can break a working app: the moment of selection is the moment the default flips. Always know which pods a policy selects before applying it, and expect to add the allow rules the app actually needs in the same change.

Selectors: podSelector, namespaceSelector, and ipBlock peers for external CIDRs.

Policy peers are expressive: podSelector matches pods by label in the policy's namespace, namespaceSelector matches whole namespaces by label, and ipBlock matches external CIDRs for traffic leaving or entering the cluster. Rules combine peers with ports and protocols, so "frontend pods may reach API pods on TCP 8080" is one ingress rule. The design discipline is least-privilege per port, not per pod — allowing "all ports between these tiers" is barely better than no policy. Write rules that name the actual ports your application uses, and the policy becomes executable documentation of your architecture.

Ports and protocols in rules: least-privilege per port, not per pod.

Multiple policies selecting the same pod don't conflict — their allow rules union. Two policies with different ingress rules for one pod produce the combined allow set, not an intersection, which means policies compose additively across teams and concerns (platform team writes the baseline, app team writes the app-specific rules). The catch is that there is no deny rule to override an allow: once any selecting policy allows traffic, it's allowed. Design with this in mind — union semantics reward small, composable policies and punish anyone hoping to carve exceptions out of someone else's allow.

Egress to DNS: forgetting port 53 UDP/TCP breaks name resolution under default-deny egress.

Egress default-deny has a famous footgun: DNS. Pods resolve names through CoreDNS on port 53 (UDP and TCP), so an egress policy that forgets DNS breaks name resolution for every selected pod — and the symptom ("can't reach the database") misleads you away from the cause. Under default-deny egress, the two rules you must add to keep the cluster working are DNS (port 53 to the kube-dns endpoints) and the Kubernetes API (port 443 to the API server), before any application egress. The checkpoint's answer is a scar every network-policy author earns once; earn it in the lab instead of production.

CNI dependency: policies are declarative intent; enforcement requires a policy-capable CNI.

NetworkPolicies are declarative intent, not magic: something must enforce them, and that something is a policy-capable CNI plugin. Apply a perfect policy set on a cluster whose CNI ignores policies and everything still flows — the manifest applied cleanly because the API accepts it regardless of enforcement. This is why the CNI choice from the administrator sequence matters to developers too: your policies are only as real as the dataplane underneath. Verify enforcement empirically (the labs' curl probes before and after) rather than trusting that "applied" means "enforced."

Learning objectives

  • Write ingress and egress NetworkPolicies scoped by podSelector and namespaceSelector.
  • Predict default-allow versus default-deny behavior when policies select pods.
  • Test policy enforcement with in-cluster curl probes before and after applying rules.
  • Layer policies for a three-tier app: frontend, API, and database isolation.

Hands-on labs

  1. Lab: Apply a default-deny ingress policy to a namespace and watch cross-pod traffic stop.

    1. In a test namespace, confirm two pods can curl each other with no policies in place — the default-open baseline.
    2. Apply a default-deny ingress policy selecting all pods in the namespace, and watch the same curls fail.
    3. Record the exact moment the default flipped: policy selection, not policy content, is what changed the posture.

  2. Lab: Whitelist only frontend-to-API on port 8080 and prove database is unreachable from frontend.

    1. With default-deny in place, write an ingress policy allowing only frontend-labeled pods to reach API pods on the app's port.
    2. Prove it: frontend-labeled client succeeds, unlabeled client fails, and direct-to-database from frontend fails.
    3. You now have a working whitelist — the shape of every tiered policy you'll write.

  3. Lab: Add an egress policy and debug the classic symptom: DNS lookups failing for selected pods.

    1. Add an egress default-deny policy and immediately try DNS lookups from a selected pod — watch them fail, the classic symptom.
    2. Add egress rules for DNS (port 53) and the API server, confirm lookups recover, then add your application's genuine egress needs.
    3. Document the rule set as the namespace's egress baseline for future apps.

  4. Lab: Model a three-tier policy set and document the allowed traffic matrix as a table.

    1. Model a three-tier app (frontend, API, database) with a policy set: frontend may reach API, API may reach database, nothing else crosses tiers.
    2. Write the allowed traffic as a matrix table, implement it, and probe every cell of the matrix with curl from labeled test pods.
    3. Every cell should behave as the matrix predicts — this table is the deliverable, suitable for a security review.

Self-check questions

Two policies select the same pod with different ingress rules — is the result union or intersection?
Answer: Union — policies are additive. Traffic allowed by ANY selecting policy is allowed. There is no "deny rule" in NetworkPolicy; isolation comes from default-deny plus explicit allows.
Under default-deny egress, which two rules must you add to keep DNS and the API working?
Answer: Egress to UDP/TCP port 53 for DNS (usually to kube-dns/CoreDNS), and egress to TCP 443 to the Kubernetes API server. Without these, name resolution and API access break immediately.
Why does a NetworkPolicy manifest apply cleanly on a cluster with no policy enforcement?
Answer: NetworkPolicy is just API configuration — kubectl validates schema, not enforcement. Without a CNI/plugin that implements policies, the rules are stored and ignored. "Applied" ≠ "enforced" — verify with actual traffic tests.

Module 8

State Persistence: Volumes, PVCs, and StorageClasses

PV lifecycle: provisioning, binding, using, reclaiming — and what Retain versus Delete means for data.

A PersistentVolume moves through four phases: Available (unclaimed), Bound (a claim holds it), Released (the claim is gone, the data may remain), and Failed (something broke). Reclaim policy decides the Released transition: Retain preserves the data for an administrator to handle, Delete destroys the backing storage automatically. The lifecycle matters because storage outlives pods by design — the whole point is that data survives rescheduling, and the phase tells you exactly where in that story a volume currently sits. Reading PV phases fluently is how you answer "where did my data go" without panic.

Access modes: RWO, ROX, RWX and why most cloud block storage is RWO-only.

Access modes are the mount contract: ReadWriteOnce (single node, read-write), ReadOnlyMany (many nodes, read-only), ReadWriteMany (many nodes, read-write). The practical constraint is that most cloud block storage is RWO-only — one node at a time — which is why a single-writer database is the natural fit and multi-writer sharing needs a real shared filesystem. The checkpoint's eviction scenario resolves here: an RWO pod evicted from its node can restart elsewhere only after the volume detaches from the old node and attaches to the new one, which takes time and can fail if the old node is unresponsive. Design stateful apps around attach/detach latency; it's a property of the storage, not a bug.

Static versus dynamic provisioning: pre-created PVs versus StorageClass-driven claims.

Static provisioning means an administrator pre-creates PVs and claims bind to them by matching capacity, access modes, and selectors. Dynamic provisioning means a StorageClass provisioner creates the volume on demand when a claim appears with no matching PV — the cloud-native default, and the reason most developers never touch a PV object directly. The tradeoff is control versus convenience: static gives the admin exact placement over exotic storage, dynamic gives developers self-service. Know which your cluster uses, because "who creates the actual disk" determines who you call when provisioning fails.

StorageClass parameters, provisioner, and volumeBindingMode (Immediate vs WaitForFirstConsumer).

The StorageClass is where provisioning policy lives: the provisioner (which driver creates volumes), parameters (disk type, performance tier, filesystem), reclaim policy, and volumeBindingMode. Immediate binds the volume at claim creation; WaitForFirstConsumer delays binding until a pod needs it — which matters when the volume is topology-constrained (a zonal disk must be created in the same zone as the pod that will use it). With Immediate on zonal storage, the classic failure is a volume provisioned in zone A for a pod the scheduler places in zone B. WaitForFirstConsumer lets the scheduler choose first, and the provisioner follows — the correct default for topology-aware storage.

emptyDir versus PVC: node-local scratch that dies with the pod versus durable claimed storage.

emptyDir and PVC answer different questions. emptyDir is node-local scratch that lives as long as the pod: fast, simple, and gone forever when the pod dies — perfect for caches, temp files, and sidecar-shared working space. A PVC is durable claimed storage that survives pod deletion and rescheduling — the home of data you can't afford to lose. The lab's side-by-side comparison makes the distinction physical: delete the pod and see which data comes back. Choosing wrong in either direction is expensive: PVCs for temp files waste real storage infrastructure, emptyDir for real data loses it.

StatefulSets preview: stable identity and per-replica storage for stateful apps.

StatefulSets are the controller for applications where identity is load-bearing: stable pod names, stable network identities, and per-replica storage via volumeClaimTemplates. Each replica gets its own PVC (data-web-0 for web-0, forever), so rescheduling preserves the pod-to-data binding by identity rather than by chance. This is the primitive that makes databases, queues, and clustered systems operable on Kubernetes — ordered startup, ordered teardown, and storage that follows the name. The preview in this module is intentional: full StatefulSet operations belong to the administrator sequence, but developers designing stateful apps need to know the shape exists.

Learning objectives

  • Claim storage with PersistentVolumeClaims: access modes, capacity, and selector matching.
  • Mount PVCs into pods and reason about ReadWriteOnce versus ReadWriteMany scheduling.
  • Select StorageClasses for dynamic provisioning with parameters and reclaim policies.
  • Design for pod rescheduling: where data survives and where it does not.

Hands-on labs

  1. Lab: Provision a PVC via a StorageClass, write data from a pod, delete the pod, and verify data survives rescheduling.

    1. Create a PVC against your cluster's default StorageClass, mount it in a pod, and write a sentinel file.
    2. Delete the pod (not the PVC) and recreate it; confirm the sentinel survives — data outlives pods.
    3. Delete the PVC and check what the reclaim policy did to the PV and the data; record the behavior for your cluster's class.

  2. Lab: Try to mount one RWO PVC into pods on two nodes and observe the scheduling conflict.

    1. Try to mount a single ReadWriteOnce PVC into two pods constrained to different nodes, and observe the scheduling conflict.
    2. Read the events: the second pod waits on volume attachment — the RWO constraint made visible.
    3. Explain in your own words why most cloud block storage can't be RWX, and what storage class you'd need for genuine shared writable storage.

  3. Lab: Compare emptyDir and PVC behavior across a pod delete: document which data persists.

    1. Run two pods side by side: one with an emptyDir volume, one with a PVC; write a sentinel file in each.
    2. Delete both pods and recreate them; document which sentinel survived and which didn't.
    3. Write the one-paragraph decision rule you'd give a teammate: when is emptyDir correct, and when is a PVC mandatory?

  4. Lab: Set reclaimPolicy Retain, delete the PVC, and recover the data from the released PV manually.

    1. Set a PV's reclaimPolicy to Retain (via its StorageClass or by patching), create the claim, write data, then delete the PVC.
    2. Observe the Released phase with data intact; then manually recover: inspect the volume, copy the data out, and clean up.
    3. This is the disaster-recovery drill for someone deleted the claim — practice it before it's real.

Self-check questions

A pod using an RWO volume is evicted — under what condition can it restart on another node?
Answer: Only after the volume is detached from the old node — RWO means one node at a time. If the old node is unresponsive, detachment may hang until the node is fenced/deleted or the attach/detach controller times out; force-deleting the pod without detach risks data corruption.
When does WaitForFirstConsumer binding mode matter, and what breaks with Immediate?
Answer: With topology-constrained storage (e.g. local volumes, zonal disks): Immediate binds the PV before the pod is scheduled, possibly in the wrong zone — then the pod can never schedule there. WaitForFirstConsumer delays binding until scheduling, so the volume lands where the pod lands.
Your PVC stays Pending: list the binding checks in order (class, capacity, access mode, selector).
Answer: storageClassName matches a real class → requested capacity ≤ available → access mode compatible (RWO/RWX/ROX) → selector labels match (if set). Walk them in order; the first mismatch is the fix.
