Bitcoin Protocol Engineering

From UTXOs to Lightning: how the Bitcoin protocol moves value without a central authority — transactions, script, keys, mining, networking, and nodes.

Start the sequence All sequences

SCIENTIA OMNIA VINCIT

The sequence

What you will learn, and how.

Bitcoin is a decentralized ledger: thousands of independent nodes agree on a single history of value transfers with no central authority, no accounts, and no trusted intermediaries. The protocol achieves this with a small set of interlocking ideas — unspent transaction outputs as the unit of value, a stack-based scripting language for spending conditions, public-key cryptography for ownership, proof-of-work for leader election, and a peer-to-peer network for propagation.

This sequence teaches the protocol as an engineer would need it: the UTXO model and how coins live and die, raw transaction structure and sighash semantics, Script execution and the standard output types, key derivation and address formats, mining and the most-work chain rule, P2P networking and mempool policy, full-node operation and RPC, and a conceptual tour of the Lightning Network layered on top.

You will work primarily on testnet and regtest — free, resettable Bitcoin networks where mistakes cost nothing. The developer documentation at developer.bitcoin.org is the authoritative reference for exact semantics; this page teaches the mental models that make that documentation readable.

Who this sequence is for

  • Software engineers who want to understand how Bitcoin works at the protocol level, not the price level.
  • Backend and infrastructure engineers evaluating Bitcoin integration, custody, or node operation.
  • Cryptography-curious developers with basic programming skills and a tolerance for hexadecimal.

Prerequisites

  • Comfortable with the command line and basic programming (any language).
  • High-level familiarity with hashes and public-key cryptography — the sequence explains what it uses, but not from zero.
  • A machine where you can run Bitcoin Core on testnet/regtest; no real bitcoin is ever needed.

How to use it

  • Work the modules in order — each layer (UTXO, transaction, script, keys) is the vocabulary of the next.
  • Run every lab on testnet or regtest. Reading about script execution is abstract; tracing a real spend is concrete.
  • Keep a block explorer for testnet open while you study, and look up every transaction hash you create. The chain is the textbook.
  • When this guide states a consensus rule, verify it in the developer documentation or Bitcoin Core source behavior — the protocol is the authority.

The curriculum

8 modules, in order.

Module 1

Money and the Ledger: UTXO Model

Learning objectives

  • Contrast UTXO-based ledgers with account-based ledgers
  • Trace a coin's lifecycle from coinbase output to spent input
  • Explain how double-spending is prevented without a central authority
  • Read block explorers as a raw view of the UTXO set

Key concepts, explained

Unspent transaction output (UTXO) as the unit of value

Bitcoin has no accounts and no balances at the protocol level. Value exists only as unspent transaction outputs — discrete chunks of bitcoin, each locked to a spending condition, each created by an earlier transaction. Your "balance" is simply the sum of the UTXOs your keys can unlock.

This is closer to physical cash than to a bank account: you hold specific bills (UTXOs) of specific denominations, and spending means handing whole bills over and receiving change. The model makes every coin's history traceable and every spend explicitly authorized.

UTXO set and chainstate

The UTXO set — called the chainstate in Bitcoin Core — is the collection of all currently spendable outputs. It is the ledger's present tense: everything a node needs to validate new transactions, without replaying all of history.

Full nodes maintain this set in a database, applying each new block's deltas: spent inputs are removed, new outputs are added. The chainstate is small relative to the full blockchain, which is why nodes can validate quickly once synced.

Coinbase transactions and issuance schedule

Every block begins with a coinbase transaction, which has no inputs and creates new bitcoin out of nothing — the block subsidy plus the block's transaction fees. This is the protocol's only issuance mechanism: new coins enter circulation exclusively through mining.

The subsidy halves every 210,000 blocks (roughly four years), converging toward the 21 million cap. Issuance is therefore a known, decaying schedule — monetary policy as consensus code rather than committee decision.

Outpoints (txid + vout) as inputs

A transaction input does not name an amount or an address — it names an outpoint: the transaction ID of the previous transaction plus the output index (vout) within it. That pair uniquely identifies one UTXO in the entire history.

This precision is what makes double-spending detectable: the rules can check exactly whether that specific outpoint has already been consumed. An input is a pointer to a coin; the signature proves you may spend it.

No accounts or balances at the protocol layer

Nothing in the consensus rules knows about "accounts." Wallets compute balances by scanning for UTXOs locked to your keys; the protocol only knows individual outputs and whether each has been spent. Address reuse is discouraged partly because it fights this model — it clusters your UTXOs visibly.

Internalizing this pays off everywhere: fee estimation, coin selection, privacy, and change outputs all follow from the absence of accounts.

Deterministic validation of inputs vs outputs

Validation is purely mechanical: for each input, the referenced UTXO must exist and be unspent; the unlocking script must satisfy the locking script; and the total output value must not exceed the total input value. Any node, given the same UTXO set and transaction, reaches the same verdict.

This determinism is what lets thousands of mutually distrusting nodes agree. There is no judgment call in validation — only rules, applied identically everywhere.

Dust and economic spendability

Outputs below a tiny value threshold are called dust: they cost more in fees to spend than they are worth. Nodes' mempool policy typically refuses to relay dust outputs, because they bloat the UTXO set for no economic purpose.

Dust is a reminder that the ledger has real costs — every UTXO ever created must be stored by every full node forever. Economically rational transacting means consolidating small outputs rather than scattering them.

Hands-on labs

  1. Spin up a testnet full node and list its chainstate entries via RPC
    Syncing a testnet node gives you a live UTXO set to inspect. Querying it via RPC makes the chainstate concrete — it is a database you can read, not an abstraction.
  2. Follow one UTXO from coinbase to spend across three transactions on a testnet explorer
    Pick a coinbase output and trace it forward through spends on the explorer. Watching a coin's lifecycle across transactions teaches the UTXO model faster than any diagram.
  3. Compare your node's `gettxoutsetinfo` output before and after syncing one block
    The RPC reports the UTXO set size and total value. Observing it change by exactly one block's delta shows validation as bookkeeping.
  4. Model a UTXO ledger in a small script: apply and rollback a block's UTXO deltas
    Implement the add/remove logic yourself on toy data, including a rollback. Reorganizations make sense only once you have felt why the set must be revertible.

Self-check

  • Why can the same outpoint never be spent twice by valid rules?
  • Given a 0.5 BTC input and two outputs (0.3 + 0.15 BTC), what happened to the remainder?
  • What distinguishes a coinbase output from a regular output?

Module 2

Transactions: Inputs, Outputs, and Sighash

Learning objectives

  • Dissect raw transaction structure field by field
  • Explain how inputs reference and consume prior outputs
  • Describe what sighash flags commit a signature to
  • Compute and explain transaction fees and weight

Key concepts, explained

Version, inputs, outputs, locktime

A transaction is a small structured message: a version number, a list of inputs (outpoints plus unlocking data), a list of outputs (amounts plus locking scripts), and a locktime. Locktime sets the earliest block height or timestamp at which the transaction becomes valid — a built-in "do not confirm before" constraint.

Reading raw transactions field by field is a rite of passage: the format is compact and every byte is accounted for. Once you can decode one by hand, the whole protocol feels legible.

nSequence and relative lock-time signaling

Each input carries a sequence number. Originally for a replaced-by-fee precursor that never shipped, nSequence now signals relative lock-times: with the CHECKSEQUENCEVERIFY opcode, an output can require that a given number of blocks or seconds pass after the funding transaction confirms before it may be spent.

Relative timelocks are the foundation of Lightning channels and other second-layer contracts — they express "this coin is locked for N blocks from when it was created," a constraint the protocol enforces absolutely.

Witness data and segregated witness

Segregated witness (segwit) moved the unlocking signatures out of the traditional transaction structure into a separate witness section. The transaction ID is computed without the witness, which fixed the transaction-malleability problem: signatures can no longer alter the txid.

Witness data counts at a discount toward block limits, which effectively raised throughput for segwit transactions. Understanding the witness as "the signatures, relocated" demystifies most segwit discussion.

Sighash flags (ALL, NONE, SINGLE, ANYONECANPAY)

A signature does not sign "the transaction" vaguely — the sighash flag declares exactly which parts it commits to. SIGHASH_ALL (the default) commits to all inputs and outputs. SIGHASH_NONE commits to inputs but no outputs, letting others fill in outputs. SIGHASH_SINGLE commits to the input and the output at the same index. ANYONECANPAY variants commit to only the signer's own input, letting others add inputs.

These flags are the protocol's composability mechanism: partially-signed transactions, crowdfunding transactions, and coinjoin coordination all work because signers can commit to exactly their part and no more.

Fee as implicit difference of inputs minus outputs

Transactions have no fee field. The fee is implicit: the sum of inputs minus the sum of outputs, claimed by the miner as part of the block reward. If you construct a transaction whose outputs equal its inputs, the fee is zero — and miners will likely ignore it.

This design means fee bugs are expensive: a typo that makes outputs much smaller than inputs silently donates the difference to the miner. Always compute and sanity-check the fee before signing.

Weight units and virtual size (vB)

Block limits are measured in weight units: non-witness bytes count as 4, witness bytes as 1. Virtual size (vbytes) is weight divided by 4 — the number miners and fee estimators actually use. The block limit is 4 million weight units, equivalent to 1 million vbytes of legacy data.

Fee rates are quoted in satoshis per vbyte, so fee estimation is arithmetic on virtual size. Segwit transactions pay less per byte of signature data because witness bytes are discounted — the incentive that drove segwit adoption.

Transaction malleability and its mitigations

Before segwit, a transaction's signatures were part of the data hashed into its txid, so third parties could alter the signature encoding and change the txid without invalidating the transaction. Any system tracking transactions by txid — like Lightning — could be confused by this malleability.

Segwit fixed it by excluding witness data from the txid computation. For legacy transactions, standardness rules require low-S signatures and canonical encodings, narrowing the malleability surface. The lesson generalizes: identifiers should commit to intent, not to signatures.

Hands-on labs

  1. Decode a raw testnet transaction with a local decoder and annotate each field
    Take a real raw transaction and label every field: version, input count, each outpoint, sequence, output values, locking scripts, locktime. The annotated hex is worth more than a chapter of prose.
  2. Build a funding transaction and a spending transaction by hand on regtest with bitcoin-cli
    Constructing transactions manually — createrawtransaction, signing, broadcasting — teaches the input/output mechanics that wallets hide. Regtest gives you coins and instant blocks for free.
  3. Sign the same input with SIGHASH_ALL and SIGHASH_SINGLE and compare the signed bytes
    The two signatures commit to different message preimages, so the bytes differ. Comparing them makes the sighash flag concrete rather than theoretical.
  4. Calculate fees and vsize for three real transactions and rank them by fee rate
    Pull three transactions from a block, compute each fee from inputs minus outputs, divide by vsize, and rank. Fee estimation stops being mysterious once you have done the arithmetic.

Self-check

  • Which sighash flag lets other inputs be added after you sign?
  • Why does the witness not count toward legacy block size?
  • What does nLockTime prevent, and what does it not prevent?

Module 3

Script: Locking, Unlocking, and Standard Types

Learning objectives

  • Trace script execution for a P2PKH spend
  • Classify P2PKH, P2SH, P2WPKH, P2WSH, and P2TR by their locking semantics
  • Construct a multisig redeem script and its spending path
  • Apply absolute and relative timelocks correctly

Key concepts, explained

Stack-based execution, no loops

Bitcoin Script is a deliberately minimal, stack-based language: data is pushed onto a stack and opcodes manipulate it — no loops, no recursion, no persistent state. Every script terminates, because termination is a consensus requirement: nodes must agree on the result, and unbounded execution would break that.

The lack of loops is a feature, not a limitation. Script expresses spending conditions — signatures, timelocks, hash preimages — and anything more expressive belongs in layers above the protocol.

locking script (scriptPubKey) vs unlocking script (scriptSig/witness)

Every output carries a locking script (scriptPubKey) stating the condition for spending; every input carries the unlocking data (scriptSig, or witness for segwit) that must satisfy it. Validation concatenates the two and executes: the spend is valid if the script finishes with a true value on the stack and no errors.

This split is the protocol's programmability: the output author writes the lock, the spender provides the key. All of Bitcoin's contract types are compositions of this one mechanism.

Standardness vs consensus validity

Consensus rules define what is valid in a block — the hard law. Standardness is the softer relay policy: nodes refuse to relay or mine transactions that are valid but non-standard (unusual script types, excessive size, dust outputs). A non-standard transaction can still confirm if a miner includes it directly.

The distinction matters for contract design: exotic scripts may be consensus-valid yet practically unspendable because the network will not propagate them. Build within standardness unless you have a miner relationship.

Multisig m-of-n and CHECKMULTISIG semantics

The CHECKMULTISIG opcode verifies m signatures against n public keys — 2-of-3 being the classic: any two of three keyholders can spend. It is the primitive behind escrow, shared custody, and Lightning funding outputs.

The opcode has a famous quirk: it consumes one more stack item than expected (the "off-by-one bug"), so multisig spends begin with a dummy OP_0. The bug was never fixed because fixing it would fork the chain — a lesson in how consensus ossifies even mistakes.

OP_CHECKLOCKTIMEVERIFY (absolute timelock)

CHECKLOCKTIMEVERIFY (CLTV) fails the script unless the spending transaction's locktime has reached the specified height or time — an absolute timelock: "this coin cannot move before block 800,000." Combined with a signature requirement, it builds escrows with expiry and refund paths.

Absolute timelocks express deadlines. They are simple, predictable, and the reason old "dead man's switch" and inheritance contracts are expressible in Script.

OP_CHECKSEQUENCEVERIFY (relative timelock)

CHECKSEQUENCEVERIFY (CSV) enforces relative timelocks: the output can only be spent by a transaction whose input sequence indicates enough blocks or time have passed since the funding output confirmed. "Locked for 144 blocks from now" rather than "locked until block X."

Relative timelocks are what Lightning channels use for their dispute windows — the safety period only starts when the channel closes, whenever that happens. Absolute timelocks could not express this; relative ones can.

Taproot key-path and script-path spending (conceptual)

Taproot outputs can be spent two ways: the key path — a single Schnorr signature that looks like an ordinary payment, hiding that any contract existed — or the script path, revealing one of several committed scripts. Unused contract branches stay hidden, improving both privacy and efficiency.

Conceptually, Taproot makes complex contracts look simple on chain when everyone cooperates, and only reveals complexity when there is a dispute. It is the "optimistic" design philosophy applied to Script.

Hands-on labs

  1. Write a P2SH 2-of-3 multisig on regtest and spend it with two valid signatures
    Generate three keys, build the redeem script, fund the P2SH address, then spend with two signatures — including the leading OP_0 the CHECKMULTISIG quirk demands. The spend working is the proof you understood the quirk.
  2. Build a timelocked output (CLTV) and confirm it fails before height, succeeds after
    Fund a CLTV-locked output, attempt the spend early and watch consensus reject it, then mine past the height and spend successfully. The protocol enforcing time is worth witnessing.
  3. Execute a hand-written P2PKH script trace with a stack visualizer
    Step through a pay-to-public-key-hash spend opcode by opcode, tracking the stack. The trace turns "script execution" from a phrase into a mechanism you have operated.
  4. Compare address encodings for P2PKH, P2SH, and bech32 outputs of the same keys
    Derive the three address forms from one keypair and note the prefixes and character sets. Address formats are encodings of the same underlying scripts — the comparison proves it.

Self-check

  • Why is the redeem script revealed only at spend time in P2SH?
  • What goes wrong if CSV is applied to the wrong input's sequence?
  • Give one case where a consensus-valid script is still non-standard.

Module 4

Keys, Signatures, and Addresses

Learning objectives

  • Derive a public key from a private key on secp256k1
  • Explain how ECDSA and Schnorr signatures commit to the message
  • Describe HD wallet derivation paths conceptually
  • Map key material to address formats and their risks

Key concepts, explained

secp256k1 curve and discrete-log hardness

Bitcoin keys live on the secp256k1 elliptic curve: the private key is a large random number, the public key is that number multiplied by the curve's generator point. The multiplication is easy; reversing it — the discrete logarithm problem — is computationally infeasible, and that one-way gap is the entire basis of ownership.

Key security therefore reduces to randomness: a private key must be generated from a proper cryptographic random source. Weak randomness has caused real thefts; the curve itself has never been the failure point.

Private key, compressed vs uncompressed public keys

A private key is 256 bits of secret; the public key is the corresponding curve point, encodable in compressed (33 bytes, with a prefix indicating the y-coordinate's parity) or uncompressed (65 bytes) form. Compressed keys are the modern standard — same security, smaller transactions.

The encoding choice affects the address derived from the key, so wallets must be consistent. This is a frequent source of "my address doesn't match" confusion when moving keys between software.

ECDSA signatures (legacy) vs Schnorr signatures (Taproot)

Legacy Bitcoin signatures use ECDSA, which has known quirks: signatures are malleable in their encoding and cannot be straightforwardly aggregated. Taproot introduced Schnorr signatures, which are linear — multiple signers can combine their signatures into one that verifies against a combined key.

Schnorr enables key-path spends that hide multisig participation and makes signature aggregation practical. ECDSA remains valid for older output types; the protocol carries both, with Schnorr as the modern path.

BIP32 HD wallets: master seed, chain codes, hardened derivation

Hierarchical deterministic (BIP32) wallets derive a tree of keypairs from a single master seed: each child key comes from the parent key plus a chain code, so one backup covers every address the wallet will ever generate. Public derivation lets a server generate receiving addresses from an extended public key without ever touching private keys.

Hardened derivation breaks the public-derivation link for sensitive branches, protecting the tree if a child private key leaks. The account structure (BIP44/49/84 paths) organizes keys by purpose and script type so wallets interoperate.

BIP39 mnemonics and BIP44/49/84 account paths

BIP39 encodes the master seed as 12 or 24 human-readable words with a checksum — the "seed phrase" users back up on paper or steel. The words are not the keys; they deterministically regenerate the seed, which regenerates the whole tree.

Derivation paths like m/84'/0'/0' (BIP84, native segwit) tell any compliant wallet exactly which keys to generate, so the same seed phrase restores the same addresses in different software. Guard the phrase as the master secret it is: anyone holding it holds everything.

Address formats: base58check, bech32, bech32m

Addresses are encodings of locking scripts with checksums: base58check (starting with 1 or 3) for legacy P2PKH and P2SH, bech32 (bc1q...) for segwit v0, bech32m (bc1p...) for Taproot. The checksum catches typos — sending to a mistyped address fails loudly instead of burning funds.

Each format corresponds to a script type, so the address prefix tells you what kind of spend to expect. Modern wallets default to bech32/bech32m for lower fees and better error detection.

Key hygiene: offline signing, gap limits, xpub exposure

Operational key hygiene: generate and store seeds offline, sign transactions on air-gapped or hardware devices, and keep private material off networked machines. Wallets scan a gap limit of consecutive unused addresses when restoring — funds beyond the gap look missing until the limit is raised.

Sharing an extended public key (xpub) with a third party — a block explorer service, an auditor — lets them derive all your addresses and watch every payment. It is a complete privacy leak of the account's activity, even though it cannot spend. Share xpubs deliberately or not at all.

Hands-on labs

  1. Generate a keypair locally, derive its P2WPKH address, and verify the encoding by hand
    Do the full pipeline yourself: private key to public key to hash to bech32. Verifying the checksum by hand once removes all magic from addresses.
  2. Create a BIP39 seed in an offline environment and derive three receiving addresses
    Generate the mnemonic offline, derive the BIP84 path addresses, and confirm a wallet restores the same addresses. The offline discipline is the point as much as the derivation.
  3. Sign a message with a regtest private key and verify it with the public key
    Message signing proves key ownership without moving coins. Sign, then verify with only the public key — the asymmetric property made tangible.
  4. Demonstrate why reusing addresses harms privacy by clustering outputs on a testnet explorer
    Send several payments to one address and one payment each to fresh addresses, then compare what the explorer reveals. The reused address tells a story; the fresh ones do not.

Self-check

  • What does the checksum in an address protect against?
  • Why is sharing an xpub with a third party a privacy leak?
  • What breaks if a signature commits to the wrong sighash preimage?

Module 5

Mining and Consensus

Learning objectives

  • Explain proof-of-work as a leader-election lottery
  • Describe the difficulty adjustment algorithm's goal
  • Apply the longest-chain (most-work) rule to a fork scenario
  • Dissect block structure: header fields and merkle trees

Key concepts, explained

Block header: version, prev hash, merkle root, timestamp, bits, nonce

The 80-byte block header is the unit miners hash: version, the previous block's hash (chaining blocks together), the merkle root committing to all transactions, a timestamp, the difficulty bits, and the nonce. Mining is the search for a nonce making the header's double-SHA256 fall below the target.

Everything about a block's validity is committed to in the header except the transactions themselves, which the merkle root covers. Light clients can therefore verify chain membership from headers alone.

Hashcash-style PoW and target thresholds

Proof-of-work adapts Hashcash: miners grind nonces until the header hash is numerically below the target threshold. There is no shortcut — each attempt is an independent lottery ticket, and the expected number of tickets to win is proportional to the difficulty.

The work is deliberately useless except as a cost signal: producing a valid block proves real computation was spent, which is what makes rewriting history expensive. The security assumption is economic, not cryptographic.

Difficulty retarget every 2016 blocks

Every 2016 blocks (roughly two weeks), the protocol retargets difficulty from the actual time those blocks took versus the 20,160-minute target. If blocks came too fast — hashrate grew — difficulty rises; too slow, it falls. The adjustment is capped per period to prevent shocks.

This feedback loop is what holds the 10-minute average against wildly varying global hashrate. It is the protocol's monetary-policy-adjacent mechanism: predictable issuance regardless of how much mining power exists.

Chainwork and the most-work rule

Nodes follow the chain with the most accumulated work — the sum of difficulty across its blocks — not simply the longest by height. A shorter chain of harder blocks beats a longer chain of easy ones, which is why the rule is "most work" rather than "longest chain."

This resolves forks deterministically: when two miners find blocks simultaneously, the network converges on whichever branch accumulates more work first. Reorganizations are the visible form of this convergence.

Merkle trees and inclusion proofs

Transactions in a block are hashed pairwise up a binary tree to a single merkle root in the header. A merkle proof — the handful of sibling hashes along one leaf's path — lets anyone verify a transaction is in the block knowing only the header and the proof, in logarithmic space.

This is what makes light clients possible: a phone can verify its payment is buried under proof-of-work without downloading the block. Inclusion proofs are the scalability primitive of the whole system.

Orphan/stale blocks and reorganization depth

When two miners find competing blocks, one becomes stale — valid work that the network abandons when the other branch wins more work. A reorganization swaps the active chain tip, rolling back the UTXO set changes of the abandoned blocks and reapplying the winner's.

Deeper confirmations mean exponentially more work to reverse, which is why recipients wait for multiple confirmations on large payments. Finality in Bitcoin is probabilistic, deepening with every block.

Coinbase maturity and block reward schedule

Coinbase outputs cannot be spent until 100 blocks have buried them — the maturity rule. This prevents miners from spending rewards on blocks that might later be reorganized away, which would cascade invalid spends through the chain.

The block reward is the subsidy (halving every 210,000 blocks) plus the block's fees. As the subsidy decays toward zero, fees must eventually carry miner incentives alone — the protocol's long-term security budget question.

Hands-on labs

  1. Mine blocks on regtest with `generatetoaddress` and inspect header fields
    Regtest mining is instant and free. Pull a mined block's header apart field by field and confirm each one's role — the header stops being abstract immediately.
  2. Build a merkle tree from a block's transactions and verify the root matches the header
    Hash the transaction list pairwise up the tree yourself and compare against the header's merkle root. The match is the proof you understand the commitment.
  3. Simulate a two-block reorg on regtest and observe mempool/UTXO rollback behavior
    Mine competing chains on two nodes, reconnect them, and watch the shorter branch's transactions return to the mempool. Reorganization as an observable event, not a diagram.
  4. Plot inter-block times from testnet data and compare to the 10-minute target
    Collect timestamps across a few hundred testnet blocks and histogram the intervals. The exponential distribution around the 10-minute mean is the Poisson process made visible.

Self-check

  • Why does consensus follow most accumulated work, not longest height?
  • How does the difficulty adjustment respond to hashrate doubling?
  • What is a merkle proof and why does it let light clients verify inclusion?

Module 6

P2P Networking and the Mempool

Learning objectives

  • Describe how nodes discover peers and gossip transactions
  • Explain mempool admission policy and fee-based eviction
  • Walk through initial block download (IBD) and headers-first sync
  • Interpret inventory messages (inv/getdata) and compact blocks

Key concepts, explained

Peer discovery: DNS seeds, addr gossip

A new node finds the network through DNS seeds — hardcoded domain names returning IP addresses of listening nodes — then learns more peers from addr messages gossiped between nodes. No central directory exists; the peer list is emergent.

This bootstrapping is deliberately simple and hard to censor: seeds are many, gossip is constant, and a node needs only one honest peer to learn the rest. Eclipse attacks target this process by surrounding a node with attacker peers.

Transaction relay policy vs consensus rules

Consensus rules decide what is valid in a block; relay policy decides what a node will propagate and keep in its mempool. Policy is stricter: minimum fee rates, dust limits, standard script types. A transaction can be consensus-valid yet refused relay — policy is each node's local spam filter, not law.

This split lets the network evolve its spam defenses without consensus changes. But it means "my transaction is valid" does not imply "the network will relay it" — a distinction that confuses newcomers exactly once.

Mempool: ancestor/descendant fee packages, RBF

Each node's mempool holds unconfirmed transactions, admitted by fee rate and evicted lowest-fee-first when full. Child-pays-for-parent lets a stuck low-fee transaction be rescued by a high-fee child spending its output — miners evaluate the package's combined fee rate.

Replace-by-fee (RBF) lets a sender replace their own unconfirmed transaction with a higher-fee version, given the original signaled replaceability. Together, CPFP and RBF are the fee-bumping toolkit for stuck transactions.

Initial block download and headers-first synchronization

A new node syncs with headers-first IBD: it downloads all 80-byte headers first — cheap to verify via proof-of-work — then fetches full blocks in parallel from multiple peers. Headers-first means the node knows the most-work chain before downloading any transactions.

This protects against resource-exhaustion attacks: a node never downloads gigabytes on the word of one peer. The header chain is the skeleton; blocks are the flesh, fetched only once the skeleton checks out.

Compact blocks and high-bandwidth relay

Compact block relay exploits the fact that miners' mempools mostly overlap: instead of sending full blocks, a node sends short transaction IDs and the receiver reconstructs the block from its own mempool, requesting only the missing pieces. High-bandwidth mode pushes this proactively.

The result is dramatically faster block propagation, which reduces stale-block rates and keeps mining decentralized — propagation delay is a centralization pressure, and compact blocks fight it directly.

Eclipse and Sybil attack concepts

A Sybil attack floods the network with attacker-controlled identities; an eclipse attack isolates one victim by occupying all of its peer slots, letting the attacker feed it a false view of the chain. Bitcoin's defenses are economic and structural: proof-of-work makes false chains expensive, and diverse peer selection makes isolation hard.

Running your own node over Tor or with diverse peers is the practical mitigation. The threat model assumes adversaries exist; the protocol assumes they cannot cheaply out-compute or out-connect the honest network.

Network magic, message framing (conceptual)

P2P messages are framed with a network magic prefix (identifying the network — mainnet, testnet, regtest each differ), a command name, a length, a checksum, and the payload. The magic bytes prevent cross-network confusion: a mainnet node ignores testnet chatter.

You will rarely touch this layer directly, but knowing the framing exists explains inventory messages, version handshakes, and why nodes on different networks simply cannot peer.

Hands-on labs

  1. Run a node with `-debug=net` and log its peer connections and addr traffic
    Watch the node discover peers, exchange version handshakes, and gossip addresses. The P2P network stops being a diagram and becomes log lines you can read.
  2. Submit a low-fee transaction on testnet and watch its mempool position over time
    Broadcast below the prevailing fee rate and observe the transaction linger — then bump it with RBF and watch it confirm. Fee markets are learned by participating in one.
  3. Compare IBD time with and without `assumevalid` on a pruned testnet sync
    Sync twice with different assumevalid settings and compare. The flag skips script verification below a known-good block — the tradeoff between validation thoroughness and sync speed, measured.
  4. Use `getpeerinfo` and `getmempoolinfo` to snapshot your node's network and mempool state
    These two RPCs are the node operator's dashboard: who you are connected to, and what your mempool holds. Learn to read them the way a pilot reads instruments.

Self-check

  • Why can a consensus-valid transaction still be rejected by mempool policy?
  • How does replace-by-fee change the fee-bumping options for a stuck transaction?
  • What does headers-first sync protect a new node against?

Module 7

Node Operation: Full, Pruned, and RPC

Learning objectives

  • Choose full vs pruned node configurations for a use case
  • Operate a node via bitcoin-cli RPC calls
  • Harden a node: configuration, firewall, and backups
  • Monitor node health and troubleshoot sync stalls

Key concepts, explained

Full validation vs pruned storage trade-offs

A full node downloads and validates every block and keeps all block data — hundreds of gigabytes — serving history to new peers. A pruned node validates everything identically but discards old block data below a configured threshold, keeping only recent blocks plus the full UTXO set.

Pruning sacrifices nothing in validation security: the node still checked every signature. What it sacrifices is service to others — a pruned node cannot serve historical blocks to syncing peers. Run full if you can afford the disk; prune when you cannot.

bitcoin.conf: key options for networking, RPC, indexing

Bitcoin Core is configured through bitcoin.conf: network options (listen, ports, peer limits), RPC options (which interfaces serve, authentication), and indexing options (txindex for arbitrary transaction lookup, blockfilterindex for light-client serving).

Treat the config file as infrastructure: version it, comment it, and understand each option before enabling it. Most node problems are config problems wearing a networking disguise.

RPC authentication (cookie vs user/password)

The RPC interface authenticates via a cookie file — automatically generated credentials readable only by the local user — or via explicit rpcuser/rpcpassword. The cookie is the default and the safer choice: no password to manage, scoped to local filesystem access.

Never expose RPC to the network without authentication and TLS-like protections; the interface can spend funds. Bind it to localhost and reach it remotely only through SSH tunnels or Tor hidden services.

Wallet backup: wallet.dat vs descriptor/xpub backups

Legacy wallets back up wallet.dat, the Berkeley DB file holding keys and metadata — it must be copied while the node is stopped or via the backup RPC to be consistent. Modern descriptor wallets back up the output descriptors (or the seed they derive from), which regenerate everything deterministically.

Test your restore procedure on a fresh datadir before you need it. A backup you have never restored is a hope, not a backup — and descriptor backups are strictly simpler to verify than wallet.dat copies.

Reindex, rewind, and corruption recovery

If block data corrupts, -reindex rebuilds the indexes and chainstate from the block files; if the corruption is deeper, a fresh sync from peers is the reliable path. There is no repair-in-place for consensus data — the network is the backup.

This is why multiple independent copies matter for operators: re-syncing from scratch costs days. Keep known-good snapshots of the datadir for fast recovery.

Tor/onion peer support and privacy posture

Bitcoin Core can route P2P traffic over Tor, connect to onion peers, and serve as an onion service — hiding the node's network location from observers. Combined with a personal Electrum or wallet backend, this keeps your transaction broadcasting unlinkable to your IP.

Privacy is a configuration discipline: Tor for P2P, your own node as your wallet's backend, no address reuse. Each layer removes one observer's vantage point.

Resource footprint: disk, RAM, bandwidth

A full mainnet node needs hundreds of gigabytes of disk (or tens pruned), several gigabytes of RAM for the UTXO cache during sync, and significant bandwidth for initial block download — then modest ongoing usage. These are the sizing inputs for any deployment decision.

Raise the dbcache during initial sync to trade RAM for speed, then lower it for steady state. Operators who size from these three numbers rarely get surprised.

Hands-on labs

  1. Deploy a pruned mainnet node in a VM, configure RPC, and query block data
    A pruned mainnet node is the practical operator's setup: full validation, modest disk. Configure RPC access and pull real block data — mainnet makes it feel consequential.
  2. Create an encrypted backup of wallet descriptors and test a restore on a fresh datadir
    Back up, wipe the datadir, restore, and confirm the wallet sees its funds. The restore test is the lab; the backup is just preparation.
  3. Simulate a stalled sync, then diagnose it with debug.log and peer/ban RPCs
    Throttle or break connectivity mid-sync, then read debug.log to find the stall, inspect peers, and recover. Sync stalls are the most common operator incident — rehearse the diagnosis.
  4. Benchmark initial sync resource usage and document your hardware sizing rule
    Record disk, RAM, and bandwidth during a sync and write down the sizing rule you would give a colleague. Operators document; hobbyists guess.

  • What must you back up to recover funds from a descriptor wallet?
  • Which bitcoin.conf settings reduce bandwidth without weakening validation?

Module 8

Lightning Network Overview

Learning objectives

  • Explain how a payment channel moves value off-chain
  • Describe HTLCs as the primitive for routed payments
  • Trace a multi-hop payment at a conceptual level
  • Identify watchtower and liquidity failure modes

Key concepts, explained

Funding transaction and 2-of-2 multisig channel

A Lightning channel opens with a funding transaction that locks bitcoin into a 2-of-2 multisig output owned jointly by the two participants. The funds are on chain, spendable only by mutual agreement — the channel's entire off-chain life is a series of pre-signed ways to split that output.

Opening and closing touch the chain; everything between is instant and nearly free. The funding output is the anchor that makes the off-chain promises enforceable.

Commitment transactions and revocation keys

Each channel state is a pair of commitment transactions, one held by each party, splitting the funding output per the current balance. When the balance updates, both parties sign new commitments and exchange revocation keys for the old ones — invalidating the prior state.

Revocation is the security mechanism: broadcasting an old commitment lets the counterparty claim all funds via the penalty transaction. Cheating is therefore unprofitable as long as someone is watching — which is what watchtowers are for.

Hash Time-Locked Contracts (HTLCs)

HTLCs are the primitive for routed payments: an output locked by both a hash condition (reveal the preimage) and a time condition (refund after expiry). Each hop in a multi-hop payment adds an HTLC conditional on the same preimage, chaining trust across strangers.

The hashlock makes payment atomic across hops — either every hop's HTLC completes or all refund — and the timelock bounds how long funds can be held hostage. HTLCs are conditional payments with cryptographic enforcement.

Onion routing and invoice preimages

Lightning routes payments with onion routing: each intermediate node learns only its predecessor and successor, not the payment's origin or destination. The recipient generates an invoice containing a payment hash; the preimage — revealed on delivery — is the proof of payment that unwinds the HTLC chain, releasing funds hop by hop.

Privacy and atomicity compose: no intermediary sees the full path, and no intermediary can steal the payment, because each HTLC only resolves with the preimage.

Channel liquidity: inbound vs outbound capacity

A channel's capacity is fixed at funding; what matters operationally is direction. Outbound liquidity is what you can send; inbound is what you can receive. Opening a channel gives you outbound only — receiving requires someone to open to you, or to spend first.

Liquidity management — rebalancing, splicing, choosing peers — is the real operational skill of running a Lightning node. Channels are inventory, and inventory must be positioned where demand is.

Force-close vs cooperative close

A cooperative close has both parties agree on the final split and broadcast one clean closing transaction — cheap and fast. A force-close unilaterally broadcasts the latest commitment transaction, starting the dispute timelock during which the counterparty can punish an old state.

Cooperative close is the happy path; force-close is the safety valve. Force-closes cost more, take longer, and reveal your balance on chain — avoid them by keeping peers responsive, but never fear them: they are the guarantee that unilateral exit is always possible.

Watchtowers and penalty transactions (conceptual)

If you go offline, a counterparty could broadcast an outdated commitment and steal funds — unless a watchtower watches for you. Watchtowers are services that hold your revocation data and broadcast the penalty transaction if they see a revoked state confirmed.

Conceptually, watchtowers outsource vigilance: you trade a small fee or trust assumption for the ability to stay offline safely. They complete the security model for participants who cannot monitor the chain continuously.

Hands-on labs

  1. Open two regtest Lightning channels between local nodes and send an off-chain payment
    Run two Lightning nodes on regtest, open channels, and route a payment that never touches the chain. The instant settlement after Bitcoin's 10-minute blocks is the Lightning value proposition, felt directly.
  2. Force-close a channel on regtest and observe the on-chain settlement flow
    Close unilaterally and watch the commitment transaction confirm, the timelock expire, and funds settle. The dispute machinery working correctly is reassuring to witness.
  3. Route a payment through an intermediate node and inspect the HTLC lifecycle in logs
    Set up three nodes in a line, pay across them, and read the HTLC add/settle messages in the logs. Multi-hop routing as log lines makes the onion concrete.
  4. Test invoice expiry by letting an invoice lapse and requesting a fresh one
    Generate an invoice, wait out its expiry, and attempt payment — then generate a fresh one and succeed. Expiry is a small feature with real operational consequences for integrations.

Self-check

  • Why can a channel only send up to its local balance?
  • What stops an old commitment transaction from being broadcast profitably?
  • What does the payment preimage prove, and to whom?
