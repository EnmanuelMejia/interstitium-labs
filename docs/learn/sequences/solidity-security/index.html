Solidity and Smart Contract Security

Learn how the EVM actually executes your code, where the classic vulnerabilities live, and how professionals test, audit, and deploy contracts that hold real value.

Overview

What this sequence is.

This sequence teaches smart contract engineering from the machine up: how the Ethereum Virtual Machine meters and executes code, how Solidity's language semantics map onto that machine, which battle-tested patterns the ecosystem's audited libraries provide, what the known vulnerability classes look like at the opcode level, and how professionals test, fuzz, audit, and deploy contracts that hold real money. It is organized around the public Solidity documentation and the OpenZeppelin Contracts library, but it teaches the engineering underneath — the mental models that let you read any contract and see where the value can leak.

Smart contracts are unusual software: they run on a adversarial, transparent, immutable computer where every bug is publicly visible and often directly monetizable. That changes the engineering discipline — testing must be adversarial, upgrades must be designed in (or explicitly rejected), and "it works on my machine" is replaced by "it survives the mempool." Every module here exists to make one layer of that discipline concrete.

Who this is for

  • Software developers moving into smart contract development who want the security-first path, not the tutorial path.
  • Security-minded engineers who want to understand EVM-level vulnerability classes deeply enough to audit.
  • Web3-curious backend engineers with solid programming fundamentals and no blockchain background yet.

Prerequisites

  • Fluency in at least one programming language (JavaScript/TypeScript or Python is ideal).
  • Basic blockchain concepts: what a transaction is, what an address is, that computation costs gas.
  • A machine you can install developer tooling on; all labs run on local chains and public testnets — never mainnet with real funds.
  • Comfort reading documentation; the Solidity docs are the textbook, this sequence is the study guide.

How to use this sequence

  • Work the modules in order — Modules 0 and 1 are the machine and the language; everything after assumes them.
  • Do every lab on a local EVM (Anvil is the modern default) before touching a testnet; local iteration is free and fast.
  • For each vulnerability class, write the exploit yourself before reading the fix — the attacker's view is what makes the defense stick.
  • Never deploy unaudited code holding real value as a result of this sequence; the sequence teaches you why professionals don't, either.

The curriculum

Eight modules, from raw storage slots to mainnet launch.

Module 1

EVM execution model

Account model: EOAs vs contract accounts, code hash, storage root, balance, nonce

Ethereum has two account types with the same address space but different natures. An externally owned account (EOA) is controlled by a private key: it has a balance and a nonce, and it can initiate transactions. A contract account holds code (identified by its code hash), has its own storage trie (identified by its storage root), a balance, and a nonce that starts at 1 on creation and increments only when the contract itself deploys other contracts. The distinction drives everything: only EOAs sign transactions, so every state change on chain traces back to an EOA's signature — contracts never act spontaneously, they only react to calls.

Gas as metering for every EVM operation; gas limit, gas price, priority fee mechanics

Gas is the metering of computation: every EVM operation costs a defined amount of gas, and the transaction pays gas used times the effective gas price. The gas limit caps how much work one transaction may attempt (exceed it and the transaction reverts, consuming the gas), while the price side is a two-part auction: maxFeePerGas is the most you'll pay per unit, maxPriorityFeePerGas is the tip to the block builder, and you pay the base fee plus tip up to your max. The checkpoint's arithmetic is therefore max total fee = gas limit × maxFeePerGas — the worst case you're signing for. Gas exists to price denial of service out of existence: infinite loops cost infinite money, so they don't happen.

Transaction fields: nonce, gasLimit, maxFeePerGas, to, value, data, signature

A transaction is a signed message with a fixed set of fields: nonce (the sender's sequence number, preventing replay), gasLimit, maxFeePerGas and maxPriorityFeePerGas (the price terms), to (the recipient address, empty for contract creation), value (native currency sent along), data (the call payload), and the signature itself (v, r, s proving an EOA authorized exactly these fields). The nonce rule is strict: transactions from an account must execute in nonce order, so a stuck transaction with too-low a fee blocks everything behind it. Reading raw transactions field by field is the skill that turns "the chain did something" into "this exact signed intent executed.

Storage layout: 32-byte slots, slot packing of sub-256-bit types, mapping and dynamic-array hashing schemes

Contract storage is 2^256 slots of 32 bytes each, and layout follows strict rules: state variables occupy slots in declaration order, and values smaller than 32 bytes pack together within a single slot (two uint128s share one slot; a uint256 never shares). Mappings and dynamic arrays don't live "at" their declared slot — a mapping's values live at keccak256(key concatenated with slot), and a dynamic array's elements start at keccak256(slot). This is why the checkpoint asks you to compute exact slot keys: storage is fully deterministic, and anyone can read any contract's raw storage whether the contract exposes it or not. "Private" state variables are private only by convention — never by cryptography.

Memory and calldata: volatile regions, memory expansion cost, calldata immutability

Beyond storage, the EVM has two volatile data regions: memory, a byte-addressable scratch space that a call can read and write (with costs that grow as it expands — memory expansion cost is quadratic-ish, so unbounded memory use is its own gas bomb), and calldata, the read-only region holding the transaction's input data. Calldata is immutable and cheap to read, which is why external function parameters should live there rather than being copied to memory. The placement decision — storage vs memory vs calldata — is simultaneously a correctness decision (persistence and visibility) and a cost decision (storage writes dominate everything). Getting it wrong is either a bug or a gas hemorrhage, usually both.

Contract ABI: function selectors (first 4 bytes of keccak256 signature), argument encoding

Calls between contracts go through the ABI: the first 4 bytes of the keccak256 hash of the function's canonical signature (name plus parameter types, like transfer(address,uint256)) select the function, and the arguments follow in tightly packed 32-byte words. This is what "hand-encoding a call" means in the lab: selector plus encoded arguments is the complete data field of the transaction. Because the selector is only 4 bytes, collisions are theoretically possible but practically never engineered accidentally — the real lesson is that the ABI is a convention over raw bytes, and anything that can produce the right bytes can call any function, which is exactly what the vulnerability modules will exploit.

State trie commitments and why storage writes are the dominant cost

All state changes commit through Merkle tries: each account's storage root and the global state root are cryptographic commitments to the full state, embedded in every block header. This is why storage writes are the dominant cost — a write doesn't just change a value, it recomputes hashes up the trie to produce a new committed root. It also explains light clients and proofs: anyone can prove a storage value against a block header without trusting the prover. The cost hierarchy to internalize: storage writes dwarf everything, storage reads are next, memory and computation are cheap by comparison — optimize in that order.

Learning objectives

  • Distinguish externally owned accounts from contract accounts by code, storage, and nonce behavior
  • Compute the total cost of a transaction from gas price, gas used, and intrinsic cost components
  • Predict storage versus memory versus calldata placement for function data and its cost implications
  • Decode a raw transaction's input data against a contract ABI by hand
  • Trace how a signed transaction flows from mempool to state transition in a block

Hands-on labs

  1. Lab: Craft a raw transaction by hand-encoding a function selector and arguments, then broadcast it on a testnet

    1. Pick a simple contract function (for example transfer(address,uint256)), compute its 4-byte selector with a keccak tool, and hand-encode the arguments as 32-byte words.
    2. Assemble the full data field, craft the transaction with your library of choice, and broadcast it on a public testnet.
    3. Verify on a block explorer that the intended function executed — you have now spoken raw ABI.

  2. Lab: Deploy a contract that writes values of packed types and read the raw storage slots to verify the packing scheme

    1. Deploy a contract with several packed state variables (uint128 pairs, small uints, a bool) and record the declaration order.
    2. Read the raw storage slots with the node's storage RPC and map each value back to its slot and offset, verifying the packing scheme by hand.
    3. Add a mapping and a dynamic array, compute their element locations with keccak256, and read those slots too — deterministic layout, confirmed empirically.

  3. Lab: Measure gas differences between storage reads/writes, memory ops, and event emission using a local node trace

    1. Write three functions that do equivalent work against storage, memory, and emitted events, and trace each on a local node.
    2. Compare the gas breakdowns: confirm storage writes dominate, memory is cheap, and events sit in between.
    3. Write down the cost hierarchy as your personal optimization order for all future contract work.

  4. Lab: Decode the input data of five mainnet transactions with a local ABI decoder and label each call

    1. Pick five real mainnet transactions to contracts you can find ABIs for, fetch their input data, and decode each call by hand with a local ABI decoder.
    2. Label each: which function, which arguments, how much value moved alongside.
    3. The chain stops being opaque the moment you can read its calls — this lab is that moment.

  5. Lab: Run a local EVM (e.g., anvil or ganache) and replay a failed out-of-gas transaction, inspecting the consumed gas breakdown

    1. On a local EVM, submit a transaction with a gas limit deliberately too low for its work, and capture the out-of-gas revert.
    2. Inspect the trace's gas consumption per operation and identify which operation exhausted the budget.
    3. Raise the limit to sufficiency and confirm success — the gas limit as a circuit breaker, experienced directly.

Self-check questions

  • Given slot layout of a struct, write the exact slot key and offset for each member
  • Explain why a contract account's nonce stays 1 while an EOA's increments per transaction
  • Compute max total fee for a transaction from maxFeePerGas, maxPriorityFeePerGas, and gas limit
  • Identify which operations in a trace are cold vs warm storage accesses and state the cost difference

Module 2

Solidity language semantics

Value types: uint/int widths, address vs address payable, bytes, enums; reference types: arrays, structs, mappings

Solidity's type system splits into value types and reference types. Value types — uint/int in explicit widths (uint8 through uint256), address versus address payable (only the latter can receive native currency via transfer/send), fixed bytes, and enums — are copied by value and live where you put them. Reference types — arrays, structs, and mappings — point at data elsewhere, which is why every reference-type variable must declare a data location. The width discipline matters: arithmetic on uint8 wraps at 255 exactly like uint256 wraps at its max (pre-0.8 semantics aside), so choosing widths is about packing and intent, never about "safety from overflow" — that's the compiler's checked arithmetic, not the type's.

Data locations: storage, memory, calldata and the assignment rules between them

Every reference-type variable lives in exactly one data location: storage (persistent, on-chain, expensive), memory (transient, per-call, cheap), or calldata (read-only transaction input, cheapest to read). Assignment between locations follows strict rules — storage to memory copies, memory to storage copies, and mappings can never leave storage (they have no serializable form to copy, which is the checkpoint's answer: a mapping cannot be copied to memory because there is nothing finite to copy). External function parameters should be calldata when only read; public functions copy them to memory automatically. The location annotations aren't decoration — they decide cost, persistence, and whether your function can even compile.

Visibility: external, public, internal, private; state mutability: pure, view, payable, nonpayable

Visibility controls who can call: external (only from outside the contract — cheapest for large calldata), public (outside plus internal), internal (this contract and its children), private (this contract only). State mutability controls what the function may do: pure (no state access at all), view (reads but never writes), payable/nonpayable for whether it accepts native currency. The checkpoint's deliberate-mistakes lab exists because the defaults punish inattention — a function you meant to be internal but left public is an attack surface, and a nonpayable function receiving value reverts. Annotate every function deliberately; the compiler's defaults are not your design.

Inheritance: linearized C3 order, virtual/override, abstract contracts and interfaces

Inheritance in Solidity uses C3 linearization to flatten the parent graph into a single method-resolution order: when two parents define the same function, the most-derived override wins, and the override specifier must name every parent it overrides. Virtual marks a function as overridable; abstract contracts declare structure without full implementation; interfaces declare only external function signatures. The lab's conflicting-overrides hierarchy teaches the resolution order empirically — write it, deploy it, and confirm which implementation actually executes rather than guessing. Diamond-shaped hierarchies are legal but demand explicit override lists, which is the language forcing you to confront the ambiguity rather than inheriting it silently.

fallback() vs receive(): when each triggers and why both should be minimal

A contract receiving native currency needs a way to accept it: receive() handles plain transfers with empty calldata, fallback() handles everything else — calls with non-empty calldata that match no function, and plain transfers when no receive exists. The checkpoint's rule: a payable transfer with non-empty calldata that matches no selector runs fallback, not receive. Both should be minimal — log an event, update a balance, nothing more — because they execute in untrusted contexts (anyone can send value, and the caller may be a contract with hostile code). The vault lab's three cases (empty calldata, unknown selector, non-empty calldata) map the dispatch table completely; know it cold, because misrouted value is lost value.

Events: topics vs data, indexed parameter limits, LOG opcode cost

Events are the contract's log output: LOG opcodes write topics (up to three indexed parameters plus the event signature hash) and data (the non-indexed parameters) into the transaction receipt's logs. Indexed parameters are searchable — eth_getLogs filters on them — while data is cheaper per byte but only retrievable by fetching the log. The design rule: index what you'll filter by (addresses, IDs), leave the rest as data. Off-chain indexers, block explorers, and frontends all consume events, which makes event design part of your contract's API — emit for every state change that anyone off-chain might need to know about.

Custom errors vs require strings vs assert: failure semantics and gas refunds

Solidity offers three failure mechanisms with different intent: require (with a string or, better, a custom error) for input validation and preconditions — it refunds remaining gas; assert for invariants that should never be false — it consumes all gas and signals a bug, not a user error; and custom errors (introduced as the gas-efficient standard) which are cheaper than revert strings because they avoid storing string data. The checkpoint's selection guide: user input validation gets require/custom errors, impossible-state checks get assert, and gas-optimized library code gets custom errors everywhere. Replacing strings with custom errors is a mechanical gas saving the lab measures — do it as a matter of course in new code.

Constructor semantics, immutables, and constants

The constructor runs once at deployment, setting initial state — but upgradeable proxies don't use constructors on the logic contract (more in Module 2), which is why the initializer pattern exists. Immutable variables are set once in the constructor and then embedded in the deployed bytecode (cheap to read, like constants), while constant variables are compile-time fixed. The distinction matters for gas: immutables cost a deployment-time write and then read like constants; regular state variables cost a storage read every time. Use immutables for deployment-configured values (owner addresses, token parameters) and constants for true compile-time values.

Learning objectives

  • Select correct types, data locations, and visibility specifiers for a given function contract
  • Implement inheritance hierarchies and resolve override conflicts predictably
  • Design fallback and receive handlers that route native-token transfers safely
  • Choose between custom errors, require, and assert based on intent and gas cost
  • Emit indexed events that support reliable off-chain indexing of on-chain state changes

    2. Call each function externally and internally, record the actual behavior versus your intent, then fix every annotation.

    2. Deploy and call the function; verify which parent's logic the linearization selected, and reorder the inheritance list to observe the change.

  3. Lab: Implement a vault contract with separate receive and fallback paths; test native-token transfers, empty calldata, and unknown selectors

    2. Test all three dispatches: plain transfer (empty calldata), call with an unknown selector, and call with data matching no function.

  4. Lab: Replace require strings with custom errors across a contract and measure the deployment and call gas savings

    2. Filter by an indexed address and confirm only matching logs return; try filtering by a non-indexed field and confirm it can't be done server-side.
    3. This is the indexer-developer's view of your contract — design events for the queries you'll actually run.

Module 3

OpenZeppelin patterns: tokens, access, and upgradeability

ERC-20 interface: balanceOf, transfer, approve, allowance, transferFrom; allowance double-spend mitigation

The ERC-20 interface is five functions plus events: balanceOf, transfer, approve, allowance, and transferFrom, with Transfer and Approval events. The allowance mechanism — approve a spender, spender calls transferFrom — enables contracts to move your tokens, which is also where the classic allowance race lives: changing an allowance from N to M while a spender has a pending transferFrom can let both go through. The mitigations are set-allowance-to-zero-first or the increaseAllowance/decreaseAllowance pattern. The lab's with-and-without-approval exercise makes the mechanism physical: transferFrom without allowance reverts, with allowance it moves tokens — the entire DeFi permission model in one call pair.

ERC-721 interface: ownerOf, tokenURI, safe transfer checks against onERC721Received

ERC-721 adds non-fungibility: ownerOf identifies a token's holder, tokenURI points at its metadata, and the safe transfer functions check that the recipient can actually handle NFTs. The "safe" in safeTransferFrom is a receiver check — if the recipient is a contract, it must implement onERC721Received and return the magic value, proving it knows what an NFT is. The checkpoint names the three functions involved: safeTransferFrom (both overloads) and the receiver's onERC721Received. Tokens sent with plain transfer to a contract that can't handle them are stuck forever; the safe variants exist because that happened enough times to standardize against.

Ownable: single-owner pattern, ownership transfer pitfalls; AccessControl: role identifiers, admin hierarchies

Access control comes in two standard shapes. Ownable is the single-owner pattern: one address holds exclusive privilege, with transferOwnership (and the safer two-step variant) for handover — simple, but a single key is a single point of failure and ownership-transfer pitfalls (typo'd address, lost key) are permanent. AccessControl is the role-based pattern: keccak256 role identifiers, per-role admin hierarchies, grantRole/revokeRole — the right shape the moment more than one privileged actor exists. The lab's admin/minter/pauser system demonstrates the selection rule: one human owner, use Ownable; structured operations with multiple actors, use AccessControl. Never hand-roll either — the audited implementations exist precisely so you don't have to get the edge cases right yourself.

Upgradeable proxies: delegatecall-based execution, storage collision between proxy and implementation

Upgradeable proxies separate state from logic: the proxy contract holds all storage and delegates every call to an implementation contract via delegatecall, so upgrading means pointing the proxy at new code while state stays put. The hazard is storage collision — because delegatecall executes the implementation's code against the proxy's storage, both contracts' state variables share the same slots, and a misaligned layout corrupts state silently. The checkpoint's avoidance rules: never change the order or type of existing variables, only append new ones, and use storage gaps (below) as reservation. Upgrades trade immutability for maintainability; the collision discipline is the price.

Transparent vs UUPS proxy patterns: who holds the upgrade authorization and the upgradeTo entrypoint

The two proxy standards differ in who holds the upgrade power. In the transparent proxy pattern, the proxy itself intercepts upgrade calls (only the admin can call them; everyone else is forwarded), keeping upgrade logic out of the implementation. In UUPS (Universal Upgradeable Proxy Standard), the implementation contract contains the upgrade function and the proxy is dumb — which means a UUPS implementation must never forget its upgrade authorization, or the proxy bricks permanently at the next upgrade. The lab's UUPS upgrade — deploy, upgrade to add a function, verify state persisted — demonstrates the happy path; the cautionary tale is the UUPS contract deployed without the upgrade function, which is upgradeable in name only.

Initializer pattern replacing constructors; disabling initializers on the implementation contract

Constructors don't work for upgradeable logic contracts — the constructor runs at implementation deployment, not at proxy initialization, so it would initialize the implementation's own storage (useless) and leave the proxy's storage zeros. The initializer pattern replaces constructors: an initialize() function guarded to run exactly once, called on the proxy (not the implementation) right after deployment. The checkpoint's rule falls out directly: calling initialize on the implementation instead of the proxy sets state nobody will ever read. Always disable initializers on the implementation contract itself, so nobody can initialize it later and claim its (irrelevant but confusing) state.

Storage gaps (__gap arrays) as layout reservation for upgradeable hierarchies

Storage gaps are layout reservation for the future: an array like uint256[50] __gap at the end of each upgradeable contract, consuming slots that later versions can repurpose for new variables without shifting everything after them. In an inheritance hierarchy, each parent's gap absorbs its own growth, so adding a variable to a base contract doesn't collide with the child's variables. The lab proves the discipline: upgrade with new variables placed into the gap space and verify no existing value moved. Gaps are the mechanical answer to "how do we upgrade safely" — reserve the space now, spend it later, never shift the past.

SafeMath history: pre-0.8 silent wraparound, checked arithmetic defaults since 0.8.0, unchecked blocks for gas

Before Solidity 0.8, arithmetic wrapped silently on overflow — the bug class that made SafeMath (explicit checked math as a library) mandatory in every serious contract. Since 0.8.0, the compiler inserts overflow and underflow checks by default, reverting instead of wrapping; unchecked{} blocks opt back out for gas savings where the developer can prove safety (loop counters are the canonical case). The lab's pre-0.8-style exploit contract, written in modern Solidity, demonstrates the change: the same code that once drained funds now reverts. The history matters because you'll read old code and old audits — know which arithmetic regime you're looking at before judging it.

Module 4

Vulnerability class deep dives I: control flow and access

Reentrancy: external call before state update lets the callee re-enter; single-function vs cross-function vs cross-contract variants

Reentrancy is the EVM's most famous bug: when your contract calls an untrusted contract before updating its own state, the callee can call back into your function and observe (and exploit) the not-yet-updated state. The classic withdraw pattern — check balance, send ether, then zero the balance — lets an attacker's fallback recursively withdraw until the contract is drained. Variants extend the shape: single-function (reenter the same function), cross-function (reenter a different function sharing the state), and cross-contract (the shared state lives in another contract). The lab's trace-the-call-sequence exercise makes the interleaving concrete: your code, their code, your code again — with your invariants violated in the middle.

Checks-effects-interactions ordering; reentrancy guards and their limits

The defense is ordering plus guards: checks-effects-interactions — validate first, update your state second, interact with untrusted contracts last — so that by the time external code runs, there's nothing left to exploit. Reentrancy guards (a mutex locked during execution) add a second layer for cases where ordering alone is awkward, such as functions that must interact mid-flow. The guards have limits: they don't help across contracts unless every entry point shares the guard, and they cost gas on every call. The professional standard is both: correct ordering as the primary defense, guards where the flow demands them, and the lab's fix-the-vulnerable-withdraw as the muscle memory.

tx.origin vs msg.sender for authentication and the phishing vector of tx.origin

tx.origin is the original EOA that started the transaction chain; msg.sender is the immediate caller. Using tx.origin for authentication breaks the moment a user interacts through any intermediary contract — a multisig, a relayer, a DeFi router — because tx.origin is still the user while msg.sender is the intermediary. Worse, it's a phishing vector: trick a privileged user into calling your malicious contract, and your contract calls the victim contract where tx.origin (the victim) passes the check. The rule is absolute: authenticate with msg.sender, never tx.origin. Any tx.origin check you find in an audit is a finding, full stop.

delegatecall: runs callee code in caller storage context; proxy-call injection and function selector collisions

delegatecall executes the callee's code in the caller's context — caller's storage, caller's balance, caller's msg.sender — which is what makes proxies possible and what makes delegatecall to untrusted targets catastrophic. Two hazards dominate: storage layout must align exactly between caller and callee (or the callee's variable writes land on the caller's unrelated slots — the lab's hijacked-proxy overwrite of the owner slot), and function selector collisions let a malicious implementation expose functions the proxy didn't intend. Proxy-call injection — where an attacker supplies the implementation address — turns the proxy into the attacker's puppet with the proxy's storage and funds. Delegatecall is safe only to trusted, layout-matched, non-malleable targets.

Access control failures: unprotected init functions, missing onlyOwner on sensitive setters, default visibility traps

Access control failures are the most common finding in real audits and the most embarrassing: functions that move value or change privilege with no modifier, initializers anyone can call, sensitive setters missing onlyOwner. The default-visibility trap is historical (early Solidity defaulted to public) but the modern form persists — forgetting the modifier on one function in a large contract. The lab's audit-the-sample-set exercise builds the scanning reflex: read every external/public function, ask "who may call this, and what does it let them do," and flag anything whose answer is "anyone" and "something valuable." Access control is not a feature; it's the absence of a bug, verified function by function.

Gas griefing: unbounded iteration over user-controlled arrays, push payments to contracts that revert

Gas griefing turns the block gas limit into a weapon: any unbounded iteration over user-controlled arrays (airdrop loops, mass payouts) eventually exceeds what fits in a block, bricking the function permanently as the list grows. Push payments — sending funds to recipients in a loop — add a second failure: one recipient whose fallback reverts (or just costs too much gas) breaks the entire payout for everyone. The lab measures both: grow the airdrop list until it exceeds the block limit, and break one recipient to freeze the push payout. Gas is a security property, not just a cost — any loop whose bound an attacker influences is a denial-of-service vector.

Pull-payment pattern: escrow balances and withdrawal functions as the safe payout shape

The pull-payment pattern is the answer to push-payment fragility: instead of sending funds to recipients, record what each is owed in a balances mapping and let them withdraw it themselves. A failing recipient then affects only themselves, reentrancy surface shrinks to a single well-guarded withdraw function, and the payout loop disappears entirely. The refactor lab — push contract bricked by one reverting recipient, rewritten as pull — demonstrates the resilience difference directly. Escrow-then-withdraw is the safe payout shape for bounties, revenue splits, and auctions alike; push is reserved for cases where you've proven the recipient set is trusted and bounded.

Module 5

Vulnerability class deep dives II: economics and ordering

Oracle manipulation: spot-price reads from a single DEX pool are manipulable within one block via flash capital

A price oracle that reads a spot price from a single DEX pool can be manipulated within one block: an attacker with flash capital moves the pool's price, has the victim contract read the distorted quote, and profits before the price reverts — all atomically, so there's no market risk. The lab's drain-the-lending-contract exercise demonstrates the full cycle on a forked mainnet: borrow big, distort the pool, exploit the mispriced quote, repay, keep the difference. Any protocol decision (liquidations, mint ratios, payouts) driven by a single-block spot price is an invitation to this attack. The defense starts with admitting that on-chain spot prices are attacker-influenced inputs, not ground truth.

TWAP oracles, multi-source aggregation, staleness checks, and circuit breakers as layered defense

Time-weighted average prices (TWAPs) raise the attacker's cost from one block's flash capital to sustained capital over the averaging window — manipulation becomes expensive instead of free. Layered defense adds multi-source aggregation (no single pool decides), staleness checks (reject prices older than the freshness bound — a dead feed is worse than no feed), and circuit breakers (pause when prices move impossibly fast). The lab's add-TWAP-and-staleness step shows the same exploit failing after the fix: the manipulation transaction can no longer move the averaged, freshness-checked price enough to profit. Oracles are a system — source, averaging, freshness, bounds — not a single call.

Front-running: public mempool ordering, sandwich attacks on DEX trades, commit-reveal as mitigation

Front-running exploits the public mempool: pending transactions are visible before they're mined, so an attacker can order their own transaction around a victim's — the sandwich attack places a buy before and a sell after a victim's DEX trade, profiting from the victim's slippage. The information the attacker needs is all public: the victim's trade size, direction, and slippage tolerance, straight from the mempool. Commit-reveal schemes mitigate by hiding intent until it's too late to front-run (commit the hash now, reveal the details later), and private mempools / MEV-protection RPCs hide the transaction entirely. Any transaction whose profitability depends on ordering is MEV-exposed by construction — design as if the mempool is adversarial, because it is.

Integer issues: truncation in division, rounding favoring one party, precision scaling with token decimals

Integer bugs extend far beyond overflow: division truncates, so computing a share as (a / b) * c loses the remainder that (a * c) / b would have kept — the multiply-before-divide rule minimizes precision loss. Rounding direction is a value judgment with winners: rounding down systematically favors the protocol (or early actors), rounding up favors the other side, and the choice must be deliberate and documented. Token decimals multiply the subtlety: mixing 18-decimal and 6-decimal tokens without scaling is a precision bug wearing a units bug's clothes. The lab's vault-with-bad-rounding makes the favoritism concrete: run the numbers, see who gains, fix the direction, re-verify.

Signature schemes: EIP-712 domain separation, nonce invalidation, malleability and replay across chains (chainId)

Signatures authorize actions off-chain, and EIP-712 structures them with a domain separator — name, version, chainId, verifyingContract (plus salt) — so a signature for one contract can't be replayed against another, or the same contract on another chain. The checkpoint's replay lab omits chainId from the domain and demonstrates the cross-chain replay: a valid signature on one chain authorizes the same action on another. Nonces complete the scheme: each signature carries a nonce that's invalidated on use, preventing the same signature from executing twice. Signature verification code must check the domain, the nonce lifecycle, and malleability (rejecting non-canonical s values) — miss any one and the authorization is forgeable or replayable.

Timestamp dependence: miner-influenced block.timestamp and the 15-second rule of thumb for safe use

block.timestamp is miner-influenced within bounds — validators can shift it slightly, which is safe for long-interval logic (vesting cliffs, auction ends measured in days) and dangerous for anything finer. The 15-second rule of thumb: don't use timestamps for randomness or for decisions where seconds matter, because the block producer's discretion covers roughly that window. Randomness deserves special emphasis: block variables (timestamp, prevrandao, blockhash) are all observable or influenceable before use, so on-chain "randomness" from block data is predictable to a motivated party. Use commit-reveal or verifiable randomness oracles for anything where unpredictability has value.

Economic DoS: forcing expensive callbacks, dusting to bloat iteration, first-depositor share inflation

Economic denial of service doesn't break code — it breaks incentives: forcing expensive callbacks the attacker triggers for free, dusting to bloat iteration (tiny deposits that make loops cost more than they're worth), or the first-depositor share inflation where an attacker donates to inflate share price and trap later depositors' value. These attacks exploit the gap between "the code is correct" and "the economics are sound" — the contract does exactly what it says, and what it says is exploitable. The defense is economic modeling during design: ask who pays for each operation, what happens at extreme parameter values, and whether the first/last actor has an advantage. Code review finds bugs; economic review finds these.

  • Recognize economic denial of service: dust attacks, griefing via required callbacks, and rent extraction

Module 6

Secure development workflow: tests, analysis, fuzzing

Testing layers: unit tests per function, integration tests across contracts, fork tests against mainnet state

Testing smart contracts has layers, each catching what the others miss. Unit tests exercise individual functions in isolation — happy paths, revert paths, access-control boundaries. Integration tests exercise contracts calling each other, where composition bugs (the reentrancy family) actually live. Fork tests run against real mainnet state, so your upgrade or integration behaves against the actual tokens, oracles, and liquidity it will meet in production. The lab's full-suite exercise builds all three for one vault: the unit tests prove the functions, the integration tests prove the composition, the fork test proves the deployment context. No single layer suffices — the bug classes are layer-specific.

Static analysis concepts: taint tracking, dataflow facts, known detector patterns (reentrancy, unprotected selfdestruct)

Static analysis reads code without running it: taint tracking follows untrusted input through the program, dataflow facts propagate what the analyzer knows, and detector patterns match known bug shapes (reentrancy, unprotected selfdestruct, tx.origin use). Tools in this family are fast and exhaustive over the code they see — and blind to everything semantic: they flag patterns, not exploits. The lab's classify-every-finding exercise is the essential skill: true positive (real bug), false positive (pattern without exploitability), informational (worth knowing, not a bug). An analyzer you can't triage is a noise generator; triage is the skill, the tool is just the sensor.

Slither-style detectors vs symbolic execution: speed and coverage tradeoffs of each approach

Symbolic execution explores program paths mathematically rather than randomly: it finds the inputs that reach deep, specific states — the bugs static detectors miss because they require a precise sequence of calls with precise values. The price is scaling: path explosion makes it exponentially expensive on large codebases, which is why it's aimed at critical functions rather than whole protocols. The checkpoint's tradeoff is the selection guide: static analysis for broad, fast coverage of known patterns; symbolic execution for deep verification of the functions where a bug would be catastrophic. Use each where its economics make sense.

Fuzzing: random input generation against function selectors; stateful fuzzing with persistent chain state

Fuzzing generates random inputs against your functions and watches for crashes and assertion failures; stateful fuzzing keeps chain state between calls, exploring sequences — deposit, transfer, withdraw, in hostile orders — rather than single calls. Invariant testing is fuzzing with a property to defend: "total assets always equal the sum of user shares" must hold after every random sequence, and the fuzzer's job is to find the sequence that breaks it. The lab's stateful harness with the assets-invariant catches reentrancy and accounting drift that no hand-written test would think to try. Write the invariants first — they encode what "correct" means — then let the machine attack them.

Invariant testing: properties that must hold across arbitrary call sequences (e.g., sum of balances equals total supply)

Differential testing compares your implementation against a reference: same inputs to both, outputs must match — the technique for numeric code where "correct" means "agrees with the trusted implementation." It's the answer to precision and rounding bugs that unit tests miss because the test author shares the implementer's blind spots. The reference can be a high-precision off-chain model, a previous audited version, or a straightforward (if gas-inefficient) implementation. When your optimized fixed-point math agrees with the naive reference across millions of random inputs, you have evidence — not proof, but strong evidence — that the optimization preserved semantics.

Differential testing against a reference implementation for numeric correctness

Coverage is a means, not a metric: high line coverage with zero invariant coverage is false confidence — every line executed once, in the friendly order, by the friendly caller. What matters is branch coverage of critical paths (every revert branch of the withdrawal function, not just its happy path) and invariant coverage across adversarial sequences. The lab's CI pipeline enforces the meaningful gates: lint clean, critical-file branch coverage above threshold, no new analyzer findings — and fails the build otherwise. Measure what the attackers measure: they don't care about your line percentage, they care about the one untested branch that moves money.

Coverage pitfalls: high line coverage with zero invariant coverage gives false confidence

The workflow ties together in CI: every commit runs the linter and formatter (style is a security property — inconsistent code hides bugs), the full test suite, the static analyzer with findings triaged as blocking or informational, and the coverage gates on critical files. Fuzzing runs longer — nightly or on release branches — because meaningful campaigns need time. The lab's pipeline-fails-on-violations setup makes the standard enforceable rather than aspirational: the build is red until the code meets the bar. Professional contract development is 50% writing code and 50% operating the machinery that proves the code correct — budget accordingly.

Learning objectives

  • Write unit tests that cover happy paths, revert paths, and access-control boundaries of a contract
  • Run a static analysis tool on a codebase and triage its findings into true positives and noise
  • Design a stateful fuzzing campaign with invariants that catch reentrancy and accounting drift
  • Integrate linting, formatting, and CI checks into a contract repository
  • Measure test coverage meaningfully: branch coverage of critical paths rather than raw line percentages

Module 7

Audit workflow: threat modeling to reporting

Threat modeling: enumerate assets (funds, roles, data), actors (users, admins, attackers, MEV searchers), trust boundaries

Threat modeling precedes code review: enumerate the assets (funds, privileged roles, sensitive data), the actors (users, admins, keeper bots, attackers, MEV searchers), and the trust boundaries each actor crosses. The staking-contract example from the checkpoints — admin, keeper bot, users — has boundaries everywhere the bot's automation meets user funds and where the admin's power meets both. A threat model without named actors is a vulnerability list without priorities; the actors tell you who wants what and what they'll try. Write it before reading code, and let it direct where your review time goes.

Attack surface mapping: external entrypoints, privileged functions, upgrade paths, oracle dependencies

Attack surface mapping turns the threat model into a checklist: every external entrypoint, every privileged function, every upgrade path, every oracle dependency — each is a place value or control changes hands. External functions are the surface attackers touch; privileged functions are the surface insiders (or key-thieves) touch; upgrade paths and oracles are the surface the protocol's assumptions touch. The lab's two-contract staking map makes this concrete: list every function, mark its accessibility, and the review order writes itself. Unmapped surface is where the missed bugs live.

Review order: architecture first, then access control, then arithmetic, then control flow, then economics

Manual review follows a fixed order because bugs hide behind each other: architecture first (does the design even make sense?), then access control (who can do what?), then arithmetic (precision, rounding, overflow regimes), then control flow (reentrancy, ordering), then economics (incentives, griefing, oracle games). The order matters — there's no point perfecting arithmetic in a function anyone can call, and no point auditing control flow in a design that's economically broken. The checklist-driven timed review lab practices exactly this: work the list in order, log as you go, don't chase the interesting bug past the boring-but-critical layer.

Finding anatomy: title, severity, description, vulnerable code location, PoC, impact, recommendation

A complete audit finding has five required sections: title (the bug, named), severity (below), description (what's wrong and where — file, line, function), proof of concept (the exploit, ideally as runnable code), and impact plus recommendation (what it costs, how to fix it). The PoC is what separates a finding from an opinion — "here is the transaction sequence that drains the vault" ends arguments about exploitability. The lab's write-one-finding-end-to-end exercise produces exactly this artifact: exploit contract, impact in token value, concrete fix. Write findings for the developer who must fix them and the stakeholder who must prioritize them — both audiences, one document.

Severity frameworks: critical/high/medium/low/informational based on impact times likelihood

Severity is impact times likelihood, in the standard four-plus-one scale: critical (direct loss of funds, exploitable now), high (funds at risk under plausible conditions), medium (limited impact or difficult exploitation), low (minor issues, best-practice deviations), informational (no security impact, worth noting). The ranking lab — three findings, one line of justification each — practices the judgment: a critical that's hard to exploit versus a medium that's trivially exploitable is the kind of call auditors make daily. Severity is a communication tool, not a mathematical truth — its job is to make the fix order obvious.

Audit artifacts: scope statement, assumptions, centralization risks, acknowledged vs fixed findings

Audit artifacts extend beyond findings: the scope statement (which files, which commit hash — anything outside it wasn't reviewed), the assumptions (trusted roles, economic conditions, out-of-scope components), centralization risks (admin keys that could rug the protocol — reported in every audit even with no code bug, because key compromise is a protocol risk), and the finding lifecycle (fixed, acknowledged, or unresolved after re-audit). Time-boxed audits differ from open security contests in incentives and depth — contests reward novel criticals at scale, audits reward systematic coverage — and knowing which you're doing (or buying) sets expectations correctly. The one-page scope lab is the engagement's foundation: if it isn't in scope, it wasn't audited, and everyone should know that.

Contest and review dynamics: how time-boxed audits differ from open security contests

Re-audit closes the loop: after fixes are applied, every original finding is re-tested and classified as fixed (the PoC no longer works), acknowledged (the team accepts the risk deliberately), or unresolved (still exploitable). Fixes themselves get reviewed — patches introduce bugs too, especially rushed ones — which is why the re-audit examines the diff, not just the finding list. The lab's re-audit pass practices the discipline: re-run every PoC, read every changed line, update every status. An audit without a re-audit is a list of suggestions; with one, it's a verified security posture at a point in time.

  • Produce a threat model for a contract system: assets, trust boundaries, actors, and attack surfaces
  • Conduct a checklist-driven manual review covering each vulnerability class in this sequence
  • Write a finding with severity, likelihood, impact, proof of concept, and remediation guidance
  • Prioritize findings by exploitability and economic impact rather than by code aesthetics
  • Scope an audit engagement: time-boxing, in-scope contracts, and out-of-scope assumptions

Module 8

Deployment hygiene: testnets, verification, key management

Testnet staging: deploying to public testnets, faucet discipline, mirroring mainnet dependencies via forks

Testnet staging is where deployment procedures get debugged: deploy to a public testnet first, exercise the full flow (deploy, initialize, verify, transfer ownership), and treat faucet discipline as real — testnet tokens are free but rate-limited, and spamming faucets is how you learn patience. Mirror mainnet dependencies via forks where testnets diverge: if your protocol integrates with mainnet-only liquidity, a fork test against real state (Module 5's lab) catches what the testnet can't. The deployment runbook lab produces the artifact that matters: a script performing the entire deployment reproducibly, because mainnet deployment should never be a human typing commands from memory.

Source verification: flattened vs standard-json input, compiler version and optimizer settings must match exactly

Source verification lets anyone confirm the deployed bytecode matches the published source: the explorer recompiles your standard-JSON input with your exact compiler version and optimizer settings and compares the output. The metadata hash is why "identical sources" can produce different bytecode — the compiler appends a CBOR blob with the source hash and compiler version, so even whitespace-identical sources compiled with different settings verify differently. The lab's deliberate optimizer mismatch demonstrates the failure: change the runs setting, watch verification fail, restore it, watch it pass. Verification is also a security control — users should never trust an unverified contract with funds, and neither should you.

Metadata hash: the appended CBOR blob and why it makes bytecode differ between identical sources

Key hygiene separates three roles that must never share one private key: the deployer (used once, then retired), the admin (ongoing privileged operations), and the treasury/user funds (never on a hot key at all). Admin keys live on hardware wallets, private keys never touch repositories or chat logs, and the deployment runbook records which key did what without recording the keys. The testnet multisig lab practices the operational shape: transfer ownership to the multisig, execute an admin action through the threshold, and feel the coordination cost — that friction is the security. Lost-key and compromised-key procedures belong in the runbook before mainnet, not after an incident.

Key hygiene: hardware wallets for admin keys, never committing private keys, separating deployer from admin

Multisigs and timelocks convert unilateral admin power into governed power: threshold signatures mean no single key can act alone, and a timelock's delay window means users can see a privileged action coming and exit before it executes. The checkpoint's distinction is the point: a plain multisig still lets the signers act instantly and opaquely; a timelock guarantees transparency and an exit window that no multisig alone provides. Pausable patterns add the emergency stop — but design who can pause (a fast, low-threshold role for incidents) separately from who can unpause or upgrade (slower, higher-threshold governance), or your emergency stop becomes an emergency hostage situation.

Multisig and timelocks: threshold signatures for privileged actions, delay windows for user exit

Monitoring is the deployed contract's immune system: event-based alerting on privileged calls (ownership transfers, role grants), large transfers (thresholds tuned to the protocol's normal flow), and proxy upgrades (the implementation address changing is always worth a human look). The lab's local-chain alert — fire when the proxy implementation changes — is the template: watch the events that indicate control changes, not just value movement. Alerts must be tuned and owned: an alert nobody reads is noise, and a noisy alert system trains everyone to ignore the one that matters. Monitoring is part of the launch checklist, not a post-launch aspiration.

Pausable patterns and emergency stops: who can pause, what pause blocks, and unpausing governance

Pausable patterns and emergency stops need a designed incident flow, not just a pause function: who can pause, what exactly pause blocks (deposits? withdrawals? both — and with what user impact?), who investigates, what the unpause criteria are, and how users are told what's happening. The lab's simulated incident — pause, investigate on a fork, unpause — practices the coordination, because the technical pause is the easy part and the human process is what fails. Guarded launch phases belong here too: deposit caps and rate limits for new protocols, so a bug's blast radius is bounded while the system earns trust. Launch limits are humility encoded in parameters.

Monitoring: event-based alerting on privileged calls, large transfers, and proxy upgrades

The mainnet launch checklist is the final gate before real funds: contracts deployed via the runbook and verified on the explorer, ownership transferred to the multisig/timelock, monitoring alerts live and tested, pause authority assigned and the incident process rehearsed, launch limits (caps, rate limits) configured, and a rollback/upgrade path confirmed working. The checkpoint's "minimum items" are these — each one is a story about a protocol that launched without it and regretted it. Treat the checklist as a ceremony: run it in order, sign it off, and only then announce. Mainnet is forever; an extra day of checklist is cheap.

Launch limits: deposit caps, rate limits, and guarded launch phases for new protocols

Incident response for exploits follows the same shape as any other incident, compressed: detect (monitoring fires), assess (what's happening, how much is at risk — on a fork if needed), contain (pause, following the rehearsed process), communicate (users deserve timely, honest status), remediate (fix, re-audit the fix per Module 6), and recover (unpause deliberately, with limits if warranted). The tabletop lab — a bad apply deleted a queue, adapted here as an exploit tabletop — practices the decisions without the adrenaline: who calls the pause, who talks to users, what "safe to resume" means. Write the incident runbook before you need it; during the incident, you execute, you don't design.

Learning objectives

  • Deploy a contract system through testnet staging with a documented deployment runbook
  • Verify contract source on a block explorer and confirm the exact deployed bytecode matches
  • Design a key-management plan: deployer keys, admin keys, multisig thresholds, and timelocks
  • Plan an incident response: pause mechanisms, upgrade paths, and communication steps for an exploit
  • Evaluate mainnet readiness with a launch checklist covering monitoring, limits, and rollback options

Hands-on labs

  1. Lab: Write a deployment runbook script that deploys, initializes, verifies, and transfers ownership in one reproducible run

    1. Write a deployment runbook script that, against a testnet, deploys your contract system, runs initialize, verifies the source, and transfers ownership — in one reproducible run.
    2. Execute it twice (two separate deployments) and confirm both produce the same verified result — reproducibility is the requirement.
    3. Break one step deliberately (wrong constructor arg) and confirm the script fails loudly rather than deploying something subtly wrong.

  2. Lab: Verify a contract on a block explorer, then intentionally mismatch the optimizer runs and observe the verification failure

    1. Verify a contract's source on a block explorer, confirming the exact deployed bytecode matches.
    2. Now recompile with a different optimizer runs setting and attempt verification — observe the failure the metadata hash causes.
    3. Restore the exact settings and verify successfully: the settings are part of the source, for verification purposes.

  3. Lab: Set up a multisig wallet on a testnet, transfer contract ownership to it, and execute an admin action through the threshold

    1. Set up a multisig wallet on a testnet with a 2-of-3 threshold; transfer a contract's ownership to it.
    2. Execute an admin action (a parameter change) through the full threshold flow: propose, collect signatures, execute.
    3. Document the coordination steps and time — this friction is the security working as designed.

  4. Lab: Implement a pausable token sale with a timelocked admin, then simulate an incident: pause, investigate, unpause

    1. Deploy a pausable token sale (or similar) with a timelocked admin; run a normal purchase to establish the baseline.
    2. Simulate an incident: trigger the pause from the fast-pause role, investigate on a fork, then unpause through the proper governance path.
    3. Time the full cycle and note every human decision point — the incident process, rehearsed.

  5. Lab: Build a monitoring alert on a local chain that fires when the proxy implementation address changes

    1. On a local chain, build a monitoring alert that fires when the proxy's implementation address changes (watch the upgrade event or poll the slot).
    2. Perform an upgrade and confirm the alert fires with the old and new addresses; perform a normal admin action and confirm it doesn't.
    3. Extend the alert set: ownership transfers and large transfers — the deployed contract's immune system, bootstrapped.

Self-check questions

  • Explain why two identical sources can produce different deployed bytecode and what the metadata hash is
  • State the three roles that should never share one private key in a production deployment
  • Describe what a timelock guarantees users that a plain multisig does not
  • List the minimum items on a mainnet launch checklist before real funds are accepted
