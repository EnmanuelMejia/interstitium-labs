Module 1 of 8

Anonymous Blocks and Block Structure

Every PL/SQL program is a block: DECLARE, BEGIN, EXCEPTION, END. This module teaches the block anatomy, anonymous blocks versus named program units, and the DBMS_OUTPUT debugging workflow. You will write, compile, and run your first blocks against a scratch schema.

Objectives

  • Describe the DECLARE / BEGIN / EXCEPTION / END sections of a PL/SQL block and identify which are optional.
  • Execute anonymous blocks in SQL*Plus or SQLcl against Oracle Database Free (23ai Free) and observe output via DBMS_OUTPUT.
  • Predict variable scope and shadowing behavior in nested blocks.
  • Trace execution flow when an exception interrupts a block.

Key concepts

Anonymous block vs named program unit

An anonymous block is PL/SQL code with no name — written, executed once, and gone. Named program units (procedures, functions, packages, triggers) are stored in the database, compiled, and callable by name. Anonymous blocks are the scratchpad: testing logic, running one-off tasks, and learning the language. Everything you learn in anonymous blocks transfers directly, because a procedure body is an anonymous block with a header.

DECLARE section (optional): declarations

The DECLARE section is where variables, constants, cursors, and types are introduced before use. It is optional — a block can go straight to BEGIN — but any named thing the block uses must be declared here first. The lab's section drill shows what you give up without it: no persistent names across statements, everything inline. Declarations are the block's vocabulary; BEGIN is its sentences.

BEGIN: the mandatory executable section

BEGIN opens the one section a block cannot skip: the executable statements. Assignments, SQL, control flow, and procedure calls all live here. Execution runs top to bottom until it hits END or an exception diverts it. The lab's exception-flow trace maps this precisely — print before, divide by zero, print after — so you can see the exact moment control leaves the normal path.

EXCEPTION section (optional): error handlers

The EXCEPTION section catches errors raised in the BEGIN section and routes them to handlers matched by exception name. It is optional, and its absence means an error propagates straight to the caller — the lab's nested-block checkpoint asks where execution ends up in exactly that case. Handlers run, then control leaves the block; there is no resume into the middle. A later module makes this section a full discipline.

END: closing the block

END closes the block, optionally repeating the block's label for readability. Every BEGIN needs its END, and the compiler is unforgiving about the pairing — most early syntax errors are mismatched or missing ENDs. In nested blocks, labeled ENDs (END outer_block;) turn a wall of ENDs into something a human can audit. Close what you open, label what you nest.

Nested blocks and variable scope/shadowing

Blocks nest inside blocks, and an inner block sees the outer block's variables — unless it declares its own with the same name, which shadows the outer one inside the inner scope. The lab demonstrates this directly: print the variable inside the inner block and after it ends, and watch the value change back. Shadowing is legal and occasionally useful, but mostly it is a bug factory; the experiment teaches you to recognize it on sight.

DBMS_OUTPUT.PUT_LINE for observable output

DBMS_OUTPUT.PUT_LINE writes text to a buffer the client can display — the standard way to observe a block's behavior while learning. It is not logging, not a result set, and not visible unless the client enables it. The lab runs the same block with server output off and on to make that dependency visceral. In production code you will use proper logging; in the lab, PUT_LINE is your microscope.

SET SERVEROUTPUT ON in SQL*Plus/SQLcl

DBMS_OUTPUT fills a buffer, but SQL*Plus and SQLcl only drain and display that buffer when server output is enabled — hence SET SERVEROUTPUT ON. Without it, your PUT_LINE calls execute silently and you conclude, wrongly, that nothing happened. The lab's hello-block run isolates this variable first, because half of all beginner PL/SQL confusion is this one setting. When output vanishes, check the switch before doubting the code.

Hands-on labs

  1. Hello-block run — write an anonymous block that prints a greeting with DBMS_OUTPUT.PUT_LINE. Run it with SET SERVEROUTPUT OFF, then ON, and note exactly what changes. (Oracle Database Free 23ai Free, free container or local install; connect with SQL*Plus or SQLcl — no paid license needed.)
  2. Section drill — write a block with a DECLARE section containing a counter, loop from 1 to 5, and print each value. Then rewrite it so all work happens without a DECLARE section and describe what you had to give up.
  3. Scope experiment — declare v_msg in an outer block, then redeclare v_msg with a different value in a nested inner block. Print v_msg inside the inner block and again after it ends; explain the shadowing you observe.
  4. Exception flow trace — write a block that prints 'before', then performs 1/0, then prints 'after', with an exception section that prints 'handled'. Run it and map the exact execution order to the block structure.

Self-check

  1. Which two sections of a block are optional, and what happens if the EXCEPTION section is absent when an error occurs?
    Answer key
    DECLARE and EXCEPTION are optional; BEGIN is mandatory. With no EXCEPTION section, the error is not trapped — it propagates to the enclosing block's exception section, or out to the caller if none exists. Absent handlers do not mean absent errors; they mean errors travel.
  2. Predict the output of a nested block where the inner block redeclares the outer block's variable with a different value.
    Answer key
    The inner declaration shadows the outer: inside the inner block, the name refers to the inner variable (the new value); the outer variable is temporarily invisible but unharmed. After the inner block ends, the name refers to the outer variable again with its original value. Predict: inner PUT_LINE shows the inner value, outer PUT_LINE after shows the outer value.
  3. Why does DBMS_OUTPUT.PUT_LINE appear to do nothing until you run SET SERVEROUTPUT ON?
    Answer key
    DBMS_OUTPUT.PUT_LINE writes to a session buffer — it does not write to your screen. SET SERVEROUTPUT ON tells the client tool to drain that buffer to the display after execution. Without it, the procedure ran fine and the output sat in the buffer, unread. It is a client display setting, not a code problem.
  4. An unhandled exception is raised in the inner block of two nested blocks, and neither has an exception section. Where does execution end up?
    Answer key
    Execution ends up outside both blocks — the exception propagates through the inner block (no handler), then through the outer block (no handler), to whatever called the outer block. If the caller has no handler either, the session reports the unhandled exception. Unhandled does not mean vanished; it means traveling upward until someone deals with it or the user sees it.

Module 2 of 8

Variables, %TYPE, and %ROWTYPE

Declarations are where PL/SQL programs meet the database schema. This module covers scalar types, the %TYPE and %ROWTYPE anchoring that keeps declarations synchronized with tables, constants, and scope rules. You will learn why anchored types are the professional default.

Objectives

  • Declare scalar variables with appropriate datatypes, NOT NULL constraints, and defaults.
  • Anchor declarations to table columns with %TYPE and to whole rows with %ROWTYPE.
  • Explain why anchored declarations are resilient to schema changes.
  • Choose between PL/SQL datatypes deliberately, including the limits of BOOLEAN.

Key concepts

Scalar datatypes: VARCHAR2, NUMBER, DATE, BOOLEAN

PL/SQL's core scalars are VARCHAR2 for variable-length strings, NUMBER for numerics, DATE for dates and times, and BOOLEAN for true/false logic. VARCHAR2 — not VARCHAR — is the Oracle idiom; NUMBER covers integers and decimals alike. BOOLEAN deserves special attention: it is a PL/SQL-only type, fully usable in procedural logic but not selectable in SQL. The lab's boolean-boundary exercise proves the boundary by hitting it.

NOT NULL and DEFAULT constraints on declarations

A declaration can require a value (NOT NULL) and supply one when none is given (DEFAULT) — small constraints that remove whole classes of bugs. NOT NULL turns a missing assignment into a compile-time or immediate error instead of a NULL propagating silently through logic. DEFAULT documents intent: this variable starts life with a sensible value. The checkpoint asks when each pays for itself; the answer is whenever the variable's absence would be a lie.

%TYPE: anchoring a variable to a column's datatype

Declaring v_name employees.last_name%TYPE anchors the variable to the column's datatype — whatever the column is today, the variable matches. When the DBA widens the column, anchored declarations recompile against the new definition automatically. The lab proves it: widen first_name to 200 characters and the anchored block runs unchanged while the hardcoded VARCHAR2(50) version breaks. Anchor to the schema; never hand-copy its types.

%ROWTYPE: anchoring a record to a table or cursor row

table%ROWTYPE declares a record with one field per column — the whole row as a single variable. SELECT ... INTO a %ROWTYPE record fetches an entire row in one statement, and cursor%ROWTYPE does the same for cursor rows. It is the DRY answer to declaring a dozen scalars that mirror a table. The lab fetches a full lab_emp row into a record and prints fields by name; adding a column later changes nothing in the code.

Anchored declarations surviving schema changes

The resilience story is the point of anchoring: schema evolution — wider columns, added columns — flows through anchored code without edits. Hardcoded declarations rot silently until they fail loudly at runtime. The lab's before/after contrast is the argument in miniature. In a database that will outlive its developers, anchored declarations are how code stays correct without being touched.

BOOLEAN as a PL/SQL-only datatype

BOOLEAN lives in PL/SQL but not in SQL: you can branch on it, return it from functions, and store it in variables, but you cannot SELECT it or put it in a table column. The lab computes a BOOLEAN flag, uses it in IF logic, then tries to SELECT it and documents the expected error. The boundary exists because the SQL engine predates the type. Know which side of the line each piece of your code stands on.

CONSTANT declarations

A CONSTANT declaration fixes a value at compile time — tax rates, status codes, magic strings given names. Constants document intent and centralize change: one edit updates every use. They pair naturally with anchored types and DEFAULT. Use them for every literal that means something; literals that mean something and appear twice are a future inconsistency.

Implicit conversion pitfalls between SQL and PL/SQL types

PL/SQL converts between types silently when it can — strings to numbers, dates to strings — and silently is the problem. A conversion that works for a thousand rows fails on row 1001 with an unexpected value, or worse, succeeds with a wrong one. DATE-to-string conversions depend on session NLS settings, which differ between environments. Convert explicitly with TO_NUMBER, TO_DATE, TO_CHAR and named format models; implicit conversion is a convenience that bills you later.

Self-check

  1. What is the practical difference between v_name employees.last_name%TYPE and v_emp employees%ROWTYPE?
    Answer key
    v_name employees.last_name%TYPE declares a scalar anchored to that column's datatype — it tracks the column if the DBA changes it. v_emp employees%ROWTYPE declares a record holding an entire row of the table, with one field per column. Practical difference: %TYPE for single values, %ROWTYPE when you fetch whole rows (SELECT * INTO v_emp).
  2. A DBA widens a VARCHAR2 column from 30 to 100 characters. Which declarations break, and which survive untouched?
    Answer key
    Hardcoded VARCHAR2(30) declarations break (values up to 100 chars no longer fit, or assignments fail); %TYPE-anchored declarations survive untouched — they widen automatically. This is the entire economic argument for anchored types: schema changes stop being code changes.
  3. Why is BOOLEAN legal in PL/SQL logic but not directly usable in a SQL statement?
    Answer key
    PL/SQL's BOOLEAN has no SQL equivalent — the SQL engine has no boolean datatype, so a BOOLEAN variable cannot appear in a SQL statement (no WHERE bool_col, no inserting into a table). Keep booleans in procedural logic; translate to 'Y'/'N' or 1/0 at the SQL boundary.
  4. When would you add NOT NULL or a DEFAULT to a declaration, and what risk does each remove?
    Answer key
    NOT NULL removes the risk of the variable ever holding NULL — the declaration fails fast at assignment time instead of corrupting logic downstream. DEFAULT removes the risk of uninitialized use — every path starts from a known value. Add NOT NULL when null is never meaningful; add DEFAULT when there is a sane starting value. Both are cheapest at declaration time.

Module 3 of 8

Cursors: Implicit, Explicit, and FOR Loops

Cursors are how PL/SQL walks through query results row by row. This module covers explicit cursors, cursor attributes, cursor FOR loops, and the parameterized patterns that keep cursor code clean. You will also learn when not to use a cursor — the set-based alternative is usually faster.

Objectives

  • Read implicit cursor attributes (SQL%ROWCOUNT, SQL%FOUND, SQL%NOTFOUND) after DML and single-row queries.
  • Implement the full explicit cursor lifecycle: declare, open, fetch in a loop, close.
  • Replace manual cursor code with cursor FOR loops where appropriate.
  • Parameterize cursors and select the right loop form for a given task.

Key concepts

Implicit cursors and their attributes: SQL%ROWCOUNT, SQL%FOUND, SQL%NOTFOUND, SQL%ISOPEN

Every DML statement and single-row SELECT runs in an implicit cursor, and its attributes report what happened: SQL%ROWCOUNT says how many rows were affected, SQL%FOUND and SQL%NOTFOUND say whether any were, SQL%ISOPEN is always false (the engine manages it). The lab updates a department's salaries and branches on SQL%FOUND to print a confirmation — the attributes turn a blind statement into an observed one. Check them immediately after the statement; any intervening SQL overwrites them.

Explicit cursor lifecycle: DECLARE, OPEN, FETCH, CLOSE

An explicit cursor is a named handle on a multi-row query, and its lifecycle is four verbs: DECLARE names the query, OPEN executes it, FETCH pulls rows one at a time, CLOSE releases it. The lab walks lab_emp in a loop and then comments out the CLOSE to observe the hygiene failure — unclosed cursors leak resources and eventually hit session limits. Explicit cursors are verbose on purpose: the verbosity is the control.

Cursor FOR loops: implicit open, fetch, and close

The cursor FOR loop — FOR rec IN cursor LOOP ... END LOOP — performs the open, fetch, and close automatically, declaring the loop record implicitly. The lab rewrites the explicit walk as a FOR loop and counts the lines that vanish. For straightforward row processing it is the idiomatic form: less code, no forgotten CLOSE, no manual exit condition. Reach for explicit lifecycle only when you need control the FOR loop does not offer.

Parameterized cursors

A cursor can take parameters — CURSOR c(p_dept_id NUMBER) IS SELECT ... WHERE dept_id = p_dept_id — so one definition serves many executions. The lab opens the same cursor once per department and prints a header per department. Parameters make cursors reusable logic rather than single-use queries. They are the cursor equivalent of a function's arguments, with the same readability payoff.

Loop records anchored with cursor%ROWTYPE

In a cursor FOR loop the loop record is implicitly declared as cursor%ROWTYPE — one field per selected column, correctly typed, no declaration needed. For explicit cursors you can declare the fetch target the same way. Anchoring the record to the cursor means SELECT-list changes flow through without declaration edits. It is %ROWTYPE doing exactly the job it was designed for.

SELECT ... INTO as a single-row implicit cursor operation

SELECT ... INTO is the implicit cursor for the single-row case: it fetches exactly one row into variables. Zero rows raises NO_DATA_FOUND; more than one raises TOO_MANY_ROWS — the lab's exception module catches the first deliberately. It is not a loop and not a multi-row tool; for those, use a cursor. The exceptions are features: they tell you your single-row assumption was wrong.

Cursor FOR UPDATE and WHERE CURRENT OF for safe row locking

Declaring a cursor FOR UPDATE locks the selected rows, and WHERE CURRENT OF in the loop's UPDATE targets exactly the row the cursor is positioned on — no re-specifying the key, no race between the SELECT and the UPDATE. This is the safe pattern for read-modify-write row processing. Without it, a separate UPDATE ... WHERE key can hit a different row than the one you read, or none at all. Lock what you intend to change, change what you locked.

Hands-on labs

  1. Rowcount lab — populate lab_emp with 10 rows across two departments. Run an UPDATE that gives everyone in one department a raise, then print SQL%ROWCOUNT and branch on SQL%FOUND to print a confirmation message.
  2. Explicit cursor walk — declare an explicit cursor over lab_emp ordered by emp_id; OPEN it, FETCH in a loop printing each name, then CLOSE it. Deliberately comment out the CLOSE once, re-run, and describe what you observe about cursor hygiene.
  3. FOR loop conversion — rewrite the previous walk as a cursor FOR loop. Count the lines of both versions and note which cursor operations disappeared.

Self-check

  1. List the implicit cursor attributes and state what each one tells you after an UPDATE.
    Answer key
    After an UPDATE: SQL%ROWCOUNT (rows affected), SQL%FOUND (TRUE if ≥1 row), SQL%NOTFOUND (TRUE if 0 rows), SQL%ISOPEN (always FALSE for implicit cursors — they open and close themselves). The practical trio is ROWCOUNT/FOUND/NOTFOUND: 'did my update hit anything?' is SQL%NOTFOUND.
  2. What three cursor operations does a cursor FOR loop perform for you automatically?
    Answer key
    A cursor FOR loop automatically performs OPEN, FETCH (repeatedly, until exhausted), and CLOSE — plus declaring the loop record. You write the query and the loop body; the ceremony disappears. It is also the form least likely to leak cursors, because CLOSE cannot be forgotten.
  3. You need to run the same query twice with different department ids. Which cursor form fits best and why?
    Answer key
    A parameterized explicit cursor (CURSOR c(p_dept NUMBER) IS SELECT ... WHERE dept = p_dept): open it once per department id with a different argument. The query is parsed once, executed twice with different binds — the exact use case cursor parameters exist for. A FOR loop re-parses per iteration conceptually; the parameterized cursor is the reusable form.
  4. After OPEN, FETCH in a loop, and CLOSE: which step is most commonly forgotten, and what is the consequence?
    Answer key
    CLOSE is most commonly forgotten. Consequence: the cursor stays open, holding its resources — repeat this in a loop or long session and you hit ORA-01000: maximum open cursors exceeded. The cursor FOR loop exists largely to make this bug impossible.

Module 4 of 8

Stored Procedures and Functions

Procedures do work; functions compute values. This module covers parameter modes (IN, OUT, IN OUT), the function purity rules, autonomous transactions, and the invoker/definer rights model. You will build a small library of stored subprograms with proper contracts.

Objectives

  • Create stored procedures and functions with IN, OUT, and IN OUT parameters.
  • Call functions from both SQL statements and PL/SQL blocks, respecting side-effect rules.
  • Diagnose compilation failures with SHOW ERRORS and the USER_ERRORS view.
  • Apply parameter design basics: modes, defaults, and calling notations.

Key concepts

CREATE OR REPLACE PROCEDURE and FUNCTION

CREATE OR REPLACE compiles a named program unit into the database, replacing any previous version — the fundamental deployment verb for server-side logic. Procedures perform actions; functions compute and return a value. Both are stored, compiled, and dependency-tracked by the database. The lab builds give_raise and annual_salary against lab_emp, establishing the pattern every later module extends: write it, compile it, call it, verify it.

Parameter modes: IN, OUT, IN OUT

IN parameters carry values into the subprogram and are read-only inside it. OUT parameters carry values back to the caller and start uninitialized. IN OUT does both. The lab's get_dept_stats fills two OUT parameters with aggregates, demonstrating the multi-value return that functions cannot do. Mode choice is interface design: IN for inputs, OUT for results, IN OUT for state the caller owns and the routine transforms.

RETURN clause and RETURN statement in functions

A function's header declares RETURN <type> — the contract — and its body executes RETURN <value> on every path — the fulfillment. Every code path must return, or the compiler complains. Functions called from SQL have extra rules: no OUT parameters, no DML (with defined exceptions), because SQL expects a pure computation. The checkpoint's broken-function question — OUT parameter plus INSERT, called from SELECT — violates both rules at once.

Calling functions from SQL vs from PL/SQL

A function can be called in a SELECT list or WHERE clause and in PL/SQL assignments alike — the lab does both with annual_salary and confirms both work. SQL-callable functions must be well-behaved: deterministic-ish, side-effect free, no transaction control. PL/SQL callers tolerate more. Design the function for its strictest caller; a function safe in SQL is safe everywhere.

Positional vs named parameter notation

Positional notation passes arguments in declared order — concise but brittle. Named notation (p_emp_id => 42) labels each argument — verbose but self-documenting and immune to parameter reordering. The checkpoint asks when the verbosity pays: whenever the call is read more than written, which is always in production code. Defaulted parameters practically require named notation to skip positions.

SHOW ERRORS and USER_ERRORS for compilation diagnostics

When compilation fails, the database records exactly where: SHOW ERRORS in SQL*Plus/SQLcl prints the errors for the last compiled object, and the USER_ERRORS view holds them queryably. The lab introduces a bad column name on purpose, reads the reported line and column, fixes it, and recompiles cleanly. Compilation errors are precise — line, column, message — so read them literally instead of guessing. The database is telling you the answer.

Dependency invalidation and recompilation

The database tracks dependencies: if a table or called object changes incompatibly, dependent procedures invalidate and recompile automatically on next call. Most invalidations heal silently; breaking changes (a dropped column) surface as runtime errors after recompilation fails. The packages module explores spec-change versus body-change invalidation in depth. The concept to carry: stored code is a living dependency graph, not a pile of files.

Default parameter values

Parameters can declare defaults (p_pct IN NUMBER DEFAULT 5), letting callers omit them — usually combined with named notation. Defaults stabilize interfaces: new optional behavior does not break existing callers. They also document the common case at the declaration site. Use defaults for genuinely optional inputs, not to hide required ones.

Self-check

  1. What can an IN parameter do that an OUT parameter cannot, and vice versa?
    Answer key
    An IN parameter passes a value in (read-only inside; the caller's variable is untouched). An OUT parameter passes a value out (write-only inside; it starts as NULL regardless of what the caller passed). IN OUT does both. The asymmetry matters: you cannot read an OUT param's incoming value, and you cannot write to the caller through an IN param.
  2. A function you want to call from a SELECT statement has an OUT parameter and performs an INSERT. What two problems does that create?
    Answer key
    Two problems: (1) a function called from SQL cannot have OUT parameters — SQL expressions return values, they do not take output arguments (compile error PLS-00231); (2) a function called from a SELECT cannot perform DML (ORA-14551) — queries must not change data mid-read. The function needs redesigning: pure computation in, single value out.
  3. What is the difference between positional and named notation when calling a subprogram, and when is named notation worth the verbosity?
    Answer key
    Positional notation binds by order (p(a, b)); named notation binds by name (p(x => a, y => b)). Named is worth the verbosity when the subprogram has many parameters, defaults you want to skip, or a signature that may grow — new optional parameters slot in without breaking existing calls, and the call documents itself at the call site.

    Answer key
    Two sources: (1) USER_ERRORS (or ALL_ERRORS) — one row per compilation error with line and position; (2) SHOW ERRORS in SQL*Plus / SQL Developer after the failed CREATE. Both beat re-reading the code: the compiler already did the locating.

Packages: Specification and Body

Packages are PL/SQL's unit of modularity: a specification declaring the public interface and a body hiding the implementation. This module covers package structure, state, initialization, and the design patterns that keep large codebases maintainable. You will refactor loose procedures into a coherent package.

Objectives

  • Separate a package's public interface (specification) from its implementation (body).
  • Group related procedures and functions behind a single package API with shared private state.
  • Keep helper routines private to the package body using encapsulation.
  • Explain how spec changes versus body changes affect dependent objects.

Key concepts

Package specification: the public interface

The package specification declares what callers may use: procedure and function headers, public variables, types, and exceptions — the API contract. Nothing in the spec has a body; it is pure interface. Clients compile against the spec, which is why spec changes ripple and body changes do not. The lab's emp_admin spec declares hire_emp, terminate_emp, and give_raise: three verbs that promise behavior without revealing implementation.

Package body: implementation and private items

The body implements every spec-declared subprogram and may add private items — helpers, variables, cursors — visible only inside the package. The lab's log_action lives in the body and is called by each public routine; the privacy check proves outsiders cannot reach it. Bodies are where encapsulation happens: the spec is the promise, the body is the machinery, and the machinery is none of the caller's business.

Public vs private procedures, functions, and variables

Public items are declared in the spec and callable from anywhere with privileges; private items exist only in the body. This is the module boundary of database programming: public surface is designed, private surface is free to change. The lab demonstrates both directions — using public routines across sessions, failing to call the private helper. A package with a small public surface and rich private machinery is a well-designed package.

Package-level state and session persistence

Variables declared at package level persist for the session: the lab increments g_hire_count across three hire_emp calls and sees it accumulate, then opens a second session and sees it reset. Package state is per-session memory — useful for caching and counters, dangerous as hidden coupling between calls. It vanishes when the session ends and never crosses sessions. Treat it as convenient, private, and ephemeral.

Initialization section of a package body

A package body may end with an initialization block that runs once per session, the first time the package is referenced — for setting up state, validating configuration, or warming caches. It runs invisibly, which is both its power and its hazard: expensive or failing initialization punishes the first caller mysteriously. Keep initialization light and failure-proof; heavy setup belongs in explicit routines.

Forward declarations within a body

Inside a body, a subprogram must be declared before it is called — forward declarations (a header without a body, completed later) resolve mutual recursion and ordering constraints. They are the body's private scaffolding, invisible to spec consumers. Most bodies never need them; when two private helpers call each other, they are the clean answer.

Spec-change vs body-change invalidation behavior

Changing only the body — the lab edits a log message — leaves dependents valid: the contract did not change. Changing the spec invalidates dependents, because their compiled contract may no longer hold. This asymmetry is the economic argument for packages: stable specs let implementations evolve without recompiling the world. Design specs to be stable; relegate churn to the body.

Grouping related subprograms into a cohesive API

A package should be a cohesive API around one responsibility — employee administration, in the lab — not a junk drawer of unrelated routines. Cohesion is what makes the package learnable, testable, and safe to change. Related subprograms share private state and helpers naturally; unrelated ones share only a name. If you cannot state the package's single responsibility in a sentence, split it.

Module 6 of 8

Collections and Bulk Binds (BULK COLLECT / FORALL)

Row-by-row processing is the classic PL/SQL performance trap. This module covers collections — nested tables, varrays, associative arrays — and the bulk binds that move data between SQL and PL/SQL in batches: BULK COLLECT and FORALL. You will measure the difference and never write a slow loop again.

Objectives

  • Declare and use associative arrays, nested tables, and VARRAYs, stating the differences.
  • Fetch multi-row result sets efficiently with BULK COLLECT, bounding memory with LIMIT.
  • Apply DML across collections with FORALL instead of row-by-row loops.
  • Combine BULK COLLECT and FORALL to eliminate slow-by-slow processing.

Key concepts

Associative arrays (INDEX BY tables)

An associative array — TYPE t IS TABLE OF X INDEX BY PLS_INTEGER — is a key-value structure indexed by integer or string, existing only in PL/SQL memory. Indexes need not be dense: the lab skips an index and observes the sparse behavior directly. Associative arrays are the workhorse for in-memory lookup tables and for staging rows before bulk DML. They cannot be stored in a database column; they are purely procedural.

Nested tables

A nested table — TABLE OF X without INDEX BY — is a dense, integer-indexed collection starting at 1, and unlike associative arrays it can be stored in a database column. BULK COLLECT fetches naturally into nested tables. The lab bulk-fetches into one with a LIMIT clause, looping in batches. Choose nested tables when the collection models a multi-row result set or must persist; choose associative arrays for sparse or keyed in-memory work.

VARRAYs and their fixed maximum size

A VARRAY (variable-size array) is a dense, ordered collection with a declared maximum size — VARRAY(100) OF NUMBER can never hold 101 elements. The bound is the point: VARRAYs model fixed-cardinality things and can be stored in columns with their order preserved. Exceeding the max raises an error, which is a feature when the business rule says there are at most N. For unbounded or sparse data, prefer nested tables or associative arrays.

BULK COLLECT for multi-row fetches

BULK COLLECT fetches an entire result set into a collection in one context switch instead of row-by-row — SELECT ... BULK COLLECT INTO t_coll. The lab fetches 500 rows with LIMIT 100, printing batch counts per pass. It is the read half of eliminating slow-by-slow processing. Without a LIMIT clause on a large table it can exhaust PGA memory, which is why the checkpoint asks what goes wrong on a million-row table.

LIMIT clause to bound memory use

LIMIT caps how many rows each BULK COLLECT fetch pulls — the standard pattern is a loop fetching LIMIT 100 (or 1000) until the collection comes back empty. It bounds memory to one batch regardless of table size. The lab's batched fetch is the template to memorize. BULK COLLECT without LIMIT is a bet that the result set fits in memory; LIMIT makes it engineering instead of gambling.

FORALL for bulk DML over collections

FORALL sends DML for every element of a collection to the SQL engine in one context switch — FORALL i IN 1..t_ids.COUNT UPDATE ... WHERE id = t_ids(i). It is not a loop; it is a single bulk operation, and the lab's timing comparison against row-by-row UPDATE quantifies the difference. FORALL is the write half of bulk processing. Note the syntax quirk: the statement inside uses the collection index, and only one DML statement is allowed per FORALL.

SQL%BULK_ROWCOUNT for per-statement row counts

After a FORALL, SQL%BULK_ROWCOUNT(i) reports how many rows the i-th iteration affected — the bulk analogue of SQL%ROWCOUNT. It lets you verify per-element effects without re-querying. Combined with SAVE EXCEPTIONS it gives a complete accounting: which elements succeeded, which failed, and how many rows each touched. Bulk operations are not fire-and-forget; the rowcount array is how you audit them.

SAVE EXCEPTIONS and SQL%BULK_EXCEPTIONS

By default one failing element aborts the whole FORALL; SAVE EXCEPTIONS lets the rest continue and collects the failures in SQL%BULK_EXCEPTIONS — each entry holding the failing index and error code. The lab seeds a duplicate key, runs the bulk insert, then loops the exceptions array printing each failure. This is the production pattern: bulk for speed, exceptions array for accountability. Never let a bulk operation fail silently, and never let one bad row veto ten thousand good ones without a record.

Hands-on labs

  1. Associative array — declare TYPE t_ids IS TABLE OF NUMBER INDEX BY PLS_INTEGER; load it with employee ids from lab_emp in a loop, then iterate and print them. Note the sparse-index behavior if you skip an index.
  2. Bulk fetch — build a 500-row staging table, then BULK COLLECT into a nested table with LIMIT 100 inside a loop, printing the batch count each pass until done.
  3. Speed comparison — time a row-by-row UPDATE loop over 5,000 rows with DBMS_UTILITY.GET_TIME, then time the equivalent FORALL UPDATE over a BULK COLLECTed collection. Record both timings and the speedup factor.
  4. Graceful bulk errors — seed one bad row (e.g., a duplicate key) into a FORALL INSERT with SAVE EXCEPTIONS; after it runs, loop over SQL%BULK_EXCEPTIONS and print each failing index with its error code.

Exception Handling: Predefined, User-Defined, RAISE_APPLICATION_ERROR

Production code expects failure. This module covers the exception model: predefined and user-defined exceptions, the EXCEPTION block, RAISE and RAISE_APPLICATION_ERROR, and the logging patterns that make errors diagnosable. You will build error-handling that informs instead of obscures.

Objectives

  • Catch and handle predefined exceptions deliberately instead of letting raw errors surface.
  • Declare, raise, and handle user-defined exceptions for business rules.
  • Raise application errors with RAISE_APPLICATION_ERROR inside the legal error-number range.
  • Write WHEN OTHERS handlers that log diagnostics and re-raise rather than swallowing errors.

Key concepts

Exception section structure and handler order

The EXCEPTION section is a list of WHEN handlers evaluated in order: WHEN NO_DATA_FOUND THEN ... WHEN OTHERS THEN .... The first matching handler runs, then control leaves the block — there is no fall-through and no resume. Order matters because WHEN OTHERS matches everything; the checkpoint's DUP_VAL_ON_INDEX-before-OTHERS question tests exactly this. Put specific handlers first, OTHERS last, and never assume an unlisted exception is handled.

Predefined exceptions: NO_DATA_FOUND, TOO_MANY_ROWS, DUP_VAL_ON_INDEX, ZERO_DIVIDE

The language pre-names the common failures: NO_DATA_FOUND (SELECT ... INTO found nothing), TOO_MANY_ROWS (it found several), DUP_VAL_ON_INDEX (unique constraint violated), ZERO_DIVIDE. The lab catches NO_DATA_FOUND on a missing employee and prints a friendly message instead of surfacing a raw stack. Predefined exceptions turn predictable failures into designed behavior. Handle the ones your code can genuinely produce; do not blanket-catch the ones it cannot.

User-defined exceptions: declaration, RAISE, handling

Business rules get their own exceptions: DECLARE e_raise_too_big EXCEPTION, RAISE it when p_pct exceeds the policy limit, and handle it in the caller with a clear message. The lab wires exactly this through a raise procedure. User-defined exceptions name the business failure instead of abusing a predefined one — e_raise_too_big says more than a generic error ever could. Declare near the code that raises, handle where the decision belongs.

RAISE_APPLICATION_ERROR and the -20000..-20999 range

RAISE_APPLICATION_ERROR(-20001, 'message') raises an error that propagates to clients like a database error, with your message attached. The legal range is -20000 to -20999 — the checkpoint's -19999 question has exactly one answer: out of range, it fails. The lab uses -20001 for a terminate-with-active-projects rule and the caller reads SQLCODE and SQLERRM. Reserve this for errors that must cross the PL/SQL-to-client boundary with meaning intact.

SQLCODE and SQLERRM for diagnostics

Inside a handler, SQLCODE returns the error number and SQLERRM the message — the diagnostics of the caught exception. The lab prints both when catching the application error, and the honest-OTHERS pattern logs both to an error table. They are only meaningful inside the handler for the current exception; capture them immediately. Diagnostics you do not record are diagnostics you never had.

EXCEPTION_INIT pragma for naming Oracle error numbers

PRAGMA EXCEPTION_INIT(e_dup_emp, -20001) binds a name to an Oracle error number, so you can handle ORA-00001 as e_dup_emp instead of parsing messages. The lab names the duplicate-key error and handles the named exception specifically. Named errors read as intent; magic numbers read as archaeology. Use EXCEPTION_INIT for the handful of Oracle errors your code deliberately anticipates.

Exception propagation across call stacks

An exception with no handler in its block propagates to the enclosing block, then to its caller, unwinding the call stack until something handles it or it reaches the client. The lab's honest-OTHERS procedure demonstrates the disciplined endpoint: log the diagnostics, then re-raise with bare RAISE so the original error continues upward. Propagation is the default error channel — design for it rather than catching everything locally. Handle where you can act; let the rest travel.

WHEN OTHERS: log and re-raise, never swallow

WHEN OTHERS catches everything, which makes it the most dangerous handler in the language: catch, print, and continue silently, and you have built a bug-hiding machine. The lab's error_log pattern is the only honest shape — insert SQLCODE, SQLERRM, and a timestamp, then re-raise. The checkpoint asks for two concrete harms of swallowing: corrupted data nobody notices, and incidents that cannot be diagnosed. Log and re-raise, or do not catch at all.

Performance Basics: Avoiding Row-by-Row, Bind Variables

Fast PL/SQL is a discipline, not an accident. This module covers the performance toolkit: bulk binds, the NOCOPY hint, deterministic and result-cached functions, native compilation, and the DBMS_PROFILER workflow for finding hot spots. You will profile real code and document each optimization with timings.

Objectives

  • Identify row-by-row (slow-by-slow) patterns and the context switches that make them expensive.
  • Rewrite row-by-row logic as set-based SQL first and bulk binds second.
  • Explain why bind variables reduce hard parsing in the shared pool.
  • Measure performance claims with timings instead of asserting them.

Key concepts

SQL/PL/SQL context switches and slow-by-slow processing

Every hop between the PL/SQL engine and the SQL engine — each row fetched, each single-row DML — is a context switch with real cost. Row-by-row (slow-by-slow) processing multiplies that cost by the row count: the lab's 10,000-row loop versus a single INSERT ... SELECT makes the ratio tangible. The switches are the tax; the loop is what multiplies it. Recognize the pattern on sight: a loop whose body is one SQL statement.

Set-based SQL as the first and cheapest rewrite

Before reaching for bulk binds, ask whether the loop is SQL in disguise: one UPDATE, one INSERT ... SELECT, one MERGE usually replaces the entire cursor. The lab rewrites the cursor-loop UPDATE as a single statement and times both — the set-based version wins on speed and on readability. Set-based is the first rewrite because it removes the loop instead of accelerating it. If the logic fits in SQL, it belongs in SQL.

Bulk binds (BULK COLLECT/FORALL) as the second line of defense

When procedural logic genuinely cannot be expressed as set SQL, bulk binds are the fallback: BULK COLLECT the rows, process the collection, FORALL the writes. The collections module built the mechanics; this module places them in the strategy — second choice, not first. Two context switches for ten thousand rows beats ten thousand switches. Reserve row-by-row for the residue that survives both rewrites.

Bind variables vs literals in the shared pool

A SQL statement with literals is a new statement to the shared pool every time the values change — each requiring a hard parse. The same statement with bind variables parses once and reuses the plan: soft parses thereafter. The lab runs 1,000 iterations both ways and times the gap. Bind variables are also the primary defense against SQL injection in dynamic SQL. Literals in repeated SQL are a performance bug and a security smell at once.

Hard parse vs soft parse

A hard parse builds an execution plan from scratch: syntax, semantics, optimization — expensive. A soft parse finds the existing plan in the shared pool by matching the statement text — cheap. Bind variables maximize soft parses; literals maximize hard parses. The shared pool is a cache, and like every cache it only hits on identical keys. Write SQL that repeats and you get plan reuse for free; write SQL that varies and you pay full price every execution.

Measuring with DBMS_UTILITY.GET_TIME

Performance claims without timings are opinions. DBMS_UTILITY.GET_TIME brackets code with hundred-of-a-second timestamps — the lab wraps every comparison in it and records the ratio. Measure the same workload before and after, on comparable data, more than once. The checkpoint's 3%-on-100-rows question is the skepticism to internalize: tiny wins on tiny data are noise. Time it, or do not claim it.

Row-by-row as the option of last resort

After set-based rewrites and bulk binds, a small residue of genuinely row-dependent logic remains — complex per-row branching with side effects that resist both. That residue earns its loop honestly. The discipline is ordering: SQL first, bulk second, loop last — and documenting why the loop survived. Row-by-row is not forbidden; it is the option you choose after proving the better ones do not fit.

Documenting before/after timings for every optimization claim

Every optimization ends with a memo: what changed, the before timing, the after timing, and why the new version is faster. The lab's optimization memo is five lines — short enough to actually write, complete enough to actually trust. Undocumented speedups regress silently when someone rewrites the code. The memo is the difference between tuning and folklore.

  2. Loop-to-SQL rewrite — take the cursor-loop UPDATE from the cursors module and rewrite it as one UPDATE statement; time both and note which is simpler to read as well as faster.

About this guide

This page is an original study guide by Interstitium Labs, keyed to the public Oracle Database PL/SQL documentation. It is not affiliated with or endorsed by Oracle, and it does not reproduce Oracle's course content — the official documentation lives at the sources linked throughout. Explanations here are our own distillation, written for study.

Every lab in this sequence runs on free tooling — public testnets, free database editions, and open-source software. Where a module touches security tooling, labs target only systems and data you own.

Scenario exam — prove the sequence.

Fourteen original scenario questions — the failure modes PL/SQL developers actually hit: shadowed variables, leaked cursors, impure functions, swallowed exceptions, and context-switch storms. Misses remediate into Adapt and Noah. Honest boundary: PL/SQL runs on Oracle Database — the widgets below test your reasoning about PL/SQL semantics; only an Oracle instance can execute it. These scenarios are written for this sequence; they are not real exam questions from any certification.
