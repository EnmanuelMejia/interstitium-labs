SCIENTIA OMNIA VINCIT

Overview

What this sequence is.

This sequence teaches Linux system administration as a craft: the command-line fluency to move fast, the storage and permission models to stay safe, the packaging and service management to keep software running, the networking to connect it all, and the troubleshooting method to fix it when it breaks. It is organized around the public Linux Foundation Certified System Administrator (LFCS) curriculum, but it teaches the engineering underneath — the mental models that transfer across distributions and survive every tooling fashion.

The administrator's job is stewardship of running systems: keep them up, keep them secure, know what changed, and recover when they fall over. Every module here builds one facet of that stewardship, and the labs are deliberately destructive — you will break filesystems, permissions, services, and networks in a VM, because the only way to learn recovery is to need it.

Who this is for

  • Aspiring system administrators, SREs, and DevOps engineers who will own Linux machines.
  • Developers who are tired of treating servers as mysterious black boxes.
  • Career changers who can already use a computer confidently and want the professional-grade skill set.

Prerequisites

  • Basic computer literacy; no prior Linux experience assumed.
  • A lab VM (or spare machine) running any mainstream Linux distribution, with root or sudo access — you will break things in it on purpose.
  • Willingness to read manual pages: man is the textbook, this sequence is the study guide.

How to use this sequence

  • Work the modules in order; each builds vocabulary the next one assumes.
  • Do every lab, and snapshot your VM before the destructive ones so you can break fearlessly and compare before/after.
  • When a command surprises you, read its man page immediately — the habit matters more than any single fact.
  • Keep a lab journal of every failure and fix; it becomes your personal runbook and your interview stories.

Module 1

CLI Fluency and Text Processing

FHS directory layout (/, /etc, /var, /usr, /opt, /srv)

The Filesystem Hierarchy Standard gives every Linux system the same map: /etc holds configuration, /var holds variable data like logs and spools, /usr holds the bulk of user programs and libraries, /opt holds self-contained third-party software, /srv holds data served by the system, and / is the root everything hangs from. Knowing the map means knowing where to look — logs live under /var/log on every distribution, service configs under /etc — which is half of all troubleshooting. When you're lost on an unfamiliar machine, the FHS is your compass: the layout is a contract the whole ecosystem honors.

Globbing vs regex: *, ?, [], brace expansion

Globbing and regex are different languages that look similar, and confusing them is a rite of passage. Globbing (*, ?, [...], brace expansion) is performed by the shell before the command runs — ls *.log hands the command a list of matching filenames. Regex is interpreted by the command itself (grep, sed) to match patterns inside text. Brace expansion (file{1,2,3}) generates strings without needing anything to exist. The checkpoint's 300k-file directory fails with ls * because the shell expands the glob into an argument list too long for execve, while find works because it traverses the directory itself without building that list — same goal, fundamentally different mechanism.

Redirection operators (>, >>, <, <<, 2>, &>) and pipe semantics

Redirection operators rewire a command's file descriptors: > truncates and writes stdout to a file, >> appends, < feeds a file to stdin, << feeds a here-document, 2> captures stderr separately, and &> merges both streams. Pipes (|) chain commands by wiring one's stdout to the next's stdin, building pipelines where each stage transforms a text stream. The composition is the power: grep the errors, cut the fields, sort, uniq -c, sort -rn — a one-liner that would take a script in another environment. Mastering redirection means never losing output you needed and never mixing streams you wanted separate.

Exit status propagation and PIPESTATUS

Every command exits with a status: 0 means success, anything else means failure, with 1 as generic error, 126 as "found but not executable," and 127 as "command not found." In a pipeline, the exit status you get is the last command's — which is why false | true exits 0 and hides the left side's failure. PIPESTATUS (an array holding every stage's status) and pipefail (make the pipeline fail if any stage fails) are the two answers, and robust scripts use pipefail always. The discipline: check exit codes where they matter, and never assume a pipeline succeeded because its tail did.

grep -E/P, sed -n s///, awk field processing with FS/OFS

The text-processing core is five tools deep: grep finds lines (with -E for extended regex, -P for Perl-compatible where available), sed edits streams (sed -n with s/// for surgical substitution), awk processes fields (FS splits input, OFS joins output, $1..$NF address columns), and cut/sort/uniq/xargs handle the mechanical shaping around them. awk's field model is the workhorse — the checkpoint's one-liner sums column five with awk -F, '{s+=$5} END {print s}'. The learning curve is real but the payoff is permanent: log analysis, report generation, and data munging become shell one-liners instead of afternoon projects.

Learning objectives

  • Navigate and manipulate the filesystem efficiently from a bare shell
  • Compose pipelines using globbing, redirection, pipes, and filters
  • Extract and transform text with grep, sed, awk, cut, sort, uniq, and xargs

Hands-on labs

  1. Lab: Reconstruct a destroyed directory tree from a find/printf inventory using only coreutils

    1. In a scratch directory, save a find . -printf inventory (paths, types, sizes) of a sample tree, then delete the tree.
    2. Reconstruct the directory structure from the inventory using only mkdir, touch, and shell loops driven by the saved listing.
    3. Verify with diff against a fresh find of the rebuilt tree — the exercise teaches that find's output is a complete structural description.

  2. Lab: Write a one-liner pipeline that parses auth logs for top 10 offending IPs and emits a report

    1. Take a sample auth log (or generate one) and build a pipeline: grep failed logins, extract IPs, sort, uniq -c, sort -rn, head.
    2. Format the top 10 into a small report with a header line and timestamps, written to a dated file.
    3. Parameterize the log path and the count as variables — your first reusable log-analysis one-liner.

  3. Lab: Rename 200 files with parameter expansion plus a sed-based bulk rename, verifying before/after with diff

    1. Create 200 files with a consistent-but-wrong naming pattern, then rename them all with a for loop using parameter expansion (${f/old/new}).
    2. Do a second bulk rename with sed driving the transformation, previewing with echo before executing.
    3. Verify before/after with diff of directory listings — the preview-then-execute discipline that prevents rename disasters.

  4. Lab: Use tar, gzip, and rsync to build a timestamped incremental backup rotation in ~/backups

    1. Build ~/backups and write a script using tar and gzip that creates timestamped archives of a data directory.
    2. Add rsync for incremental behavior (only changed files transferred) and keep a rotation (daily.0..daily.6 style).
    3. Restore one file from an archive to prove the backups are real — an untested backup is a rumor.

Self-check questions

Explain why `ls *` in a 300k-file directory fails but `find . -name '*.log'` works
Answer: The shell expands * before ls runs — 300k arguments exceed the kernel's ARG_MAX. find receives the quoted pattern and matches internally, never building a giant argument list. Quote globs you want the tool (not the shell) to expand.
Produce an awk one-liner that sums the 5th column of a CSV and prints the total
Answer: awk -F, '{s+=$5} END {print s}' — -F, sets the field separator, $5 is the fifth field, END runs once after all input. (Real CSVs with quoted commas need a real parser — awk is for simple, predictable formats.)
Predict the exit code of `false | true` and how to capture the left side's failure
Answer: Exit code 0 — a pipeline's status is the LAST command's. Capture the left side with set -o pipefail (pipeline fails if any stage fails) or read ${PIPESTATUS[0]} immediately after.

Module 2

Filesystems, Partitions, and Storage Basics

Partitioning with parted/gdisk; GPT vs MBR tradeoffs

Partitioning divides a disk into isolated regions, each holding a filesystem; parted and gdisk are the modern tools, and GPT is the modern table format — larger disks, more partitions, and checksums, versus MBR's 2 TB limit and four-primary-partition ceiling. The tradeoff is compatibility: GPT needs UEFI-era firmware or BIOS boot partitions to boot on old systems, while MBR boots anywhere but can't address modern disk sizes. For new systems the answer is GPT unless you have a specific legacy constraint. Partition before you format, label what you create, and never partition a disk with mounted filesystems you care about.

ext4 vs XFS: journaling, online growth, inode allocation

ext4 and XFS are both journaling filesystems, but they make different bets: ext4 is the general-purpose default with mature tooling and easy shrinking, XFS excels at large files and parallel I/O with online growth but can't be shrunk. Journaling means metadata changes are written to a journal first, so a crash replays the journal instead of requiring a full filesystem check — the reason modern systems usually boot cleanly after power loss. Inode allocation differs too: ext4's fixed inode tables can run out of inodes while blocks remain (the checkpoint's mkfs.ext4 -i tuning), while XFS allocates inodes dynamically. Choose ext4 for flexibility, XFS for large-scale throughput, and know both exist because you'll inherit both.

mount options (noatime, ro, nodev, nosuid, discard) and fstab fields

Mount options tune a filesystem's behavior at attach time: noatime skips access-time updates (a classic performance win), ro mounts read-only, nodev/nosuid block device nodes and setuid execution (hardening for untrusted mounts), and discard enables TRIM for SSDs. /etc/fstab makes mounts persistent across boots, with six fields — device, mountpoint, type, options, dump, pass — where the pass field controls fsck order at boot. The checkpoint's missing-device field is the options column: nofail lets boot continue without the device, while the default blocks boot waiting for it — the difference between a server that boots degraded and one that drops to emergency shell over a dead USB disk.

df vs du semantics; inode exhaustion vs block exhaustion

df reports filesystem-level free space (blocks and inodes); du sums the space used by walking directories — and they disagree for honest reasons. The classic: df shows 40% free but writes fail because the inode table is exhausted (millions of tiny files consume inodes, not blocks), or because a deleted-but-still-open file holds space df counts as used while du can't see it. The diagnostic pair is df -i (inode usage) alongside df -h (block usage): when blocks are free but inodes are 100% used, you have an inode problem, and the fix is deleting the small files, not adding disk. Knowing which exhaustion you're facing determines whether the fix is "more disk" or "fewer files."

fsck/xfs_repair workflow and when never to run them mounted

fsck (ext4) and xfs_repair (XFS) walk filesystem structures and fix inconsistencies, but they must run on unmounted filesystems — repairing a live filesystem is like performing surgery on a running patient, and the tools will warn you for good reason. The workflow is: unmount (or boot from rescue media), run the check, answer its prompts (or -y in non-interactive recovery), then remount and verify. Corrupt journals are the common trigger after unclean shutdowns; the journal replay usually handles it, and fsck is for when replay isn't enough. The lab's safe simulation teaches the sequence without risking real data — learn it in a VM, because the first time you need it, it will be 3 AM.

Learning objectives

  • Partition a disk and create filesystems with the appropriate type for the workload
  • Mount filesystems with correct options and make mounts persistent via fstab
  • Inspect and reason about disk usage, inodes, and filesystem health

Hands-on labs

  1. Lab: On a loop device or cloud VM, partition a disk, format ext4 and XFS, mount with options, and persist via fstab

    1. Attach a loop device (or use a spare cloud volume), partition it with gdisk, and create one ext4 and one XFS partition.
    2. Format each, mount with deliberate options (noatime on both, nodev/nosuid on one), and add both to /etc/fstab with nofail.
    3. Reboot and confirm both mount automatically — fstab persistence proven, not assumed.

  2. Lab: Fill a filesystem with small files until inode exhaustion, diagnose it, then fix it

    1. On a small test filesystem, write hundreds of thousands of tiny files until writes fail, then run df -h and df -i side by side.
    2. Diagnose: blocks free, inodes exhausted — the checkpoint scenario, reproduced on demand.
    3. Delete the files, confirm both counters recover, and note the mkfs option (-i) you'd tune if this were a mail spool by design.

  3. Lab: Simulate a corrupt journal scenario safely and walk the fsck recovery sequence

    1. In a VM snapshot, simulate journal trouble (unclean shutdown of a loop-mounted ext4), then boot to recovery and run fsck.
    2. Walk the prompts, let it repair, remount, and verify the data.
    3. Write down the exact command sequence — this is your personal fsck runbook for the real incident.

  4. Lab: Move a directory tree across filesystems preserving ownership, xattrs, and hardlinks with rsync -aHAX

    1. Create a directory tree with varied ownership, permissions, xattrs, and hard links, then move it across filesystems with rsync -aHAX.
    2. Verify on the destination: owners, modes, xattrs, and hard-link relationships all preserved (compare link counts).
    3. Repeat with plain cp -r and document what was lost — the comparison is the lesson in why flags matter.

Self-check questions

Which fstab field controls boot behavior if the device is missing, and why does it matter?
Answer: The 4th field (options): nofail lets boot continue if the device is absent. Without it, a missing non-critical disk drops you to emergency shell — a boot outage caused by a data disk. (The 6th field, pass, controls fsck order.)
Explain a scenario where df shows 40% free yet writes fail
Answer: Inode exhaustion (millions of tiny files — df -i shows it), or deleted-but-still-open files holding space (df counts them as used until the process closes them), or a quota. "Disk full" has three causes: bytes, inodes, quotas.
Compare mkfs.ext4 -i vs default inode ratio and when you would tune it
Answer: -i bytes-per-inode sets inode density; the default (~16KB per inode) suits general use. Tune smaller (more inodes) for mail spools / millions of tiny files; larger for large-file stores (media archives) to avoid wasting inode table space.

Module 3

Permissions, Ownership, and Access Control

rwx meaning differs on files vs directories (x = traversal)

The rwx bits mean different things on files versus directories, and the directory meaning is the one that bites: on a file, r reads, w writes, x executes; on a directory, r lists entries, w creates/deletes entries, and x traverses — you need x on every directory in a path to reach anything inside it. A file can be perfectly readable and still inaccessible if one parent directory lacks the x bit, which is why "permission denied" on a readable file sends you walking up the path checking each directory. The checkpoint's nested-cat trace is this walk made explicit: check x on /, on each component, then r on the file itself.

umask 022 vs 027: subtractive semantics on file 666/dir 777 bases

The umask is subtractive: new files start from 666 and new directories from 777, and the umask clears the bits it names. umask 022 yields files 644 and directories 755 (group and others lose write); umask 027 yields files 640 and directories 750 (group loses write, others lose everything). The checkpoint's arithmetic: directory base 777 minus mask 027 — write removed for group, all removed for other — gives 750. Set umask in shell profiles and service environments deliberately; the default 022 is permissive for multi-user systems, and 027 or 077 is the hardening choice.

setuid/setgid/sticky: where they live and what each enables

The special bits extend the model: setuid (4) on an executable runs it with the file owner's privileges (passwd updating /etc/shadow is the canonical example), setgid (2) on an executable runs with the file group's privileges and on a directory forces new files to inherit the directory's group, and the sticky bit (1) on a directory (like /tmp) lets users delete only their own files. The lab's mode-4755 demonstration teaches the crucial nuance: setuid elevates to the owner's privileges, not to root in general — a setuid binary owned by a service account gains that account's power, which is precisely why auditing setuid binaries system-wide is a security staple.

ACLs: getfacl/setfacl, mask entries, default ACL inheritance on directories

POSIX ACLs add per-user and per-group entries beyond owner/group/other: getfacl reads them, setfacl writes them, and default ACLs on directories propagate to new children. The subtlety is the mask entry: it caps the effective permissions of all named users/groups (and the owning group), so setfacl -m u:carol:rw can grant less than rw if the mask is r — the checkpoint's gotcha, fixed by recalculating the mask or setting it explicitly. Use ACLs for the cases chmod can't express (two specific users needing different access to one directory), and prefer the setgid-plus-group model when a plain group suffices — simpler is auditable.

Hard links (inode sharing) vs symlinks (path indirection); link count behavior on delete

Hard links are multiple directory entries pointing at one inode: same data, same inode number, and the file survives until the last link is deleted (the link count in ls -l tells you how many names exist). Symbolic links are separate files containing a path: they can cross filesystems and point at directories, but they break when the target moves. The checkpoint's cross-mount hard link fails because inodes are per-filesystem — a hard link can't reference an inode on another filesystem, full stop. Deleting the last hard link frees the data; deleting a symlink never touches the target — two deletion semantics you must never confuse.

Learning objectives

  • Apply chmod/chown/chgrp with symbolic and octal modes confidently
  • Predict a process's effective access from owner/group/other, umask, and setuid/setgid/sticky bits
  • Manage fine-grained access with ACLs and reason about hard vs symbolic links

Hands-on labs

  1. Lab: Build a shared project directory with setgid so new files inherit the group, plus a default ACL for two users

    1. Create a shared project directory, set it setgid and group-owned by a project group, and add a default ACL granting two users rwx.
    2. As each user, create files and confirm the group inheritance and ACL behavior on the new files.
    3. Document the resulting permission matrix — this is the standard pattern for team-shared directories.

  2. Lab: Create a file with mode 4755 and demonstrate what setuid actually does vs what people think it does

    1. Create a script owned by a test user with mode 4755 that writes the effective UID to a file, and run it as another user.
    2. Confirm the file shows the owner's UID, not the runner's — setuid elevation demonstrated, and specifically not root elevation.
    3. Find all setuid binaries on your system and decide which ones you'd justify keeping in a hardening review.

  3. Lab: Lock down an SSH authorized_keys setup: diagnose and fix permission failures step by step

    1. Deliberately break an SSH setup: wrong permissions on ~/.ssh (not 700), authorized_keys (not 600), and the home directory (group-writable).
    2. Attempt login, read the server's refusal in the auth log, and fix each layer in order, testing after each fix.
    3. SSH's strict permission checks are the best teacher of the permission model because it refuses to be lenient.

  4. Lab: Trace every permission decision for one failing `cat` on a deeply nested path and document the denial point

    1. Create a deeply nested path, remove the x bit from one middle directory, and attempt cat on a file below it as an unprivileged user.
    2. Trace the denial: check each path component's x bit in turn until you find the missing one — document the exact denial point.
    3. Restore the bit and confirm access returns; the walk-up-the-path method is now a reflex.

Self-check questions

What mode results from umask 027 on a new directory, and show the arithmetic
Answer: 750. Directories start at 777; umask 027 masks 027: 777 − 027 = 750 (rwxr-x---). (Files: 666 − 027 = 640. umask removes permission bits; it never adds them.)
Why does setfacl -m u:carol:rw file sometimes grant less than expected?
Answer: The ACL mask: the group-class mask caps all named-user and group entries. If the mask is r--, carol's rw is reduced to r--. Check getfacl output — the mask:: line is the effective ceiling.
Predict what happens when you hard-link a file across two mounts
Answer: It fails — hard links cannot cross filesystem boundaries (inodes are per-filesystem). Use a symlink instead, or copy. (Same-filesystem hard links share the inode; deleting one name does not delete the data.)

Module 4

Package Management and Repositories

dpkg vs apt vs aptitude layering; rpm vs dnf layering

Package management is layered: dpkg/rpm are the low-level tools that install and track individual package files, while apt/dnf are the high-level managers that resolve dependencies, fetch from repositories, and orchestrate upgrades. You can query the low level directly (dpkg -l, rpm -qa) when the high level is confused, and understanding the layering tells you which tool's database is actually broken. aptitude is an alternate high-level frontend on Debian-family systems with its own resolver — useful, but the apt/dpkg pair is the canonical core. When packaging breaks, knowing which layer you're debugging saves hours.

Repository metadata, GPG signing, and sources.list / .repo formats

Repositories are signed package feeds: the client downloads metadata (package lists, checksums), verifies the metadata signature against trusted GPG keys, then downloads packages whose checksums match the metadata. The trust chain is metadata → signature → key → keyring, and every link matters — which is why piping curl to apt-key add was dangerous: it added keys to the global trusted keyring with no scoping. The modern replacement is per-repository keyrings: the key lives in a keyring directory and the source entry names it with signed-by, so a key can only vouch for its own repository. A repository whose key you can't verify is a repository you don't add.

apt pinning (preferences) and dnf module streams / excludes

Version control for packages has three related mechanisms: holds/pins keep a package at its version (apt hold, apt preferences pinning), module streams (dnf) select among parallel versions of a software stack, and excludes simply hide packages from consideration. Pinning answers "stay exactly here" (critical for a database major version during an OS upgrade window); streams answer "track this branch" (Node.js 20 vs 22 as maintained streams); excludes answer "never consider this." The checkpoint's use cases: hold the database during the distro upgrade, pin the stream for the app's runtime, exclude the conflicting driver. Each is the right tool for a different stability promise.

Version locking, holds, and downgrade semantics

Holds, pins, and downgrades interact with dependency resolution in ways that bite: a held package can block an upgrade that needs its newer version, and downgrading requires the older package to still be available and its reverse dependencies to tolerate it. apt policy and dnf info/list show you the candidate versions and where each comes from — read them before forcing anything. The lab's pin-then-verify loop builds the habit: set the constraint, then confirm the resolver actually honors it, because a pin in the wrong file or with the wrong syntax is silently ignored. Version intent that isn't verified is version hope.

Recovery from dpkg interruptions and rpm database corruption

Package databases corrupt in recognizable ways: dpkg interrupted mid-install leaves packages half-configured (fixed by dpkg --configure -a, which completes the pending configuration), and rpm database corruption manifests as queries failing or hanging (rebuilt from the package headers). The recovery principle is the same on both families: finish what was interrupted before starting anything new, and never delete the database files as a "fix" — rebuild them with the proper tool. The lab's simulated breakage teaches the sequence in safety: interrupt, diagnose the state, run the recovery command, verify clean. Interrupted package operations are routine in automation; recovery should be too.

Learning objectives

  • Install, query, and remove software on both apt and dnf families
  • Configure repositories, keys, and pinning/preferences safely
  • Troubleshoot broken dependency states and locked package databases

Hands-on labs

  1. Lab: Add a third-party repo with its GPG key the correct modern way (keyring dir, signed-by), then install from it

    1. Pick a reputable third-party repository, fetch its GPG key into /etc/apt/keyrings (or the rpm equivalent), and add a source entry using signed-by pointing at that keyring.
    2. Update metadata, verify the key is scoped (it can't sign for other repos), and install one package from it.
    3. Document each step — this is the only correct way to add external repos, and you'll do it many times.

  2. Lab: Pin a package to a specific version on apt and to a stream on dnf; verify with policy/info

    1. On an apt system, pin a package to its current version with apt-mark hold or a preferences file; on dnf, pin a package to a module stream.
    2. Run apt policy / dnf info and confirm the resolver shows the pin honored and no upgrade candidate selected.
    3. Remove the pin and confirm the candidate reappears — the full pin lifecycle, verified at each step.

  3. Lab: Simulate a broken dpkg state and recover with dpkg --configure -a; simulate an rpm db issue

    1. In a VM, simulate a dpkg interruption (kill an install mid-way or craft the state) and recover with dpkg --configure -a; confirm the package reaches a clean installed state.
    2. Simulate rpm database trouble per your distro's docs and rebuild it; verify queries work again.
    3. Write both recovery sequences into your runbook — package DB recovery is pure procedure, and procedure should be written down.

  4. Lab: Build a local offline repo mirror (apt-ftw/create-repo) and install from it on a second VM

    1. Build a small local repository mirror (apt-ftw/deb mirror tooling, or createrepo for rpm) containing a handful of packages.
    2. Point a second VM's sources at your mirror and install from it — you are now the repository operator.
    3. Note what the mirror gives you: offline installs, version freezing, and auditability of exactly what's available.

Self-check questions

Why is piping curl to apt-key add (deprecated) dangerous, and what replaces it?
Answer: It trusts a key globally for ALL repositories (any repo can then sign any package) and fetches over whatever transport curl used. Replacement: download the key to /usr/share/keyrings/ or /etc/apt/trusted.gpg.d/ and reference it per-repo with signed-by= in the sources entry.
Distinguish hold, pin, and exclude; give one use case each
Answer: Hold (apt-mark hold): freeze a package at its version — e.g. keep a working kernel. Pin (preferences/pin): prefer versions from a specific repo — e.g. take nginx only from backports. Exclude (dnf): skip packages from transactions — e.g. exclude kernel updates on a tuned host.
Explain what `dnf provides /usr/bin/foo` queries versus `dnf list installed`
Answer: provides queries repository metadata: which package (installed or not) ships that file. list installed shows only what is on the system. Use provides to find the package that WOULD give you a missing binary.

Module 5

systemd: Units, Services, Timers, and the Journal

Unit types and dependency directives: Wants/Requires, Before/After, PartOf

systemd manages units — services, sockets, timers, targets, and more — with dependency directives declaring ordering and requirement: After/Before set ordering, Wants pulls in a unit weakly (failure tolerated), Requires pulls it in strongly (failure propagates), and PartOf ties lifecycles together. The distinction between Wants and Requires is operational: Wants says "start this too if you can," Requires says "I cannot run without this." Reading a unit's dependency directives tells you what the service assumes about the world — and wrong assumptions here are why services fail at boot but start fine by hand.

Type=simple vs forking vs notify; ExecStart/ExecReload/ExecStop semantics

Type= tells systemd how to know the service started: simple (the ExecStart process is the service — don't fork), forking (the process daemonizes and the parent exits), and notify (the service signals readiness explicitly). The checkpoint's trap: Type=simple with a program that daemonizes makes systemd track the exiting parent, conclude the service died, and fight the actual daemon with restarts. ExecStart/ExecReload/ExecStop define the lifecycle commands, and they must match the Type — a forking service needs the parent-exit semantics, a simple service needs a foreground process. Match the Type to what the program actually does, not what you wish it did.

Environment, WorkingDirectory, User/Group, sandboxing directives (ProtectSystem, PrivateTmp)

Unit files carry the service's whole execution environment: Environment/EnvironmentFile for variables, WorkingDirectory, User=/Group= to drop privileges, and the sandboxing directives that make systemd a security tool — ProtectSystem (read-only /usr and /boot), PrivateTmp (isolated /tmp), and their siblings. The lab's hardening loop (add directives, re-run systemd-analyze security, watch the exposure score drop) teaches defense in depth at the service layer: even if the application is compromised, the unit confines what it can touch. A service running as root with no sandboxing is a choice; make it a deliberate one or, better, don't.

timer OnCalendar/OnBootSec/OnUnitActiveSec; Persistent=true semantics

Timers are systemd's cron replacement with two trigger families: OnCalendar for wall-clock schedules (with expressive calendar syntax) and monotonic triggers like OnBootSec and OnUnitActiveSec for "X after boot" or "X after last run." Persistent=true is the killer feature over cron: if the machine was off when a timer would have fired, it runs at the next opportunity instead of silently skipping — the checkpoint's 2 AM cron becomes an OnCalendar daily timer that catches up after downtime. The semantic difference to note: cron assumes the machine is always on; timers with Persistent=true assume it isn't. For laptops and VMs that sleep, timers are simply correct where cron is lossy.

journalctl filtering by unit, boot, priority; persistent vs volatile storage

The journal is systemd's centralized logging: journalctl filters by unit (-u), by boot (-b), and by priority (-p), turning "what happened" into a query instead of a grep expedition. Storage can be persistent (/var/log/journal) or volatile (/run/log/journal, lost on reboot) — check which yours is before assuming yesterday's logs exist. The diagnostic habit is journalctl -u <service> --since "10 minutes ago" for service failures and journalctl -b -p err for boot problems. Centralized, indexed, queryable logs are why "check the journal first" has replaced "find the log file" in the systemd world.

  • Control service lifecycle and diagnose failures from unit state and logs
  • Use timers as cron replacements with calendar and monotonic triggers

Self-check questions

Why does Type=simple with a daemonizing program break Restart= handling?
Answer: Type=simple expects the main process to stay in the foreground; a daemonizing program forks and exits, so systemd thinks the service died and restarts it — fork-bombing itself. Match Type= to behavior: forking programs need Type=forking (or better, run them in foreground with Type=simple).
Translate `0 2 * * *` cron into an OnCalendar expression and note one semantic difference
Answer: OnCalendar=*-*-* 02:00:00. Semantic difference: systemd timers are timezone-aware per unit, support monotonic triggers, randomized delays, and Persistent=true (catch up missed runs) — cron just fires on wall-clock matches and silently skips missed runs.
Explain the difference between `systemctl reload` and `restart` for a running nginx-style service
Answer: reload rereads configuration without dropping connections (the master re-execs workers gracefully); restart stops and starts the process (brief outage, new PID). Reload when the service supports it; restart when the binary itself changed.

Module 6

Networking: ip, Routing, DNS, Firewall, SSH

ip addr/route/link; ss vs netstat; nmcli/networkd vs static config

The iproute2 toolkit replaced the old net-tools: ip addr shows addresses, ip route shows the routing table, ip link shows interface state, and ss shows sockets (faster and more detailed than netstat ever was). Address configuration itself may live in nmcli/NetworkManager profiles or systemd-networkd files depending on the distro — know which manager owns your interfaces before hand-editing anything. The lab's second-interface exercise builds the core skill: add an address, add a route, and prove with ping -I which source address is used. If you can't configure an interface by hand, you can't debug one either.

CIDR, longest-prefix match, default route, source address selection

Routing is longest-prefix-match: the most specific route covering the destination wins, with the default route (0.0.0.0/0) as the catch-all. CIDR notation defines the prefix length, and source address selection picks the outgoing address based on the interface the route uses — which ping -I overrides explicitly. The checkpoint's "pings the gateway but nothing beyond" has three classic causes: no default route (check ip route), the gateway not forwarding/NATing (test from the gateway itself), or a firewall dropping forwarded traffic (check counters). "Layer by layer" isn't a slogan — it's the order: link, local, gateway, beyond, each proven before moving on.

DNS resolution path: /etc/resolv.conf, nsswitch, systemd-resolved stubs

Name resolution follows a path, not a single file: /etc/resolv.conf names the servers (often a stub pointing at systemd-resolved), /etc/nsswitch.conf decides the lookup order (files before DNS, traditionally), and the stub resolver forwards upstream. Break any link — empty resolv.conf, nsswitch missing dns, upstream down — and you get a different symptom, which is why the lab breaks all three separately. Diagnose with getent hosts (exercises the full nsswitch path) and dig/drill @server (bypasses the local stack to test the upstream directly). "DNS is down" is never the diagnosis; it's the symptom — the path tells you where.

iptables/nftables chains and tables; default-deny posture, stateful ESTABLISHED,RELATED

iptables and its successor nftables filter packets in chains (INPUT, OUTPUT, FORWARD) organized into tables; the sane posture is default-deny with explicit allows. The stateful rule that makes default-deny usable is accepting ESTABLISHED,RELATED: return traffic for connections you initiated must be allowed, or every outbound connection breaks on the reply — the checkpoint's answer, and the single most important firewall rule to understand. A minimal host ruleset is: allow loopback, allow established/related, allow the service ports you actually run (22/80/443 as needed), log and drop the rest. Write it, save it persistently, and test from another host — a firewall you haven't tested is a firewall you don't have.

sshd_config hardening: key-only auth, root login, AllowUsers, nonstandard port tradeoffs, fail2ban basics

SSH hardening is a short list with outsized impact: key-only authentication (PasswordAuthentication no), no direct root login (PermitRootLogin no or prohibit-password), AllowUsers/AllowGroups to name exactly who may connect, and fail2ban to throttle brute-force attempts. Moving off port 22 cuts log noise from internet-wide scanners but is not real security — it's obscurity that helps the logs, and the checkpoint asks you to state exactly that limit. The lab's verify-with-a-second-terminal discipline is non-negotiable: never close your working session until the new config is proven, or a typo locks you out of your own machine. SSH is the remote administrator's lifeline; harden it, then prove you can still use it.

  • Diagnose connectivity layer by layer: link, local, gateway, DNS, remote
  • Implement host firewall rules and lock down SSH to a sane posture

    2. Prove source selection: ping -I <new-addr> a destination and capture which source the far side sees.
    3. Remove the route and confirm the failure mode — you now understand what no route to host actually means.

Self-check questions

A host pings its gateway but nothing beyond: list three distinct causes and how to test each
Answer: 1) Missing/wrong default route — ip route shows no default; test with ping -I and trace. 2) Gateway not forwarding/NATing — test from another host behind the same gateway. 3) Upstream firewall blocking — traceroute dies at the same hop consistently; compare against a known-good host.
Why does allowing ESTABLISHED,RELATED matter in a default-deny INPUT chain?
Answer: Without it, return traffic for connections YOU initiated is dropped — DNS replies, HTTP responses, SSH session packets all die. The rule permits the reply half of legitimate conversations while the default-deny still blocks unsolicited inbound.
Explain the security value and limits of moving SSH off port 22
Answer: Value: eliminates ~99% of automated botnet scanning noise and log spam. Limits: zero protection against a targeted attacker (port scan finds it in seconds) — it is obscurity, not security. Real SSH security: key-only auth, no root login, fail2ban, updated OpenSSH.

Module 7

Users, Groups, sudo, and Security Posture

/etc/passwd, /etc/shadow, /etc/group field semantics; UID/GID allocation

/etc/passwd maps names to UIDs, home directories, and shells (seven colon-separated fields, world-readable by design); /etc/shadow holds the password hashes and aging fields, readable only by root; /etc/group maps group names to GIDs and membership. UID allocation follows convention: low numbers for system accounts, regular users from 1000 up (distro-dependent). The security property to internalize: passwd is public because the system needs name-to-UID mapping everywhere, shadow is private because hashes are crackable — the split is the design. Reading these three files fluently is prerequisite to every user-management task that follows.

sudoers syntax, visudo, Cmnd_Alias, NOPASSWD risks, sudo -l auditing

sudo delegates root privileges per the sudoers policy: who may run what as whom, with Cmnd_Alias grouping commands and NOPASSWD removing the password prompt (convenient, and a real risk if the account is compromised). Editing /etc/sudoers directly is dangerous because a syntax error locks out all sudo access — visudo exists to check syntax before saving, and it is the only safe editor. sudo -l audits what the invoking user may actually run, which answers the checkpoint: it reveals your effective privilege boundary, while id only shows your identity. The lab's deploy-user exercise is least privilege in miniature: exactly two service restarts, provably nothing else.

PAM stack basics: auth/account/password/session; pam_faillock, pam_pwquality

PAM (Pluggable Authentication Modules) is the stack that decides "may this authentication succeed": auth (verify identity), account (is the account valid now), password (can the password change), and session (setup/teardown around login). pam_faillock counts failures and locks accounts after too many; pam_pwquality enforces password strength rules. The stack order matters — modules run in sequence and each can require, requisite-fail, or optionally contribute — which is why PAM misconfiguration locks everyone out in creative ways. You don't need to master every module; you need to know the four management groups, where the stack files live, and to test changes from a second session before logging out.

chage password aging; locked vs expired vs nologin accounts

Account states are distinct and the auth behavior differs: passwd -l locks the password (prepends ! to the hash — key-based SSH may still work, which surprises people), chage -E sets an expiry date after which the account itself is invalid, and /bin/nologin or /usr/sbin/nologin as the shell blocks interactive login while allowing the account to own processes. chage manages aging policy: maximum password age, warning windows, inactivity lockout. The checkpoint's distinction is operational: a locked account can be unlocked by root instantly; an expired account needs its expiry extended — know which you're looking at before promising a user they'll be back in five minutes.

SELinux/AppArmor modes awareness; auditd watch rules for sensitive files

Beyond discretionary permissions sit the mandatory systems: SELinux (enforcing/permissive/disabled — check with getenforce before blaming it for denials) and AppArmor (profile-based confinement, common on Debian-family). They don't replace chmod; they add a second decision layer that can deny even root, which is why "permissions look fine but access is denied" points here. auditd complements them with watch rules: auditctl -w /etc/passwd -p wa logs every write or attribute change to the file, giving you an immutable-ish trail of who touched the crown jewels. The baseline posture this module builds: correct ownership, least-privilege sudo, sane PAM, awareness of the MAC layer, and audit watches on the files that matter.

  • Delegate privilege with least-privilege sudoers rules and validate them
  • Apply a baseline hardening pass: PAM basics, password policy, audit trail

    2. As the deploy user, run sudo -l to confirm the boundary, successfully restart one allowed service, and confirm a third service restart is denied.
    3. Save the sudoers snippet as the template for all future service-account delegation.

  2. Lab: Enforce password quality and lockout policy via PAM on a test VM; trigger and clear a faillock

Self-check questions

What does `sudo -l` reveal that `id` does not?
Answer: id shows who you ARE (uid/gids). sudo -l shows what you MAY DO — your sudo privileges, including NOPASSWD entries and command restrictions. Identity vs authorization, same split as everywhere else.
Explain why editing /etc/sudoers directly is dangerous and what visudo buys you
Answer: A syntax error in sudoers breaks ALL sudo — including the ability to fix it. visudo locks the file and syntax-checks before saving, refusing to write a broken policy. It is the seatbelt for the most dangerous config file on the system.

Module 8

Shell Scripting and Automation

set -euo pipefail and where it still bites; quoting "$@" vs $*

set -euo pipefail is the strict-mode preamble every serious script starts with: -e exits on any command failure, -u errors on unset variables, -o pipefail makes pipelines fail if any stage fails. But it has sharp edges the checkpoint names: set -e is suspended inside if conditions and || / && lists (that's by design — you're handling the failure explicitly there), so cmd || fallback won't abort even when cmd fails. The discipline is to know where strict mode applies and to handle the exceptions deliberately rather than being surprised by them. Combine with quoting "$@" (each argument preserved exactly) instead of $* (word-split and glob-expanded) and a whole class of "works until filenames have spaces" bugs vanishes.

Exit codes: 0-255, 127/126 meanings, capturing vs masking in pipelines

Exit codes are the script's API: 0 for success, 1–255 for failures, with 126/127 carrying their command-not-found semantics from the shell itself. Capturing a code (rc=$?) must happen immediately — the next command overwrites $? — and pipelines mask codes unless pipefail is set, which is why the previous concept and this one are inseparable. Design your codes deliberately: distinct non-zero values for distinct failure modes (config missing vs. dependency failed vs. partial completion) turn "the script failed" into a diagnosable event. Monitoring systems consume these codes, so treat them as a contract with your future on-call self.

trap on EXIT/ERR/INT for cleanup; mktemp for temp files; flock for mutual exclusion

trap registers cleanup handlers: trap 'rm -f "$tmp"' EXIT guarantees the temp file dies whether the script succeeds, fails, or is interrupted — which manual cleanup at the end of the script cannot promise, because failures skip the end. mktemp creates the temp files safely (no predictable-name races), and flock provides mutual exclusion so overlapping runs don't corrupt shared output — the checkpoint's answer for colliding cron jobs, alongside "don't schedule them to overlap." The pattern for any script touching shared state: mktemp for scratch, trap for cleanup, flock for serialization. These three lines prevent the messes that make people distrust automation.

Functions, getopts, here-docs; idempotency as a design goal

Beyond the guards, scripts need structure: functions to name units of work, getopts for real argument parsing (not positional-parameter soup), and here-docs for embedded multi-line content like configs or SQL. Idempotency is the design goal that separates scripts from footguns: running the script twice should produce the same state as running it once — check-before-create, converge-don't-append. The refactor lab (make shellcheck pass clean) enforces the mechanical side: quoting, test constructs, and subshell discipline. A script that is idempotent, locked, logged, and lint-clean is infrastructure; anything less is a liability with a shebang.

cron environment minimalism (PATH), MAILTO, and overlap protection

cron's environment is famously minimal — a bare PATH, no login shell, none of your interactive aliases — which is why "works by hand, fails in cron" is almost always an environment bug, fixed by setting PATH (and any needed variables) explicitly in the crontab or the script. MAILTO controls where cron mails output (set it, or arrange log redirection, or failures vanish silently), and overlap protection (flock, or systemd timers with their serialization) handles the long-job-collides-with-next-run case. The fix-and-prove loop in the lab — broken cron job, explicit PATH, observed unattended success — builds the reflex: when cron misbehaves, suspect the environment first, the code second. For anything needing dependency ordering or catch-up semantics, Module 4's timers are the modern answer.

  • Schedule and supervise recurring work with cron and systemd timers

    2. Run it twice against the same destination and confirm the second run is a clean no-op — idempotency demonstrated.
    3. Kill it mid-run and confirm the trap cleaned up the staging area — the guards, proven under fire.

Self-check questions

Why does `set -e` not save you inside `if` conditions or `cmd || fallback`?
Answer: set -e is suppressed where failure is "expected and handled": if/while conditions, && / || lists, and commands whose status is tested. The shell assumes you are handling the error yourself there. Explicit || exit 1 / || return 1 is the reliable pattern.
Explain what `trap 'rm -f $tmp' EXIT` guarantees that manual cleanup does not
Answer: The trap runs on EVERY exit path — normal end, errors, signals (INT/TERM) — while manual cleanup at the script's end is skipped by early exits and kills. (Quote carefully: single quotes defer $tmp expansion to trap time.)
Two cron jobs overlap and corrupt output: name two mechanisms that prevent this
Answer: 1) flock — the second instance exits/waits if the lock is held. 2) A PID-file with stale-PID checking. flock is the standard: flock -n /var/lock/job.lock -c ... makes overlap structurally impossible.

Module 9

Troubleshooting Methodology: Boot, Services, Disk, Network

The layers: hardware -> bootloader -> kernel -> init -> services -> app; bisect at layer boundaries

Every Linux system is a stack of layers — hardware, bootloader, kernel, init, services, application — and the troubleshooting method is to bisect: determine which layer the fault lives in before diving into any of them. "Service up but clients time out" is a network-or-firewall layer problem until proven otherwise; "machine won't boot" is a bootloader-or-filesystem problem. Bisecting at layer boundaries first prevents the classic waste of debugging the application when the disk is full. The method is always the same: form a hypothesis about the layer, test it with the cheapest command that could disprove it, and narrow — isolate and verify, on repeat.

GRUB rescue, initramfs shell, systemd rescue/emergency targets, chroot from live media

When the machine won't boot, the recovery toolkit is: GRUB's rescue/edit mode (fix a bad kernel line or boot an older entry), the initramfs shell (early-userspace failures, missing drivers or devices), systemd's rescue and emergency targets (a minimal shell with the root filesystem mounted), and chroot from live media (full repair environment when nothing local works). The checkpoint's emergency-shell first three commands are the triage: check what's mounted (mount / findmnt), read the journal of the failed boot (journalctl -b), and identify the failure (failed mount? missing device?). Boot failures feel catastrophic but they're procedural — the tools exist precisely because this happens.

dmesg/journal -b for boot faults; blkid/fstab mismatches as classic no-boot cause

Boot-time forensics start with dmesg and journalctl -b: the kernel ring buffer and the failed boot's journal narrate exactly where the boot died. The single most common no-boot cause after updates is a blkid/fstab mismatch — a UUID changed (reformatted partition, cloned disk) and fstab still names the old one, so a mount fails and the boot drops to emergency shell. The fix loop is: identify the wrong UUID from the journal, get the real one from blkid, correct fstab (from emergency shell, remounting / read-write), reboot. The lab's deliberate fstab breakage makes this sequence a practiced drill instead of a first-time panic.

iostat/vmstat/free/sar for resource pressure; distinguishing OOM from leaks

Resource pressure has a dedicated toolkit: free and vmstat for memory, iostat for disk I/O, sar for historical trends when it's been collecting. The OOM-killer versus segfault distinction from the checkpoint is a logs question: the OOM-killer announces itself in the kernel log ("Out of memory: Killed process ..."), while a segfault is the process dying by signal 11 with no kernel announcement of memory pressure. df-vs-du disagreement means deleted-but-open files (find them via /proc or lsof, fix by restarting the holder or truncating the file). Each tool answers one question; the skill is reaching for the right one first instead of running them all.

tcpdump and ss state inspection for 'service up but unreachable' cases

Network faults get the same layer treatment: ss shows socket state (is anything even listening? is the connection stuck in SYN-SENT?), tcpdump shows what's actually on the wire (are packets leaving? are replies coming back?), and traceroute/mtr locates the silent drop. "Service active but unreachable" resolves to one of: not actually listening (ss), firewalled (tcpdump shows SYN with no reply), or routed into a black hole (traceroute dies at a hop). The lab's black-hole trace is the full method in miniature: observe the symptom, capture the packets, find the hop where they stop, fix the route or rule. Networks don't lie to tcpdump — that's why it's the court of last resort.

  • Recover a system that fails to boot: GRUB, initramfs, fstab, rescue targets
  • Triangulate disk, memory, and network faults with the right first command

Concept glossary

The words this sequence uses.

  • umask — the subtractive mask on new files and directories: files start from 666, directories from 777, and the umask clears the bits it names (umask 027 → files 640, directories 750).
  • inode — the filesystem's per-file record; millions of tiny files can exhaust inodes (df -i shows 100% used) while blocks still show free — "disk full" has three causes: bytes, inodes, quotas.
  • fstab — /etc/fstab makes mounts persistent across boots (device, mountpoint, type, options, dump, pass); the options field's nofail keeps a missing data disk from dropping the machine to emergency shell.
  • systemd — the init and service system: units, services, timers (Persistent=true catches up missed runs where cron silently skips), and the journal; the Type= of a unit must match the process's actual behavior.
  • pipefail / PIPESTATUS — a pipeline's exit status is its last stage's; set -o pipefail makes any stage's failure propagate, and PIPESTATUS holds every stage's status — robust scripts use pipefail always.
  • ACL — POSIX access control lists (getfacl/setfacl) for per-user and per-group entries beyond owner/group/other; the mask entry caps the effective rights of all named entries.
  • setuid — the special bit (4) that runs an executable with its owner's privileges (passwd updating /etc/shadow is the canonical example) — an audit staple, not root-by-default.
  • OOM killer — the kernel's out-of-memory killer; "Out of memory: Killed process" in dmesg is its unmistakable signature — fix capacity or containment, not the app.

Worked procedure

Work an incident the Module-9 way.

  1. State the symptom precisely. "Writes fail" is a complaint; "df -h shows 40% free, df -i shows 100% used, writes fail with ENOSPC" is a diagnosis-ready symptom.
  2. Read the logs first. Check the journal (journalctl) and the kernel log (dmesg) — the OOM killer, failed units, and fsck findings all announce themselves there.
  3. Reproduce safely. Snapshot your lab VM, then reproduce the failure on demand — the only way to learn recovery is to need it, and snapshots make breaking fearless.
  4. Isolate by layer. Disk: df -h vs df -i. Permissions: walk up the path checking the x bit on every directory. Services: systemctl status and the unit's Type=. Network: ping the gateway, then ping beyond it — the fault is at or beyond the gateway.
  5. Fix, verify, document. Apply the fix, re-run the exact failing command to confirm, and write the sequence into your lab journal — it becomes your personal runbook and your interview stories.
