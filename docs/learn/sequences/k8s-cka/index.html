SCIENTIA OMNIA VINCIT

Overview

What this sequence is.

This sequence teaches the craft of running Kubernetes clusters: how the control plane and the nodes fit together, how to install a cluster with kubeadm, how to back up its brain (etcd), how to upgrade it without downtime, and how to schedule, expose, store, secure, and troubleshoot the workloads on top. It is organized around the public Certified Kubernetes Administrator curriculum published by the Linux Foundation and CNCF, but it teaches the engineering underneath — the mental models that survive long after any particular exam outline changes.

Kubernetes is a declarative system: you describe the desired state, and a set of cooperating controllers converges reality toward it. Every module in this sequence exists to make one piece of that loop concrete — the API that records intent, the store that remembers it, the agents that execute it, and the humans who keep it healthy when it breaks.

Who this is for

  • Systems engineers and SREs who will own production Kubernetes clusters.
  • DevOps engineers moving from running containers to running the platform containers run on.
  • Linux administrators who can already manage VMs and want the cluster layer.

Prerequisites

  • Comfortable on the Linux command line: files, processes, networking basics.
  • Basic container literacy: what an image is, what a container is, how ports map.
  • TCP/IP fundamentals: IP addresses, ports, DNS, and what a load balancer does.
  • A lab environment you can break: two or more Linux VMs (or cloud instances) with root access.

How to use this sequence

  • Work the modules in order — each one assumes the machinery of the previous ones.
  • Do every lab on real or virtual machines, not just in your head; cluster administration is a contact sport.
  • Keep a lab journal: every failure you debug is worth writing down, because troubleshooting is the skill being trained.
  • When you finish, rebuild your lab cluster from scratch without looking at your notes — if you can, you know it.

The curriculum

Seven modules, from bare metal to battle-tested.

Module 1

Cluster Architecture and kubeadm Installation

kube-apiserver, etcd, kube-scheduler, kube-controller-manager

The kube-apiserver is the front door of the cluster: it exposes the REST API that everything — kubectl, controllers, kubelets — talks to, and it is the only component that writes to etcd. etcd is the cluster's memory, a consistent distributed key-value store holding every object and its desired state; lose etcd and you lose the cluster's mind. The kube-scheduler watches for newly created pods with no node assigned and picks the best node for each one based on resource requirements, affinity rules, and constraints. The kube-controller-manager runs the control loops — node, replication, endpoints, service-account, and token controllers — that continuously compare actual state against desired state and take action to close the gap. Together these four form the control plane: the brain that decides, remembers, and reconciles.

kubelet and kube-proxy on every node

Every worker node runs a kubelet, the node agent that registers the node with the API server, watches for pods assigned to it, and makes sure their containers are running and healthy — it is the component that turns API objects into running processes. Every node also runs kube-proxy, which maintains the network rules (traditionally iptables or IPVS entries) that implement Service virtual IPs and load-balance traffic across pod endpoints. If the kubelet stops, the node stops receiving new work, stops reporting status, and after a grace period the control plane marks the node NotReady and begins evicting or rescheduling its pods. kube-proxy failing is subtler: pods keep running, but Service routing on that node breaks, so in-cluster service discovery degrades even though the workloads look alive.

Container runtime and the CRI contract

Kubernetes never runs containers directly; it delegates to a container runtime through the Container Runtime Interface (CRI), a gRPC contract defining how to create, start, stop, and inspect containers and pull images. The CRI exists so the kubelet stays runtime-agnostic: containerd, CRI-O, or any CRI-compliant runtime can sit underneath without Kubernetes caring. This separation is why installing Kubernetes means installing three cooperating pieces — the runtime, the kubelet, and kubectl — and why a version skew between the kubelet and the runtime is a classic source of mysterious node problems. When you debug a node that cannot start pods, the kubelet-to-runtime conversation is one of the first places to look.

Pod networking requirement and CNI plugins

Kubernetes imposes a flat networking model with a hard rule: every pod gets its own IP address, and every pod can reach every other pod (and node) without NAT. This "IP-per-pod" model is what makes service discovery and direct pod-to-pod communication simple, but the base Kubernetes install does not implement it — a CNI (Container Network Interface) plugin does. Installing a CNI plugin like Calico, Flannel, or Cilium after kubeadm init is what actually wires pod networking: until you do, nodes stay NotReady and pods stay Pending because the network isn't ready. Different plugins implement the model differently — overlays, BGP routing, eBPF — but they all satisfy the same contract, and NetworkPolicy enforcement depends on choosing a plugin that supports it.

kubeadm phases: init, join, bootstrap tokens, certificates

kubeadm init bootstraps a control plane in phases: it runs preflight checks, generates the certificate authority and all component certificates, writes static pod manifests for the API server, scheduler, controller-manager, and etcd, applies the bootstrap token and RBAC rules, and finally prints the join command. Bootstrap tokens are short-lived credentials that let a new node authenticate its first request to join; kubeadm join combines the token with a hash of the CA certificate so the node can verify it is talking to the real control plane and not an impostor. Joining is a handshake: the node proves possession of the token, receives its client certificates, and starts its kubelet and kube-proxy. Because tokens expire (by default after a day), regenerating one with kubeadm token create is a routine operation when you add nodes later.

kubeconfig and cluster authentication

A kubeconfig file is how kubectl (and any client) knows which cluster to talk to, as whom, and with what credentials: it bundles clusters (server address + CA), users (client certificates, tokens, or exec plugins), and contexts that bind a user to a cluster and a default namespace. kubeadm init writes the superuser config to /etc/kubernetes/admin.conf; copying it to your own ~/.kube/config is what gives your workstation cluster-admin access. Because that file is effectively a root password for the cluster, it belongs in the same protection class as private keys — never committed, never shared casually. Understanding contexts also prevents the classic disaster of running a command against the wrong cluster, which is why disciplined operators always check their current context before applying anything destructive.

Learning objectives

  • Describe control-plane and worker-node components and how they interact.
  • Install a multi-node cluster with kubeadm on lab VMs.
  • Join worker nodes and verify cluster health with kubectl.

Hands-on labs

  1. Lab: Provision two Linux VMs and install matching kubeadm, kubelet, and kubectl versions.

    1. Create two Linux VMs with at least 2 CPUs and 2 GB RAM each, disable swap, and enable the required kernel modules and sysctl settings for bridged networking.
    2. Install a container runtime (containerd is the common default), then install kubeadm, kubelet, and kubectl at the exact same version on both machines and hold the packages so the OS updater cannot skew them.
    3. Verify each node can reach the other over the pod-network CIDR you plan to use, and confirm the kubelet service is enabled but the nodes are not yet joined to anything.

  2. Lab: Run kubeadm init with a pod-network CIDR, then install a CNI plugin.

    1. On the first VM, run kubeadm init with --pod-network-cidr set to a private range that does not overlap your LAN (for example 10.244.0.0/16 or 192.168.0.0/16 depending on your CNI choice).
    2. Copy /etc/kubernetes/admin.conf to your user kubeconfig, then install your chosen CNI plugin's manifest and wait until kubectl get nodes shows the control-plane node as Ready.
    3. Record the kubeadm join command printed at the end of init; note the token and the CA certificate hash it contains.

  3. Lab: Join a worker with the kubeadm join command and label both nodes.

    1. On the second VM, run the recorded kubeadm join command exactly as printed.
    2. Back on the first node, run kubectl get nodes and confirm two Ready nodes, then label them (for example node-role or workload labels) with kubectl label nodes.
    3. Deploy a trivial test pod and confirm it can be scheduled — this proves the scheduler, kubelet, runtime, and CNI are all cooperating.

  4. Lab: Inspect static pod manifests under /etc/kubernetes/manifests and check component status.

    1. List /etc/kubernetes/manifests and open one static pod manifest; note how it is an ordinary pod spec the kubelet watches from disk rather than from the API.
    2. Run kubectl get pods -n kube-system and map each pod back to its manifest file; then check component health through kubectl get componentstatuses or the API directly.
    3. Kill one static pod (delete its manifest temporarily or stop its container) and watch the kubelet recreate it — this is why static pods are self-healing.

Self-check questions

  • Which component serves the API and which stores cluster state?
  • What breaks on a worker when its kubelet stops?
  • Regenerate an expired bootstrap token and join a fresh node.
  • Summarize what kubeadm init does in four steps.

Module 2

etcd Backup and Restore, Upgrades, and High Availability

etcd as the authoritative cluster state store

etcd is the single source of truth for the entire cluster: every Deployment, Secret, node status, and lease lives as a key in its store, and the API server is its only writer. That makes etcd the most valuable backup target in the whole system — you can rebuild every other control-plane component from scratch, but without etcd's data your cluster's configuration is gone. In kubeadm clusters etcd usually runs as a static pod with its data on the control-plane node's local disk, which is why the backup procedure targets that pod's certificates and data directory. The administrator's job is to treat etcd like a production database: snapshot it on a schedule, store snapshots off the node, and practice restores before you need one.

Snapshot save and restore with endpoints, CA, cert, and key flags

An etcd snapshot is a point-in-time copy of the keyspace, taken with the snapshot save operation against the etcd API. Because a kubeadm etcd serves TLS, the command needs the cluster's CA, client certificate, and key — found in /etc/kubernetes/pki/etcd — plus the endpoint address, or the server will refuse the connection. After saving, snapshot status verifies the file is a valid, complete snapshot rather than a truncated write. Restoring is the reverse: write the snapshot into a fresh, empty data directory, then point the etcd static pod manifest at that directory and let it start from the restored state. The discipline that matters is doing this on a schedule and testing the restore path — an untested backup is a rumor.

Quorum math and why odd member counts are used

etcd keeps its members consistent with the Raft consensus protocol, which requires a majority — a quorum — of members to agree before any write commits. With three members, one can fail and writes still succeed; with two members, one failure kills writes, which is why etcd clusters use odd member counts (1, 3, 5) and never 2 or 4. An even count adds failure surface without adding fault tolerance: four members still only survive one failure, same as three. The practical lesson for Kubernetes HA is that a three-control-plane-node cluster survives the loss of one control-plane node with the API and scheduling intact, while a single-control-plane lab cluster has no such safety net — plan maintenance windows accordingly.

kubeadm upgrade plan and upgrade apply sequencing

kubeadm upgrades the control plane in a strict sequence: kubeadm upgrade plan first, which compares current and target versions and lists the component changes it intends to make, then kubeadm upgrade apply, which actually performs them. The plan step is a dry-run review — read it, because it tells you exactly which control-plane images will change. The apply step upgrades the API server, controller-manager, scheduler, and etcd in dependency order, waiting for each to become healthy. This sequencing is why you never skip the plan: an upgrade is a controlled, observable rollout of the cluster's brain, and surprises there are the most expensive kind.

Node upgrade order: control plane first, then workers

Upgrades move through the cluster in a fixed order: control plane first, then worker nodes one at a time. The reason is version skew policy — kubelets may be at most a couple of minor versions behind the API server, but the API server must never be behind the kubelets, so you lift the brain before the limbs. For each worker, the ritual is drain (evict its pods gracefully), upgrade the kubeadm/kubelet/kubectl packages, restart the kubelet, verify the node is Ready, then uncordon it to accept work again. Upgrading one minor version at a time matters because each release only guarantees upgrade paths from its immediate predecessor; jumping two minors skips migration logic that your cluster's stored objects may depend on.

Stacked versus external etcd topologies

A stacked etcd topology runs etcd on the same nodes as the other control-plane components — simple, and the kubeadm default — while an external etcd topology runs etcd on its own dedicated hosts, separate from the API servers. Stacked is easier to operate and perfectly fine for most clusters; external etcd isolates the state store's disk I/O and failure domain from the API servers at the cost of more machines and more operational surface. The failure behavior differs in the details but not the principle: in both, losing quorum means the API goes read-only-or-down and nothing new can be scheduled, while existing workloads keep running. Choosing between them is a tradeoff between operational simplicity and blast-radius isolation, not between safety and recklessness.

  • Back up and restore etcd with etcdctl snapshots.
  • Execute a kubeadm control-plane upgrade one minor version at a time.
  • Describe HA topology options and their failure behavior.

Hands-on labs

  1. Lab: Take an etcd snapshot to local disk and verify it with snapshot status.

    1. Locate the etcd client certificates under /etc/kubernetes/pki/etcd and the etcd endpoint (usually https://127.0.0.1:2379 on the control-plane node).
    2. Run the snapshot save command with --endpoints, --cacert, --cert, and --key pointing at those files, writing to a timestamped file on local disk.
    3. Verify the snapshot with snapshot status, note the reported revision and size, and copy the file off the node to safe storage.

  2. Lab: Restore a snapshot into a fresh data directory and restart the static etcd pod.

    1. On a scratch directory, run the snapshot restore operation into a fresh data directory (never over the live one).
    2. Edit a copy of the etcd static pod manifest to mount the restored data directory, or stop kubelet, swap the data directory, and restart — in a lab, either demonstrates the mechanics.
    3. Confirm the API server serves the restored objects (for example, that a test namespace or deployment you created before the snapshot is present), then revert to the original data directory.

  3. Lab: Run kubeadm upgrade plan and apply on a lab control-plane node.

    1. Run kubeadm upgrade plan and read its output: current version, target version, and which component images will change.
    2. Run kubeadm upgrade apply to the next minor version and watch each control-plane static pod roll in sequence.
    3. Afterward, verify with kubectl get nodes and a test workload that the API, scheduling, and existing pods are healthy.

  4. Lab: Drain a worker, upgrade its kubelet and kubectl, then uncordon it.

    1. Pick a worker node and run kubectl drain on it, confirming its pods reschedule elsewhere (or complete, for DaemonSets).
    2. Upgrade the kubeadm package, run kubeadm upgrade node, then upgrade kubelet and kubectl and restart the kubelet service.
    3. Verify the node returns to Ready with the new kubelet version, then kubectl uncordon it and confirm workloads can schedule there again.

Self-check questions

  • Which flags does etcdctl need to reach a TLS-secured etcd?
  • What happens to writes when etcd loses quorum?
  • Write the exact upgrade sequence for a single-control-plane lab.
  • Why must minor versions be upgraded one at a time?

Module 3

Workloads and Scheduling

Deployment, ReplicaSet, rollout history, and rollback

A Deployment is the standard way to run stateless applications: you declare the desired pod template and replica count, and the Deployment manages a ReplicaSet that keeps that many identical pods running. Every change to the pod template creates a new ReplicaSet revision while the old one is scaled down, which is what makes rollouts and rollbacks possible — the history is literally the sequence of ReplicaSets. kubectl rollout history and kubectl rollout undo let you inspect that history and return to a previous revision when a release misbehaves. The golden rule is to never hand-edit the ReplicaSet's replica count directly: the Deployment owns it, and fighting your own controller is a losing game.

DaemonSet one-pod-per-node scheduling and updates

A DaemonSet guarantees one pod per (matching) node: it is how you run node-level agents like log collectors, monitoring exporters, or CNI components themselves. When a new node joins the cluster, the DaemonSet controller immediately schedules its pod there; when a node leaves, the pod goes with it — no replica math involved. Updates roll across nodes one (or a few) at a time, so agent upgrades don't take down fleet-wide observability at once. If you find yourself wanting "exactly one copy on every machine," you want a DaemonSet, not a Deployment with one replica per node hacked together with affinity.

Resource requests versus limits and QoS classes

Requests are what the scheduler uses to place pods: a pod is only scheduled on a node whose allocatable resources can cover the sum of its containers' requests, which makes requests a scheduling guarantee. Limits are what the kernel enforces at runtime: exceed your CPU limit and you get throttled; exceed your memory limit and the container is OOM-killed. Kubernetes derives a Quality of Service class from how requests and limits relate: Guaranteed when every container sets requests equal to limits, Burstable when requests are set below limits (or only one side is set), and BestEffort when neither is set. Under memory pressure the kubelet evicts in QoS order — BestEffort first, then Burstable, Guaranteed last — which is why production workloads always set requests, and critical ones set both.

nodeSelector, node affinity, pod affinity and anti-affinity

nodeSelector is the blunt instrument: a pod goes only to nodes carrying a matching label. Node affinity is the expressive version, with required rules (hard constraints) and preferred rules (soft, weighted preferences) that can match on labels, node fields, and set operators like In and NotIn. Pod affinity and anti-affinity constrain placement relative to other pods — "run near the cache" or "never put two replicas of me on the same node" — which is how you build topology-aware, failure-domain-spread deployments. Together these are the vocabulary for telling the scheduler not just how many pods you want, but where in the fleet they are allowed to live.

Taints, tolerations, and NoSchedule/NoExecute effects

Taints are the inverse of affinity: applied to nodes, they repel pods that don't explicitly tolerate them. A toleration on a pod declares which taints it accepts, with effects NoSchedule (don't place new pods here), PreferNoSchedule (try not to), and NoExecute (evict existing pods that lack the toleration, optionally after tolerationSeconds). The classic use is dedicating nodes — taint GPU nodes so only GPU workloads tolerate them — or protecting control-plane nodes, which carry a NoSchedule taint by default. The checkpoint scenario falls out naturally: a pod stays Pending when every schedulable node carries a taint it doesn't tolerate, because the scheduler has nowhere legal to put it.

Learning objectives

  • Deploy and roll out versioned applications with Deployments.
  • Run node-level agents with DaemonSets.
  • Constrain pod placement with requests, limits, affinity, and taints/tolerations.

Hands-on labs

  1. Lab: Create a Deployment, scale it, roll out a new image, then roll back.

    1. Create a Deployment of a simple web server with 3 replicas; confirm the ReplicaSet and pods appear with matching labels.
    2. Scale it to 5 with kubectl scale, then update the container image and watch the rollout replace pods incrementally.
    3. Run kubectl rollout history, then kubectl rollout undo to return to the previous revision and verify the image tag reverted.

  2. Lab: Deploy a DaemonSet and confirm one pod lands on each node.

    1. Write a DaemonSet manifest for a trivial agent (even a busybox sleep loop) and apply it.
    2. Run kubectl get pods -o wide and confirm exactly one pod per node, on the node you expect.
    3. Add a new node (or untaint one) and watch the DaemonSet controller place a pod there automatically.

  3. Lab: Set CPU and memory requests and limits and observe the resulting QoS class.

    1. Deploy three pods: one with requests equal to limits, one with requests below limits, one with neither; describe each pod and note the reported QoS class.
    2. Apply memory pressure (or simply reason from the docs) and predict the eviction order: BestEffort, then Burstable, then Guaranteed.
    3. Set a memory limit deliberately low on a test container, push it past the limit, and observe the OOMKilled status in kubectl describe.

  4. Lab: Taint a node and schedule only tolerating pods onto it.

    1. Taint a worker node with a custom key=value:NoSchedule and try to schedule an ordinary pod — confirm it stays Pending.
    2. Add a matching toleration to the pod spec, reapply, and watch it schedule onto the tainted node.
    3. Extend the exercise: use NoExecute with tolerationSeconds on a second taint and observe timed eviction of a non-tolerating pod.

  5. Lab: Pin a workload to labeled nodes with required node affinity.

    1. Label your nodes by zone or role, then write a Deployment using required node affinity to pin it to one label value.
    2. Verify with kubectl get pods -o wide that every replica landed on correctly labeled nodes.
    3. Add a pod anti-affinity rule spreading replicas across nodes, scale up, and confirm the spread in the wide output.

Module 4

Services, DNS, Ingress, and Network Policy

Service selectors, Endpoints, and kube-proxy behavior

A Service is a stable virtual endpoint in front of a set of pods: its selector continuously matches pod labels, and the resulting Endpoint list is what traffic actually goes to. kube-proxy on every node programs the local forwarding rules (iptables, IPVS, or eBPF, depending on mode) so that the Service's virtual IP load-balances across the current healthy endpoints. This indirection is the whole point — pods are ephemeral and their IPs churn, but the Service name and IP stay fixed. When a Service has no endpoints, the selector isn't matching anything, and that empty Endpoints object is the first thing to check when "the Service doesn't work.

ClusterIP versus NodePort versus LoadBalancer versus ExternalName

ClusterIP is the default: an internal-only virtual IP reachable from inside the cluster, which is what backend-to-backend traffic uses. NodePort opens the same service on a fixed high port of every node's IP, which works with no cloud provider at all — the lab and bare-metal answer to external access. LoadBalancer asks the cloud provider to provision a real external load balancer pointing at the nodes, which is why it only does something meaningful on a cloud with that integration. ExternalName is the odd one out: no proxying at all, just a DNS CNAME record mapping the Service name to an external hostname. Choosing between them is choosing how far outside the cluster the traffic needs to come from.

CoreDNS records for Services and pods

CoreDNS runs as a cluster service and answers DNS for two kinds of names: Services and pods. A Service named web in namespace shop is reachable as web, as web.shop, and as the fully qualified web.shop.svc.cluster.local — the short forms work because pods get search domains configured automatically. Pods get DNS too, notably for headless services where each pod gets its own A record. When in-cluster name resolution fails, the debugging order is: is CoreDNS itself running, can the pod reach the cluster DNS service IP, and does the name actually exist — most "DNS is broken" incidents are really "the Service doesn't exist or has no endpoints.

Ingress resources, IngressClass, and the need for a controller

An Ingress is a declarative description of HTTP(S) routing rules — hosts, paths, and which Service each maps to — but it does nothing by itself: an ingress controller (NGINX, Traefik, HAProxy, or a cloud one) must be installed to watch Ingress objects and implement them. The IngressClass resource is how a cluster with multiple controllers disambiguates which controller owns which Ingress. If no installed controller matches the Ingress's class, the rules sit there inert — valid API objects with no one acting on them — which is the classic "my Ingress does nothing" bug. TLS termination happens at the controller using a Secret referenced by the Ingress, so certificate problems surface as controller errors, not Ingress errors.

NetworkPolicy default-deny posture and ingress/egress rules

By default, Kubernetes networking is wide open: every pod can reach every other pod. A NetworkPolicy changes that for the pods it selects — and the crucial semantic is that selecting a pod in a policy flips that pod to deny-by-default for the listed direction (ingress, egress, or both). A default-deny-all policy in a namespace is therefore the standard starting posture for zero-trust: block everything, then add explicit allow rules for the traffic the application actually needs. Ingress rules specify which peers (by pod selector, namespace selector, or IP block) may connect on which ports; egress rules do the same for outbound. Policies are additive — multiple policies selecting the same pod union their allow rules — and they are only enforced if the CNI plugin implements them, which is why your CNI choice from Module 1 matters here.

  • Expose pods with ClusterIP, NodePort, and LoadBalancer Services.
  • Verify in-cluster DNS resolution for Services.
  • Route external HTTP traffic with Ingress and isolate traffic with NetworkPolicy.

Hands-on labs

  1. Lab: Expose a Deployment via ClusterIP and curl it from a temporary debug pod.

    1. Deploy a simple HTTP server via a Deployment, then expose it with a ClusterIP Service.
    2. Launch a temporary debug pod (kubectl run with --rm -it) and curl the Service by its cluster IP and by its DNS name.
    3. Delete the debug pod afterward — the point is that in-cluster clients reach the stable Service, never pod IPs directly.

  2. Lab: Publish a NodePort Service and reach it through a node IP and port.

    1. Change or add a NodePort Service for the same Deployment and note the allocated high port.
    2. From outside the cluster (your workstation or another VM), curl http://<node-ip>:<node-port> and confirm you reach the app.
    3. Compare the experience with ClusterIP: NodePort needs no cloud integration, which is why it's the bare-metal default for external access.

  3. Lab: Install an ingress controller and route two hostnames to two Services.

    1. Install an ingress controller in your lab cluster (the NGINX ingress controller's manifest is the common lab choice).
    2. Write an Ingress with two host rules (for example app1.test and app2.test) routing to two different Services, and add those names to your workstation's hosts file pointing at a node IP.
    3. Curl each hostname and confirm you land on the correct backend; then create an Ingress with a nonexistent class and observe that nothing routes — the controller-matching lesson, firsthand.

  4. Lab: Apply a default-deny NetworkPolicy, then allow traffic only from labeled clients.

    1. In a test namespace, apply a default-deny ingress NetworkPolicy selecting all pods, then verify that pod-to-pod curls that worked a minute ago now fail.
    2. Add an allow policy permitting traffic only from pods carrying a specific label to your backend on its application port; label one client pod and confirm it alone can connect.
    3. Document the allowed matrix — this is the seed of a zero-trust posture you can carry into production namespaces.

  5. Lab: Resolve a Service DNS name from inside a pod, including cross-namespace form.

    1. From a debug pod, use nslookup or getent hosts to resolve a Service's short name, namespace-qualified name, and FQDN; record all three answers.
    2. Repeat the lookup from a pod in a different namespace to show which forms need qualification.
    3. Break a Service selector deliberately, confirm Endpoints goes empty, repair it, and re-resolve — connecting DNS behavior to the endpoint machinery.

Module 5

Persistent Storage: PVs, PVCs, StorageClasses, and Volume Modes

PV lifecycle phases: Available, Bound, Released, Failed

A PersistentVolume (PV) is a piece of storage provisioned into the cluster — by an administrator or dynamically — with a lifecycle independent of any pod. Its phases tell the story: Available means unclaimed, Bound means a claim holds it, Released means the claim was deleted but the data may still be there, and Failed means something went wrong. Reclaim policy decides what happens on release: Retain keeps the data (you must clean it up manually before reuse), Delete destroys the backing storage. The lab's Retain exercise makes this visceral: delete the claim and the PV sits in Released, data intact, waiting for an administrator's decision.

PVC requests, selectors, and the binding process

A PersistentVolumeClaim (PVC) is a pod author's request for storage: "I need this much space, with these access modes, optionally from this StorageClass or matching these labels." Binding is a matchmaking process — the control plane finds an Available PV satisfying capacity, access modes, and selectors, or asks the StorageClass provisioner to create one dynamically. A claim stays Pending when nothing matches: wrong StorageClass name, insufficient capacity, or an access mode the provisioner can't provide are the usual suspects, checked in that order. This request/claim split is what lets developers ask for storage by characteristics while administrators control the actual backends.

StorageClass provisioner, parameters, and reclaim policies

A StorageClass names a provisioner (the driver that talks to the actual storage system) plus parameters like disk type, filesystem, or replication settings, and declares the reclaim policy for volumes it creates. When a PVC names a StorageClass with no matching static PV, the provisioner creates the volume on demand — dynamic provisioning, the reason cloud clusters rarely need hand-made PVs. The class is also where volumeBindingMode lives: Immediate binds at claim creation, while WaitForFirstConsumer delays binding until a pod needs it, which matters for topology-constrained storage like zone-local disks. Choosing a class is choosing cost, performance, and failure-domain behavior in one line of YAML.

Access modes: ReadWriteOnce, ReadOnlyMany, ReadWriteMany

Access modes describe how a volume may be mounted: ReadWriteOnce (one node, read-write), ReadOnlyMany (many nodes, read-only), and ReadWriteMany (many nodes, read-write). Most cloud block storage is ReadWriteOnce-only, which is why a database pod using it cannot simply run two writers on two nodes — the second pod can't attach the same block device. ReadWriteMany needs a shared filesystem (NFS, CephFS, cloud file services) and is the mode that lets multiple pods genuinely share writable storage. Picking the wrong mode is a scheduling puzzle that can't be solved: the constraint is in the storage system, not in Kubernetes.

Volume modes: Filesystem versus Block

Volume mode distinguishes Filesystem (the default — Kubernetes formats and mounts the volume, pods see files) from Block (the raw device is handed to the pod, no filesystem). Block mode exists for applications that want to manage storage themselves: databases with their own volume managers, or software that needs direct device semantics. It is a niche but real requirement, and the lab's exercise — exposing a raw block device and confirming the pod sees a device node rather than a mountpoint — is the fastest way to internalize the difference. For everything else, Filesystem mode and let Kubernetes handle the formatting.

StatefulSet stable identity paired with per-pod storage

A StatefulSet is the workload controller for applications where identity matters: each pod gets a stable name, stable network identity, and — the point of this concept — its own PersistentVolumeClaim created from a volumeClaimTemplate. Pod web-0 always gets PVC data-web-0, so when it reschedules, its data follows it by identity rather than by luck. This pairing is what makes running databases and other stateful systems on Kubernetes tractable: stable identity plus per-pod storage turns "pets" into manageable, repeatable units. The StatefulSet doesn't replace the PV/PVC/StorageClass machinery — it automates the claim-per-replica pattern on top of it.

Learning objectives

  • Provision static PersistentVolumes and bind them through PersistentVolumeClaims.
  • Use StorageClasses for dynamic provisioning.
  • Choose access modes and volume modes suited to stateful workloads.

Hands-on labs

  1. Lab: Create a hostPath PV and bind a PVC to it, then mount it in a pod.

    1. Create a hostPath PersistentVolume on one node (lab-only; hostPath is never for production) with a modest capacity.
    2. Write a PVC requesting that capacity with a matching selector or no StorageClass, and watch it bind — kubectl get pv should show Bound.
    3. Mount the claim in a pod, write a file, delete the pod, and confirm the file survives on the volume: storage outlives pods.

  2. Lab: Enable a dynamic provisioner and claim storage through a StorageClass.

    1. Enable a dynamic provisioner in your lab (your cloud's default StorageClass, or local-path-provisioner on bare metal).
    2. Create a PVC naming that StorageClass with no pre-made PV, and watch the provisioner create the volume and bind it automatically.
    3. Describe the resulting PV to see which provisioner, parameters, and reclaim policy the class supplied.

  3. Lab: Restart the consuming pod and confirm data persists on the volume.

    1. From the previous lab's pod, write a sentinel file to the mounted volume, then delete the pod and recreate it.
    2. Confirm the sentinel file is still there after rescheduling — this is the durability contract dynamic provisioning gives you.
    3. Now delete the PVC too and check whether the PV and its data were retained or deleted, per the class's reclaim policy.

  4. Lab: Set reclaimPolicy to Retain, delete the PVC, and observe the Released phase.

    1. Patch or recreate a PV/PVC pair with reclaimPolicy: Retain, write data, then delete the PVC.
    2. Observe the PV sitting in Released with data intact; manually clear it (delete the PV and wipe the backing path) to return it to Available.
    3. Write down the operational rule this teaches: Retain means the administrator owns cleanup, always.

  5. Lab: Expose a raw block volume to a pod using volumeMode Block.

    1. If your provisioner supports it, create a PVC with volumeMode: Block and attach it to a pod.
    2. Inside the pod, list /dev and identify the raw device (no mountpoint, no filesystem) handed to the container.
    3. Note which of your applications would ever need this — and confirm that for everything else, Filesystem mode is the answer.

Self-check questions

  • What binds a PVC to a specific PV?
  • What does reclaimPolicy Delete do when the PVC is removed?
  • Which access mode fits a single-writer database?
  • Why would a PVC stay Pending when no StorageClass matches?

Module 6

Cluster Security: RBAC, ServiceAccounts, Pod Security, and TLS

RBAC subjects, resources, and verbs

RBAC describes access in three parts: subjects (users, groups, ServiceAccounts — who), resources (pods, deployments, secrets — what), and verbs (get, list, create, delete — which actions). A Role or ClusterRole is the rulebook; a Binding attaches it to subjects. The discipline is least privilege: grant exactly the verbs on exactly the resources in exactly the namespaces the subject needs, and audit the grants regularly. Every production incident involving a compromised credential is made worse by overbroad RBAC, which is why the module's audit lab — listing ClusterRoleBindings and staring at cluster-admin grants — is not busywork but hygiene.

Role and ClusterRole versus RoleBinding and ClusterRoleBinding

Roles and Bindings are namespaced; ClusterRoles and ClusterRoleBindings are cluster-scoped — and the combinations matter. A RoleBinding grants a Role (or even a ClusterRole's rules, but only within that namespace) to subjects in one namespace. A ClusterRoleBinding grants across all namespaces, which is why binding cluster-admin via a ClusterRoleBinding is the keys-to-the-kingdom grant the audit lab hunts for. The exam-style checkpoint answer: the binding type that grants access across all namespaces is the ClusterRoleBinding. Misunderstanding this matrix is how teams accidentally grant cluster-wide access when they meant one namespace.

ServiceAccount tokens mounted into pods

Every pod runs as a ServiceAccount, and by default each pod gets that account's token mounted inside it at the standard secrets path — which means any process in the pod can present that token to the API server. Running each workload under a dedicated ServiceAccount with only the RBAC it needs turns a compromised pod from a cluster-wide disaster into a contained one. The lab's inspect-the-mounted-token step makes the mechanism concrete: the token is a file in the pod, and its power is exactly the power RBAC grants that ServiceAccount. ServiceAccounts are identities for machines the same way users are identities for humans, and they deserve the same least-privilege treatment.

Pod Security admission levels: privileged, baseline, restricted

Pod Security admission enforces baseline safety rules on pods at creation time, in three levels: privileged (no restrictions), baseline (blocks known-bad configurations like host namespaces), and restricted (the strict hardening profile). The restricted level forbids a concrete list of risky settings — containers must not run as root, privilege escalation must be disabled, and only a narrow set of capabilities is allowed, among others. Enforcing restricted on a namespace and fixing the violations is the lab that teaches the standard: write pods that pass restricted from the start, and security review becomes a non-event. Admission-time enforcement beats runtime detection because the bad pod never starts.

Certificate rotation for kubelet and API aggregation

The cluster's internal TLS — API server certificates, etcd peer certificates, kubelet serving certificates — expires and rotates like any other PKI, and the administrator owns that lifecycle. Kubelet client certificates are typically auto-rotated by the kubelet itself, but serving certificates and aggregated API server certs may need manual rotation or CSR approval through the certificates API. The lab's approve-a-CSR exercise walks the machinery: a certificate signing request object appears, a human (or an approver) signs it, and the requester gets a usable certificate. Letting cluster PKI expire unnoticed is a classic cause of "the cluster just stopped working overnight," which is why monitoring certificate expiry belongs on every cluster's checklist.

NetworkPolicy as a complement to identity controls

NetworkPolicy is the complement to identity controls: RBAC answers "who may ask the API for what," while NetworkPolicy answers "which pods may actually send packets to which." A perfect RBAC setup still leaves pod-to-pod traffic wide open by default, and a perfect NetworkPolicy setup still leaves a stolen ServiceAccount token dangerous — defense in depth means both. The module's framing is deliberate: Module 3 taught you to write the policies; here you learn where they sit in the security architecture, next to authentication, authorization, admission control, and encryption. No single control carries the cluster; the layers do.

Learning objectives

  • Grant least-privilege access with RBAC Roles and Bindings.
  • Run workloads under dedicated ServiceAccounts.
  • Enforce Pod Security Standards and manage cluster TLS.
  • Audit overbroad grants such as cluster-admin bindings.

Hands-on labs

  1. Lab: Create a Role allowing pod reads in one namespace and bind it to a test user.

    1. Create a Role in a test namespace allowing only get and list on pods, and a ServiceAccount plus RoleBinding granting it to a test identity.
    2. Use that identity's kubeconfig to confirm pod reads succeed and that creating a deployment is forbidden.
    3. Record the exact error for the denied action — recognizing RBAC denials on sight is a core admin skill.

  2. Lab: Run a pod under a custom ServiceAccount and inspect its mounted token.

    1. Create a dedicated ServiceAccount, run a pod under it (set serviceAccountName in the pod spec), and exec into the pod.
    2. List the mounted token files at the standard service-account path and decode the token's claims enough to identify the account name.
    3. From inside the pod, curl the API server with the token and observe that its power matches exactly the RBAC you granted — nothing more.

  3. Lab: Enforce the restricted Pod Security Standard on a namespace and fix violations.

    1. Label a fresh test namespace to enforce the restricted Pod Security Standard.
    2. Deploy an ordinary pod that runs as root (the common default) and watch admission reject it; read the rejection message carefully.
    3. Fix the pod spec — non-root user, no privilege escalation, dropped capabilities — until it is admitted, and keep that spec as your hardened template.

  4. Lab: Approve a certificate signing request or rotate serving certificates in the lab.

    1. List CSRs in the cluster and inspect the certificates API objects; generate a test CSR and approve it manually.
    2. Alternatively, check kubelet certificate rotation status and the expiry dates on the API server certificates under /etc/kubernetes/pki.
    3. Write down the expiry dates you find and set a calendar reminder — this is the operational habit the lab is really teaching.

  5. Lab: List ClusterRoleBindings and identify any cluster-admin grants.

    1. Run kubectl get clusterrolebindings and identify every binding that grants cluster-admin; for each, decide whether the subject truly needs it.
    2. Check for the default bindings you didn't create and understand why each exists before touching anything.
    3. Document your findings as a mini audit report: subject, scope, justification or recommendation to narrow it.

Self-check questions

  • What is the difference between a Role and a ClusterRole?
  • Which binding type grants access across all namespaces?
  • Name one thing the restricted Pod Security Standard forbids.
  • Where does a ServiceAccount token appear inside a running pod?

Module 7

Troubleshooting Nodes, Pods, Control Plane, and Networking

kubectl describe, logs, and events as first-line tools

Troubleshooting Kubernetes starts with the same three commands every time: kubectl describe for the object's status, conditions, and recent events; kubectl logs for what the containers actually said; and kubectl get events for the cluster's narration of what just happened. Describe is the single highest-value command in the toolkit — the Events section at the bottom usually names the failure directly (FailedScheduling, FailedMount, ImagePullBackOff). The discipline is to read before guessing: the cluster almost always tells you what's wrong, and the administrator's edge is knowing where it wrote it down. Build the reflex — describe, logs, events — and half of all incidents resolve in minutes.

Node conditions: Ready, MemoryPressure, DiskPressure, PIDPressure

Node conditions are the node's self-reported health: Ready plus pressure signals for memory, disk, and PID exhaustion. A node reporting MemoryPressure or DiskPressure is telling you the kubelet is about to (or already is) evicting pods to protect itself, and the fix is at the resource level, not the pod level. NotReady with no pressure signals points at the kubelet or the node itself — check kubelet logs via journalctl and whether the node can reach the API server. Reading node conditions first prevents the classic waste of debugging pods when the floor they're standing on is the problem.

Static pod manifests and control-plane component logs

The control plane runs as static pods whose manifests live on disk at /etc/kubernetes/manifests, watched directly by the kubelet rather than the API server. When the API is down, you debug it like any other pod — except your kubectl may not work, so you go to the node and read the kubelet and container logs there. The signature failures are recognizable: certificate expiry (API serves nothing), etcd quorum loss (API reads fail), and manifest typos (the static pod crash-loops and the kubelet logs say why). Because the control plane is just pods with files, the recovery path is always files and logs on the control-plane node — no magic, just machinery.

CoreDNS and kube-proxy failure signatures

CoreDNS runs as ordinary pods behind a Service, which means DNS failures have the same signatures as any app failure: the pods might be down, the Service might have no endpoints, or the client's configuration might point at the wrong server. kube-proxy failures show up as Services that resolve but don't route — DNS answers, connections hang — because the forwarding rules on the node are stale or missing. The debugging order mirrors the architecture: confirm CoreDNS pods are Running, confirm the kube-dns Service has endpoints, then test resolution from a debug pod, then check kube-proxy's rules on the affected node. Naming each layer's failure signature in advance is what turns a DNS outage from panic into procedure.

Service selector mismatches and empty Endpoints

An empty Endpoints list on a Service means the selector matched zero pods — the routing table has nowhere to send traffic. The causes are a short, checkable list: the selector labels don't match any pod's labels (typo or drift), the pods exist but aren't Ready (failing readiness probes keep them out of endpoints), or the pods are in a different namespace than the Service. kubectl describe on the Service shows the selector; kubectl get pods --show-labels shows the candidates; the mismatch is usually visible in seconds. This is the single most common "my app is up but unreachable" bug, and the fix is always in the labels, never in the network.

Narrowing order: workload, node, network, control plane

When everything is broken at once, narrow in a fixed order: workload first (are my pods actually healthy?), then node (is the floor healthy?), then network (can packets move?), then control plane (is the brain healthy?). The order matters because each layer depends on the one below it — debugging pod scheduling while etcd has lost quorum is wasted motion. Within each layer, the rule from the first concept applies: describe, logs, events, then expand outward. A repeatable narrowing order is what separates administrators who flail from administrators who converge, and it is the real skill this module (and the exam's troubleshooting weight) is testing.

Learning objectives

  • Diagnose NotReady nodes and resource-pressure conditions.
  • Debug CrashLoopBackOff and Pending pods methodically.
  • Verify control-plane static pods and API availability.
  • Isolate DNS and Service networking faults.

Hands-on labs

  1. Lab: Cordon and drain a node, then debug a pod stuck Pending from insufficient resources.

    1. Cordon a worker node, then drain it, and create a pod with resource requests larger than any node can satisfy — it will sit in Pending.
    2. Run kubectl describe on the Pending pod and read the FailedScheduling event naming the exact shortfall.
    3. Uncordon the node, fix the requests, and watch the pod schedule: the loop of break, read, fix, verify is the whole method.

  2. Lab: Fix a CrashLoopBackOff by reading logs and correcting the container command.

    1. Deploy a container with a deliberately wrong command (for example, a binary name that doesn't exist) and watch it enter CrashLoopBackOff.
    2. Pull the previous container's logs to see the actual error, then fix the command and confirm the pod goes Running.
    3. Contrast with a bad image name: the error moves from container logs to the ImagePullBackOff event — two failures, two different evidence locations.

  3. Lab: Break a Service selector, confirm Endpoints empty, repair it, and retest.

    1. Edit a working Service's selector to a label no pod carries, then confirm kubectl get endpoints shows an empty list.
    2. From a client pod, show that DNS still resolves the Service name but connections fail — resolution without routing.
    3. Repair the selector, watch endpoints repopulate, and retest: the complete selector-mismatch lifecycle in five minutes.

  4. Lab: Investigate a NotReady node through kubelet logs and node conditions.

    1. Stop the kubelet on a worker node (in a lab!) and watch the node go NotReady after the grace period.
    2. Read the node conditions with kubectl describe node, then check the kubelet logs on the node itself with journalctl -u kubelet.
    3. Restart the kubelet, watch the node return to Ready, and note how the control plane rescheduled (or didn't) during the outage.

  5. Lab: Simulate a DNS failure and trace it to the CoreDNS pods.

    1. Scale the CoreDNS deployment to zero in a test cluster (lab only!) and observe pods failing name resolution while IPs still work.
    2. Restore CoreDNS, then break it differently: delete the kube-dns Service's endpoints by mislabeling the CoreDNS pods, and confirm resolution fails cluster-wide.
    3. Repair the labels and verify resolution returns — you have now seen both DNS failure signatures and know them apart.

Self-check questions

  • What are the first three commands for a pod stuck in Pending?
  • How do you distinguish a bad image from a bad command in CrashLoopBackOff?
  • What does an empty Endpoints list on a Service tell you?
  • Which log shows why a kubelet cannot register its node?
