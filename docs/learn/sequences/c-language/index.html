The sequence

What this sequence is, and how to work it.

What this is: a complete systems-programming study sequence for the C language, built from the public C language reference. It covers the full arc from source text to running program — the translation pipeline, pointers and dynamic memory, arrays and strings, structs and unions, file I/O, build tooling, debugging with gdb, and the discipline of undefined behavior — ending in a capstone that demands a sanitizer-clean, Makefile-built utility.

Who it is for: programmers who can already write code in some language and want the ground truth underneath — operating systems, embedded systems, high-performance computing, and anyone who wants to understand what higher-level languages are hiding. It is also the prerequisite foundation for the companion Modern C++ Engineering sequence.

Prerequisites: comfort with programming fundamentals (variables, loops, functions) in any language; a Linux or macOS machine (or WSL) with gcc, make, and gdb installed; willingness to read compiler errors as instruction rather than insult. No prior C experience is assumed.

How to use it: work the modules in order, and do the labs — C is not learned by reading about pointers. Compile everything with the full warning set from the start (-Wall -Wextra -Werror -std=c11 -pedantic), run every test under AddressSanitizer and UBSan, and keep a personal log of each bug the tools catch. The checkpoints are written to be answered in writing; the capstone is the proof.

Outcomes

What you will be able to do.

  • Explain the four stages of C translation and how the preprocessor, compiler, and linker cooperate to produce an executable.
  • Manage dynamic memory safely with malloc/calloc/realloc/free, and diagnose the classic lifetime bugs: leaks, double free, and use-after-free.
  • Use pointers, arrays, strings, structs, unions, and enums fluently while reasoning about object representation, alignment, and padding.
  • Build, debug, and harden small C programs with gcc flags, Makefiles, gdb, sanitizers, and a working knowledge of undefined behavior classes.

Module 1

The Translation Pipeline — From Source to Executable

Learning objectives

  • Describe the four logical translation phases: preprocessing, compilation to assembly, assembly to object code, and linking.
  • Use preprocessor directives (#include, #define, #ifdef, include guards) correctly and explain that inclusion is textual expansion.
  • Separate declarations from definitions across headers and source files to avoid multiple-definition linker errors.
  • Produce and inspect intermediate artifacts: preprocessed output (-E), assembly (-S), and object-file symbol tables (nm).

Key concepts

Translation phases: preprocessing, compilation, assembly, linking

A C program becomes an executable in four logical phases. The preprocessor handles directives (#include, #define, conditionals) as pure text manipulation. The compiler translates each preprocessed translation unit into assembly. The assembler turns assembly into object code — machine instructions plus a symbol table. The linker combines object files and libraries, resolves symbol references, and emits the executable.

You will invoke these phases separately throughout this sequence (gcc -E, -S, -c), because seeing the intermediate artifacts is the fastest way to stop thinking of compilation as magic. When a build breaks, knowing which phase broke tells you where to look.

The preprocessor is textual expansion

#include literally pastes the header's text into your file; #define performs token substitution before the compiler ever sees the code. There is no type checking, no scoping in the C sense — just text in, text out.

This explains entire classes of bugs: a macro argument with side effects gets evaluated multiple times because it is substituted multiple times, and an #include inside a function is legal (if horrifying) because by the time the compiler runs, it is just text. Run gcc -E once and the preprocessor's innocence — and danger — becomes obvious.

Include guards and the #pragma once idiom

Headers get included from multiple places, and without protection the same declarations would be pasted in twice, causing redefinition errors. The classic guard wraps the header in #ifndef HEADER_H / #define HEADER_H / #endif so the second inclusion expands to nothing.

#pragma once is the widely supported shorthand: one line at the top of the header, same effect, no symbol to invent. It is not part of the C standard, but every major compiler honors it; many codebases use both — guards for portability, pragma once for speed and simplicity.

Declarations versus definitions

A declaration says 'this thing exists, with this type' — extern int x; or int f(void);. A definition additionally creates it: int x = 0; or the full function body. Headers carry declarations; exactly one source file carries each definition.

This split is what makes separate compilation possible: every translation unit learns the shapes of things from declarations, and the linker later wires them to the single definition. The printf you call is declared in <stdio.h> and defined inside libc — you compile against the promise and link against the reality.

External vs internal linkage: extern and static

A file-scope name has external linkage by default: it is visible to the linker across translation units. Mark it static and it gets internal linkage — visible only within its own translation unit, invisible to the linker and to other files.

static at file scope is your encapsulation tool in C: helper functions and module-private variables marked static cannot collide with same-named symbols elsewhere and cannot be called from outside. Reach for it by default; use external linkage only for the deliberate public interface.

One definition per program for external symbols

If two translation units each define the same externally-linked symbol — two int counter = 0; at file scope — the linker must reject the program with a 'multiple definition' error, because it cannot know which one you meant. Exactly one definition must exist across the whole program.

This rule is the linker's only real job beyond copying bytes: matching every undefined reference to exactly one definition. Internalize it and linker errors stop being mysterious — they are always either zero definitions (undefined reference) or more than one (multiple definition).

Object files, symbol tables, and the linker's job

An object file (.o) is machine code plus a symbol table: a list of symbols it defines (marked T for text/code, D for data) and symbols it needs but does not define (marked U for undefined). The nm tool prints this table, and reading it is a core debugging skill.

The linker collects all object files, matches every U against a T or D somewhere, lays out the final memory image, and writes the executable. When it complains, nm on your .o files shows you exactly which side of the contract is broken.

Static libraries and link order basics

A static library (.a) is just an archive of object files. The linker pulls from it only the members needed to satisfy currently-undefined symbols — which is why order matters: put -lfoo after the object files that need it, because the linker processes inputs left to right and will not go back.

The classic symptom is 'undefined reference to sqrt' when -lm comes before your .o files. The fix is never to add flags randomly; it is to understand that the linker is a single left-to-right pass and order your inputs accordingly.

Hands-on labs

  1. Lab 1 — Compile in stages. Write a two-file program (main.c calling add(), declared in calc.h and defined in calc.c). Compile each file with gcc -c, link the .o files manually, then run nm on each object file and identify which symbols are defined (T/D) versus undefined (U).
  2. Lab 2 — See the preprocessor's output. Run gcc -E on a file that includes <stdio.h> and pipe it to wc -l to see how much text one include pulls in. Then write a small header with and without an include guard, include it twice from one .c file, and observe the compile error the unguarded version produces.
  3. Lab 3 — Provoke the linker. Deliberately place a non-static function definition in a header included by two .c files, link them, and record the linker's 'multiple definition' error verbatim. Fix it by moving the definition into exactly one .c file and leaving only the declaration in the header.
  4. Lab 4 — Read assembly. Compile a simple program with gcc -S -O0 and read the generated .s file: find the function label, the prologue, a call instruction to a library function, and the return sequence. Annotate each in a comment.

Self-check questions

  1. Without compiling: two files, a.c and b.c, each contain 'int counter = 0;' at file scope and both are linked into one program. State what the linker will do and why, then build it to verify your prediction.
  2. Explain in your own words why a declaration may appear in many translation units while a definition must appear in exactly one, and name one example of each from the C standard library (for instance, the printf declaration in <stdio.h> versus its definition inside libc).

Module 2

Pointers and Dynamic Memory

Learning objectives

  • Explain what a pointer value is (an address plus a type) and how pointer arithmetic scales by the size of the pointed-to type.
  • Allocate, reallocate, and free heap memory with malloc/calloc/realloc/free, checking every allocation for failure.
  • Distinguish automatic, static, and allocated storage durations and predict how long each object lives.
  • Implement ownership conventions (who allocates, who frees) that prevent leaks, double frees, and use-after-free.

Key concepts

Pointers as typed addresses: & and *

A pointer is an address plus a type. The type is not decoration — it tells the compiler how many bytes live at that address and how to interpret them. int *p means 'p holds the address of an integer'; &x takes an address, *p follows it.

Because the type rides along, dereferencing the wrong pointer type silently reinterprets memory. Every pointer bug in C is, at bottom, a disagreement between the type the pointer claims and the bytes actually there.

Pointer arithmetic scales by the pointed-to type

p + 1 does not add one byte — it adds sizeof(*p) bytes, moving to the next element of whatever p points to. This is what makes pointers usable as array iterators, and it is why pointer arithmetic on void* is forbidden: without a pointed-to type there is no scale.

Internalize the scaling rule and two things become obvious: why (p+1)-p is 1 regardless of type, and why casting a byte buffer to a wider type and then doing arithmetic is a classic alignment trap.

void* as a generic address carrier; NULL and null-pointer constants

void* is C's generic pointer: it can hold any object pointer, and any object pointer converts to it implicitly. malloc returns void* for exactly this reason — the caller supplies the type by assigning it to a typed pointer.

NULL (or plain 0 in pointer context) is the null pointer constant: a pointer value guaranteed to compare unequal to any valid object address. Dereferencing it is undefined behavior and on most systems a segfault — which is the kindest possible outcome, because at least it is loud.

Storage durations: automatic, static, allocated

Objects live in one of three durations. Automatic: local variables, born at block entry, dead at block exit — returning their address is a classic bug. Static: globals and static locals, alive for the whole program. Allocated: malloc'd memory, alive from allocation until free — its lifetime is entirely your responsibility.

Most C bugs are lifetime bugs wearing other disguises. When something crashes, ask first: is this object still alive? The three durations give you exactly three possible answers.

malloc / calloc / realloc / free semantics and failure handling

malloc(n) returns n uninitialized bytes or NULL on failure; calloc(k, n) returns k*n zeroed bytes; realloc resizes (possibly moving) an allocation; free releases it. Every one of these can fail or be misused, and 'can' means 'will, in production, at 3 AM.'

The discipline is non-negotiable: check every allocation for NULL before use, and treat an unchecked malloc as a bug even if it 'works.' calloc's zeroing matters whenever the memory will be read before it is fully written — strings, structs with padding, arrays used as accumulators.

The safe realloc idiom: temporary first, NULL check before assignment

realloc can fail and return NULL — and if you wrote p = realloc(p, n), that NULL just overwrote your only handle to the still-valid old block: a leak and a lost pointer in one line. The safe idiom assigns to a temporary: tmp = realloc(p, n); if (!tmp) { handle the failure, p is still valid }; p = tmp.

This is the single most valuable three-line pattern in C memory management. Write it from muscle memory, every time.

Dangling pointers, double free, use-after-free

A dangling pointer points at memory whose lifetime ended — a freed block or a dead stack frame. Using it is use-after-free; freeing it again is double free. Both are undefined behavior, both are exploitable, and both are silent until they are catastrophic.

The defenses are boring and effective: set pointers to NULL after freeing (so a second free is a safe no-op and a use crashes loudly), establish who owns each allocation, and run every test under AddressSanitizer, which catches all three with precise diagnostics.

Ownership conventions: who allocates, who frees

Every allocation needs a documented owner: the function that allocates either frees it, or transfers ownership to its caller, and the convention must be written down — in the function's contract comment, not in anyone's head. const-qualified pointers (const char *) are part of this: they advertise 'I will not modify or take ownership of this.'

C has no garbage collector and no borrow checker, so ownership conventions are the memory-safety system. The capstone README will ask you to state yours explicitly; start practicing the habit in every function you write from this module on.

Hands-on labs

  1. Lab 1 — Allocate and free cleanly. Write a program that reads a size from stdin, validates it (reject zero, negative, and absurd values), allocates an int array with malloc, fills and prints it, then frees it. Compile with -Wall -Wextra and fix every warning before running.
  2. Lab 2 — Growable vector. Implement a growable vector of double using realloc with doubling growth, using the safe temporary idiom. Write a test driver that pushes 1,000 values and then frees everything; confirm with a comment where each allocation is released.
  3. Lab 3 — Meet the sanitizer. Write two small buggy programs: one that leaks memory in a loop and one that calls free twice on the same pointer. Build both with -fsanitize=address and record the exact diagnostic each report gives you — learn what ASan output looks like before you need it.
  4. Lab 4 — The dangling local. Write a function that returns a pointer to a local variable. Compile without -w, read the -Wreturn-local-addr warning, then fix the design by switching to caller-provided storage and explain why that fix is correct.

Self-check questions

  1. Given 'int *p = malloc(4 * sizeof *p);' explain in writing why 'sizeof *p' is more maintainable than 'sizeof(int)', then change the allocation to zero-initialized memory with calloc and justify when zero-initialization matters.
  2. Run your Lab 2 vector under AddressSanitizer with a driver that pushes 10,000 elements and pops them all: it must report zero errors, and you must be able to point at the exact line where each allocation is released.

Module 3

Arrays and Strings

Learning objectives

  • Explain when an array decays to a pointer and when it does not (sizeof, unary &, string-literal initialization).
  • Manipulate C strings as NUL-terminated char arrays using <string.h> safely, with bounded operations and explicit length checks.
  • Compare stack arrays, variable-length arrays, and heap arrays, and choose correctly for a given size and lifetime.
  • Write functions that take array parameters together with explicit size arguments instead of trusting a bare pointer.

Key concepts

Array-to-pointer decay and its three exceptions

In most expressions, an array name 'decays' to a pointer to its first element — which is why arrays and pointers feel interchangeable. But there are exactly three exceptions where the array stays an array: as the operand of sizeof, as the operand of unary &, and when initializing a char array from a string literal.

The checkpoint's hand-trace is the whole rule in miniature: sizeof(a) is 10 (array, no decay), sizeof(p) is 8 (pointer), &a is a pointer to the whole array, a+1 steps one char, &a+1 steps ten. Memorize the three exceptions and decay stops being mysterious.

sizeof on arrays versus on pointers

sizeof(array) is the total bytes of the array; sizeof(pointer) is the size of the address itself, regardless of what it points to. This is why a function receiving char *s cannot learn the array's length with sizeof — the decay already happened at the call boundary.

The engineering consequence: array length must travel with the pointer as a separate argument. Every function in this sequence that takes an array parameter will also take an explicit size — no exceptions.

String literals live in read-only storage; char arrays are writable copies

char *s = "literal"; points s at the string literal, which typically lives in read-only memory — writing through s crashes. char a[] = "literal"; instead copies the characters into a writable array you own.

The lab where you write s[0] = 'x' and watch it die exists to burn this into reflex. If a string might ever be modified, it must be an array (or heap memory), never a bare pointer to a literal.

NUL terminator discipline and off-by-one sizing

C strings end at the first '\0', and every string of length n needs n+1 bytes of storage. Forgetting the +1 is the most common off-by-one in C — strlen returns the length excluding the terminator, so allocation must always be strlen(s) + 1.

Treat the terminator as a first-class citizen: every copy, every concatenation, every buffer size calculation must account for it explicitly. The day you stop adding +1 'just in case' and start adding it because the terminator is real data is the day your string code gets reliable.

Bounded string functions and their pitfalls

strcpy and strcat do not know your buffer's size — they are the historical source of countless overflows. The bounded family (strncpy, strncat, snprintf) takes a size, but each has its own trap: strncpy does not NUL-terminate if the source is too long, and strncat's size argument means 'space remaining,' not 'total buffer size.'

The safe habit: prefer snprintf for formatting (it always terminates and reports truncation), and when you use strncpy, follow it with an explicit buf[n-1] = '\0'. Never trust a bounded function to do the terminating for you unless you have verified its contract.

snprintf as the safe formatting workhorse

snprintf(buf, sizeof buf, fmt, ...) writes at most sizeof buf - 1 characters plus the terminator, always terminates, and returns the number of characters that would have been written — letting you detect truncation. It replaces sprintf, strcat chains, and most manual string assembly.

Make snprintf your default for building strings. Its return value is the truncation detector: if it is >= the buffer size, you know output was cut and can handle it (bigger buffer, error, log) instead of silently corrupting.

Multidimensional arrays are row-major contiguous blocks

int m[3][4] is one contiguous block of 12 ints in row-major order — row 0's four elements, then row 1's, and so on. m[i][j] is exactly *(m[0] + i*4 + j); there is no array of pointers unless you build one.

This matters when you pass 2D arrays to functions (all dimensions but the first must be declared so the compiler knows the row stride) and when you reason about cache behavior: iterating row-major matches the layout, column-major fights it.

Variable-length arrays: convenience versus stack-overflow risk

C99 variable-length arrays (int buf[n];) size a stack array at runtime — convenient, but the allocation is unchecked: a large or hostile n blows the stack with no error return to test. VLAs are optional in C11 for exactly this reason.

The rule: VLAs for small, bounded, trusted sizes only. Anything user-controlled or potentially large goes on the heap with malloc, where failure is detectable. Convenience is not worth an uncatchable crash.

Hands-on labs

  1. Lab 1 — sizeof laboratory. Write a program that prints sizeof for 'char buf[64];' and for a 'char *p' pointing at it. Explain the different results in a code comment stating the decay rule precisely.
  2. Lab 2 — Safe line reader. Implement fgets into a fixed buffer, detect a missing newline to grow the buffer dynamically, and handle EOF. Test on a 10 KB single-line input and on an empty file — both must work.
  3. Lab 3 — Bound the unbounded. Take a program using strcpy/strcat and rewrite it with snprintf/strncat using explicit size math. Construct a test input where the unbounded version overflows and show the bounded version truncating safely instead.
  4. Lab 4 — The read-only literal. Write 'char *s = "literal"; s[0] = 'x';', build and run it, observe the crash, then fix it by declaring a writable char array instead. Write down what the crash taught you.

Self-check questions

  1. Hand-trace this: 'char a[10]; char *p = a;'. List which of sizeof(a), sizeof(p), &a, a+1, and &a+1 differ from each other and why. Verify with a small printing program.
  2. Write a function 'void reverse(char *s)' that reverses a string in place using no <string.h> calls except strlen, then prove it handles the empty string and a single-character string correctly.

Module 4

Structs, Unions, and Enums

Learning objectives

  • Define structs, use the . and -> operators, and initialize with designated initializers and compound literals.
  • Predict struct size and member offsets from alignment rules, and reorder members to minimize padding.
  • Use unions for space-efficient variant storage and apply the tagged-union discipline to access them safely.
  • Model state machines and option sets with enums and apply integer-promotion rules correctly.

Key concepts

struct layout: member order, alignment, and padding

Struct members are laid out in declaration order, but each member must start at an address that is a multiple of its alignment requirement — so the compiler inserts invisible padding bytes between members and possibly at the end. struct { char a; int b; char c; } is typically 12 bytes, not 6.

This is why member order matters: grouping members by descending alignment (doubles, then ints, then chars) minimizes padding. The checkpoint's reorder exercise — char, char, int, double versus the scattered original — makes the savings concrete and measurable.

offsetof and reasoning about member addresses

The offsetof macro (from <stddef.h>) gives the byte offset of a member within its struct — the tool for reasoning about layout without guessing. Combined with sizeof, it lets you verify your hand-computed layouts against reality.

Use offsetof whenever you serialize structs, compute field positions in binary formats, or argue about padding in a code review. 'I measured it' beats 'I think the compiler does' every time.

Designated initializers and compound literals

Designated initializers (.x = 1, .y = 2) initialize struct members by name instead of position — immune to member reordering and self-documenting. Unmentioned members are zero-initialized, which is often exactly what you want.

Compound literals ((struct Point){.x=1, .y=2}) create an unnamed object on the fly, perfect for passing a struct by value to a function without declaring a temporary. Together they make struct-heavy code dramatically more readable.

Anonymous structs and unions (C11)

C11 allows a struct or union to be nested anonymously inside another struct, promoting its members to the enclosing scope: you write s.x instead of s.inner.x. It is syntactic sugar — the layout is identical to the named version.

Use it sparingly, for cases where the nesting adds no information (a point's x/y inside a rect). Overuse creates confusing scope flattening; the feature exists to reduce noise, not structure.

Unions as space-efficient variant storage; tagged unions

A union stores its members overlapping in the same memory — its size is the size of the largest member. It is the right tool when exactly one of several alternatives is live at any time, saving the space the alternatives would waste.

The danger is reading the wrong member: without discipline, nothing records which alternative is current. The tagged-union discipline adds a kind field (usually an enum) that is always set on write and always checked on read — the union becomes safe, at the cost of a few bytes for the tag.

Enums: named integer constants, promotion rules, state machines

Enums give names to integer constants — states, options, error codes — with the compiler assigning values from 0 unless you specify. Enum values promote to int in expressions, which keeps arithmetic simple but means the compiler will not stop you from mixing enum types.

Their highest-value use is state machines: an enum for the states, a transition function switching on (state, input), and the compiler warning you about unhandled cases. The word-counter lab is the canonical first example.

Bit-fields: what they guarantee and why they are non-portable

Bit-fields (unsigned x : 3;) pack members into sub-word storage — useful for hardware registers and wire protocols where every bit counts. The standard guarantees the packing is tight, but not the order of bits, the layout of straddling fields, or much else.

Consequence: bit-fields are fine for memory savings inside one program compiled by one compiler, but never for data exchanged across compilers, platforms, or the network. For wire formats, use explicit shifts and masks — verbose, but portable by construction.

Flexible array members for variable-length trailing data

A struct ending in char data[]; (no size) is C99's sanctioned way to model variable-length trailing payloads: allocate sizeof(struct) + payload bytes in one malloc, and data behaves as an array of exactly the size you allocated.

One allocation means one free, no pointer chasing, and cache-friendly locality — the classic packet-header pattern. The rules: the flexible member must be last, the struct cannot be copied by value meaningfully, and sizeof excludes the flexible part.

Hands-on labs

  1. Lab 1 — Measure the padding. Define 'struct { char a; double b; char c; int d; }', print sizeof and offsetof of each member, then reorder to 'char, char, int, double' and compare: compute the bytes saved and explain where the padding went.
  2. Lab 2 — Tagged union. Implement a tagged union 'Value' with an int kind field and a union of { long i; double d; char *s; }. Write make/print/free functions that switch on kind, freeing the string member only when kind says it is a string — and prove a misuse is caught.
  3. Lab 3 — Enum state machine. Build an enum-driven word counter with states START, IN_WORD, IN_SPACE, fed character by character through a transition function. Test on empty input, all-spaces, and words with multiple separators.
  4. Lab 4 — Flexible array member. Model a variable-length packet with a flexible array member struct: allocate with a single malloc of sizeof(struct) + payload bytes, write the payload, read it back, and free once.

Self-check questions

  1. On a typical 64-bit ABI, compute by hand the sizeof and each member offsetof for 'struct { char a; int b; char c; }', then verify with a program that prints offsetof for all three members.
  2. Explain in writing why reading a union member other than the one most recently stored is fragile, and describe the tagged-union discipline (a kind field checked before every access) that makes unions safe.

Module 5

File I/O

Learning objectives

  • Open, read, write, and close files with the <stdio.h> stream API, checking every call for failure.
  • Distinguish text versus binary mode, buffered versus unbuffered I/O, and line-oriented versus block-oriented reads.
  • Handle I/O errors robustly: check ferror/feof, report with perror/strerror, and never treat a short read as EOF.
  • Use file positioning (fseek/ftell/rewind) and write streaming programs that handle files larger than RAM.

Key concepts

FILE* streams and fopen modes

fopen(path, mode) returns a FILE* stream or NULL on failure — always check. The mode string selects read (r), write (w, truncating), append (a), update (+) for read-write, and binary (b). Text versus binary mode matters on some platforms (newline translation); on POSIX they are identical, but write the b anyway when the data is binary — it documents intent and is portable.

Opening with the wrong mode is a silent logic bomb: w destroys existing content, r fails on missing files, a never lets you overwrite. Choose the mode by stating what the program must do if the file already exists.

Buffering: fully buffered, line buffered, unbuffered

Streams buffer I/O for performance: fully buffered (blocks flushed when full — files), line buffered (flushed per newline — terminals), unbuffered (every write goes through — stderr). setvbuf lets you change the policy; fflush forces a flush.

Buffering explains 'my output didn't appear': a crashed program loses its unflushed buffers, and interleaved stdout/stderr look out of order because one is buffered and the other is not. When debugging output mysteries, ask about buffering before anything else.

fgets versus fread/fwrite: line-oriented vs block I/O

fgets reads one line (stopping at newline or buffer-full) and is the right tool for text; fread/fwrite move raw byte blocks and are the right tool for binary data and bulk copies. Mixing them on one stream without repositioning is asking for confusion.

The line-oriented/block distinction drives the capstone's design: streaming text processing uses fgets-style line reads, while the binary record lab uses fread with fseek. Pick the API that matches the data's shape.

The feof/ferror discipline: the read controls the loop

feof reports that a previous read hit end-of-file — it does not predict the next read. while (!feof(f)) processes one phantom extra iteration because feof only becomes true after a read fails. The correct loop tests the read itself: while (fgets(buf, sizeof buf, f) != NULL).

After the loop, feof versus ferror tells you why it stopped: clean EOF or an I/O error. Programs that never check ferror silently treat disk errors as end-of-file — data loss wearing an EOF costume.

errno, perror, and strerror

When a library call fails, it typically returns an error indicator and sets errno to a code naming the failure. perror(msg) prints your message plus the human-readable errno string to stderr; strerror(errno) gives you the string for logging or formatting.

The pattern is: check the return, then immediately capture errno (later calls can overwrite it), then report with context — which file, which operation. 'fopen failed: No such file or directory' is a diagnosis; a bare 'error' is a shrug.

Format-string safety

printf(user_string) is a vulnerability, not a shortcut: if the string contains % sequences, printf interprets them as format specifiers, reading (or writing, with %n) arbitrary stack memory. The compiler's -Wformat-security warning exists specifically to catch this.

The fix is printf("%s", user_string) — the format string is always a literal you control; user data is always an argument. This rule has no exceptions, and the lab where you trigger the warning exists so you recognize the pattern in other people's code.

File positioning: fseek, ftell, rewind, fgetpos/fsetpos

fseek moves the stream position (by bytes from start/current/end), ftell reports it, rewind resets to the start, and fgetpos/fsetpos handle positions portably for large files. Together they turn a stream into a random-access device.

The record-seek lab is the canonical use: fseek(f, 500 * sizeof(record), SEEK_SET) jumps straight to record 500 with no reading in between. Positioning plus fixed-size records is a tiny database; positioning on text files is fragile because line lengths vary.

Streaming design: files larger than RAM in constant memory

The capstone's headline requirement — process a 1 GB file in constant memory — is a design discipline, not a trick: read a chunk, process it, emit results, discard the chunk. No step may retain the whole input.

This rules out slurp-the-file-into-memory and forces the patterns this module teaches: line-at-a-time or block-at-a-time processing, incremental aggregation (the hash table grows with distinct words, not input size), and output written as you go. If memory grows with input size, the design is wrong.

Hands-on labs

  1. Lab 1 — wc clone. Write a wc-like tool counting bytes, words, and lines from stdin or a named file. Test on: an empty file, a file with no trailing newline, and a 1 GB generated file — confirming constant memory use with /usr/bin/time -v.
  2. Lab 2 — Random access. Write 1,000 fixed-layout records to a binary file with fwrite, then read back record #500 by seeking to offset 500 * sizeof(record). Verify the contents match what you wrote, byte for byte.
  3. Lab 3 — Copy with verification. Write a file-copy program using fread/fwrite with a 64 KB buffer; compare sha256sum of source and copy, then extend the program to correctly handle a short write from fwrite (loop until all bytes are written).
  4. Lab 4 — Format-string warning. Write a program that passes a user-supplied string as the printf format argument, observe the -Wformat-security warning, then fix it with "%s" and confirm the warning disappears.

Self-check questions

  1. Explain the bug in 'while (!feof(f)) { fgets(buf, sizeof buf, f); process(buf); }', rewrite the loop so the read itself controls iteration, and test both versions on a file whose last line has no trailing newline.
  2. Write a function that safely replaces a file's contents: write to a temporary file, fflush, then rename it over the original. Explain in writing why each step matters for crash safety.

Module 6

Build Tooling — gcc Flags and make

Learning objectives

  • Compile and link multi-file projects from the command line with explicit -c, -o, -I, -L, and -l steps in the correct order.
  • Use warning and language-standard flags (-Wall -Wextra -Werror -std=c11 -pedantic) and explain what each major class catches.
  • Write a Makefile with targets, prerequisites, recipes, variables, and pattern rules, and explain the TAB-before-recipe rule.
  • Apply -g, optimization levels, and sanitizers (-fsanitize=address,undefined) as a standard debug and hardening workflow.

Key concepts

Separate compilation: -c, then link

gcc -c compiles one source file to one object file without linking; a later gcc invocation links the objects. This is separate compilation, and it is what makes large projects buildable: change one file, recompile one object, relink.

The build labs drill this until it is reflex, because every build system — make, CMake, or otherwise — is automation around exactly these two steps.

-I, -L, and link order: -l after the objects that need it

-I adds header search paths for the compiler; -L adds library search paths for the linker; -lfoo links libfoo. And because the linker processes inputs left to right, libraries come after the object files that reference them.

'undefined reference to sqrt' with -lm present almost always means -lm was placed before the objects. The fix is ordering, not more flags — understand the single-pass linker and this error becomes a thirty-second fix forever.

Warning flags: -Wall -Wextra -Werror; standards: -std=c11 -pedantic

-Wall and -Wextra enable the warning families that catch real bugs (unused variables, suspicious comparisons, missing cases); -Werror promotes warnings to errors so they cannot be ignored. -std=c11 -pedantic pins the language dialect and rejects non-standard extensions.

This combination is the sequence's mandatory baseline — the capstone requires building clean under it. Warnings are the compiler telling you about bugs it can already see; -Werror is you agreeing to listen.

-g versus optimization levels

-g embeds debug information (variable names, line mappings) for gdb; optimization levels -O0 through -O3 (and -Os for size) trade compile time and debuggability for runtime speed. -O0 compiles fast and debugs faithfully; -O2 is the standard 'ship it' level.

The standard practice from Module 7: debug at -O0, ship at -O2, and never try to make sense of 'optimized out' variables when you could just rebuild without optimization.

Sanitizers as standard workflow: -fsanitize=address,undefined

AddressSanitizer instruments memory accesses to catch overflows, use-after-free, and leaks at runtime with precise reports; UndefinedBehaviorSanitizer catches signed overflow, misaligned access, null dereference, and the other UB classes from Module 8. The cost is roughly 2x slowdown — irrelevant during development.

Treat sanitizer builds as a second compiler you always run: the labs require ASan+UBSan-clean runs because tests that pass without sanitizers routinely hide memory bugs. A green test suite plus a clean sanitizer run is the actual definition of 'works.'

Make: targets, prerequisites, recipes; $@ $< $^

A Makefile rule reads 'target: prerequisites' followed by TAB-indented recipes. The automatic variables compress the common cases: $@ is the target name, $< is the first prerequisite, $^ is all prerequisites. A compile rule becomes '$(CC) $(CFLAGS) -c $< -o $@' — generic across every source file.

The TAB-before-recipe rule is make's most infamous gotcha: spaces do not work, and the error message ('missing separator') never says so plainly. Now you know.

Pattern rules, variables, .PHONY

Pattern rules (%.o: %.c) say how to build any object from its source, so you write the compile logic once. Variables (CC, CFLAGS) centralize toolchain choices. .PHONY marks targets like clean and all that are not files, so make runs their recipes even if a file named 'clean' exists.

These three features turn a Makefile from a list of commands into a maintainable build description — and they are exactly what the capstone Makefile must demonstrate.

Incremental rebuilds: why make rebuilds only what changed

make compares timestamps: a target rebuilds only if a prerequisite is newer than it. Touch one .c file and only its .o recompiles, then the program relinks — on a large project this is the difference between a two-second and a twenty-minute build.

The corollary: if make rebuilds everything every time, something is wrong with your dependency declarations (often a missing header dependency). Correct prerequisites are what make incremental builds trustworthy.

Hands-on labs

  1. Lab 1 — Three ways to build. Take a three-file project and build it three ways: a single gcc invocation, manual 'gcc -c' steps plus an explicit link, and a Makefile you write. Confirm all three produce identical program behavior.
  2. Lab 2 — Pattern rules and incrementals. Write a Makefile with a '%.o: %.c' pattern rule, CC/CFLAGS variables, and a .PHONY clean target. Touch one .c file and demonstrate that only its .o rebuilds before relinking.
  3. Lab 3 — Warning-zero. Take a warning-laden program and iterate with '-Wall -Wextra -Werror -std=c11 -pedantic' until it builds clean. Keep a log of each warning fixed and what it was telling you — this log is a personal bug taxonomy.
  4. Lab 4 — Sanitizers then optimization. Build your Module 2 vector program with '-fsanitize=address,undefined -g', run your test driver, fix every report, then rebuild with '-O2 -DNDEBUG' and compare runtime on a large input. Note what changed and what did not.

Self-check questions

  1. Given the link error 'undefined reference to sqrt', state the exact fix and explain why '-lm' must appear after the object files on the gcc command line.
  2. From memory, write a minimal correct Makefile for main.c + util.c + util.h with separate debug (CFLAGS_DEBUG) and release (CFLAGS_RELEASE) flag sets, then verify it builds both.

Module 7

Debugging with gdb

Learning objectives

  • Build with -g and drive gdb through its core workflow: run, break, next/step/finish, continue, print, backtrace.
  • Inspect memory directly with the x command, watch variables with watchpoints, and examine frames and locals.
  • Debug crashes: obtain a backtrace from a segfault, identify the faulting line, and distinguish null dereference from heap corruption.
  • Combine gdb with core dumps and sanitizer output to localize bugs faster.

Key concepts

Debug info with -g; -O0 is the debugging optimization level

-g embeds the mapping between machine code and your source — variable names, types, line numbers — that gdb reads. Without it you are debugging assembly with no symbols.

-O0 (no optimization) keeps the generated code in one-to-one correspondence with your source: variables live where you expect, lines execute in order. Higher optimization levels reorder, eliminate, and merge — great for shipping, actively hostile to debugging. Rebuild at -O0 before you reach for gdb; the ten seconds it costs saves hours of confusion.

Core workflow: break, run, next, step, finish, continue

break sets a breakpoint at a line or function; run starts the program; next executes one line (stepping over calls); step descends into a call; finish runs to the end of the current function; continue resumes until the next breakpoint. These six commands cover ninety percent of debugging sessions.

The rhythm is: break where it goes wrong, run to get there, then next/step through the suspect code watching state change. Everything else in gdb is specialization of this loop.

Inspecting state: print, x, info locals, info args

print expr evaluates any C expression in the current context — variables, dereferences, even function calls (carefully). info locals and info args dump the current frame's variables. x (examine) reads raw memory: x/16xb p shows sixteen bytes in hex at p.

When the bug is 'wrong value,' print finds it. When the bug is 'memory is corrupt,' x finds it. Learn the x format letters (x hex, d decimal, s string, i instruction) — they turn gdb from a variable-watcher into a memory microscope.

Backtraces and frames: bt, frame N, up/down

A segfault's first question is 'how did I get here?' — bt (backtrace) answers with the full call stack. frame N jumps to any frame; up/down move between them; then print and info locals inspect that frame's world.

Most crashes are solved in the backtrace: the faulting line is visible, and one frame up is usually the caller that passed the bad argument. The checkpoint's frame exercise builds the habit of reading the stack before reading the code.

Watchpoints: stopping when a variable changes

A watchpoint stops the program whenever a watched memory location is written — the tool for 'something corrupts this variable and I don't know what.' Set it on the victim, continue, and gdb halts at the exact instruction doing the corrupting.

Use watchpoints for heap corruption and mysterious state changes; they are slower than breakpoints (the debugger single-steps checking the location), so watch one variable at a time and only around the suspect region.

Conditional breakpoints for iteration-999 bugs

break foo.c:42 if i == 999 stops only when the condition holds — essential when a loop misbehaves on one iteration out of a thousand. Without the condition you would press continue 999 times; with it, you land directly on the crime.

The silent-logic-bug lab exists to make this reflex: when the failure is data-dependent, the breakpoint must be too.

Core dumps: ulimit -c, loading a core without re-running

A core dump is the program's memory at the moment of death, written to disk. Enable with ulimit -c unlimited, then gdb ./prog core gives you the backtrace and full state without re-running — invaluable when the crash is rare or the environment is gone.

Post-mortem debugging is a production skill: the crashed process on a customer machine cannot be re-run under your debugger, but its core can be analyzed on yours. Always know how to get a core from your systems.

Sanitizer output plus gdb: two tools, one workflow

ASan/UBSan reports tell you what went wrong and the exact stack trace; gdb lets you explore the live state around it. The combined workflow: reproduce under the sanitizer, note the faulting line, then re-run under gdb with a breakpoint just before it to inspect the state that led there.

Neither tool replaces the other. Sanitizers find bugs your eyes miss; gdb explains bugs the sanitizer only points at. The capstone README asks you to document one real bug found this way — start collecting candidates in these labs.

Hands-on labs

  1. Lab 1 — Segfault under gdb. Write a program with an off-by-one write past a stack array that segfaults. Run it under gdb, capture the backtrace, identify the faulting line and variable values, then fix the bug and confirm the fix.
  2. Lab 2 — Use-after-free with a watchpoint. Set a breakpoint after free(), place a watchpoint on the pointer variable, and step through to observe the stale access. Fix it with the set-pointer-to-NULL-after-free discipline and show the watchpoint no longer fires.
  3. Lab 3 — Core dump post-mortem. Enable core dumps ('ulimit -c unlimited'), crash a program, then load the core file in gdb and produce the backtrace without re-running the program. Write down the exact commands.
  4. Lab 4 — The silent logic bug. Debug a wrong-output-no-crash bug using a conditional breakpoint that stops only on the failing iteration of a 1,000-record loop. Record the condition you used and what it revealed.

Self-check questions

  1. From a gdb backtrace of a three-deep call stack, use 'frame N' and 'info locals' to identify which frame holds the buggy variable and display its value. Do this on your Lab 1 crashing program.
  2. Explain in writing why debugging at -O2 shows 'optimized out' variables and jumping line numbers, and state the standard practice: debug at -O0, ship at -O2.

Module 8

Undefined Behavior and Safe-Coding Discipline

Learning objectives

  • Define undefined behavior and explain why the compiler is permitted to assume it never happens, with optimization consequences.
  • Recognize the major UB classes: invalid dereference, out-of-bounds access, use-after-free/double-free, signed integer overflow, uninitialized reads, data races, strict-aliasing violations, and unsequenced modifications.
  • Use UBSan, ASan, compiler warnings, and static analysis to detect UB during development instead of in production.
  • Apply safe-coding discipline: initialize at declaration, validate all inputs, bound every loop and copy, check every fallible call, prefer size-aware APIs.

Key concepts

Three behavior classes: undefined, unspecified, implementation-defined

The standard sorts edge cases into three buckets. Undefined behavior (UB): the standard imposes no requirements — anything may happen, including appearing to work. Unspecified: the implementation must pick some behavior but need not document it (e.g., order of function argument evaluation). Implementation-defined: the implementation must pick and document it (e.g., sizeof(int)).

The checkpoint's classification drill is the whole taxonomy in five cases: (a) undefined — unsequenced modification; (b) unspecified — argument order; (c) implementation-defined — documented by your compiler; (d) undefined — null dereference; (e) undefined — shift by the width. Only (c) is portable-by-documentation.

The compiler may assume UB never happens — and optimizes on that assumption

This is the deep reason UB is dangerous: the optimizer is permitted to reason 'this program has no UB, therefore...' and transform code accordingly. A null check after a dereference can be deleted (dereferencing null would be UB, so the pointer 'must' be non-null). Signed overflow 'cannot happen,' so a + b > a folds to true.

The result: UB does not just crash — it makes the compiler generate code for a different program than the one you wrote, and the miscompilation changes with optimization level. 'Works at -O0, breaks at -O2' is the signature scent of UB.

Major UB classes: bad dereference, out-of-bounds, lifetime, signed overflow

The greatest-hits list: dereferencing null or invalid pointers; reading/writing past object bounds; lifetime errors (use-after-free, double free, returning stack addresses); signed integer overflow; reading uninitialized memory; data races; modifying a variable twice between sequence points (x = x++); strict-aliasing violations.

You have met most of these in earlier labs — deliberately. This module names the family they belong to and explains why the sanitizer reports you collected are not style suggestions but correctness verdicts.

Uninitialized reads, data races, modifying twice between sequence points

Reading uninitialized memory is UB even if you 'just' get garbage — the value is indeterminate and the compiler may exploit that. Data races (unsynchronized concurrent access with a write) are UB in the language model, not merely a timing hazard. And x = x++ is UB because the standard does not sequence the two modifications — there is no 'order it happens in' to rely on.

The common thread: in each case the programmer assumes an operational detail the standard deliberately leaves open, and the optimizer is free to disagree with the assumption.

Strict aliasing and effective type

The compiler may assume that pointers of different types do not point to the same memory (with narrow exceptions like char*), and it reorders and caches accesses based on that assumption. Writing through int* and reading through float* violates the rule — at -O0 it 'works,' at -O2 the read can return a stale cached value.

The fixes are memcpy (the blessed type-punning tool — modern compilers optimize it away) or a union. The lab's -O0/-O2 comparison makes the abstract rule viscerally concrete.

Detection tooling: UBSan, ASan, -Wall -Wextra, -fanalyzer

UBSan (-fsanitize=undefined) instruments the classic UB classes and reports them at runtime with file and line. ASan covers the memory-safety subset. -Wall -Wextra catch several at compile time (-Wsequence-point flags x = x++). GCC's -fanalyzer adds static path analysis.

No single tool catches everything — the hardening workflow layers them: warnings at compile time, sanitizers at test time, and -fanalyzer as a periodic audit. The Module 8 lab runs the full stack against hostile inputs.

Checked arithmetic and explicit bounds as defensive patterns

Where overflow is possible, check before operating: for addition, verify b <= INT_MAX - a rather than computing a + b and testing the result (the computation itself would be the UB). For indexing, validate against the known size before touching the array.

These patterns feel paranoid until the first UBSan report on a 'can't happen' input. Defensive arithmetic is not pessimism — it is the admission that inputs are adversarial and the optimizer is literal.

Safe-coding discipline: initialize, validate, check, bound

The module's closing discipline, and the sequence's: initialize every variable at declaration; validate all inputs at the boundary; bound every loop and every copy; check every fallible call; prefer size-aware APIs (snprintf over sprintf, fgets over gets — which no longer exists for good reason).

None of this is exciting. All of it is what separates C that survives contact with users from C that survives only the demo. The capstone's sanitizer-clean requirement is this discipline made gradable.

Hands-on labs

  1. Lab 1 — Signed overflow, caught. Write a program adding two ints from stdin; trigger signed overflow, capture the UBSan report with -fsanitize=undefined, then rewrite with a checked-add that detects overflow before it happens and verify UBSan stays silent.
  2. Lab 2 — Sequence points. Write 'i = i++ + ++i;' and 'a[i] = i++;', compile with -Wall -Wsequence-point, read the warnings, then rewrite each with explicit temporaries in well-defined evaluation order.
  3. Lab 3 — Strict aliasing, observed. Write the int*/float* aliasing violation, compare behavior at -O0 versus -O2, then fix with memcpy and confirm identical behavior at -O2. Write down what changed.
  4. Lab 4 — Full hardening pass. Take your Module 5 file tool through the complete gauntlet: -Wall -Wextra -Werror, ASan+UBSan clean on hostile inputs, every allocation and I/O call checked, all inputs validated. Document anything the earlier version got away with.

Self-check questions

  1. Classify each as undefined, unspecified, or implementation-defined behavior, with a one-sentence justification: (a) x = x++ (b) the order in which function arguments are evaluated (c) sizeof(int) (d) dereferencing a null pointer (e) shifting a 32-bit int left by 32.
  2. Explain in writing why 'it works on my machine' is not evidence of correctness for a program containing undefined behavior, citing one optimizer behavior you personally observed in these labs.

Capstone

Prove it: the capstone project.

The capstone pulls every module together: build wfreq, a word-frequency counter that streams arbitrarily large text files in constant memory, stores results in a dynamically grown hash table of heap-allocated strings, and writes a sorted report to an output file.

Requirements, from the curriculum: at least four translation units (main, table, io, util) plus headers, built by a Makefile you write with debug and release targets; clean under gcc -Wall -Wextra -Werror -std=c11 -pedantic; zero reports from AddressSanitizer and UBSan on a 1 GB input and on hostile inputs (empty file, no trailing newline, a 10 MB single line, binary bytes); every allocation and I/O call checked; and a README explaining your ownership conventions and how you debugged at least one real bug with gdb.

Budget your time honestly: the hash table and the streaming I/O are each a solid day's work, the Makefile and sanitizer-clean runs another day, and the README writeup is where the learning crystallizes. This is the program that proves you can write C like an engineer.
