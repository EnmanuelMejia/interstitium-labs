The sequence

What you will learn, and how.

Certifications test what you know; projects prove what you can do. This sequence is built around a simple premise: you understand a security control only after you have implemented one, and you understand an attack only after you have reproduced one in a lab you control. The work here is construction — writing and running real security tools — organized in four tiers of increasing depth, from single-file Python utilities to distributed detection systems.

The spine of the sequence is the open-source project collection at CarterPerez-dev/Cybersecurity-Projects on GitHub. It is a living repository (not a finished archive): its own badge reported 42 of a planned 70 projects carrying full source code — re-verified 2026-10-04, still 42 — licensed under AGPL-3.0, with the bulk of the implementations in Go and Python. Its four tiers — Foundations, Beginner, Intermediate, Advanced — map directly onto this page's four modules, and its ROADMAPS and RESOURCES directories supply the role-family roadmaps covered in the certification section below. Around that spine we anchor the wider ecosystem: deliberately vulnerable applications, adversary-emulation frameworks, detection labs, and free training platforms — every one verified as a live, reachable resource.

How this differs from its neighbors on this site: the Security+ → CySA+ track teaches to exam objectives; the CISSP and CISM sequences teach practitioner and management knowledge domains; the DevSecOps pipeline sequence teaches securing software delivery. This page teaches through the artifact — you finish it with a portfolio of working tools, not a set of answered questions. They complement each other; this one is where the keyboard gets warm.

Who this sequence is for

  • Aspiring SOC analysts, pentesters, and security engineers who want a portfolio of built tooling alongside any exam study.
  • IT generalists and sysadmins moving into security who learn best by taking things apart and rebuilding them.
  • Career changers with basic programming comfort who want security skills grounded in working code, not slides.

Prerequisites

  • Module 1 (Foundations) assumes nothing — it is built for someone who has barely used a terminal. The repo's Foundations projects are single heavily-commented Python files with companion learn/ folders explaining concepts from zero.
  • Modules 2 and beyond assume you can read and write basic Python and operate a Linux command line. Familiarity with virtual machines helps enormously.
  • A machine (or VM) you control where you can install packages, run containers, and spin up lab networks. Never run these projects on systems you do not own.

How to use it

  • Work the modules in order. Foundations teaches the primitives (hashes, headers, encryption); every later tier composes them.
  • Build every project twice: once by following the repo's finished source to understand it, once from a blank file from memory. The second pass is where the learning happens.
  • Keep an engineering journal per project — what the tool does, which attack or defense it models, and what broke while you built it. Interviewers ask about the breaking; this is where you prepare the answers.
  • Isolate offensive tooling. Scanners, beacons, persistence scanners, and credential tooling belong in a lab network or VM, against targets you own or are authorized to test. The lab-safety rules in each module are not decoration.

The curriculum

4 modules, in order.

Module 1

Foundations: Hashes, Headers, and Encrypted Vaults

Learning objectives

  • Identify hash algorithm families by their output shape and encoding
  • Audit a website's HTTP response for missing security headers and explain each one's purpose
  • Explain how a master password becomes an encryption key (key derivation) and why authenticated encryption matters
  • Read a heavily-commented security tool end to end and describe its control flow

Key concepts, explained

Hash families and the PHC string format

A hash identifier works the way a naturalist identifies species: by observable traits — length, character set, prefix, delimiter structure. MD5 and SHA families produce fixed-length hex digests; modern password hashes (bcrypt, Argon2) are stored as PHC strings carrying the algorithm name, parameters, salt, and hash in one delimited field. Learning to read these encodings by eye is the first forensic reflex: you will see hash dumps in credential audits, breach data, and configuration files for the rest of your career.

HTTP security headers as a defense layer

Content-Security-Policy, Strict-Transport-Security, X-Frame-Options, and their companions are server instructions that constrain what the browser is allowed to do with a page — the cheapest defense layer on the web, and the most commonly neglected. A headers scanner turns an abstract checklist into a scored audit: point it at a site and it tells you exactly which protections are missing. Running it against your own projects first makes the lesson personal.

Argon2id key derivation and AES-GCM authenticated encryption

A password manager's job is to turn a human-memorable secret into a cryptographic key without making the vault brute-forceable. Argon2id stretches the password with deliberate memory-hard work so that guessing is expensive; AES-GCM then encrypts the vault while simultaneously authenticating it, so tampering is detected instead of silently decrypted. This pair — memory-hard KDF plus authenticated encryption — is the standard construction for local secret storage, and implementing it teaches more than any diagram of the same.

Reading production-quality code as a beginner

The Foundations tier's teaching method deserves attention: the code itself is written to production standards while every line that introduces a new concept is annotated inline, with numpy-style docstrings on each function. Study the pattern — senior-level code, beginner-level explanation — because you will imitate it when you document your own projects, and clear security tooling is a professional asset.

Hands-on labs

  1. Build the hash identifier, then feed it real-world hash dumps
    Write the classifier from scratch, then test it against sample hashes from public wordlist/hash-format documentation. Misclassifications teach the edge cases (truncated digests, ambiguous lengths) that a finished source file would hide.
  2. Audit five websites you use with the headers scanner and rank the results
    Score the sites, then read each missing header's documentation to explain the concrete attack it would have mitigated. Pick one of your own projects and fix its headers until the scanner is satisfied.
  3. Implement the encrypted vault, then attack it
    After the manager works, write a second script that tries to brute-force a weak master password against the vault file, and time how Argon2id's parameters change the economics. The defense makes sense only once you have priced the attack.
  4. Rewrite one Foundations project from memory in a single sitting
    Close the source, rebuild the tool from your journal notes, and note where you get stuck. Those gaps are your actual knowledge boundaries — the finished file made them invisible.

Self-check

  • Given a 60-character string starting with $2b$12$, what algorithm and cost do you expect?
  • Which header stops your page from being framed by an attacker's site, and what attack does that prevent?
  • Why is encrypting a vault with AES-CBC alone (no authentication) insufficient?

Lab safety

  • Foundations tooling is benign, but build the habit now: all projects run on your own machine, against your own targets, from here forward.

Module 2

Beginner: Recon, Crypto Utilities, and Linux Security

Learning objectives

  • Write a port scanner and explain what open, closed, and filtered responses reveal about a target
  • Perform basic vulnerability assessment: banner grabbing, service identification, and known-weakness matching
  • Audit a Linux host against hardening expectations (CIS-style checks) and interpret the findings
  • Capture and analyze network traffic, identifying protocols and anomalies by hand

Key concepts, explained

Port scanning as conversation, not brute force

A port scan is a series of short conversations with a remote host: SYN, response, interpretation. An open port answers; a closed port refuses; a filtered port stays silent, and that silence is itself information (a firewall is eating your packets). Building the scanner yourself — sockets, timeouts, thread pools — teaches TCP behavior that reading about the three-way handshake never quite delivers, and it is the skill every later offensive technique assumes.

Vulnerability scanning: identification before exploitation

A vulnerability scanner does not hack anything; it inventories. Banner grabbing and service fingerprinting answer "what is running here," and matching versions against known weakness patterns answers "what might be wrong with it." This identification-first discipline is the professional shape of assessment work: you never touch what you have not first mapped, and the scanner is your mapmaker.

Linux hardening audits and the CIS tradition

Hardening benchmarks (the CIS benchmarks are the industry's common reference) turn "secure the server" into a checklist: file permissions, service states, kernel parameters, authentication policy. An auditing tool automates the checking and reports drift. Building one teaches you to think in desired-state terms — security as the gap between configured and correct — which is the mental model behind every compliance and configuration-management tool you will ever meet.

Traffic analysis: reading the wire

A network traffic analyzer sits between raw packets and understanding: capture, dissect, summarize. Learning to read DNS queries, TLS handshakes (including JA3/JA4-style fingerprinting concepts the intermediate tier revisits), and plaintext protocols by hand builds the packet-level intuition that makes later detection work possible. Wireshark shows you the same data; building the parser teaches you what Wireshark knows.

Steganography, canary tokens, and defensive creativity

Not every beginner project is offensive. Steganography tools hide data inside media (and their detectors find it); canary tokens are tripwires — files, URLs, or credentials that alert you when touched by an intruder. These projects teach the defensive imagination: security is not only walls, it is also alarms, decoys, and evidence.

Dual-use awareness: keyloggers, beacons, and restraint

This tier includes projects with obvious dual use — a keylogger records keystrokes, a C2 beacon phones home. They are included because defenders must understand the mechanisms they defend against, and the repo treats them as lab specimens. The rule is absolute and non-negotiable: they run only on systems you own, in isolated lab environments, and never against another person's machine. Curiosity about the mechanism is legitimate; deployment outside your own lab is not.

Hands-on labs

  1. Scan your own lab VM with your port scanner, then compare against a professional scanner's output
    Run your tool and a reference scanner against the same target and diff the results. Every discrepancy is a lesson in timeouts, packet crafting, or service behavior your implementation has not handled yet.
  2. Vulnerability-scan a deliberately vulnerable VM and document every finding by hand
    Use Metasploitable or a similar intentionally-vulnerable target (see the project-lab section), run your scanner, and write up each finding as if for a client: what it is, why it matters, how to fix it. The write-up is the deliverable that assessment work actually sells.
  3. Harden-audit your own Linux machine and remediate the top five findings
    Run your CIS-style auditor, take the five most serious findings, fix them, and re-run to confirm. Closing the loop — detect, remediate, verify — is the operational rhythm of defensive work.
  4. Capture an hour of your lab network's traffic and write an analyst's summary
    With your analyzer, produce a one-page brief: which hosts talked to whom, which protocols dominated, and anything that looked anomalous. Analysts are paid for the summary, not the capture.

Self-check

  • Your scanner reports a port as "filtered" rather than "closed" — what device behavior explains the difference?
  • Why does a vulnerability scanner's version-match produce false positives, and how do you confirm one?
  • Name two ways a canary token provides value that a firewall log does not.

Lab safety

  • Scanners and beacons stay inside your lab network. Scan only hosts you own or are explicitly authorized to test; unauthorized scanning is unlawful in many jurisdictions regardless of intent.
  • Keylogger and C2-beacon projects run on your own isolated VMs only. Delete or quarantine the artifacts when the lab is done — do not leave dual-use binaries on shared machines.

Module 3

Intermediate: Detection, AppSec, and Supply-Chain Defense

Learning objectives

  • Build a SIEM-style dashboard: ingest log events, write detection rules, and triage alerts
  • Scan an API for common security weaknesses and explain the findings in terms of the OWASP API Security Top 10
  • Generate an SBOM for a project and match its components against known vulnerabilities
  • Detect leaked secrets in code and design a prevention workflow around the findings

Key concepts, explained

SIEM thinking: from logs to detections to triage

A SIEM dashboard project compresses the analyst's daily loop into code you write yourself: events flow in, parsing normalizes them, detection rules match patterns, and the dashboard surfaces alerts for triage. Building it teaches the central defensive discipline — that detection is a pipeline, not a product — and every SOC workflow you later encounter (the repo's SOC Analyst roadmap included) will be a scaled-up version of what you built here.

API security as its own discipline

Modern applications are APIs wearing a user interface, and APIs fail in their own characteristic ways: broken object-level authorization, excessive data exposure, missing rate limits, injection. An API security scanner automates the probing; understanding the OWASP API Security Top 10 gives the findings their names. This is the bridge between the beginner tier's network scanning and the professional application-security work the roadmaps describe.

SBOMs and the software supply chain

A software bill of materials lists every component your software is built from — and therefore every component whose vulnerabilities are your vulnerabilities. An SBOM generator plus a vulnerability matcher answers the question every organization dreads after a major disclosure: "are we affected, and where?" Building this tooling teaches supply-chain thinking: your attack surface includes code you did not write, maintained by people you have never met.

Secrets scanning and the credential-leak lifecycle

API keys and tokens leak into repositories constantly — committed by accident, then cloned, forked, and scraped forever. A secrets scanner finds them by pattern and entropy analysis; the harder lesson is the lifecycle around the finding: revoke, rotate, and prevent recurrence with pre-commit hooks and pipeline gates. The scanner is the easy part; the workflow is the security.

TLS fingerprinting and container auditing

JA3/JA4 fingerprinting identifies clients by the distinctive shape of their TLS handshakes — malware and scanners often have recognizable fingerprints, which makes this a passive detection technique with no agent required. Docker security auditing applies the hardening-audit mindset from Module 2 to containers: image provenance, runtime configuration, privilege boundaries. Both extend your detection surface into the infrastructure modern workloads actually run on.

Hands-on labs

  1. Feed your SIEM dashboard a week of your lab's logs and write three detection rules
    Generate normal lab traffic plus a few scripted attacks (a port scan, a brute-force login, an odd-hour admin action), then write rules that catch the attacks without drowning in false positives from the normal traffic. Tuning out the noise is the real skill.
  2. API-scan a deliberately vulnerable API and map findings to the OWASP API Security Top 10
    Run your scanner against OWASP's vulnerable API projects or a local test API, then write each finding up with its Top 10 category, impact, and fix. The mapping exercise is what turns tool output into analyst judgment.
  3. Generate an SBOM for one of your own projects and triage its vulnerable components
    Run your generator and matcher, then for each flagged component decide: upgrade, replace, or accept the risk with a written reason. Risk acceptance with documentation is a professional act; ignoring the report is not.
  4. Plant secrets in a test repository and measure your scanner's recall
    Commit a dozen realistic secrets (fake keys in real formats) across a test repo, run the scanner, and score what it caught and missed. Then add a pre-commit hook and confirm the next commit is blocked. Measure, then prevent.

Self-check

  • Your SIEM rule fires 400 times a day on legitimate admin logins — what tuning options do you have besides deleting the rule?
  • Why is broken object-level authorization the classic API vulnerability, and what test exposes it?
  • A critical CVE lands in a transitive dependency three levels deep — how does your SBOM workflow find every affected service?

Lab safety

  • API and vulnerability scanning stay pointed at your own lab targets. Credential-enumeration tooling from this tier is lab-only; never run it against real services or other people's infrastructure.

Module 4

Advanced: Adversary Emulation, Deception, and Detection Engineering

Learning objectives

  • Deploy a honeypot network and analyze the attack traffic it collects
  • Explain how adversary-emulation frameworks model real attacker behavior for defensive testing
  • Describe what a reverse-engineering workflow looks like on an unknown binary
  • Design a detection for one attacker technique and validate it against emulated activity

Key concepts, explained

Honeypots: instrumented deception

A honeypot network is infrastructure designed to be attacked: fake services that log everything the intruder does. Unlike production systems, honeypots have no legitimate users, so every connection is suspicious by definition — which makes their logs the cleanest signal in security. Building one teaches deception as a defensive discipline and gives you real attacker traffic to analyze, the raw material of threat intelligence.

Adversary emulation and the purple-team loop

Frameworks like Atomic Red Team encode real attacker techniques as executable tests, so defenders can verify their detections against known-bad behavior on demand. This is the purple-team loop in miniature: emulate the adversary, check whether your monitoring caught it, fix the blind spot, repeat. The advanced tier's threat-detection projects live here — detection engineering as a practice of continuous, adversarial self-testing.

Reverse engineering: reading the unreadable

The reverse-engineering projects introduce the workflow of analyzing binaries without source: disassembly, control-flow reconstruction, identifying interesting functions, and dynamic analysis in a sandbox. You will not become a malware analyst in one module; you will learn what the discipline's first hour looks like, which is enough to triage a suspicious binary and know when to escalate it.

Cryptography at the systems level: HSM emulation and secure channels

An HSM emulator models the hardware that guards the world's most sensitive keys — tamper-resistant modules that perform cryptographic operations without ever exposing key material. Building an emulator teaches the key-management architecture that underpins everything from certificate authorities to payment systems. The encrypted-chat project alongside it applies the same primitives to a concrete problem: authenticated, confidential messaging between peers.

Polyglot security engineering

Note the advanced tier's language spread — Haskell reverse proxies, Zig scanners, Go tooling. Security engineering is polyglot by necessity: performance-critical scanners want systems languages, while glue and analysis live in Python and Go. The takeaway is not any one language but the habit of choosing the tool for the performance and safety profile the job demands.

Hands-on labs

  1. Deploy the honeypot network, leave it exposed for a week, and write an attacker's diary
    Document what arrived: which services were probed, which credentials were tried, which payloads were delivered. Then classify the activity — automated botnet noise versus targeted behavior — and present the findings as a threat briefing.
  2. Emulate five attacker techniques against your Module 3 SIEM and score your detections
    Use an adversary-emulation framework to execute known techniques in your lab, then check which ones your dashboard caught. For each miss, write the detection rule that would have caught it and re-run. The before/after scorecard is detection engineering, demonstrated.
  3. Reverse-engineer a crackme or known-benign binary and document the workflow
    Work a beginner crackme in a sandboxed VM: map the control flow, find the validation logic, and write up each step. Use only legal practice targets — never analyze malware outside a proper sandbox, and never distribute what you find.
  4. Build a capstone: one detection pipeline end to end
    Combine the tiers — a scanner or honeypot as the sensor, your SIEM dashboard as the brain, and a written detection rule with a validation test. Present it as a portfolio piece: architecture diagram, code, sample alerts, and the emulation test proving it works.

Self-check

  • Why does a honeypot's "no legitimate users" property make its logs more valuable than a production firewall's?
  • Your emulation test succeeds but no alert fires — is the problem the sensor, the rule, or the pipeline, and how do you isolate which?
  • What separates legal reverse-engineering practice from activity you should not touch?

Lab safety

  • Advanced tooling — honeypots, emulated C2, reverse-engineering sandboxes — runs in isolated lab networks only. Exposing a honeypot to the internet is itself a research decision with legal and abuse implications; understand your provider's terms and your jurisdiction's rules before you do it.
  • Handle any captured malware samples as hazardous material: sandboxed VM, no network route to production, snapshots for rollback, and no redistribution.

The project lab

Where to practice: the verified ecosystem.

Tools you build need targets you are allowed to touch. The resources below are verified, open or free-tier, and legal to practice against. Every link was checked live; if one dies, the category description tells you what to look for in a replacement.

Deliberately vulnerable web applications

  • OWASP Juice Shop — a modern, intentionally vulnerable web application (Node.js/Angular) covering the OWASP Top 10, packaged for local deployment. The standard target for practicing web attacks and for testing scanners you build in Modules 2 and 3. owasp.org/www-project-juice-shop
  • OWASP WebGoat — a deliberately insecure Java web application with structured lessons for each vulnerability class. Lesson-driven where Juice Shop is open-world; use it when you want guided exercises. owasp.org/www-project-webgoat
  • DVWA (Damn Vulnerable Web Application) — a PHP/MySQL application with adjustable difficulty levels per vulnerability, useful for demonstrating the same flaw from trivially exploitable to properly defended. github.com/digininja/DVWA

Free training platforms

  • PortSwigger Web Security Academy — free, lab-backed web security training from the makers of Burp Suite, with interactive labs for each vulnerability class. The deepest free web-security curriculum available; pairs directly with Modules 2 and 3. portswigger.net/web-security
  • TryHackMe — guided, browser-based security labs and learning paths with a free tier covering beginner through intermediate rooms. Good for structured practice between building your own tools. tryhackme.com
  • HackTheBox — hands-on hacking labs and machines with a free tier; the community writeups for retired machines are a study resource in their own right (read them after attempting the box, not before). hackthebox.com

Vulnerable virtual machines and detection labs

  • Metasploitable 3 — intentionally vulnerable virtual machines (Linux and Windows builds) designed as legal targets for scanning and exploitation practice. The canonical target for your Module 2 scanner labs. github.com/rapid7/metasploitable3
  • DetectionLab — an automated lab that builds a Windows domain with logging, Splunk, and attack tooling pre-configured, designed for detection engineering. The natural home for your Module 3 and 4 detection work. github.com/clong/DetectionLab
  • Security Onion — a free Linux distribution bundling network security monitoring, log management, and intrusion detection. Deploy it in your lab to see what a production-grade defensive stack looks like next to the SIEM dashboard you built yourself. github.com/Security-Onion-Solutions/securityonion

Adversary emulation and purple-team tooling

  • Atomic Red Team — a library of small, focused tests mapped to adversary techniques, executable on demand against your own lab. The engine of the purple-team loop described in Module 4. github.com/redcanaryco/atomic-red-team
  • PurpleSharp — an adversary-emulation tool for Windows environments, useful when your lab includes Windows targets and you want technique execution with telemetry. github.com/mvelazc0/PurpleSharp

SOC training data and blue-team practice

  • Splunk Boss of the SOC (BOTS) dataset — a large, realistic synthetic dataset of enterprise security logs with an attack narrative woven through it, released for the Boss of the SOC competition. Feed it to your Module 3 SIEM dashboard as realistic practice data. github.com/splunk/botsv3
  • LetsDefend — a blue-team training platform with free resources and simulated SOC alert investigations. Practice the triage workflow your dashboard project models. letsdefend.io · github.com/letsdefend

  • CarterPerez-dev/Cybersecurity-Projects — the 70-project collection (42 with full source at the 2026-10-04 re-check; "70" remains the goal, not current state) this sequence is keyed to, AGPL-3.0 licensed. Role roadmaps

Three role families, honestly described.

The spine repository ships ten role roadmaps; we cover the three this sequence prepares you for. Read these as orientations to the roles — what the work is, what the repository's roadmap suggests studying — not as promises. No page on this site certifies anyone; the certification names below belong to their vendors, and the vendors' own sites are authoritative on requirements, cost, and validity.

SOC Analyst — the defensive watch floor

A SOC (Security Operations Center) analyst monitors security telemetry, triages alerts, investigates suspicious activity, and escalates or contains incidents. It is the classic entry point into defensive security: shift work, alert queues, playbooks, and a constant stream of real events to learn from. Everything in Modules 1 through 3 feeds this role — traffic analysis, log triage, SIEM thinking — and the Module 4 capstone is a miniature version of the detection work senior analysts do.

The repository's SOC Analyst roadmap suggests a progression through vendor certifications including Security+, CySA+, GCIH, GCIA, and CISSP, with a multi-year timeline to senior level. Treat that list as one maintainer's suggested study order, not a hiring requirement: entry-level SOC postings vary widely, and demonstrated lab work (this sequence's portfolio) plus a foundational certification is a common and credible combination. Our own Security+ → CySA+ track covers the exam-knowledge side of the first two names on that list.

Pentester — authorized adversary

A penetration tester is hired to break in — legally, under contract, with defined scope — and report how it was done so the flaws get fixed. The work blends technical depth (network, web, and increasingly cloud and API attack surface) with professional writing: the report is the product the client buys. Modules 2 and 3 build the technical substrate (recon, scanning, web and API assessment); the vulnerable applications and platforms in the project-lab section are where you practice the craft lawfully.

The repository's Pentester roadmap suggests Security+, PenTest+, CEH, OSCP, OSEP, and GXPN across a multi-year path to expert level. Note the shape of that list: it moves from knowledge exams toward hands-on, lab-exam certifications (OSCP and OSEP are earned by compromising machines in a timed lab, not by multiple choice). That shape is the honest signal — pentesting is a performance discipline, and the credentials that carry weight in it test performance. Nothing here substitutes for authorized practice; there is no shortcut past the lab hours.

Security Engineer — building the defenses

A security engineer designs and implements security controls: hardening systems, building detection pipelines, automating response, securing cloud infrastructure and delivery pipelines. It is the builder's role — closest in spirit to this sequence's project work — and it draws on both sides: you must understand attacks to design controls that survive them, and you must understand systems to build controls that survive production.

The repository's Security Engineer roadmap suggests Security+, CySA+, SecurityX, CISSP, and CCSP over a multi-year path to senior level, reflecting the role's breadth across architecture, cloud, and operations. This sequence's intermediate and advanced modules — SIEM construction, SBOM tooling, container auditing, detection engineering — are the portfolio evidence for this path, and our DevSecOps pipeline sequence covers the delivery-security half of the modern security engineer's remit.

What roadmaps can and cannot do

  • A roadmap orients; it does not qualify. Employers hire for demonstrated capability, and capability is demonstrated by built work and, where relevant, vendor certifications earned from the vendors.
  • Certification names, requirements, and prices change. Verify everything against the vendor's current published information before spending money or time.
  • The repository's timelines (years to senior or expert level) are one maintainer's estimates. Your mileage will vary with prior experience, mentorship, and how many lab hours you actually put in — which is the variable this sequence exists to maximize.
