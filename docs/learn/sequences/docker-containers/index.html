Docker and Container Engineering

From kernel primitives to production hardening: how containers isolate, how images are built, and how to run them safely.

Start the sequence All sequences

SCIENTIA OMNIA VINCIT

The sequence

What you will learn, and how.

Containers are the dominant unit of software deployment, and Docker is their lingua franca. But containers are not magic and not virtual machines: they are ordinary Linux processes given an isolated view of the system through kernel namespaces and constrained through control groups. Everything Docker does — images, layers, volumes, networks — is composed from these primitives plus a client-server architecture that manages them.

This sequence builds from the kernel up. You start with namespaces, cgroups, and the image-container split, then learn images properly: layers, Dockerfile instructions, and tag discipline. Build caching and multi-stage builds follow, then the container lifecycle, storage, and networking. Registries cover distribution, Compose covers multi-service applications as code, and the final module hardens everything: non-root users, minimal bases, secret hygiene, and a systematic debugging workflow.

The official Docker documentation is the authoritative reference for exact flags and syntax; this page teaches the concepts that make those flags meaningful.

Who this sequence is for

  • Developers who run docker commands daily and want to understand what the commands actually do.
  • DevOps and platform engineers building container-based deployment pipelines.
  • System administrators moving from VMs to containers who need the isolation model explained honestly.

Prerequisites

  • A Linux machine (or VM) with Docker Engine installed, or Docker Desktop — most labs assume a Linux host for namespace inspection.
  • Comfort with the Linux command line and basic networking concepts.
  • No prior container experience required; the first module starts at the kernel.

How to use it

  • Work the modules in order — the kernel primitives in module 1 are the vocabulary for everything after.
  • Run every lab. Container knowledge is tactile: inspect, break, and rebuild until the behavior is unsurprising.
  • Read docker inspect output the way you would read source code — it is the ground truth of what Docker actually configured.
  • Verify flags and behaviors against the official Docker docs; the CLI evolves and this guide teaches concepts.

The curriculum

9 modules, in order.

Module 1

Container fundamentals: namespaces, cgroups, and the image-container split

Learning objectives

  • Explain what namespaces and cgroups provide and how they compose a container's isolation model.
  • Distinguish an image (immutable, layered template) from a container (mutable runtime instance).
  • Describe the Docker daemon/CLI/client-server architecture at a high level.
  • State what containers do not isolate, and why containers are not VMs.

Key concepts, explained

Namespaces: PID, NET, MNT, UTS, IPC, USER

Namespaces give a process its own isolated view of a system resource. PID namespaces mean the container sees its own process tree starting at PID 1; NET namespaces give it its own network interfaces and routing table; MNT namespaces give it its own filesystem mount table; UTS namespaces isolate hostname and domain; IPC namespaces isolate inter-process communication; USER namespaces map container UIDs to different host UIDs.

Isolation here means restricted visibility, not a security boundary by itself — a process that escapes its namespaces is just a host process. Understanding which namespace isolates what is the foundation for reasoning about every container behavior that follows.

cgroups: CPU, memory, I/O accounting and limits

Control groups (cgroups) account for and limit what a group of processes may consume: CPU shares and quotas, memory ceilings, block I/O bandwidth. Where namespaces control what a container can see, cgroups control what it may use.

Docker's --memory and --cpus flags are cgroup settings. When a container is OOM-killed, that is the kernel's cgroup enforcement, not Docker being unkind — the limit you set is the limit the kernel enforces.

Image = read-only layers + metadata; container = image + thin writable layer

An image is an immutable template: a stack of read-only filesystem layers plus metadata (default command, environment, exposed ports). A container is a running instance of an image: the same layers plus one thin writable layer on top where all changes go.

This split is why starting a container is fast and cheap — no copying, just a new writable layer over shared read-only layers. It is also why container filesystems are ephemeral: the writable layer dies with the container.

dockerd daemon and the docker CLI as remote API client

Docker is client-server: the docker CLI you type into is a thin client speaking a REST API, and the dockerd daemon does the actual work — managing images, containers, networks, and volumes. The CLI and daemon can even be on different machines, connected over a socket or TLS.

This architecture explains several behaviors: why the daemon needs root (it configures namespaces, cgroups, and networking), why docker commands work identically against remote daemons, and why the daemon's logs — not the CLI's — hold the truth during failures.

Layered filesystems: lower layers shared, upper layer per-container

The image's read-only layers are shared between all containers from that image — ten containers from one image share the base layers on disk once. Each container gets its own private upper layer for writes, which is why containers are isolated from each other's filesystem changes.

Sharing is also why pulls are efficient: docker only downloads layers it does not already have. Layer reuse across images is the quiet economy underlying the whole ecosystem.

Copy-on-write semantics on container writes

When a container modifies a file that lives in a read-only lower layer, the filesystem copies that file up into the writable upper layer first, then applies the change — copy-on-write. Reads of unmodified files come straight from the shared lower layers at full speed.

Copy-on-write means the first write to a large file is expensive (the whole file copies up) while subsequent writes are cheap. Workloads that rewrite big files repeatedly pay this cost on every container — a real performance consideration for databases in containers.

Container ephemerality: data lost on removal unless stored externally

The writable layer is tied to the container's lifecycle: docker rm destroys it, and with it every file the container wrote. Containers are cattle — replaceable, disposable, expected to die.

Any data that must survive the container — databases, uploads, logs worth keeping — belongs in a volume or bind mount, outside the writable layer. Designing for ephemerality is the central discipline of running stateful workloads in containers.

Hands-on labs

  1. Install Docker Engine or Desktop; run hello-world and alpine, then list containers and images.
    The hello-world run exercises the full path: pull, create, start, exit. Listing what it left behind — images, stopped containers — introduces the artifacts you will manage from here on.
  2. Run a container, write a file inside it, commit vs. remove it to observe data persistence behavior.
    Write a file, remove the container, and watch the file vanish — then repeat with docker commit to see the writable layer frozen into a new image. The contrast teaches ephemerality concretely.
  3. Inspect a running container with docker inspect and map its mounts, networks, and PID namespace.
    Read the inspect JSON and find the mounts, the network settings, and the process configuration. Inspect output is the ground truth — learn to read it fluently.
  4. Use nsenter-style tooling or /proc on a Linux host to observe a container's isolated PID/NET view.
    From the host, enter the container's namespaces and compare what you see inside versus outside: different PIDs, different interfaces. The isolation becomes observable fact.

Self-check

  • Explain, without notes, why two containers from the same image do not see each other's filesystem changes.
  • List which namespace type isolates each of: hostname, process IDs, network interfaces.
  • Describe what happens to data in the container's writable layer when docker rm runs.

Module 2

Images: layers, Dockerfile instructions, and tag hygiene

Learning objectives

  • Read and write a Dockerfile using the core instructions correctly.
  • Predict layer outcomes from instruction ordering and cache behavior.
  • Apply COPY vs ADD, CMD vs ENTRYPOINT, and ENV/ARG distinctions deliberately.
  • Choose tags deliberately and explain why latest is unreliable for reproducibility.

Key concepts, explained

One instruction = one layer; layer reuse across images

Each Dockerfile instruction that modifies the filesystem creates one layer, and layers are content-addressed and shared: if ten images share the same base, the base layers are stored once. Fewer, better-ordered layers mean smaller images and faster pulls.

This is why instruction ordering matters and why chaining related RUN commands with && is idiomatic — every layer is permanent overhead in the image's history, even if a later layer deletes the files.

RUN vs CMD vs ENTRYPOINT: build-time vs runtime roles

RUN executes a command during the build and commits the result as a layer — it is how software gets installed into the image. CMD and ENTRYPOINT do not run at build time at all; they declare what runs when a container starts: ENTRYPOINT is the fixed executable, CMD the default arguments.

Confusing them is the classic Dockerfile bug: putting the application start in RUN bakes a running process into a layer (useless), while putting installation in CMD reinstalls on every container start (slow). Build-time versus runtime is the line; RUN is left of it, CMD/ENTRYPOINT right.

COPY vs ADD: prefer COPY; ADD's URL/tar extraction caveats

COPY transfers files from the build context into the image, plainly and predictably. ADD does the same plus two extras: it fetches remote URLs and auto-extracts tar archives — conveniences that make builds less transparent and less cache-friendly.

Prefer COPY for files and use explicit RUN curl/tar steps when you need downloads or extraction, because explicit steps are cacheable, readable, and auditable. ADD's magic is rarely worth its opacity.

ENV vs ARG: runtime env vs build-time variables

ARG defines build-time variables — available during the build, for parameterizing versions or flags — while ENV sets environment variables baked into the image and visible to running containers. ARG values can also leak into image history; ENV values are visible to anyone who can inspect the image.

Neither is a secret store: both are readable from the image. Use ARG for build parameters, ENV for genuine runtime configuration, and secret mounts for anything sensitive.

WORKDIR, EXPOSE, USER, HEALTHCHECK instruction roles

WORKDIR sets the working directory for subsequent instructions and the container's default — prefer it over cd in RUN commands. EXPOSE documents which ports the container listens on; it publishes nothing by itself, it is metadata (and documentation). USER switches the user for subsequent instructions and the default runtime user — the one-line privilege drop. HEALTHCHECK defines a command Docker runs periodically to judge container health.

These four are the "production readiness" instructions: working directory sanity, port documentation, non-root execution, and health signaling. A Dockerfile without USER and HEALTHCHECK is a development Dockerfile.

Tag semantics: name:tag, immutable digests vs mutable tags

An image reference is name:tag, but tags are mutable labels — latest today points to a different image than latest next month. The digest (image@sha256:...) is the immutable content address: it names exactly one image forever.

For reproducibility, pin deployments by digest; use tags for human convenience in development. "It worked with :latest yesterday" is not a reproducible statement, and production should never depend on one.

.dockerignore to keep build context lean

The build context — everything in the build directory — is sent to the daemon before the build starts. Without .dockerignore, that includes .git histories, node_modules, and secrets-adjacent files: slow builds and accidental inclusions.

.dockerignore works like .gitignore, excluding what the image does not need. A lean context builds faster, and more importantly, it cannot accidentally COPY a private key into a layer.

Hands-on labs

  1. Write a Dockerfile for a small scripted app; build, run, and verify layer count with docker history.
    Build it, then read docker history: one row per layer, with sizes. The history table makes the instruction-to-layer mapping undeniable.
  2. Reorder a dependency-install step above source COPY and rebuild to observe cache hits.
    Build twice: once with dependencies installed after the source copy (slow rebuilds), once before (cached). The build-time difference teaches cache ordering permanently.
  3. Build the same app with :latest and a versioned tag; retag by digest and compare pinning behavior.
    Push both references, then re-pull by digest versus by tag after rebuilding. The digest always returns the identical image; the tag may not — the lesson in one experiment.
  4. Add a .dockerignore and measure build-context size before and after.
    Time the context transfer and note its size with and without the ignore file. The difference on a real project directory is usually embarrassing.

Self-check

  • Given a Dockerfile, predict which layers rebuild when only application source changes.
  • Explain the observable difference between CMD and ENTRYPOINT at docker run time.
  • Justify when COPY is preferable to ADD.

Module 3

Build caching and multi-stage builds

Learning objectives

  • Diagnose cache misses in a build and restructure the Dockerfile to maximize cache hits.
  • Build a multi-stage Dockerfile that separates build tooling from the runtime image.
  • Explain how BuildKit changes build performance and what build contexts are.
  • Shrink a final image by excluding build dependencies and caches.

Key concepts, explained

Cache invalidation: any changed layer invalidates all layers below it

Docker caches each layer: if the instruction and its inputs are unchanged, the cached layer is reused. But invalidation cascades downward — change one layer and every layer after it rebuilds, because each layer is built on its parent's exact content.

This single rule drives all Dockerfile ordering strategy: anything that changes rarely goes early, anything volatile goes late. A cache-hostile Dockerfile rebuilds the world on every source edit; a cache-friendly one rebuilds only the app layer.

Instruction ordering: stable layers first, volatile layers last

The canonical ordering: base image, system dependencies, language dependencies (which change rarely), then application source (which changes constantly). Each rebuild then reuses every cached layer down to the source copy and rebuilds only from there.

Review Dockerfiles top-to-bottom asking "how often does this change?" — any inversion you find is build time being wasted on every developer's every commit.

Multi-stage builds: named stages, COPY --from=<stage>

Multi-stage Dockerfiles define named build stages — a full toolchain stage that compiles the application, then a minimal final stage that COPY --from the build stage only the resulting binary. The final image contains the artifact, not the toolchain.

Only the final stage's layers ship: intermediate stages are build scaffolding, discarded after use. This is the single most impactful Dockerfile pattern for image size and attack surface.

BuildKit: parallel stage resolution, build mounts and secrets

BuildKit is the modern build engine: it parallelizes independent stages, offers cache mounts that persist package caches across builds without baking them into layers, and provides secret mounts for build-time credentials that never touch the image.

BuildKit also improves caching semantics and build performance generally. If a Dockerfile feature (RUN --mount, cache backends) requires it, that is BuildKit — the legacy builder is increasingly a historical artifact.

RUN --mount=type=cache for dependency caches without persisting them

Package manager caches speed rebuilds enormously but should not ship in the image. RUN --mount=type=cache gives the step a persistent cache directory that survives across builds yet is never committed to any layer.

The result is the best of both: fast incremental builds and lean images. Without the mount, you choose between slow builds (no cache) and bloated images (cache baked in).

Squashing vs layer count trade-offs

Squashing collapses multiple layers into one, shrinking metadata overhead and hiding intermediate files — but it destroys layer sharing and cache granularity: any change rebuilds the whole squashed layer. Multi-stage builds usually achieve the size goal without squashing's costs.

Prefer multi-stage over squashing in almost all cases. Squash only when image layer count itself is the constraint (some registries and runtimes have limits) and you have measured that it matters.

Base-image selection: slim/distroless/alpine size-vs-debuggability trade-off

The base image sets the floor for size and attack surface: full distributions are hundreds of megabytes with shells and package managers; slim trims them; Alpine rebuilds minimal on musl; distroless ships only the runtime. Smaller base, fewer CVEs, less to debug with.

Choose by lifecycle stage: debuggable bases in development where you exec in constantly, minimal bases in production where the CVE count matters. The comparison lab makes the tradeoff visceral.

Hands-on labs

  1. Build a compiled-language or bundled-JS app in two stages: toolchain stage, minimal runtime stage; compare image sizes.
    Build the single-stage and multi-stage variants and compare sizes — the multi-stage image is typically a fraction of the size. The number is the argument.
  2. Introduce a cache-hostile ordering, then fix it; record build times before and after.
    Deliberately put the volatile source copy first, time a rebuild, then reorder and time again. The measured delta teaches cache ordering better than any diagram.
  3. Use RUN --mount=type=cache to persist a package cache across builds without baking it into layers.
    Build twice with the cache mount and confirm the second build is fast while the final image stays lean. Then check the image has no cache directory — both properties verified.
  4. Compare final image sizes of debian-slim, alpine, and distroless variants of the same app.
    Three bases, one app, three sizes and three CVE counts. The table you produce is the base-image decision framework you will reuse for years.

Self-check

  • Explain why a package-manager install belongs before the application COPY for cache efficiency.
  • Describe what COPY --from does and which layers end up in the final image.
  • List two artifacts that must never end up in a production image layer.

Module 4

Container lifecycle: run, exec, logs, and resource constraints

Learning objectives

  • Drive the full container lifecycle: create, start, stop, restart, pause, remove.
  • Use exec, attach, cp, and logs to interact with and inspect running containers.
  • Apply CPU and memory constraints and observe their enforcement.
  • Distinguish foreground vs detached execution and container restart policies.

Key concepts, explained

docker run = create + start; flags: -d, -it, --rm, --name

docker run is two operations fused: create (build the container from the image) plus start (launch its process). The flags shape the result: -d detaches so the container runs in the background; -it allocates a TTY and keeps stdin open for interactive use; --rm deletes the container when it exits; --name gives it a stable identity instead of a generated one.

Understanding run as create+start explains the separate create/start/stop commands and why docker ps -a shows containers that ran and exited. The flags are the everyday vocabulary — know them cold.

Lifecycle states: created, running, paused, stopped, removing

A container moves through states: created (configured, not started), running, paused (processes frozen with SIGSTOP, memory retained), stopped (process exited, filesystem retained), removing (being deleted). docker ps shows running; docker ps -a shows everything.

Paused is the underused one: it freezes a container without killing it, useful for consistent snapshots or temporarily halting a misbehaving process. Stopped containers still hold their writable layer until removed — "stopped" is not "gone."

Restart policies: no, on-failure, always, unless-stopped

Restart policies tell the daemon what to do when the container's process exits or the daemon restarts: no (never restart), on-failure (restart only on nonzero exit, optionally with a retry cap), always (restart regardless, including after daemon reboot), unless-stopped (like always, but respect a manual stop).

For long-lived services, unless-stopped is usually right: it survives reboots but honors your explicit stop. always restarting a container you deliberately stopped is a classic source of confusion.

docker exec vs docker attach: new process vs main process stream

docker exec starts a new process inside the running container's namespaces — typically an interactive shell for inspection. docker attach connects your terminal to the container's main process stream (its stdin/stdout/stderr).

The critical difference: detaching from attach with Ctrl-C can signal the main process (unless detached properly), while exiting an exec shell never harms the main process. For inspection, exec is almost always the safer choice.

Log drivers, log rotation, and stdout/stderr capture

Docker captures the container's stdout and stderr through log drivers — json-file by default, writing to disk. Without rotation, a chatty container fills the disk; configure max-size and max-file so logs stay bounded.

The twelve-factor discipline applies: applications log to stdout/stderr, Docker captures and routes. docker logs reads the captured stream; the driver decides where it ultimately goes (files, syslog, cloud logging).

--memory, --cpus, --memory-swap: cgroup-backed limits

Resource flags are cgroup settings: --memory caps RAM, --cpus caps CPU time, --memory-swap caps RAM plus swap combined. Setting --memory without --memory-swap allows swapping up to a default; setting them equal disables swap for the container.

Always set memory limits on production containers — an unlimited container can OOM the host, and the kernel kills whatever it chooses. Limits convert "the host might die" into "this container might die," which is the correct failure mode.

Exit codes and docker wait for scripting around completion

A container's exit code is its process's exit code, preserved after the container stops — docker ps -a shows it, docker inspect reports it. docker wait blocks until the container exits and prints the code, which makes it the primitive for scripting batch workflows around containers.

Treat exit codes as the container's API: zero means success, nonzero means investigate the logs. Scripting around docker wait turns one-shot containers into reliable batch jobs.

Hands-on labs

  1. Run a long-lived container detached with a restart policy; stop the daemon and observe restart behavior.
    Start it with unless-stopped, restart the daemon, and confirm the container comes back. Then stop it manually, restart the daemon, and confirm it stays stopped — the policy semantics made observable.
  2. Constrain a container to 512 MB and trigger an OOM; identify the OOM-killed event in logs.
    Run a memory hog under the limit and watch the kernel kill it. Finding the OOM event in the logs teaches you what resource exhaustion actually looks like.
  3. Practice docker exec -it into a running container to inspect state; contrast with docker attach.
    Exec in, look around, exit cleanly — the container is unaffected. Then attach, and practice detaching without harming the process. The safety difference becomes muscle memory.
  4. Configure log rotation on a chatty container and verify log files stay bounded.
    Point a log-spamming container at a rotated json-file driver and watch the log files stay capped. Unbounded logs are a disk-full incident waiting; this is the prevention.

Self-check

  • Given a crashed container, list the exact commands to read its last logs and its exit code.
  • Explain when --rm is safe and when it destroys evidence you still need.
  • Describe the difference between --memory=1g and --memory=1g --memory-swap=1g.

Module 5

Volumes and storage: bind mounts, named volumes, tmpfs

Learning objectives

  • Choose correctly among bind mounts, named volumes, and tmpfs for a given data requirement.
  • Create, back up, and restore named volumes without data loss.
  • Explain volume driver behavior and the volume lifecycle independent of containers.
  • Diagnose permission and ownership issues on mounted paths.

Key concepts, explained

Bind mount: host path into container; host-managed lifecycle

A bind mount maps a host directory or file directly into the container. The lifecycle belongs to the host: the data exists before the container starts and survives after it is removed. It is the right choice for configuration you edit on the host, source code in development, and anything the host must manage.

The tradeoff is coupling: the container depends on that exact host path existing with the right contents and permissions. Bind mounts are for development and host-integrated cases, not for portable production data.

Named volume: Docker-managed, persists across container removal

A named volume is storage managed by Docker: created by name, mounted into containers, and independent of any container's lifecycle. Delete the container and the volume — and its data — remains, ready for the replacement container.

This is the production answer for databases and stateful services: the data outlives any single container, upgrades replace the container while the volume persists, and backups target the volume. Named volumes are the "data has a longer life than compute" primitive.

tmpfs: memory-only, never touches disk, gone with the container

A tmpfs mount lives purely in memory: fast, never written to disk, and destroyed with the container. It is for session data, scratch space, and secrets that must not persist — anything where "gone on stop" is a feature.

Because it is RAM, tmpfs counts against the container's memory limit. Size it deliberately; a tmpfs that grows unboundedly is a memory leak with a fancy name.

Read-only mounts (:ro) and mount propagation basics

Appending :ro mounts the path read-only inside the container — the container can read configuration but cannot modify it, which limits the damage a compromised process can do. Mount propagation controls whether mounts created inside the container propagate to the host or vice versa; the default (private) is correct for nearly all cases.

Default to read-only for anything the container does not need to write. It is a one-flag hardening win that costs nothing.

Volumes are not deleted by docker rm unless -v is given

Removing a container does not remove its named volumes — the data survives, which is the safety default. The -v flag on docker rm (or docker compose down -v) deletes the volumes too, which is the "I really mean destroy everything" operation.

This asymmetry has bitten everyone once: down -v in the wrong directory deletes production-adjacent data. Treat volume-destroying commands with the same care as rm -rf.

UID/GID mismatch: host ownership vs container user

Files in a bind mount are owned by host UIDs; the container's user may map to a different UID, causing permission denied on files the host user owns — or worse, the container running as root creating root-owned files on the host.

The fixes: run the container with the matching --user UID:GID, adjust ownership on the host, or use named volumes (where Docker manages ownership) instead of bind mounts. UID mapping is the cause of most "it works in the container but the files are wrong" mysteries.

Backup pattern: --volumes-from with a tar sidecar container

To back up a named volume, run a temporary container with --volumes-from the data container (or mounting the volume directly) that tars the volume contents to a host path or stdout. The sidecar pattern backs up live volumes without installing backup tooling in the application container.

Restore is the mirror: a fresh volume plus a sidecar that untars the archive into it. Practice the restore, not just the backup — the tarball you have never unpacked is a hope, not a backup.

Hands-on labs

  1. Persist a database across container destroy/recreate using a named volume; verify data survives.
    Create data, remove the container entirely, start a fresh one on the same volume, and read the data back. The survival is the whole point of named volumes.
  2. Back up a named volume to a tarball with a temporary sidecar container, then restore it into a fresh volume.
    Tar the volume out, destroy everything, restore into a new volume, and verify. The full backup-restore loop, rehearsed before you need it.
  3. Mount the same host directory into two containers; write from one and read from the other.
    Shared bind mounts are the simplest inter-container communication for files. Watching the write appear in the second container makes shared storage concrete.
  4. Run a container with a tmpfs mount holding session data; restart the container and confirm the data is gone.
    Write session state to tmpfs, restart, and confirm emptiness. "Gone on stop" verified empirically is a property you can design around.

Self-check

  • Name the storage type for each: config you edit on the host, database that must survive upgrades, session cache.
  • Explain what docker volume prune does and when it is dangerous.
  • Describe how to fix a container writing root-owned files into a host bind mount.

Module 6

Networking: bridge, host, none, and user-defined networks

Learning objectives

  • Describe the default bridge, host, and none drivers and when each applies.
  • Publish container ports to the host and predict the resulting reachability.
  • Create a user-defined network and use embedded DNS for service discovery.
  • Inspect network topology with docker network inspect to troubleshoot connectivity.

Key concepts, explained

Default bridge vs user-defined bridge: DNS resolution only on the latter

Every container on the default bridge network can reach others by IP, but not by name — the default bridge provides no embedded DNS. Containers on a user-defined bridge network get automatic DNS resolution by container name and network alias.

This single difference is why production Compose setups define their own networks: services find each other by name (web reaches db as "db"), while default-bridge containers are stuck with IPs that change on every restart.

Port publishing -p host:container and the published-port NAT path

The -p flag publishes a container port on the host: -p 8080:80 maps host port 8080 to container port 80 through NAT rules Docker manages. The host dials 8080; the container listens on 80; Docker translates between them.

Publishing is explicit by design: unmapped container ports are unreachable from outside the container's network. The container port is the application's business; the host port is the operator's choice — they need not match.

host network: container shares host stack; no port mapping needed

With --network host, the container shares the host's network stack directly: it sees the host's interfaces, uses the host's ports, needs no port mapping. It is the fastest networking mode (no NAT overhead) and the least isolated.

Use it for network-intensive workloads or when the container must see host network traffic — and accept the tradeoff: a port conflict with a host service breaks the container, and the container can observe host networking.

none: fully isolated, no external networking

The none network gives the container a loopback interface and nothing else: no external connectivity, no container-to-container traffic. It is for workloads that must not talk to the network at all — batch crypto operations, untrusted code execution.

none is the strongest network isolation Docker offers. When the threat model says "this must not phone home," none is how you enforce it.

Embedded DNS server at 127.0.0.11 on user-defined networks

Docker runs an embedded DNS server at 127.0.0.11 inside each container on user-defined networks, resolving container names and network aliases to their current IPs. Containers get this resolver automatically via their resolv.conf.

This is the mechanism behind name-based service discovery in Compose: the name "db" resolves because the embedded DNS knows the network's members. Debugging name resolution starts with checking the container is on a user-defined network.

Container name / network alias as resolvable hostname

On user-defined networks, a container is reachable by its --name and by any --network-alias assigned. Aliases let multiple containers share one logical name (for simple load distribution) or give one container several names.

Aliases are the poor man's service discovery and Compose uses them throughout: the service name becomes the resolvable hostname. Design service names as the API contract between containers.

iptables/nftables rules Docker manages for published ports

Docker implements port publishing and inter-container traffic rules as firewall rules on the host — traditionally iptables, increasingly nftables. The DOCKER chain and NAT rules are Docker's machinery; hand-editing them fights the daemon.

Know they exist for two reasons: debugging connectivity (the rules show exactly what Docker configured) and understanding that host firewall tools and Docker both write firewall state — conflicts between them cause the most confusing "it should work" networking failures.

Hands-on labs

  1. Run two containers on a user-defined network; ping and curl one from the other by container name.
    Create the network, attach both containers, and resolve by name. Then repeat on the default bridge and watch name resolution fail — the contrast is the lesson.
  2. Publish a web server's port; verify reachability from the host and from another machine on the LAN.
    Curl it from the host, then from another machine. The LAN reachability test confirms the publish path works end to end, not just on loopback.
  3. Run a container with --network none and demonstrate the absence of external connectivity.
    Try to ping out and watch it fail; inspect the interfaces and find only loopback. Total isolation, demonstrated.
  4. Create an overlay-free multi-network setup: one container on two networks bridging segmented services.
    Attach one container to two user-defined networks and route between segments through it. Multi-homed containers are the building block of segmented topologies.

Self-check

  • Explain why containers on the default bridge cannot resolve each other by name.
  • Given -p 8080:80, state which port the host dials and which port the container listens on.
  • List the steps to diagnose a container that cannot reach the internet.

Module 7

Registries: push, pull, tags, and authentication

Learning objectives

  • Push and pull images through a registry with deliberate tag and digest discipline.
  • Authenticate to public and private registries and store credentials safely.
  • Explain manifest lists and multi-architecture image pulls.
  • Run a local registry for testing and describe registry storage layout.

Key concepts, explained

Registry as content store; image name = registry/host/path:tag

A registry is a content-addressed store for image layers and manifests. The full image name encodes the location: registry hostname, repository path, and tag — docker.io/library/nginx:1.25 means "Docker Hub, library/nginx, tag 1.25." Omit the registry and Docker assumes Docker Hub.

Understanding the name as an address demystifies pulls: the client resolves the registry, fetches the manifest, then fetches each layer by digest. Every part of the name has a mechanical meaning.

Push/pull mechanics: layer upload by digest, deduplication across images

Push uploads only layers the registry does not already have — each layer is addressed by its digest, so identical layers across different images are stored and transferred once. Pull is the mirror: the manifest lists layer digests, and the client fetches only the missing ones.

This deduplication is why pushing a rebuilt image is fast (only changed layers upload) and why base-image sharing across your fleet saves real bandwidth and storage.

docker login credential storage; credential helpers vs plaintext config

docker login stores credentials for registry authentication. By default they land in ~/.docker/config.json — base64-encoded, which is obfuscation, not encryption. Credential helpers ( OS keychains, pass) store them in the system credential store instead.

Configure a credential helper so registry passwords never sit in plaintext on disk. On shared build machines this is not optional — config.json is readable by the user and often backed up or copied.

Digest pinning (image@sha256:...) for reproducible deploys

Referencing an image by digest pins the exact content: image@sha256:abc... always resolves to the same bytes, while image:1.25 can be repointed by whoever controls the tag. Deployments pinned by digest are reproducible by construction.

The workflow: resolve the tag to a digest at build/CI time, record it, deploy the digest. Tag mutability then cannot surprise production — the deployment names content, not a label.

Multi-arch manifests: one tag, per-platform images

A manifest list (OCI index) lets one tag point to multiple platform-specific images — amd64, arm64 — and the client automatically pulls the variant matching its architecture. One tag, many architectures, correct image everywhere.

Build multi-arch images in CI so the same deployment works on Intel servers and ARM laptops without anyone thinking about it. The manifest list is the indirection that makes it seamless.

Retention and garbage collection on self-hosted registries

Registries accumulate layers and manifests; untagged manifests and unreferenced layers consume storage until garbage collection reclaims them. The stock registry's GC requires care (it should not run against a registry being written to).

Plan retention: how many tagged versions to keep, when to GC, and how to avoid deleting a layer still referenced by a manifest you care about. Registry storage is cheap until nobody manages it.

Public registries: Docker Hub rate limits and mirror considerations

Docker Hub rate-limits anonymous and free-tier pulls — a real constraint for CI fleets that pull heavily. The responses are mirrors and pull-through caches: a local registry that caches upstream images, insulating your builds from both rate limits and upstream outages.

For any serious CI volume, run a pull-through cache or pay for the tier you need. Builds failing on rate limits at 2 AM is an avoidable incident.

Hands-on labs

  1. Run a local registry container; tag, push, and pull an image through it end to end.
    The registry itself is just a container. Pushing to localhost:5000 and pulling back demystifies the whole distribution flow — it is HTTP and content hashes, not magic.
  2. Configure a credential helper so docker login never writes a plaintext password.
    Log in with the helper configured and inspect config.json to confirm no credential material is there. The absence is the test.
  3. Pull a multi-arch image on your host and inspect its manifest to see the platform entries.
    Pull a manifest list and read the per-platform entries. Seeing amd64 and arm64 side by side explains how one tag serves two architectures.
  4. Deploy with a digest-pinned reference instead of a tag and demonstrate immunity to tag mutation.
    Deploy by digest, then push a new image to the same tag and confirm the deployment is unaffected. Tag mutation happened; the deployment did not notice.

Self-check

  • Explain what is actually transferred during docker push when the registry already holds most layers.
  • Describe where docker login credentials land and how to keep them out of plaintext.
  • State when a digest pin is preferable to a version tag.

Module 8

Compose: multi-service applications as code

Learning objectives

  • Model a multi-service app (app + database + cache) as a Compose file.
  • Wire services through networks, volumes, environment, and dependencies.
  • Use env files, interpolation, and profiles for dev/prod variants.
  • Run the full lifecycle: up, down, logs, scale, and config validation.

Key concepts, explained

services, networks, volumes top-level blocks

A Compose file declares the application's services (the containers), networks (how they connect), and volumes (where state lives) as data. One file describes the whole multi-container application: the web tier, the database, the cache, their networks, their storage.

This is infrastructure as code for development and small production: the file is reviewable, versioned, and the single source of truth for "what does this app need to run."

depends_on: startup order, not readiness (healthcheck + condition)

depends_on controls startup order: the database container starts before the app container. It does not wait for readiness — the database process may still be initializing when the app tries to connect, which is the classic Compose race condition.

The fix is healthchecks plus the condition: depend on the database service being healthy, not merely started. Order without readiness is a hope; order with health gating is a guarantee.

Environment: environment, env_file, variable interpolation, .env

Compose has layered configuration: environment sets values inline, env_file loads them from a file, and ${VAR} interpolation pulls from the shell or .env file. The layers compose — .env defaults, env_file overrides, explicit environment wins.

Keep secrets out of the Compose file itself: interpolate them from the environment or a secrets file. The Compose file is versioned; secrets are not.

Volume and network declarations shared across services

Volumes and networks declared at the top level are shared resources: multiple services mount the same named volume or join the same network. This is how the app service and a backup sidecar share data, or how frontend and backend share a network while the database sits on a second, private one.

Shared declarations with per-service attachment give you topology as data: which services share fate, which are isolated. Read the networks section to understand the security segmentation.

docker compose up/down/logs/exec/scale lifecycle commands

The lifecycle verbs: up creates and starts the stack, down stops and removes it, logs tails the aggregated logs, exec runs commands in a service container, scale adjusts replica counts. Together they are the complete operational interface for the stack.

Learn them as a set: up/down for lifecycle, logs/exec for debugging, config for validation. A Compose stack you can operate fluently is a development environment that never surprises you.

docker compose config to render and validate the effective file

docker compose config renders the merged, interpolated, fully-resolved Compose file and validates its schema. With multiple -f files, env interpolation, and profiles, the effective configuration is not obvious from reading the sources — config shows the truth.

Run config before up whenever the setup is non-trivial. It catches interpolation mistakes, invalid references, and merge surprises before any container starts.

Profiles and multiple -f files for environment variants

Profiles tag services for selective startup (a debug tool only in the dev profile); multiple -f files layer configurations — base compose.yaml plus compose.override.yaml for development tweaks, or compose.prod.yaml for production. Later files merge over earlier ones.

This is how one application definition serves many environments: the base file holds the stable truth, overlays hold the differences. Variants as overlays, not as copied-and-edited files that drift apart.

Hands-on labs

  1. Write a Compose file for a web app with a database and cache; bring it up and exercise the app.
    The three-service stack is the canonical Compose shape. Getting it running end to end — app serving, database persisting, cache caching — is the core skill.
  2. Add a healthcheck to the database and gate app startup on the healthy condition.
    Watch the app wait for the database to actually be ready, not just started. The race condition from the previous lab disappears — the fix demonstrated, not described.
  3. Split config into compose.yaml + compose.override.yaml for a dev variant; validate with docker compose config.
    Layer the override, render the effective config, and confirm the merge did what you intended. Overlays you have validated are safe; overlays you assume are not.
  4. Tear the stack down with volumes removed, then restore from your earlier volume backup.
    Down with -v destroys the data volumes — deliberately, in the lab — then restore from backup. Destruction and recovery rehearsed together is the complete lesson.

Self-check

  • Explain why depends_on alone does not guarantee the database is ready.
  • Describe how docker compose config helps catch errors before up.
  • State what docker compose down -v destroys.

Module 9

Security hardening and debugging workflows

Learning objectives

  • Harden an image: non-root user, minimal base, no secrets in layers, read-only filesystem.
  • Scan images for known vulnerabilities and interpret the findings pragmatically.
  • Apply a systematic debugging workflow: logs, inspect, exec, events, network traces.
  • Explain capability drops, seccomp, and AppArmor as defense-in-depth.

Key concepts, explained

USER instruction: never run production workloads as root

Containers default to running as root, and a container-root process with a kernel vulnerability or a misconfigured volume is a host-compromise path. The USER instruction drops to a dedicated non-root user for the application — the single highest-value hardening step.

Creating the user, setting file ownership, and switching with USER belongs in every production Dockerfile. "It runs fine as root" is not a security argument; it is an unexamined default.

Minimal bases reduce attack surface; fewer packages, fewer CVEs

Every package in the image is attack surface and CVE inventory: the scanner reports on what is installed, so installing less means fewer findings and fewer patches. Minimal bases — slim, Alpine, distroless — are a security control, not just a size optimization.

The hardening workflow is subtractive: start from the minimal base that runs your application and add only what it needs. Each added package should justify itself against the CVE burden it brings.

Secrets hygiene: build secrets via --mount=type=secret, never ENV in layers

Secrets baked into layers are compromised by design: anyone with the image can extract them from layer history, even if a later layer deletes the file. BuildKit secret mounts expose secrets to a single build step without persisting them anywhere.

Audit with docker history and layer inspection: if the secret appears, the image is burned — rotate the secret and rebuild correctly. Runtime secrets arrive via environment, mounted files, or secret stores — never via the image.

Read-only root filesystem (--read-only) with tmpfs for writable scratch

Running with --read-only makes the container's filesystem immutable; the application gets writable scratch space via tmpfs mounts for temp files. A compromised process cannot persist malware, modify binaries, or alter configuration.

This breaks applications that expect to write to their own directory — which is exactly the information you want, because unexpected writes are either bugs or attacks. Fix the legitimate writes with tmpfs; the rest were liabilities.

--cap-drop/--cap-add, --security-opt seccomp/AppArmor profiles

Linux capabilities split root's powers into pieces; Docker grants containers a default subset. --cap-drop removes capabilities the workload does not need (start by dropping ALL, then adding back), --cap-add restores specific ones. Seccomp filters which syscalls the container may invoke; AppArmor confines file and capability access by profile.

These are defense-in-depth layers: each narrows what a compromised container process can do. Apply them progressively — drop capabilities first (high value, low breakage), then seccomp/AppArmor profiles tuned to the workload.

Image scanning: vulnerability databases, base-image freshness as the real fix

Scanners match installed packages against CVE feeds, but the fix for base-image CVEs is almost always "rebuild on a fresher base," not "patch the package by hand." Base-image freshness — rebuilding regularly from current upstream tags — is the operational control; scanning is the measurement.

Wire scanning into CI as a gate and schedule base rebuilds. A green scan on a six-month-old base is luck, not hygiene; freshness is what keeps it green.

Debugging order: docker ps, logs, inspect, events, exec, network inspect, stats

Debug in escalating order of invasiveness: ps (is it running? what exited?), logs (what did it say?), inspect (how is it configured?), events (what happened recently?), exec (look inside live), network inspect (can it reach things?), stats (is it resourced?).

The order matters because each step is cheaper than the next and answers the question the previous step raised. Random debugging — exec'ing into containers before reading logs — wastes the information the cheap steps give for free.

Hands-on labs

  1. Take a root-running image, add a non-root USER, fix file ownership, and verify with docker exec whoami.
    Convert the Dockerfile, rebuild, and confirm the application runs as the unprivileged user. The whoami output is the proof; the still-working application is the rest of the proof.
  2. Scan a base image with an open-source scanner; update the base tag and re-scan to compare.
    Scan, note the findings, bump the base tag, re-scan. The findings that vanish are the argument for base-image freshness as a practice.
  3. Reproduce a failing container and debug it strictly in order: logs, inspect, events, exec.
    Break a container on purpose, then work the debugging order without skipping steps. The discipline — cheapest evidence first — is the skill being trained.
  4. Run a service with --read-only and a tmpfs scratch mount; prove it functions without a writable root.
    Launch read-only with tmpfs for temp space and exercise the application fully. Working correctly with an immutable root is the hardened state, verified.

Self-check

  • List three concrete checks to run before shipping any image to production.
  • Explain why a secret baked into a layer is compromised even if later deleted in a higher layer.
  • Describe the debugging sequence for a container that exits immediately on start.
