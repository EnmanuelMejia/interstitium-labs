Module 1 — T-SQL vs Standard SQL: What's Actually Different

T-SQL is SQL Server's dialect, and the differences from standard SQL are exactly what this sequence teaches. This module maps the territory: TOP versus LIMIT, square-bracket identifiers, the type system, and the functions that differ. Everything after assumes this map.

Objectives

  • Name the major T-SQL deviations from ANSI SQL syntax and semantics.
  • Predict how TOP, OFFSET/FETCH, and bracketed identifiers behave differently from other dialects.
  • Convert a LIMIT/OFFSET query and an ANSI quoting example into idiomatic T-SQL.
  • Explain when a 'portable' query is and isn't worth the effort.

Key concepts

TOP (n) vs LIMIT; OFFSET/FETCH as the ANSI paging path

T-SQL pages with TOP (n) — the first n rows, unordered unless ORDER BY is present — or with the ANSI OFFSET/FETCH syntax (ORDER BY ... OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY), which requires ORDER BY. The lab runs the same paging query three ways — TOP, OFFSET/FETCH, and a ROW_NUMBER() window — and compares plans and logical reads. OFFSET/FETCH is the portable, deterministic choice for grids; TOP is the idiomatic quick form. Neither is deterministic without ORDER BY.

Bracketed [identifiers] vs double-quoted identifiers vs QUOTED_IDENTIFIER

T-SQL traditionally quotes identifiers with brackets ([Order Details]); ANSI uses double quotes, which T-SQL honors only with QUOTED_IDENTIFIER ON. The lab's porting exercise converts backticks and double-quoted aliases to brackets, annotating each change. Brackets are the idiomatic T-SQL choice and survive reserved words and spaces in names. Pick one quoting style per codebase and enforce it.

NULL handling quirks and collation-dependent string comparison

NULL semantics in T-SQL follow ANSI when ANSI_NULLS is ON — NULL never equals NULL — but legacy databases with the setting OFF behave differently, which is why the lab probes the toggle. String comparison additionally depends on collation: case sensitivity and accent sensitivity vary by database and even by column. The lab joins tables with different collations to feel the failure. In T-SQL, comparison behavior is a configuration question, not just a logic question.

SET options (ANSI_NULLS, ANSI_PADDING) and why legacy databases break without them

SET options change statement behavior per session: ANSI_NULLS governs NULL comparison, ANSI_PADDING governs trailing-space handling in varchar, and others affect indexed views, computed columns, and more. Legacy databases and old code depend on specific settings, which is why the lab writes a one-paragraph rule for session options in every new script. Set them explicitly at the top of scripts; inherited connection defaults are how subtle bugs travel between environments.

N-prefix for Unicode literals (N'text') and the nvarchar default habit

In T-SQL, 'text' is a non-Unicode literal and N'text' is Unicode — and comparing or assigning between varchar and nvarchar triggers implicit conversion with collation-dependent behavior. The checkpoint's enmanuel-versus-N'enmanuel' question is exactly this trap. The habit to build: N-prefix every string literal, nvarchar every string column and variable, unless you have a measured reason otherwise. Unicode by default prevents the class of bug you only find in production with real names.

@@ variables, system functions, and catalog views as dialect surface area

T-SQL exposes engine internals through @@ variables (@@ROWCOUNT, @@TRANCOUNT, @@ERROR), system functions, and catalog views (sys.tables, sys.dm_exec_query_stats) — a far richer introspection surface than ANSI provides. Working in T-SQL means learning this surface: it is how you inspect plans, sessions, and locks. The dialect's power is inseparable from its proprietary surface; portability and introspection trade against each other.

Hands-on labs

  1. Run the same paging query three ways — TOP, OFFSET/FETCH, and a ROW_NUMBER() window — and compare plans and logical reads; record which one you would use for a web grid.
  2. Create two tables with different collations, run a JOIN and an equality filter, and document where the comparison fails or silently succeeds.
  3. Write a porting exercise — take a 20-line MySQL/Postgres-flavored script (LIMIT, backticks, AUTO_INCREMENT, double-quoted aliases) and rewrite it in T-SQL, annotating each changed line with why.
  4. Probe SET options — toggle ANSI_NULLS ON/OFF in a session and run NULL comparisons, then write a one-paragraph rule for how you will set session options in every new script.

Self-check

  1. Without looking: rewrite SELECT * FROM Orders ORDER BY Id DESC LIMIT 10 OFFSET 20 in two T-SQL ways, and state which is guaranteed deterministic.
    Answer key
    T-SQL way 1: SELECT * FROM Orders ORDER BY Id DESC OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY; — way 2: the same with a ROW_NUMBER() OVER (ORDER BY Id DESC) subquery filtering rows 21–30. The OFFSET/FETCH form with an explicit ORDER BY is deterministic; TOP without ORDER BY promises nothing about which rows. Determinism comes from the ordering, not the paging keyword.
  2. Explain to an imaginary Postgres peer why WHERE Name = 'enmanuel' and WHERE Name = N'enmanuel' can behave differently on a varchar column with a non-default collation.
    Answer key
    On a varchar column, 'enmanuel' is a non-Unicode literal and N'enmanuel' is Unicode (nvarchar). Comparing a varchar column to an N literal can force an implicit conversion on the column side — killing index seeks and, under some collations, changing comparison semantics. Match the literal type to the column type; do not sprinkle N blindly.
  3. List three T-SQL-isms that would silently change meaning (not just error) if pasted into a standard-SQL engine.
    Answer key
    Three silent-changers: (1) = NULL never errors in some engines' lenient modes but is never true — always IS NULL; (2) TOP 10 without ORDER BY returns some 10 rows, and which 10 can change run to run; (3) string + concatenation with a NULL operand yields NULL (unlike some engines' || which treats it as empty). Silent wrong beats loud error every time — these are the ones to memorize.

Module 2 — Variables, Batches, and Control of Flow

Variables, batches, and control-of-flow statements are T-SQL's programming skeleton. This module covers DECLARE and SET, the GO batch separator, IF/WHILE logic, and the scoping rules that surprise newcomers. Labs build the scripting fluency every later module assumes.

Objectives

  • Declare, assign, and scope variables correctly across batches and GO boundaries.
  • Use IF/ELSE, WHILE, CASE, and the BREAK/CONTINUE pattern without infinite loops.
  • Choose between scalar variables, table variables, and temp tables for scratch data.
  • Debug a batch by reading messages, PRINT output, and the actual execution plan.

Key concepts

DECLARE/SET/SELECT assignment and the multi-row SELECT-assignment trap

Variables are declared with DECLARE, assigned with SET (one value) or SELECT (which can assign from a query). The trap: SELECT @x = col FROM t with five rows assigns the last row's value silently — no error, arbitrary row. The checkpoint calls it a bug factory for good reason. Use SET for scalar assignment; use SELECT assignment only when you have guaranteed single-row semantics, and even then prefer SET.

Batches, GO, and why a variable dies at the batch boundary

A batch is the unit of compilation — everything between GO markers compiles and executes together — and variables live only within their batch. The lab deliberately crosses a GO boundary and captures the must-declare error, then writes the fix as a comment. GO is a client-tool separator, not a T-SQL statement; the engine never sees it. Structure scripts so each batch is self-contained, and never assume state survives the separator.

IF/ELSE, WHILE loops, CASE expressions vs CASE statements

Control of flow is IF/ELSE for branching, WHILE for looping (with BREAK and CONTINUE), and CASE — which in T-SQL is an expression returning a value, not a statement. The lab's WHILE loop batches a staging table in 100-row chunks with a BREAK on an error flag, verifying no infinite loop on empty input. WHILE loops in T-SQL are a last resort (set-based first), but batching and maintenance scripts need them; write the exit condition before the loop body.

Table variables vs #temp tables: scope, statistics, and recompilation trade-offs

Table variables (@t) live in memory-ish scope, have no column statistics, and do not trigger recompiles — fine for small sets. Temp tables (#t) get statistics and indexes, handle large sets better, but participate in recompilation. The lab loads 50,000 rows into each, joins against a real table, and compares estimated versus actual row counts to derive the rule of thumb. Small and simple: table variable. Large or joined: temp table. Measure when it matters.

PRINT vs SELECT for debugging; RAISERROR (low severity) for progress messages

PRINT sends messages to the client without a result set — the quick debugging channel — while SELECT returns data. Low-severity RAISERROR with NOWAIT flushes progress messages immediately instead of buffering them to batch end, which is why long-running scripts use it for heartbeat output. The lab debugs by reading messages, PRINT output, and actual plans together. In production code, prefer proper logging tables; in development, PRINT and RAISERROR are the microscope.

Hands-on labs

  1. Build a scratch-lab script that declares variables, assigns them via both SET and SELECT, then deliberately crosses a GO boundary — capture the exact error and write the fix in a comment.
  2. Write a WHILE loop that processes a 1,000-row staging table in 100-row batches using a table variable as the work queue; add BREAK on an error flag and verify no infinite loop when the table is empty.
  3. Performance comparison lab — load 50k rows into a table variable and into a #temp table, join each against a real table, and compare estimated vs actual row counts in the plans; write the rule of thumb you would teach.
  4. Refactor a 40-line batch that repeats the same subquery three times into one that computes it once into a variable; measure logical reads before and after.

Self-check

  1. What does SELECT @x = col FROM t assign when t has 5 rows? Why is this a bug factory?
    Answer key
    It assigns the value from one arbitrary row — in practice the last row processed, but with no ORDER BY the order is undefined. Bug factory because it looks like an aggregation or a single-row fetch, silently discards 4 of 5 values, and 'works' in testing when the table has one row. If you expect one row, enforce it (TOP 1 + ORDER BY, or aggregate); if you expect many, you wanted a table, not a scalar.
  2. A variable works on line 10 but errors 'must declare' on line 12 — name the most likely cause in one sentence.
    Answer key
    A GO between line 10 and line 12. GO is a batch separator (a client-tool command, not T-SQL): everything after it is a new batch, and variables do not survive batch boundaries. The fix is structural — move the logic into one batch, or persist across batches with a temp table — not 'declare it again and hope'.
  3. Table variable vs #temp table: state one scenario where each is the better choice, with the reason.
    Answer key
    Table variable (@t): small work queues and short-lived sets — no statistics rebuilds, minimal logging, dies with the batch. #temp table: larger sets (rule of thumb: tens of thousands of rows and up), where the optimizer needs statistics and indexes to pick a sane plan. The lab in this module makes the crossover visible: table variables assume 1 row (older CE) and can produce catastrophic plans at 50k rows.

Module 3 — Stored Procedures: Input, Output, and Return

Procedures are T-SQL's unit of reusable server-side logic. This module covers parameter passing, output parameters, return codes, and the plan-caching behavior that makes procedures fast. You will build a procedure library with proper contracts and error handling.

Objectives

  • Write CREATE PROCEDURE with input parameters, OUTPUT parameters, and return codes used correctly.
  • Apply parameter defaults, named invocation, and the OUTPUT keyword at the call site.
  • Avoid the parameter-sniffing trap with local variables, OPTIMIZE FOR, or RECOMPILE — and know the cost of each.
  • Grant EXECUTE without granting direct table access (ownership chaining basics).

Key concepts

Input vs OUTPUT parameters; RETURN codes are for status, not data

Input parameters feed the procedure; OUTPUT parameters return data to the caller (declared with OUTPUT at both definition and call site); the RETURN code is an integer status — 0 for success, nonzero for failure modes. The lab refactors a data-via-RETURN procedure into OUTPUT-plus-status to establish the convention. Returning result sets is the third channel, for row data. Three channels, three jobs: status, scalar data, row data — never mix them.

Default values, named vs positional invocation

Parameters can declare defaults, and callers can invoke by position (@a, @b) or by name (@CustomerId = 42). Named invocation survives parameter reordering and documents intent at the call site — the checkpoint asks why it makes refactoring safer, and the answer is that positions shift while names persist. The lab calls its procedure all three ways. Use named notation in production code; reserve positional for ad-hoc queries.

Parameter sniffing: what it is, when it helps, when it wrecks a plan

The optimizer compiles the procedure's plan for the first parameter values it sees and reuses it — parameter sniffing. It helps when data is uniform (one good plan serves all) and wrecks when data is skewed (the plan built for the 5-order customer runs against the 100,000-order one). The lab builds the skew, observes the flip by varying the first call, and fixes it. When one procedure is fast for A and 50x slow for B on the same code path, sniffing is the prime suspect.

Local-variable copy, OPTION (RECOMPILE), OPTIMIZE FOR UNKNOWN — trade-offs

Parameter sniffing mitigations each cost something: copying the parameter to a local variable defeats sniffing but forfeits the good plan too; OPTION (RECOMPILE) builds a fresh plan per execution at CPU cost; OPTIMIZE FOR UNKNOWN uses average statistics, good for the typical case, bad for extremes. The lab fixes a skewed-data flip with a local-variable copy and re-measures. There is no free fix — choose the mitigation whose cost fits the procedure's call pattern.

Ownership chaining and the EXECUTE AS options at a high level

Ownership chaining lets a procedure access tables its caller cannot, when caller, procedure, and tables share an owner — the lab grants only EXECUTE to a low-privilege login and verifies the caller gets results without SELECT rights. EXECUTE AS changes the execution context deliberately (CALLER, OWNER, a specified user). The concept is privilege encapsulation: users get the procedure's controlled interface, not the tables' raw access. Design the chain before granting anything.

Hands-on labs

  1. Write usp_GetOrdersByCustomer with @CustomerId INT and @OrderCount INT OUTPUT; call it three ways (positional, named, with OUTPUT variable) and confirm the output value.
  2. Parameter-sniffing lab — build a skewed table (one customer with 100k orders, many with 5), write a procedure filtering by @CustomerId, and observe the bad-plan flip by calling with different first parameters; fix it with a local-variable copy and re-measure.
  3. Refactor a procedure that returns data via RETURN code into one using an OUTPUT parameter plus a status code; write a one-line comment at each call site explaining the convention.
  4. Security lab — create a low-privilege login/user, grant only EXECUTE on your procedure, and verify the caller can get results without SELECT rights on the base table.

Self-check

  1. OUTPUT parameter vs RETURN code vs result set: give one correct use for each.
    Answer key
    OUTPUT parameter: returning scalar values to the caller (e.g. the new @OrderId). RETURN code: an integer status — 0 for success, non-zero for failure modes the caller branches on. Result set: tabular data for the client to display. Mixing them up (returning data via RETURN, or status via a result set) forces every caller to parse the wrong channel.
  2. Your procedure is fast for customer A and 50x slower for customer B on the same code path — what is the prime suspect and what is the cheapest experiment to confirm it?
    Answer key
    Prime suspect: parameter sniffing — the plan was compiled for customer A's parameter values and is poisonous for B's data distribution. Cheapest experiment: run the slow case with OPTION (RECOMPILE); if it goes fast, the plan (not the code) was the problem. Then choose the durable fix: recompile hint, OPTIMIZE FOR, or plan guides — not 'it works on my machine'.
  3. Why does calling with named parameters (@CustomerId = 42) make future refactoring safer than positional calls?
    Answer key
    Positional calls bind by order: adding a parameter in the middle silently shifts every argument. Named calls (@CustomerId = 42) bind by name, so new optional parameters can be added anywhere without breaking existing callers. It is a one-word insurance policy against the most common stored-procedure refactoring accident.

Module 4 — User-Defined Functions: Scalar and Table-Valued

Scalar, inline table-valued, and multi-statement table-valued functions each have their place — and their performance traps. This module covers all three, the determinism rules, and why inline TVFs usually win. You will benchmark the types against each other.

Objectives

  • Write scalar, inline table-valued, and multi-statement table-valued functions, and state the performance profile of each.
  • Predict where a scalar UDF in a WHERE/SELECT will kill performance and rewrite it.
  • Use CROSS APPLY with an inline TVF to replace a correlated subquery.
  • Decide function vs procedure vs view for a given requirement.

Key concepts

Scalar UDFs: row-by-row execution and why they poison query plans (pre-2019) and scalar UDF inlining (2019+)

Scalar UDFs historically executed row-by-row — invoked per row, invisible to the optimizer, plan poison. The lab times a formatting UDF over 100,000 rows against an inline-TVF rewrite and the gap is the lesson. SQL Server 2019+ inlines eligible scalar UDFs into the query plan, removing the penalty when the function qualifies — but ineligible functions still pay it. The rule survives inlining: scalar UDFs in hot paths need proof, not hope.

Inline TVFs: parameterizable views the optimizer can fold in

An inline table-valued function is a single SELECT with parameters — a parameterizable view. Because it is one statement, the optimizer folds it into the outer query and plans the whole thing together. The lab's TopOrders function consumed via CROSS APPLY keeps a single efficient plan shape. Inline TVFs are the function form with (almost) no performance penalty: prefer them whenever the logic fits one query.

Multi-statement TVFs: flexible but opaque to the optimizer (fixed cardinality guesses)

A multi-statement TVF builds its result with control flow into a table variable and returns it — flexible, but the optimizer cannot see inside and guesses a fixed (historically tiny) row count. The lab observes the estimate-versus-actual gap in the plan and writes the code-review sentence it deserves. Use them when the logic genuinely needs procedural steps; expect plan-quality costs. The fixed guess poisons downstream joins, so keep their results small or materialize deliberately.

CROSS APPLY / OUTER APPLY as the TVF join pattern

APPLY invokes a table-valued function per row of the left side — CROSS APPLY keeps rows where the function returns rows, OUTER APPLY keeps all left rows (NULLs where empty). It replaces correlated subqueries in the SELECT clause with a join the optimizer can reason about. The lab rewrites a correlated scalar subquery as CROSS APPLY against an inline TVF from memory. APPLY is the idiom that makes TVFs composable in queries.

Determinism and schemabinding where it matters

A deterministic function returns the same output for the same input — required for indexed views and persisted computed columns. SCHEMABINDING locks the function's dependencies so underlying objects cannot change incompatibly, and it is a prerequisite for those performance features. Most functions need neither, but the ones that do fail cryptically without them. Declare determinism honestly; the optimizer trusts your declaration.

Hands-on labs

  1. Write a scalar UDF that formats an order total, use it in a SELECT over 100k rows, and time it; then rewrite as an inline TVF with CROSS APPLY and compare elapsed time and plans.
  2. Build an inline TVF TopOrders(@CustomerId, @N) returning the N most recent orders; consume it with CROSS APPLY over a customer list and verify the plan stays a single efficient shape.
  3. Multi-statement TVF lab — write one that builds a result via a table variable and control flow, use it in a join, and observe the plan's row estimate vs actual; write the sentence you would put in a code review.
  4. Decision lab — for five small requirements (lookup formatting, parameterized report slice, audit stamp, running total, permission-filtered rowset) pick function/procedure/view and defend each choice in one line.

Self-check

  1. Why can the same logic run 100x faster as an inline TVF than as a scalar UDF in a SELECT list?
    Answer key
    A scalar UDF in a SELECT list is a black box the optimizer cannot see into: it executes once per row (RBAR — row by agonizing row), blocking parallelism and hiding its cost from the plan. An inline TVF's body is expanded into the calling query — one set-based plan, indexes usable, parallelism possible. Same logic, different execution shape; the 100x gap is the per-row invocation overhead plus the lost optimization.
  2. When would you deliberately choose a multi-statement TVF despite its optimizer cost?
    Answer key
    When the logic genuinely needs multiple statements — procedural steps, intermediate temp work, conditional branches that cannot be expressed as a single query. A multi-statement TVF is still set-returning and composable (unlike a scalar UDF), so you pay the optimizer cost only where the single-statement form is impossible. Deliberate choice, documented reason — not a default.
  3. Rewrite a correlated scalar subquery in the SELECT clause as a CROSS APPLY against an inline TVF — do it from memory.
    Answer key
    Start from the scalar subquery: SELECT o.Id, (SELECT MAX(d.Amt) FROM Details d WHERE d.OrderId = o.Id) FROM Orders o. Rewrite: SELECT o.Id, x.MaxAmt FROM Orders o CROSS APPLY (SELECT MAX(d.Amt) AS MaxAmt FROM Details d WHERE d.OrderId = o.Id) x — or against an inline TVF: CROSS APPLY dbo.MaxAmtForOrder(o.Id) x. The APPLY form correlates per row but stays inside one set-based plan, and the TVF version names and reuses the logic.

Module 5 — Triggers: DML and INSTEAD OF

Triggers fire automatically on data changes — powerful, invisible, and easy to misuse. This module covers DML triggers, the inserted and deleted tables, INSTEAD OF triggers, and the discipline that keeps trigger logic maintainable. You will build audit triggers and learn their costs.

Objectives

  • Write AFTER triggers using the inserted/deleted pseudo-tables for multi-row operations.
  • Use INSTEAD OF triggers to make non-updatable views updatable and to enforce complex rules.
  • Explain trigger firing order, nesting, and recursion settings and their dangers.
  • Argue for and against triggers vs constraints vs application logic for a given rule.

Key concepts

inserted and deleted: set-based, possibly multi-row — never assume one row

Triggers expose the inserted and deleted pseudo-tables holding the new and old row versions — as sets, possibly containing many rows. The lab's multi-row trap writes a trigger assuming one row, fires a 3-row insert, and documents exactly what breaks; the fix is set-based logic joining inserted. Production DML is multi-row (bulk loads, application batches), so single-row assumptions fail precisely when it matters. Every trigger must be correct for N rows, including zero.

AFTER (FOR) vs INSTEAD OF: timing, what each can and cannot do

AFTER triggers fire after the DML completes (and can roll it back); INSTEAD OF triggers replace the DML entirely — the trigger's code performs the actual writes. AFTER is for auditing and cascading logic on real tables; INSTEAD OF is for making views updatable and intercepting writes. The lab builds both: an AFTER audit logger and an INSTEAD OF view writer. The original INSERT never touches the base tables under INSTEAD OF — the trigger owns the write.

UPDATE() and COLUMNS_UPDATED() for column-level logic

UPDATE(column) reports whether a specific column was part of the SET clause; COLUMNS_UPDATED() returns a bitmask of touched columns. They answer did the statement mention this column — not did the value change. The lab's audit trigger can use them to log only meaningful columns. Use them to skip expensive logic when irrelevant columns were updated, not as change detection.

Nested triggers, recursive triggers, and sp_configure 'nested triggers'

Triggers can fire other triggers (nesting) and, if enabled, themselves (recursion) — the lab wires two tables' triggers to update each other and observes the cascade, then writes the guard it would ship. The server's nested-triggers setting gates the behavior globally. Recursion without a guard is an infinite loop wearing a trigger costume. Default posture: design triggers to never need recursion, and guard the ones that might.

Why triggers hide logic: debugging, performance, and the case for constraints first

Triggers execute invisibly — no call in the application code, nothing in the procedure — which makes behavior surprising and debugging hard. They also run per DML with plan and locking consequences the caller never sees. The checkpoint's placement question is the discipline: CHECK constraints for simple rules, triggers for complex row logic, application for workflow. Triggers are the right tool sometimes; they are never the first tool. Prefer the visible mechanism.

Hands-on labs

  1. Write an AFTER UPDATE trigger that logs every price change to an audit table with old/new values, user, and timestamp; test with a single-row and a 500-row UPDATE and verify both log correctly.
  2. INSTEAD OF lab — create a view joining two tables, make it updatable with an INSTEAD OF INSERT trigger that splits the row correctly; then attempt a bad insert and confirm your validation fires.

Self-check

  1. Your trigger works in testing but misses rows in production — what is the single most likely cause?
    Answer key
    The trigger assumes one row — it was tested with single-row inserts, but production does multi-row INSERT...SELECT and bulk loads. Code like SELECT @x = col FROM inserted silently processes one arbitrary row and drops the rest. The single most likely cause of 'works in test, misses rows in prod' is always row-count assumptions in trigger code. Triggers must be set-based: join against inserted/deleted, never scalar-assign from them.
  2. INSTEAD OF trigger on a view: who performs the actual base-table writes, and what happens to the original INSERT?
    Answer key
    The trigger performs the writes: an INSTEAD OF trigger replaces the original INSERT/UPDATE/DELETE — the statement never touches the base tables itself. Whatever the trigger does not explicitly write simply does not happen. That is the power (updatable views, custom write logic) and the danger (forget a table and data silently vanishes).
  3. Name one rule that belongs in a CHECK constraint, one that belongs in a trigger, and one that belongs in the application — with the reason for each.
    Answer key
    CHECK constraint: single-row, declarative rules ('quantity > 0') — the optimizer understands them and they are cheap. Trigger: cross-row or cross-table rules ('an order's total must equal the sum of its lines') that constraints cannot express. Application: workflow and UX rules ('managers approve discounts over 10%') that need process context the database does not have. Each layer enforces what it can see cheapest; pushing app rules into triggers (or integrity rules into the app) is the classic layering mistake.

Module 6 — Error Handling: TRY/CATCH, THROW, and Transactions

Production code expects failure. This module covers the TRY/CATCH model, THROW versus RAISERROR, error functions, and the transaction discipline that keeps partial failures from corrupting data. You will build procedures that fail cleanly and log usefully.

Objectives

  • Structure TRY/CATCH blocks so no error path leaves a transaction open.
  • Use THROW vs RAISERROR correctly and re-throw with original context preserved.
  • Pair XACT_ABORT with explicit transactions and know what each setting changes.
  • Write an idempotent, retry-safe data-load procedure with proper rollback semantics.

Key concepts

TRY/CATCH scope: what is catchable, batch-aborting vs statement-aborting errors

TRY/CATCH catches most runtime errors, but not all: compilation errors, batch-aborting errors (like broken connections), and errors of severity that terminate the batch escape the CATCH. Statement-aborting errors (constraint violations, divide by zero) are catchable. The lab's money-transfer procedure proves the pattern: inject failure between debit and credit, and no partial commit survives. Know your error's class before trusting the CATCH — test the failure you fear, not a convenient one.

ERROR_NUMBER/MESSAGE/SEVERITY/STATE/LINE/PROCEDURE in the CATCH block

Inside CATCH, the ERROR_* functions report the caught error's number, message, severity, state, line, and procedure — but only inside the CATCH block; outside, they return NULL. The lab's logging procedure records all six for both a divide-by-zero and a foreign-key violation. Capture them immediately into variables or a log table. Diagnostics have a scope; respect it.

THROW (no args) re-throw vs RAISERROR; custom error numbers >= 50000

THROW with no arguments inside CATCH re-throws the original error with its context intact — the correct re-throw. RAISERROR with a copied message loses the original number, line, and state. Custom errors use numbers at or above 50000. The checkpoint asks why bare THROW beats RAISERROR: fidelity of context. Modern code uses THROW; RAISERROR survives for legacy and for low-severity informational messages.

BEGIN/COMMIT/ROLLBACK TRAN, @@TRANCOUNT, and the nested-transaction myth

T-SQL transactions nest only in name: @@TRANCOUNT counts BEGINs, but there is one real transaction — inner COMMITs merely decrement the count, and only the outermost COMMIT commits. The checkpoint asks how many real transactions exist when a procedure calls another with its own BEGIN/COMMIT: one. The myth bites when an inner ROLLBACK resets the count to zero and the outer COMMIT then errors. Write transaction logic as if nesting does not exist, because functionally it does not.

SET XACT_ABORT ON and why most production procedures want it

XACT_ABORT ON makes any runtime error abort the batch and roll back the entire transaction; OFF leaves behavior error-dependent — some errors roll back the statement, some the batch, some nothing. The lab runs the same failing batch both ways and documents the difference. Most production procedures want ON because partial transactions are worse than failed ones. Put it in the team template and stop debating per procedure.

Hands-on labs

  1. Write a money-transfer-style procedure (debit A, credit B) with TRY/CATCH; inject a failure between the two statements and prove with @@TRANCOUNT and a balance query that no partial commit survives.
  2. XACT_ABORT lab — run the same failing batch with XACT_ABORT OFF and ON, and document the difference in what rolls back; write the one-paragraph rule for your team's template.
  3. Error-context lab — catch a divide-by-zero and a foreign-key violation, and build a logging procedure that records ERROR_NUMBER(), ERROR_MESSAGE(), ERROR_LINE(), and ERROR_PROCEDURE(); verify the log row for both.
  4. Idempotency lab — write a staging-to-fact loader that can be re-run safely after a mid-load failure (checkpoints table or MERGE semantics), and test by killing it halfway twice.

Self-check

  1. After a CATCH block runs ROLLBACK, what is @@TRANCOUNT and why does that matter to the caller?
    Answer key
    @@TRANCOUNT is 0: ROLLBACK rolls back everything to the outermost transaction and resets the count. It matters because the caller can no longer COMMIT — any COMMIT with @@TRANCOUNT = 0 errors ('no corresponding BEGIN'). The callee must signal the rollback (return code / re-throw) so the caller does not blunder into committing nothing.
  2. THROW; with no arguments inside a CATCH block does what — and why is that better than RAISERROR with a copied message?
    Answer key
    THROW; with no arguments re-throws the original error — same number, severity, state, and original line number. That beats RAISERROR with a copied message because the copy loses fidelity: wrong line number, possibly wrong severity, and a maintenance burden (every message edit in two places). In a CATCH block, bare THROW; is almost always the right call.
  3. A procedure opens a transaction, calls another procedure that also has BEGIN/COMMIT TRAN — how many real transactions are there, and what does the inner COMMIT actually do?
    Answer key
    There is one real transaction. Nested BEGIN TRAN only increments @@TRANCOUNT; inner COMMIT only decrements it. The inner procedure's COMMIT does not commit anything — and worse, if the inner proc ROLLBACKs, the outer's COMMIT will fail. Procedures that manage their own transactions must check @@TRANCOUNT on entry and only commit what they began.

Module 7 — Dynamic SQL and Injection Defense

Dynamic SQL builds queries as strings — powerful and dangerous. This module covers sp_executesql, parameterization, and the injection attack patterns you must understand to defend against. You will attack a deliberately vulnerable lab procedure, then fix it properly.

Objectives

  • Build dynamic SQL with sp_executesql and strongly-typed parameters instead of EXEC().
  • Sanitize object names with QUOTENAME and never concatenate user input into identifiers raw.
  • Demonstrate a working injection attack on a lab database, then close it.
  • Decide when dynamic SQL is justified (optional filters, dynamic pivots, DDL automation) vs when static SQL wins.

Key concepts

sp_executesql with @params: plan reuse and type safety

sp_executesql takes a parameterized statement plus typed @params — the engine caches one plan per statement shape and binds values safely at execution. The lab builds the optional-filter report three ways and compares plans and reads: dynamic-with-params wins on skewed data where static OR-chains and recompile-everything do not. Typed parameters also enforce type safety at the boundary. Dynamic SQL is justified for optional filters, dynamic pivots, and DDL automation; everywhere else, static SQL wins on clarity alone.

EXEC('...') string concatenation: the injection surface

EXEC with a concatenated string builds SQL by gluing user input into command text — every glued value is a potential injection payload. It also defeats plan reuse, since each distinct string is a new plan. The lab's vulnerable search procedure is the specimen: attack it, watch it fall, then replace it. EXEC('...') has legitimate uses (DDL automation with no user input); user input is never one of them.

QUOTENAME() for identifiers; parameterize values, quote names, never mix

Dynamic object names cannot be parameterized — so QUOTENAME() brackets them safely, escaping any embedded bracket. Values, by contrast, must be parameters, never quoted names. The lab's table-name procedure demonstrates both the raw-concatenation injection and the QUOTENAME fix, plus the allow-list alternative (validate against sys.tables). The preference order is allow-list first, QUOTENAME second, raw concatenation never. Two kinds of input, two defenses, never mixed.

Classic payloads: ' OR 1=1 --, stacked queries, and why parameterization kills them

The classic payloads exploit string concatenation: ' OR 1=1 -- turns a login check into a tautology, stacked queries append a second statement (a DROP TABLE in the lab's scratch demo). Parameterization kills them because parameters are never parsed as SQL — the engine treats the input as a value at the protocol level, whatever characters it contains. The lab attacks the vulnerable version, then re-runs both attacks against the parameterized rewrite and watches them fail. Understanding the payload is what makes the defense obvious.

Dynamic SQL scope: temp tables and variables don't cross the EXEC boundary

Code run through sp_executesql or EXEC shares the session — so #temp tables created outside are visible inside — but not the batch scope: outer variables are invisible, and variables declared inside do not return. The lab documents the rule by testing both. Pass values in through sp_executesql's @params; bring results out the same way or through the temp table. Scope bugs in dynamic SQL are silent until runtime, so learn the boundary deliberately.

Hands-on labs

  1. Vulnerable-then-fixed lab — write a search procedure that concatenates @SearchTerm into the SQL string; attack it with ' OR '1'='1 and a stacked DROP TABLE on a scratch table; then rewrite with sp_executesql parameters and re-run both attacks to prove they fail.
  2. QUOTENAME lab — write a procedure that takes a @TableName and returns row counts; first version concatenates raw (demonstrate injection via a crafted name), fixed version uses QUOTENAME; also show the allow-list alternative.
  3. Optional-filter lab — build a report procedure with 5 optional filters three ways — dynamic SQL with sp_executesql, static SQL with (@p IS NULL OR col = @p), and OPTION (RECOMPILE); compare plans and reads on skewed data and write the guidance.
  4. Scope lab — create a #temp table in the outer batch, try to read it inside sp_executesql (works — same session), then try to reference an outer variable (fails); document the rule.

Self-check

  1. Why does sp_executesql with parameters defeat ' OR 1=1 -- while string concatenation does not? Answer at the level of how the engine treats the input.
    Answer key
    sp_executesql with parameters sends the SQL text and the values separately: the engine parses the text once, then binds values as data — ' OR 1=1 -- arrives as a string value, never as syntax. String concatenation builds one blob of text that is then parsed, so the attacker's input is parsed as SQL. The boundary is parse-time: parameters cross it as data; concatenation smuggles them in as code.
  2. You must accept a table name from the user. List the two safe approaches in order of preference.
    Answer key
    Preferred: (1) do not accept it at all — map user input to a fixed allowlist of table names (or an enum) and reject everything else. (2) If truly dynamic, sanitize with QUOTENAME() so the name is always bracket-delimited as a single identifier. Never concatenate raw input; QUOTENAME is the seatbelt, the allowlist is not driving off the cliff.
  3. A dynamic pivot query is slow on every run — what plan-cache behavior explains it, and what is the standard mitigation?
    Answer key
    Each distinct concatenated string is a different plan-cache entry: the dynamic pivot generates a new string per column list, so every run compiles fresh and the cache fills with single-use plans. Standard mitigation: parameterize with sp_executesql so one plan serves all executions (or, where the shape genuinely varies, accept recompilation consciously with OPTION (RECOMPILE) instead of polluting the cache).

Module 8 — SSMS / Azure Data Studio Workflow and Query Store Basics

The final module is the workflow: SSMS Object Explorer, the actual execution plan, Query Store, and Extended Events. You will capture a baseline, identify a regression, and document the fix — the complete performance-troubleshooting loop in the tools professionals use.

Objectives

  • Set up a productive SSMS or Azure Data Studio workflow: templates, snippets, actual plans, and client statistics.
  • Enable and read Query Store: regressed queries, wait stats, and plan forcing.
  • Capture a baseline, introduce a regression on purpose, and identify it in Query Store.
  • Write a personal runbook: the 5 checks you run when 'the database is slow'.

Key concepts

SSMS vs Azure Data Studio: when each shines; both are free

SSMS is the full Windows-native management studio — deep administration, graphical plans, mature tooling. Azure Data Studio is the lighter, cross-platform editor with notebooks, source control integration, and a modern extension model. The lab does the same plan capture in both and notes one strength per tool. Both are free; the choice is workflow, not budget. Learn one deeply, know the other exists.

Actual execution plans, live query stats, SET STATISTICS IO/TIME

Actual execution plans show what the engine did — operators, row counts, costs — versus estimated plans' predictions; live query stats animate long queries in flight. SET STATISTICS IO reports logical and physical reads per table; SET STATISTICS TIME reports parse, compile, and execution milliseconds. The lab captures plan plus IO/TIME as the baseline file for its slowest query. These three outputs are the evidence kit: capture them before asking anyone for help, as the checkpoint demands.

Query Store: query_id/plan_id model, runtime stats, wait categories

Query Store persists query history in the database: each query gets a query_id, each plan shape a plan_id, with runtime stats and wait categories recorded per plan. The model answers what changed: the checkpoint's two-plan_ids scenario means the plan flipped, and remediation is forcing the good plan or fixing the statistics that caused the flip. Wait categories attribute the time — CPU, I/O, locks — so tuning starts from evidence. It is flight-data recording for queries; enable it on every database you care about.

Regressed queries report and plan forcing (and when to un-force)

The Regressed Queries report surfaces queries whose recent performance diverged from baseline — the lab finds its deliberately regressed workload there. Plan forcing pins the good plan_id as treatment, but the checkpoint insists it is treatment, not cure: the underlying cause (stale statistics, data skew, schema change) still needs investigation. Un-force when the cause is fixed and the optimizer chooses well again. Forcing without follow-up is how a good plan becomes tomorrow's bad one.

Baselines: capturing 'normal' before you need it

A baseline is the recorded normal — plan shapes, IO counts, durations — captured while the system is healthy. The lab's Query Store exercise builds history with 20 workload runs, then introduces a regression on purpose and finds it in the Regressed Queries view. Without a baseline, every slowdown is a mystery; with one, it is a diff. Capture baselines for the queries that matter before the incident, because you cannot reconstruct normal afterward.

Hands-on labs

  1. Tooling setup lab — install SSMS (or Azure Data Studio), configure 'Include Actual Execution Plan' shortcut, save two code snippets (TRY/CATCH transaction template, sp_executesql template), and connect to your lab instance.
  2. Query Store lab — on a scratch database enable Query Store, run a workload 20 times to build history, then force a bad plan (hint or stats change) and find the regression in the 'Regressed Queries' view; force the good plan and verify recovery.
  3. Slow-database drill — pick your slowest lab query from Module 4, capture its plan + STATISTICS IO/TIME output as a baseline file, then write the 5-step runbook you would follow if a teammate reported it slow tomorrow.
  4. Cross-tool lab — do the same plan capture in both SSMS and Azure Data Studio and note one thing each tool does better for your workflow.

  1. Query Store shows two plan_ids for one query_id with very different avg durations — what happened, and what are your two remediation options?
    Answer key
