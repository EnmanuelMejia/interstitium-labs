The sequence

What this sequence is, and how to work it.

What this is: a complete engineering study sequence for modern C++, built from the public C++ language reference. It bridges from C to C++20 across eight modules: the compilation model and toolchain, RAII and smart pointers, STL containers and algorithms, move semantics, templates and concepts, concurrency, CMake build systems, and sanitizer-driven testing and debugging — ending in a capstone that demands a concurrent, tested, sanitizer-clean C++20 program.

Who it is for: programmers comfortable in C or another systems language who want idiomatic modern C++ — the RAII, move-semantics, template-metaprogramming C++ of the last decade, not the C-with-classes of the 1990s. It pairs with the companion C Programming for Systems sequence: take C first if pointers and manual memory are new to you.

Prerequisites: fluency with pointers, memory management, and compilation in C (or equivalent experience); a Linux or macOS machine (or WSL) with g++ or clang++, CMake, and gdb; comfort reading template-heavy compiler errors without panic. The sequence names which standard (C++11/14/17/20) each feature comes from, so you always know what you are using.

How to use it: work the modules in order — RAII before move semantics before concurrency is a deliberate dependency chain. Compile everything with -Wall -Wextra -Werror -std=c++20, run every test under ASan+UBSan (and TSan for the concurrency module), and keep a bug log: each sanitizer report, what it meant, and the fix. The checkpoints are designed to be answered in writing; the capstone is the proof.

Outcomes

What you will be able to do.

  • Close the gap from C to modern C++: write idiomatic, resource-safe code using RAII, move semantics, and the STL.
  • Build, test, and debug a multi-file C++ project with CMake, sanitizers, and gdb on a home machine or free-tier CI.
  • Apply concurrency primitives (threads, mutexes, atomics) correctly and reason about data races and lifetimes.
  • Design generic, reusable components with templates and know which features come from C++11, 14, 17, and 20.

Module 1

From C to C++: the compilation model and toolchain refresher

Learning objectives

  • Explain how a C++ program is compiled: preprocessing, translation units, one-definition rule, and linking.
  • Read and fix the most common compiler and linker errors (undefined reference, multiple definition, ODR violations).
  • Set up a sane modern toolchain (g++/clang++) with warnings enabled and a chosen language standard.

Key concepts

Translation units and header/source separation

A C++ program is built from translation units — each .cpp file plus everything it includes — compiled independently and linked together. Headers declare the interface; sources define the implementation. The separation is what lets large codebases compile incrementally and what makes the linker's contract (one definition per program) enforceable.

Coming from C, the model is familiar; what is new is how much more the language does per translation unit — templates, inline functions, and constexpr all bend the old rules, and this module maps exactly where.

The one-definition rule (ODR)

Across the whole program, each variable, function, and class must have exactly one definition — but inline functions, templates, and classes defined identically in headers are exempt, because the linker merges the duplicates. Violating the ODR (different definitions in different units) is undefined behavior that the linker usually cannot catch.

The checkpoint's true/false is the key case: inline in a header is ODR-safe by design — that is what inline means to the linker, not (only) a hint to the compiler.

Name mangling basics and extern "C"

C++ encodes function signatures into symbol names (mangling) so overloads can coexist — which is why a C++ function and a C function with the same name produce different symbols. extern "C" disables mangling for a declaration, giving the symbol C linkage so C++ code can call C libraries and vice versa.

The lab's nm comparison makes this visible: build without the guard, watch the link fail on mismatched symbols, add extern "C", watch it succeed. Mangling is invisible until it bites; now you have seen the teeth.

Compiler flags: -Wall -Wextra -Werror, -std=c++20

The same warning discipline as C, plus a language-standard flag that selects which C++ you are writing. -std=c++20 enables concepts, ranges, and the rest of the modern feature set this sequence teaches — without it, the compiler defaults to an older dialect and modern code simply fails.

Pin the standard explicitly in every build. 'It compiled' means nothing if you do not know which language version compiled it.

Build-time vs link-time errors

Build-time (compile) errors are about one translation unit: syntax, types, missing declarations. Link-time errors are about the whole program: undefined references (a promise with no definition) and multiple definitions (two definitions keeping the promise).

The diagnostic habit: read which phase failed first. An 'undefined reference' after a clean compile is a linker problem — check the three causes from the checkpoint (never defined, defined but not linked in, or C/C++ linkage mismatch) before touching the code.

Static vs shared libraries at a high level

Static libraries (.a) are archives of object files linked into your binary — self-contained, larger binaries, no runtime dependency. Shared libraries (.so) are linked at load time — smaller binaries, shared in memory, but a runtime dependency that must be present and version-compatible.

For learning and for the capstone, static linking keeps deployment simple. Know the tradeoff exists; reach for shared libraries when distribution size or in-memory sharing actually matters.

Include guards vs #pragma once

Same problem as C, same solutions: include guards (portable, standard) and #pragma once (concise, universally supported in practice though not in the standard). The checkpoint asks why the non-standard one thrives — because it is one line, cannot collide with another header's guard macro, and every major compiler honors it.

Many codebases use both. Pick one convention per project and move on; the important thing is that every header has protection.

Forward declarations and reducing compile dependencies

A forward declaration (class Widget;) lets you declare pointers and references without including the full header — which means fewer includes, faster builds, and fewer rebuild cascades when a header changes. Include what you use, forward-declare what you only name.

This is a build-performance discipline that compounds: in large codebases, include-what-you-use plus forward declarations is the difference between seconds and minutes per rebuild. Start the habit on small projects so it is automatic on large ones.

Hands-on labs

  1. Lab 1 — C to C++ warnings. Take a small C program (hello world plus one helper in a separate .c file), compile it, then rename the sources to .cpp and compile with g++ -std=c++20 -Wall -Wextra -Werror. Record every new warning and explain each one in your own words.
  2. Lab 2 — ODR violation, three fixes. Deliberately define the same non-inline function in two translation units, link them, and observe the linker error. Fix it three ways: mark one static, move the definition to a single .cpp file, and declare it inline — and explain why each fix is legal.
  3. Lab 3 — Missing symbol. Declare a function in a header but never define it; build, read the undefined-reference error, fix it. Repeat with a variable declared extern but never defined. Learn the error message's shape.
  4. Lab 4 — extern "C" bridge. Create a tiny C library (add.c/add.h) and call it from C++. Build without the linkage guard to see mangling break the link (use nm to compare symbols), then fix with extern "C".

Self-check questions

  1. Given a linker error message showing 'undefined reference to X', list the three most likely causes and how to check each one.
  2. True or false with justification: a function marked inline in a header can be defined in multiple translation units without violating the ODR.
  3. Explain in two sentences why #pragma once is common practice even though it is not part of the language standard.

Module 2

RAII and resource management

Learning objectives

  • Internalize the rule of three/five/zero and know when each applies.
  • Implement RAII wrappers that acquire in the constructor and release in the destructor, surviving exceptions.
  • Use std::unique_ptr, std::shared_ptr, and std::weak_ptr correctly, including the cyclic-reference pitfall.

Key concepts

RAII: resource acquisition is initialization

RAII ties a resource's lifetime to an object's lifetime: the constructor acquires (opens the file, allocates the memory, takes the lock), the destructor releases. Because C++ guarantees destructors run when objects go out of scope — including during exception unwinding — the resource is released on every path, with no explicit cleanup code to forget.

This is the single most important idea in C++. Every smart pointer, lock guard, and container is RAII; every leak and double-free you fought in C is what RAII eliminates. Internalize it and modern C++ starts making sense.

Rule of Three (C++98), Rule of Five (C++11), Rule of Zero

If a class needs a custom destructor, copy constructor, or copy assignment (the Three), it almost certainly needs all three — otherwise copying does the wrong thing (the classic double-free). C++11 adds move constructor and move assignment (the Five). The Rule of Zero says: design so you need none of them — let member smart pointers and containers do the work.

The checkpoint's logging-destructor trap: defining any destructor suppresses the implicit move operations, silently turning moves into copies. The Rule of Zero avoids the trap entirely: no custom destructor, no problem.

std::unique_ptr: exclusive ownership; std::make_unique (C++14)

unique_ptr is sole ownership of a heap object: it cannot be copied, only moved, and it deletes on destruction. It is the default smart pointer — reach for it first, always. std::make_unique constructs the object and the pointer in one call, avoiding the (brief, real) window where a raw new could leak if an exception intervenes.

Use unique_ptr for every 'this function/class owns that object' relationship. If you cannot name a second owner, you do not need shared_ptr.

std::shared_ptr: reference counting; std::make_shared

shared_ptr implements shared ownership via reference counting: the object is deleted when the last shared_ptr dies. std::make_shared allocates the object and the control block together — one allocation instead of two, and exception-safe.

Shared ownership is genuinely needed sometimes (graphs, caches, observers with lifetime requirements), but it is also the most abused smart pointer: cycles leak (see weak_ptr), and shared mutable state is a design smell. The checkpoint's observer question has one right answer — weak_ptr — because observation must not extend lifetime.

std::weak_ptr and breaking cycles

weak_ptr observes a shared_ptr-managed object without owning it: it does not keep the object alive. lock() attempts to get a shared_ptr — returning empty if the object is already gone, which is exactly the information the observer needs.

The parent/child lab makes the cycle concrete: shared_ptr both ways, use_count never reaches zero, destructors never run — a leak with no raw pointers in sight. The fix is one word: make the back-reference weak.

Custom deleters

Smart pointers are not only for delete: a custom deleter lets unique_ptr manage any resource — fclose for FILE*, close for file descriptors, or a pool-release function. unique_ptr<FILE, decltype(&fclose)> turns a C file handle into an RAII object in one declaration.

This is how RAII absorbs C APIs: the acquisition stays a C call, the release becomes a destructor. The FileHandle lab's first exercise is the pattern in miniature.

Exception safety of destructors: noexcept by default in C++11

Since C++11, destructors are implicitly noexcept — if a destructor throws during stack unwinding, the program terminates. Destructors must never throw: they release resources, they do not report errors.

Design accordingly: if cleanup can fail, provide a separate close() that can report errors, and make the destructor a best-effort release. Throwing from a destructor is not an error-handling strategy; it is a termination strategy.

Raw new/delete as a code smell

In modern C++, a raw new or delete in application code is a smell: it means ownership is being managed by hand where a smart pointer or container should manage it. The capstone bans them outright — zero raw new/delete — and the codebase gets simpler, not harder.

new still exists for library authors and truly custom allocation. For everyone else, make_unique, make_shared, and containers cover every legitimate need. If you type 'new', stop and ask what is managing the delete.

Hands-on labs

  1. Lab 1 — FileHandle RAII. Write a class FileHandle that opens a FILE* in its constructor and fclose()es in its destructor. Leak a raw handle on purpose to compare, then show the RAII version cleans up even when an exception is thrown mid-scope.
  2. Lab 2 — Rule of Three, violated then honored. Write a class with a heap buffer that violates the rule of three (copy it twice, double-free). Observe the crash, then fix it three ways: user-defined copy operations, deleted copies plus moves, and finally std::vector replacing the raw pointer — the Rule of Zero.
  3. Lab 3 — The cycle. Build a parent/child graph with shared_ptr in both directions; print use_count() to show the leak. Fix with weak_ptr on the back-reference and verify destruction order with constructor/destructor prints.
  4. Lab 4 — No raw new. Refactor an existing lab to never call new or delete directly — replace with make_unique/make_shared — and confirm it still compiles and passes a smoke run.

Self-check questions

  1. When is the Rule of Zero the right answer, and what two conditions must the member types satisfy for it to work?
  2. Your class manages no raw resources but you define a custom destructor for logging. What happens to the implicitly generated copy operations, and why is that a hazard?
  3. Design question: you need shared ownership with occasional observation that must not extend lifetime. Which smart pointer goes on the observer, and what does lock() tell you?

Module 3

STL containers, algorithms, and iterators

Learning objectives

  • Choose the right container for the job from vector, deque, list, set/map, and unordered set/map, with complexity reasoning.
  • Compose generic code with iterators and the <algorithm> library instead of hand-written loops.
  • Avoid iterator invalidation bugs by knowing which operations invalidate which iterators per container.

Key concepts

std::vector as the default sequence container

vector is contiguous, cache-friendly, and the right default for sequences: push_back amortized O(1), random access O(1), and iteration at memory speed. The other sequence containers exist for specific needs — deque for efficient front insertion, list for stable iterators under insertion — not as general replacements.

Default to vector; switch only with a measured reason. Most 'I need a list' instincts are wrong on modern hardware, where cache locality beats pointer-chasing asymptotics for realistic sizes.

Associative vs unordered containers and complexity guarantees

Ordered associative containers (map, set) are tree-based: O(log n) operations with iteration in sorted order — the checkpoint's 'ordered unique keys with range queries' answer is std::map. Unordered containers (unordered_map) are hash-based: average O(1) lookup with no ordering — the second answer.

The tradeoff is ordering versus speed, plus hash quality: a bad hash function turns O(1) into a bad day. Choose by the access pattern you actually have, and benchmark the lab's three word-counters to feel the difference.

std::array (C++11) and std::string_view (C++17)

array is a fixed-size sequence with vector-like interface and zero overhead — the modern replacement for C arrays when the size is known at compile time. string_view is a non-owning view over character data: pointer plus length, no allocation, no copy.

string_view is the performance answer to 'I need to look at this string but not own it' — the case-insensitive search lab shows the allocation savings directly. The rule: string_view for parameters and views, std::string for ownership.

Iterator categories and ranges (C++20 std::ranges)

Iterators abstract 'position in a sequence' with capability categories (input through random-access); algorithms are written against categories, not containers, which is why sort works on vector and deque alike. C++20 ranges lift this further: views compose lazily (filter | transform) without intermediate containers.

The lab's rewrite — copy_if + transform versus ranges views — shows the readability payoff: the ranges version says what it computes, not how it iterates. Prefer algorithms and views over hand loops; the hand loop is where the off-by-one lives.

The erase-remove idiom

std::remove does not remove anything — it shuffles the kept elements forward and returns the new logical end, leaving the tail in a valid-but-unspecified state. The idiom v.erase(v.remove(...), v.end()) pairs it with erase, which actually destroys the tail and shrinks the container.

The checkpoint's true/false exists because this misnaming has burned everyone once. C++20's std::erase / std::erase_if finally do the whole job in one call — use them in new code, know the idiom for old code.

Lambda expressions (C++11) and generic lambdas (C++14)

Lambdas are anonymous function objects defined inline — the predicates and comparators that algorithms take as arguments. Capture lists ([&], [=], or explicit captures) control what surrounding state the lambda sees; C++14's auto parameters make lambdas generic.

Capture discipline matters: [&] captures by reference (dangling risk if the lambda outlives the scope), [=] by value (copy cost, and the classic 'this' capture surprise). Capture explicitly and minimally — the default captures are for quick code, not for code that lives.

if constexpr (C++17) for generic code

if constexpr evaluates the condition at compile time and discards the untaken branch — including branches that would not compile for the given template arguments. It replaces tag dispatch and SFINAE tricks for the common 'do X for this type, Y for that type' pattern inside templates.

The concept entry notes what it is not: it does not choose containers at runtime. It is a compile-time tool for generic code — use it to write one template that handles several type families cleanly.

Iterator invalidation rules per container

vector invalidates iterators at and after an insertion point on reallocation, and at erase positions; list invalidates only the erased element; associative containers invalidate only erased elements; deque invalidates on most insertions. These rules are per-container contracts you must know cold.

The lab's dangling-iterator demonstration — store iterators, push_back past capacity, watch ASan complain — exists because this bug is silent without sanitizers and catastrophic with them. When in doubt, reserve() up front or re-acquire iterators after mutation.

Hands-on labs

  1. Lab 1 — Three word counters. Write a word-frequency counter three ways: std::map, std::unordered_map, and std::vector<std::pair> with linear search. Benchmark all three on a 1 MB text file with std::chrono and write up which wins and why.
  2. Lab 2 — Algorithms vs ranges. Rewrite a filter-and-transform loop twice: once with std::copy_if + std::transform, once with C++20 ranges views. Confirm identical output on edge cases (empty input, all-filtered-out).
  3. Lab 3 — Dangling iterator, caught. Store iterators into a vector, push_back past reallocation, and demonstrate the dangling iterator with ASan. Fix by reserving capacity up front or by re-acquiring iterators.
  4. Lab 4 — string_view search. Implement case-insensitive word search using std::string_view (no copies) over a large buffer; compare against a std::string version for allocation count with simple instrumentation.

Self-check questions

  1. You need ordered unique keys with range queries; you need average O(1) lookup with no ordering. Name the container for each and justify.
  2. True or false with justification: std::remove actually removes elements from a vector.
  3. After v.erase(it) on a std::vector, which iterators remain valid? Contrast with std::list.

Module 4

Move semantics and value categories

Learning objectives

  • Classify expressions as lvalue, xvalue, or prvalue and know which can bind to which reference type.
  • Implement correct, noexcept move constructors and move assignment operators.
  • Apply perfect forwarding with forwarding references and std::forward without reference-collapse mistakes.

Key concepts

Value categories: lvalue, xvalue, prvalue

Every expression has a value category. lvalues name persistent objects (things with addresses you can take). prvalues are temporaries — pure rvalues like 42 or a returned-by-value object. xvalues are 'expiring' lvalues: objects you have marked as movable-from, typically via std::move.

The taxonomy exists to answer one question: is it safe to steal this object's resources? lvalue: no (someone still uses it). prvalue/xvalue: yes (it is dying or dead). Move semantics is the machinery that acts on the answer.

rvalue references (T&&) vs forwarding references

T&& in a non-template context (void f(std::string&&)) binds only to rvalues — it is an rvalue reference, the move-constructor parameter. But template<typename T> void f(T&&) deduces T from the argument: lvalue arguments deduce T as an lvalue reference (T = int&), rvalues as plain T — so the parameter binds to anything. This deducible form is the forwarding reference.

The checkpoint's deduction question is the whole rule: int lvalue → T is int&; int rvalue → T is int. Reference collapsing (int& && → int&) does the rest. Get this and perfect forwarding follows.

std::move as a cast, not a move

std::move does nothing at runtime — it is a cast to an rvalue reference, a way of saying 'treat this object as expiring; you may steal from it.' The actual moving is done by the move constructor or move assignment operator that receives the cast expression.

This is why 'std::move doesn't move anything' is the checkpoint: the cast enables the move, the move constructor performs it. Moving from a const object silently copies instead — the move constructor cannot steal from const — which is a classic performance trap worth knowing.

std::forward and perfect forwarding

std::forward<T> preserves the value category: inside f(T&& x), forward<T>(x) passes an lvalue as an lvalue and an rvalue as an rvalue to the next function. Without it, the named parameter x is an lvalue regardless of what was passed in — and everything downstream would copy.

The lab's overload experiment shows the failure mode: forward incorrectly and the rvalue overload never fires. Perfect forwarding is how factory functions (make_unique) and wrappers pass arguments through untouched — learn it once, use it in every generic wrapper you write.

noexcept moves and vector reallocation

When a vector grows, it must move elements to new storage — but if a move constructor might throw, the vector cannot risk leaving the old storage half-moved, so it falls back to copying (copies can be retried safely). A noexcept move constructor lets the vector move with confidence.

The checkpoint's penalty is real and measurable: the lab counts copies versus moves with and without noexcept, and the difference is the price of an unmarked move. Mark move operations noexcept whenever they truly cannot throw — which, for resource-stealing moves, is almost always.

Copy elision and guaranteed elision (C++17)

Copy elision lets the compiler construct a returned object directly in its destination, skipping the copy/move entirely. Since C++17, elision is guaranteed in certain cases (returning a prvalue) — the standard mandates it, not just permits it.

The lab's -O0 comparison across standards shows the guarantee working: identical behavior regardless of optimization. Practical upshot: return heavy objects by value without fear — the language promises the efficient path.

Moved-from state: valid but unspecified

After std::move(x), x is in a valid-but-unspecified state: you may destroy it or assign to it, but you may not assume anything about its value. For std::string the typical implementation leaves it empty, but that is not guaranteed.

The safe pattern from the lab: move, then either reassign or destroy — never read. Treating moved-from objects as usable is the use-after-move bug, and it is as real as use-after-free, just quieter.

std::move_if_noexcept

move_if_noexcept casts to an rvalue only if the move is noexcept (or copying is impossible) — otherwise it casts to a const lvalue, forcing a copy. It is the standard library's way of encoding the vector-growth rule as a utility.

You will rarely call it directly, but it is the mechanism behind 'vector moves when safe, copies when not.' Knowing it exists completes the picture: the language does not just hope moves are safe, it checks.

Hands-on labs

  1. Lab 1 — Count the moves. Write a String class with deep-copy semantics and instrumented copy/move constructors that print. Push temporaries into a vector and count copies vs moves; mark the move constructor noexcept and watch reallocations switch from copies to moves.
  2. Lab 2 — Forwarding experiment. Write a function template taking a forwarding reference that forwards to two overloads (const T& and T&&). Pass lvalues, rvalues, and const lvalues; print which overload fires; fix any case that forwards incorrectly.
  3. Lab 3 — Use after move. Deliberately use an object after std::move and demonstrate the valid-but-unspecified state (e.g., moved-from std::string). Then write the safe pattern — move, then reassign or destroy — and document the rule.
  4. Lab 4 — Guaranteed elision. Return a large vector by value under -O0 with C++14 vs C++17 flags; compare copy/move constructor call counts to observe guaranteed copy elision in action.

Self-check questions

  1. Explain why std::move does not move anything by itself, and what actually performs the move.
  2. A move constructor that is not noexcept: what penalty does std::vector pay during growth, and why?
  3. Given template<typename T> void f(T&& x), what is the deduced type of T when called with an int lvalue? With an int rvalue?

Module 5

Templates and generics

Learning objectives

  • Write function and class templates with correct syntax and sensible constraints.
  • Use variadic templates and fold expressions (C++17) for genuinely generic utilities.
  • Apply C++20 concepts to constrain templates and produce readable error messages.

Key concepts

Function templates and class templates

A function template generates overloads from argument types; a class template generates classes from its parameters (Matrix<double, 3, 3> is a different type from Matrix<float, 3, 3>). Deduction usually fills in the arguments — you write clamp(a, b) and the compiler figures out the types.

Templates are compile-time code generation with type checking per instantiation: the template is checked loosely at definition, strictly at each use. That two-phase checking is why template errors point deep inside library headers — and why concepts (below) were invented.

Template argument deduction

Deduction matches the function arguments against the template parameters to infer the types — clamp(1, 2.5) fails because int and double deduce conflicting types for one parameter. Understanding deduction is understanding template error messages: the compiler is telling you what it inferred and where the inference broke.

When deduction fails, the fixes are explicit template arguments (clamp<double>(1, 2.5)) or constraints that guide the user to valid calls. The lab's mismatched-types call is the canonical first encounter.

Non-type template parameters

Templates can take values, not just types: Matrix<T, Rows, Cols> bakes dimensions into the type itself, enabling compile-time size checks (static_assert on zero dimensions) and stack-allocated fixed storage with no runtime overhead.

The lab's Matrix is the pattern: dimensions as parameters, static_assert rejecting nonsense, constexpr operations on the fixed size. Non-type parameters turn runtime invariants into compile-time guarantees.

Variadic templates (C++11) and fold expressions (C++17)

Variadic templates accept any number of arguments via a parameter pack; the classic implementation recurses over the pack with a base case. C++17 fold expressions collapse the whole pattern into one expression: (args + ...) or (args && ...) with no recursion and no base case to write.

The checkpoint's question is the payoff: the fold version is one line where the recursive version is two functions. The type-safe printf lab shows folds at their best — mixed-type argument handling in a single expression.

SFINAE and std::enable_if: the C++11-era technique

SFINAE ('substitution failure is not an error') let C++11/14 code enable or disable template overloads by making invalid substitutions silently remove candidates rather than erroring. std::enable_if was the workhorse: incomprehensible to read, but it made overload sets behave.

Know it because you will read it in older codebases — and because understanding what concepts replaced tells you why concepts are better. You should write new code with concepts, not enable_if.

Concepts and requires clauses (C++20)

Concepts name requirements on template arguments: template<std::totally_ordered T> says exactly what clamp needs. Violations fail at the call site with a readable message naming the unsatisfied concept — instead of a hundred-line error from deep inside the template body.

The lab's before/after comparison is the whole argument for C++20: same misuse, one-line diagnostic versus template vomit. Concepts are documentation the compiler enforces and diagnostics the user can read.

constexpr functions across the standards

constexpr functions can execute at compile time; each standard revision allows more inside them (C++11: single return; C++14: loops and locals; C++17/20: ever more). The lab's constexpr 2x2 determinant computes at compile time when given constant inputs.

constexpr is how compile-time computation grows up: the same function runs at runtime when inputs are dynamic, at compile time when they are constant. Write constexpr by default for pure computations — it costs nothing and buys compile-time evaluation.

Template instantiation and code bloat awareness

Each distinct set of template arguments generates a separate instantiation — vector<int> and vector<double> are entirely separate code. Used carelessly across many types, this bloats binaries; used well, it is the price of zero-cost abstraction.

Awareness, not fear: prefer type-erased interfaces (virtuals, std::function) at module boundaries where many types flow through, and templates where performance or type safety demands it. The checkpoint's 'what still needs runtime polymorphism' question points at exactly this boundary — heterogeneous collections chosen at runtime are the virtual interface's home turf.

Hands-on labs

  1. Lab 1 — Constrain the error. Write a generic clamp as a function template; call it with mismatched types (int, double) and read the deduction error. Constrain with a C++20 concept and compare the diagnostic quality before and after.
  2. Lab 2 — Variadic logger. Implement a type-safe printf-like logger with variadic templates and a C++17 fold expression. Test with zero, one, and many mixed-type arguments.
  3. Lab 3 — Matrix class template. Write Matrix parameterized on element type and dimensions as non-type parameters; add a static_assert rejecting zero dimensions and a constexpr 2x2 determinant.
  4. Lab 4 — requires at the call site. Take a template that fails deep inside its body for the wrong type; rewrite with a requires clause so misuse fails at the call site with a one-line message. Show before/after compiler output.

Self-check questions

  1. What is the difference between a fold expression over && and a recursive variadic base-case implementation, in terms of code you must write?
  2. Why does a concept-constrained template usually give a better diagnostic than the same template with a static_assert inside the body?
  3. Name one thing you still cannot do with templates that requires runtime polymorphism, and when you would choose a virtual interface instead.

Module 6

Concurrency: threads, mutexes, and atomics

Learning objectives

  • Launch and join std::thread workers and pass data safely between threads.
  • Protect shared state with std::mutex/std::lock_guard and avoid deadlocks with consistent lock ordering or std::scoped_lock (C++17).
  • Use std::atomic for lock-free counters and flags, and explain the data-race rule in plain language.

Key concepts

std::thread lifecycle: join vs detach

std::thread launches a thread running a callable; you must either join() it (wait for completion) or detach() it (let it run independently) before the thread object is destroyed — destroying a joinable thread terminates the program. Joining is the norm; detaching is for fire-and-forget background work whose lifetime you have genuinely reasoned about.

The capstone's thread pool joins everything at shutdown: no detached threads, no orphaned work. A thread you cannot join is a thread you cannot reason about.

Data races are undefined behavior

A data race — two threads accessing the same memory, at least one writing, with no synchronization — is undefined behavior in C++, not merely a timing bug. The compiler may assume races never happen and optimize accordingly, which is why the checkpoint's counter loses increments: x++ compiles to load-add-store, and two threads' load-add-store sequences interleave, each overwriting the other's increment.

The hardware-level two sentences: each core loads x into its cache, increments its private copy, and stores it back; when both threads load before either stores, one increment is silently lost. ThreadSanitizer exists to catch exactly this — run it before you theorize.

std::mutex, std::lock_guard, std::unique_lock

A mutex serializes access to shared state: lock it, touch the data, unlock it. lock_guard is RAII for the simple case — locks on construction, unlocks on destruction, exception-safe by construction. unique_lock adds flexibility (deferred locking, timed tries, manual unlock) for the cases lock_guard cannot express.

The rule is lock_guard by default: its very inflexibility prevents the forgotten-unlock bug. Reach for unique_lock only when you need its features — condition variables being the classic case.

std::scoped_lock for multi-mutex acquisition (C++17)

Acquiring two mutexes in opposite orders in different threads is the textbook deadlock: each thread holds one lock and waits forever for the other. std::scoped_lock acquires multiple mutexes atomically in a deadlock-safe order — the lab's deliberate deadlock, fixed in one line.

The deeper discipline is consistent lock ordering everywhere, with scoped_lock as the enforcement mechanism. If your design needs more than two locks held simultaneously, reconsider the design; if it genuinely does, scoped_lock every acquisition site.

std::atomic and lock-free programming basics

std::atomic<T> makes individual operations (load, store, increment, compare-exchange) indivisible — the counter lab's fix is std::atomic<int>, and the total comes out exact. Atomics are the right tool for simple shared state: counters, flags, and lock-free algorithms built on compare-exchange loops.

The one-sentence test from the checkpoint: if the shared state fits in one atomic operation, use an atomic; if the operation spans multiple variables that must change together, use a mutex. The lab's second shared variable proves the boundary — one atomic plus one plain variable is still a race.

Memory ordering at a high level

Atomic operations default to sequential consistency — every thread observes a single global order of operations, the intuitive model. Weaker orderings (acquire/release, relaxed) permit more hardware reordering for performance, at the cost of reasoning difficulty.

For this sequence: use the default unless you can prove the weaker ordering safe and the performance matters. Memory-ordering bugs are among the hardest to diagnose in existence; the default ordering exists so most code never has to think about them.

Condition variables

std::condition_variable lets a thread sleep until another thread signals that some condition holds — the producer/consumer queue's 'wait until the queue is non-empty.' Always wait in a loop re-checking the predicate (spurious wakeups are real), and always hold the associated mutex while checking and waiting.

The pattern is fixed: lock, while (!ready) cv.wait(lock), consume, unlock; producer: lock, produce, unlock, notify. Deviate from the pattern and you get lost wakeups or data races — the lab's queue is the pattern to memorize.

ThreadSanitizer as the ground truth

-fsanitize=thread instruments memory accesses to detect data races at runtime, reporting the two threads, the memory location, and both stack traces. It is the ground truth for 'is this actually race-free' — reasoning is not, code review is not, testing is not.

Run the full test suite under TSan as standard practice (the capstone requires it), alongside ASan/UBSan runs. Note the constraint: TSan and ASan cannot combine in one build — run them as separate configurations, which is what the CMake Debug/Sanitizer presets are for.

Hands-on labs

  1. Lab 1 — The race, measured. Two threads increment a plain int 1M times each; run 5 times, record the varying wrong totals. Rebuild with -fsanitize=thread, capture the race report. Fix with std::atomic and confirm the exact expected total.
  2. Lab 2 — Deadlock, then scoped_lock. Implement a producer/consumer queue with mutex + condition_variable. Deliberately deadlock by acquiring two mutexes in opposite orders; detect the hang, fix with std::scoped_lock and consistent ordering.
  3. Lab 3 — Thread pool. Build a tiny thread pool: N workers, a task queue of std::function<void()>, shutdown flag. Submit 100 tasks, verify each runs exactly once, shut down cleanly with all threads joined — no detach.
  4. Lab 4 — One atomic is not enough. Add a second shared variable updated alongside the atomic counter without synchronization; show with TSan that the race persists, then protect both under one mutex.

Self-check questions

  1. Two threads each do x++ on a plain int one million times and the result is 1,432,887. Explain precisely what went wrong at the hardware level, in two sentences.
  2. When is std::atomic the right tool versus a mutex, and what is the one-sentence test?
  3. Your program hangs intermittently. Name the two most likely concurrency causes and the tool/flag you would use to confirm each.

Module 7

Build systems with CMake

Learning objectives

  • Write a CMakeLists.txt for a multi-target project: library, executable, and tests.
  • Manage dependencies with find_package and target-based commands (target_link_libraries, target_include_directories).
  • Configure Debug vs Release builds and pass the project to a second machine or CI cleanly.

Key concepts

Out-of-source builds

Building in a separate directory from the sources keeps generated files (objects, binaries, CMake cache) out of the source tree: the repo stays clean, multiple configurations (Debug, Release, sanitizer builds) coexist as sibling directories, and 'clean' is rm -rf build. In-source builds pollute the tree and make configuration switches unreliable.

The lab proves reproducibility the hard way: delete the build directory, rebuild from scratch, get the same binary. If your build cannot survive that, it is not a build system — it is a hope.

Targets, not variables: modern CMake practice

Modern CMake describes targets (libraries, executables) and their properties; legacy CMake set global variables. The difference matters because targets carry their requirements with them: include directories, compile options, and link dependencies propagate to dependents automatically.

The checkpoint's PUBLIC/PRIVATE question is the mechanism: PRIVATE means 'needed to build this target'; PUBLIC means 'needed to build this target and anyone linking it.' Get the propagation right and downstream targets just link — no manual -I flags, no ordering rituals.

target_include_directories / target_link_libraries with PUBLIC/PRIVATE

target_include_directories declares a target's header search paths with a scope; target_link_libraries declares its library dependencies with a scope. PUBLIC propagates to consumers, PRIVATE does not, INTERFACE propagates without applying to the target itself.

The lab's compile-fail test makes scope tangible: link a dependency PRIVATE to one target and prove a second target cannot see its headers. Scoping is dependency hygiene — every over-exposed include directory is a coupling you will regret.

find_package for system libraries

find_package(LibName) locates an installed library and exposes it as an imported target with its include paths and link requirements already configured. It replaces hand-rolled Find modules and pkg-config guesswork for well-behaved libraries.

Prefer config-mode packages shipped by the library; fall back to module mode only when the library provides none. Either way, the consuming code just target_link_libraries against the imported target.

CMAKE_BUILD_TYPE and generator expressions

Single-configuration generators (Make, Ninja) take CMAKE_BUILD_TYPE=Debug or Release to select optimization and debug-info flags. Generator expressions ($<CONFIG:Debug>) evaluate per-configuration inside multi-config generators (Visual Studio, Ninja Multi-Config) — the portable way to say 'this flag only in Debug.'

The checkpoint's Debug-works-Release-crashes triage starts here: optimization level, NDEBUG (which disables assert), and any config-specific flags. The lab's dual build directories make the comparison mechanical.

FetchContent for vendored dependencies

FetchContent downloads a dependency at configure time and builds it as part of your project — vendoring without submodules or system installs. It is ideal for small header-only libraries and for pinning exact dependency versions in CI.

The tradeoff is configure-time cost and network dependence; for large dependencies, prefer find_package against a system install. The lab's header-only FetchContent exercise shows the sweet spot.

CTest integration

CTest is CMake's test runner: enable_testing(), add_test() registering executables, and ctest runs them all with pass/fail reporting. Tests become part of the build — 'the full build fails on test failure' is not a slogan but a property of the lab's setup.

Wire tests in from the start, not at the end: a test suite that runs with every build is a living specification; one that runs manually is a wish.

Install rules and package basics

install() rules declare what gets deployed — binaries, headers, libraries — and where; CPack can turn those rules into distributable packages. Even for learning projects, writing install rules forces you to decide what your project's public surface is.

The capstone does not require packaging, but a project with install rules is a project someone else can actually use. It is the difference between code and software.

Hands-on labs

  1. Lab 1 — Makefile to CMake. Convert a hand-rolled Makefile (or raw g++ commands) project with lib/ and app/ split into CMake. Build out-of-source, delete the build directory, rebuild from scratch to prove reproducibility.
  2. Lab 2 — PRIVATE scope, proven. Add a third-party dependency via FetchContent, link it PRIVATE to one target, and verify a second target cannot see its headers (compile-fail test). Document what the failure proves.
  3. Lab 3 — Debug vs Release sanitizers. Set up two build dirs: Debug with -fsanitize=address,undefined and Release with -O2. Run the same test binary under both; document any behavioral difference and explain it.
  4. Lab 4 — The missing source. Add a new .cpp file without listing it in CMakeLists, observe the stale build, fix it, and note the lesson about globbing versus explicit source lists.

Self-check questions

  1. Why are out-of-source builds the standard practice, and what breaks if you build in-source?
  2. PUBLIC vs PRIVATE in target_link_libraries: what does each propagate, and to whom?
  3. Your CI builds Debug fine but Release crashes. List three build-configuration differences you would check first.

Module 8

Testing and debugging: sanitizers, gdb, and unit tests

Learning objectives

  • Write unit tests for C++ code with a lightweight framework and run them under CTest.
  • Use AddressSanitizer, UndefinedBehaviorSanitizer, and ThreadSanitizer to find bugs tests miss.
  • Drive gdb (or lldb) to get backtraces, inspect variables, and set conditional breakpoints.

Key concepts

Unit test structure: arrange/act/assert

A unit test arranges preconditions, acts on the unit under test, and asserts the outcome — three phases, each visible. Tests that mix phases become unreadable; tests that assert multiple unrelated behaviors become undebuggable.

The capstone's 'meaningful assertions' requirement is this discipline graded: each test names one behavior and verifies it precisely. A test suite is executable documentation — write it as carefully as the code.

CTest as the test runner

CTest runs the test executables CMake registers and reports pass/fail per test — the 'make the full build fail on test failure' property from the CMake module. CI runs ctest; developers run ctest; the suite is the gate.

Keep tests fast and hermetic: a suite that takes an hour or depends on the network does not get run. The tests you actually run are the only tests that protect you.

AddressSanitizer: heap/stack/global overflows, use-after-free

ASan instruments every memory access and catches spatial and temporal errors at runtime: heap, stack, and global buffer overflows, use-after-free, use-after-return, double-free, leaks (with LeakSanitizer). The checkpoint's paradox — tests pass but ASan reports an overflow — resolves here: the test never read the corrupted memory in a way that changed the outcome, but the bug is real regardless.

Tests verify behavior; sanitizers verify correctness. You need both, because passing tests prove the code did the right thing this time, while a clean sanitizer run proves it did not cheat to get there.

UndefinedBehaviorSanitizer: signed overflow, null deref, misalignment

UBSan instruments the language-level UB classes: signed integer overflow, null pointer dereference, misaligned access, out-of-bounds on known sizes, and more. It catches the bugs that are 'not memory errors' but are still undefined — the ones that make optimizers miscompile.

Run ASan and UBSan together routinely (they compose); add TSan as a separate configuration (it does not compose with ASan). The three-sanitizer matrix is the capstone's bar and should become your default.

ThreadSanitizer: data races

TSan detects data races at runtime with precise reports — the two threads, the location, both stacks. It is the only reliable way to verify concurrent code: reasoning about interleavings does not scale, and stress-testing finds races by luck.

The plant-a-race lab teaches the report format before you need it under pressure: read one TSan report carefully now, and the 3 AM race later becomes a thirty-minute fix instead of a three-day mystery.

gdb: backtrace, frame, print, break, watch

The C module's gdb curriculum transfers directly: break stops at locations, watch stops on data changes, catch stops on events (exceptions, syscalls) — the checkpoint's three-way distinction. backtrace shows the call stack, frame selects one, print inspects.

C++ adds name-mangled symbols and template-heavy stacks to the reading, but the workflow is identical: reproduce, break near the fault, inspect, understand. The debugger does not change; only the code it reads gets more expressive.

Core dumps and post-mortem debugging

Same discipline as C: enable cores, load the core in gdb, read the backtrace without re-running. Production C++ crashes rarely reproduce in the lab — the core dump is often the only witness.

For the capstone, know how to get a core from your system before you need one. Post-mortem skill is what separates 'it crashed in prod' from 'here is the faulting line and the fix.'

Fuzzing at a glance: libFuzzer/AFL concept

Fuzzing feeds generated inputs to your code under sanitizers, hunting for crashes automatically — the force-multiplier beyond handwritten tests. libFuzzer (in-process, LLVM) and AFL (coverage-guided, general) are the standard tools; the concept to take from this module is the workflow: fuzz target + sanitizer + corpus = bugs found while you sleep.

You are not required to fuzz the capstone, but knowing the concept exists changes how you write parsers and input handling: every input boundary is a future fuzz target. Write code you would not fear fuzzing.

Hands-on labs

  1. Lab 1 — Tests pass, sanitizers fail. Take a small string-utility module with 3 planted bugs (off-by-one heap overflow, use-after-free, signed integer overflow). Write unit tests that pass despite the bugs, run under ASan+UBSan, fix each reported bug. Write down why the tests missed each one.
  2. Lab 2 — gdb on C++. Debug a segfaulting program with gdb: backtrace, walk frames, print the offending pointer, set a watchpoint on the corrupted variable. Record the exact command sequence you used.
  3. Lab 3 — CTest wiring. Write a minimal test suite for the Matrix class from the templates module, wire it into CMake via CTest, and make the full build fail on test failure.
  4. Lab 4 — Plant a race. Plant a data race in test-adjacent code, run the suite under ThreadSanitizer, read the race report (threads, location, stacks), and fix it.

Self-check questions

  1. Your tests pass but ASan reports a heap-buffer-overflow in code the tests cover. Explain how both can be true.
  2. Name the sanitizer for each: use-after-free, signed integer overflow, data race.
  3. In gdb, what is the difference between break, watch, and catch, and when would you use each?

Capstone

Prove it: the capstone project.

Design and build a concurrent, tested C++20 utility of your choosing — a multithreaded file hasher, a parallel word-frequency analyzer, or a small TCP echo server are all good choices. Requirements from the curriculum: a CMake build with Debug/Release configurations; RAII resource handling with zero raw new/delete; STL algorithms over hand loops; at least one class template or concept-constrained function; a thread pool or worker threads with sanitizer-clean runs (ASan/UBSan/TSan); a CTest suite with meaningful assertions; and a README documenting the C++ standard features used per module and how each sanitizer run came back clean.

Deliverable: a git repo link or archive plus a one-page writeup of the hardest bug the sanitizers caught. That writeup is the real deliverable — it proves you can find, understand, and fix the bugs that separate C++ that compiles from C++ that is correct.
