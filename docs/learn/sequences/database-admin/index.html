Database Administration & Engineering

The working DBA's craft on SQL Server and Oracle: installation, backup and recovery, high availability, security hardening, monitoring, performance troubleshooting, migrations, and capacity planning — every skill practiced on free editions.

Study sequence

Overview

Eight modules covering the working DBA's craft on SQL Server and Oracle: installation and configuration, backup and recovery, high availability and replication, security hardening, monitoring and alerting, performance troubleshooting, migration planning, and capacity planning. Each module pairs concepts with labs on free editions — SQL Server Developer and Oracle Database Free — so every skill is practiced, not just read.

It is for aspiring database administrators, backend developers inheriting database responsibility, and systems engineers who want the operational side of data. No prior DBA experience is assumed; administrative confidence is the outcome.

Prerequisites are basic SQL (the Core SQL Engineering sequence covers it), a machine that can run containers or install a database engine, and a lab journal — you will document every install choice, every backup test, and every incident drill. The journal is a graded artifact of the sequence, even if the only grader is you.

Modules 1 and 2 build the foundation (install it, back it up); modules 3 through 5 cover keeping it alive and safe; modules 6 through 8 cover keeping it fast and planning its future. Do the labs in order on a dedicated lab instance you are free to break — breaking it is part of the curriculum. The checkpoints are scenario-based; answer them in writing before moving on.

Module 1 of 8

Installation and Configuration

Every DBA journey starts with an install done right. This module walks through SQL Server and Oracle Database installation and initial configuration — editions, collations, character sets, storage layout — and the post-install hardening checklist. Your lab journal starts here; document every choice.

Objectives

  • Install a free database engine (SQL Server Developer or Oracle Database Free) via installer or container with a repeatable, documented process.
  • Configure server-level memory limits and storage layout so the database does not starve its host.
  • Compare editions and licensing concepts at a planning level, including which features free editions lack.
  • Verify the install with a smoke test: create a database, create a table, and round-trip data through it.

Key concepts

Editions and licensing concepts: which features are gated behind paid editions

Every major database vendor ships a free edition and one or more paid editions, and the dividing line is features, not just support. High-availability replicas, online index operations, partitioning, advanced security, and higher resource caps commonly sit behind the paywall. Planning on a free edition means knowing exactly which features you are giving up and designing around each gap deliberately — the lab's one-page brief forces that exercise. Licensing is a design constraint, not an afterthought.

Physical file layout: data files, transaction logs, and temp/scratch space

A database's files have different I/O personalities: data files take random reads and writes, transaction logs take sequential writes, and temp/scratch space takes bursty mixed I/O. Putting them on separate volumes isolates their contention and lets each be sized, backed up, and monitored on its own terms. It also contains failure: a runaway log cannot fill the volume holding your data files. The lab builds this layout explicitly and sketches the result.

Instance vs database vs schema terminology and how vendors differ

Instance, database, and schema mean different things on different platforms — SQL Server's instance hosts many databases, Oracle's instance serves one database (with pluggable databases inside), and Postgres flips the hierarchy again. Schemas are namespaces inside a database nearly everywhere, but their security semantics vary. Misreading the terminology leads to misdesigned access control and botched migrations. Learn your platform's map before you build on it.

Memory architecture: buffer pool/cache and max server memory settings

Database engines are memory-hungry by design: the buffer pool caches data pages so queries avoid disk, and an uncapped engine will happily consume everything on the host. Setting max server memory is the single most important sizing decision on a shared host — the lab caps it at roughly half of host RAM and records the before/after. Too low starves the cache and slows every query; too high starves the OS and risks paging or the OOM killer. Size it deliberately, then verify under load.

Collation and character sets: chosen at install time, painful to change later

Collation controls string comparison and sorting; the character set controls which characters can be stored. Both are chosen at install or database-creation time, and changing them later ranges from disruptive to effectively a rebuild. Applications that assume a default collation break in subtle ways — joins fail, sorts surprise — when they meet a different one. The lab stands up a second instance with a different collation precisely to feel that breakage early.

Service accounts and file-system permissions for database processes

The database engine runs as an operating-system account, and that account's file-system permissions are a security boundary. Give the service account exactly the directories it needs — data, log, backup — and nothing else; a compromised engine with broad permissions becomes a compromised host. On Windows this means dedicated service accounts rather than Local System; on Linux it means a dedicated user with a tight umask. Permissions are infrastructure, and the lab journal records them as such.

Containerized deployment: volumes for persistence, ports, environment variables

Containers make database installs repeatable, but only if persistence is explicit: data must live on mounted volumes, or it dies with the container. The lab proves this by restarting a container and verifying data survives. Ports, passwords, and edition choices go in environment variables or compose files — never baked into images. A containerized database is still a database: backups, memory caps, and file layout all still apply.

Repeatable installs: documenting every choice so the build is reproducible

The deliverable of an install is not a running server; it is a document from which anyone can rebuild that server. The lab journal records every choice — edition, paths, memory cap, collation, accounts — and the final checkpoint tests it: rebuild from notes alone, and note everything that required guessing. Undocumented installs become snowflakes, and snowflakes become 3 AM mysteries. Reproducibility is the difference between administration and archaeology.

Hands-on labs

  1. Install SQL Server Developer Edition (or run the official container image) and document every setup choice in a lab journal.
  2. Deploy Oracle Database Free in a container with persistent volume mounts; restart the container and prove data survives the restart.
  3. Cap the engine's max memory at roughly half of host RAM, capture the before/after settings, and record the exact commands used.
  4. Create a sample database with data and log files on separate paths; sketch the resulting file layout.
  5. Stand up a second containerized instance with a different collation/character set and note what breaks when applications assume the default.

Self-check

  1. Explain in your own words why data files and log files should live on separate volumes.
  2. What happens if the engine's max memory setting is left unbounded on a shared host, and how would you detect it?
  3. Name three features gated to paid editions and describe how you would plan around each on a free edition.
  4. Rebuild your container instance from scratch using only your setup notes. Did anything require guessing?

Module 2 of 8

Backup and Recovery

Backups are the one DBA skill that gets tested at 3 AM. This module covers the full backup taxonomy — full, differential, transaction log, RMAN — and the recovery models that determine what you can restore. You will prove your backups work by restoring them, because an untested backup is a rumor.

Objectives

  • Distinguish full, differential, and log/incremental backups and explain when each is used.
  • Translate business RPO/RTO statements into a concrete backup schedule.
  • Perform complete point-in-time restores in a lab and verify data integrity afterward.
  • Adopt the discipline that an untested backup is not a backup: schedule and document restore drills.

Key concepts

Full vs differential vs transaction-log/incremental backups and when each is used

A full backup copies everything; a differential copies what changed since the last full; a log or incremental backup copies the smallest unit of change since the last backup of its kind. Fulls are the restore foundation, differentials shorten restore chains, and log backups enable point-in-time recovery. The lab takes all three and records size and duration, because the trade-off is concrete: smaller, faster backups mean longer, more fragile restore chains. Choose the mix that fits your RPO, not your comfort.

Recovery models (simple vs full logging) and their trade-offs

The recovery model decides how much of the transaction log the engine keeps. Simple recovery truncates the log aggressively — smaller logs, but no point-in-time restore. Full recovery keeps the log chain intact, enabling restore to any moment, at the cost of log management discipline. The lab breaks a chain on purpose to feel exactly what full recovery demands. Pick the model per database, per RPO — never by default.

RPO: how much data the business can afford to lose; RTO: how fast you must be back

Recovery Point Objective is the maximum acceptable data loss, measured in time: RPO of 15 minutes means backups (or log shipping) must capture everything at least that often. Recovery Time Objective is the maximum acceptable downtime: RTO of 2 hours means the whole restore must complete inside two hours. These are business statements first, and the backup schedule is their translation into engineering. The checkpoint's RPO-15/RTO-2 exercise is the core DBA planning skill.

Point-in-time recovery and why the log chain must stay unbroken

Point-in-time recovery replays the log chain from the last full backup forward to a chosen moment — the minute before someone dropped a table, in the lab's disaster simulation. Every link in the chain must be present and in order; one missing or out-of-sequence log backup ends the replay there. That is why the lab deliberately breaks a chain and documents the failure: the chain is the recovery. Protect it with the same seriousness as the data.

Backup verification: checksums, test restores, and treating untested backups as no backups

A backup that has never been restored is a hope, not a backup. Verification has layers: checksums catch corruption in the backup file, and test restores — automated, scheduled, to a staging server — prove the whole chain actually recovers. The lab scripts a nightly backup with a verification step that restores to staging and reports success or failure. If the restore drill is not in the calendar, it does not exist.

Off-host copies and the 3-2-1 rule concept for backup copies

The 3-2-1 concept: keep three copies of data, on two different media, with one off-site (off-host). A backup on the same disk as the database dies in the same disk failure — the checkpoint asks exactly why that is not a real backup. Ransomware made off-host, ideally immutable or offline, copies non-negotiable: the attacker who reaches your primary will reach your on-host backups. Distance is a feature.

Managed backup tooling concepts (e.g., RMAN catalogs) vs native backup commands

Native backup commands are simple and transparent; managed tooling like Oracle's RMAN adds catalogs, retention policies, incremental-forever strategies, and cross-checks. A catalog tracks every backup piece across time and media, which matters at scale. The concept to carry is not the tool's syntax but its job: knowing what exists, where it is, and whether it is still valid. Use native commands to learn; use managed tooling to survive.

Corruption detection: page checksums and consistency checks

Databases detect bit rot with page checksums written as pages hit disk and verified on read, plus periodic consistency checks that walk allocation structures. A checksum failure on backup or restore is the early warning — the lab's consistency-check exercise teaches you to read that output line by line. Detection without a restore plan is just earlier bad news, so checks feed the same runbook as backups. Trust, but verify, continuously.

Hands-on labs

  1. Take a full backup of a lab database, then a differential and a log backup; record the size and duration of each.
  2. Simulate a disaster — drop a table, then restore the database to the minute before the drop using the log chain.
  3. Break the chain on purpose (change recovery model mid-sequence or skip a log backup) and document exactly how the restore fails.
  4. Script an automated nightly backup with a verification step that restores to a staging database and reports success or failure.
  5. Run a consistency check against a lab database and interpret the output line by line.

Self-check

  1. A business states RPO 15 minutes and RTO 2 hours. Sketch the backup schedule and justify each piece.
  2. One log backup in the middle of the chain is missing. Which restores are still possible, and which are lost?
  3. Why is a backup file stored on the same disk as the database not a real backup?
  4. Perform your restore drill from your notes alone and time it against the stated RTO.

Module 3 of 8

High Availability and Replication

Downtime is the DBA's report card. This module covers the availability ladder from log shipping to Always On availability groups and Oracle Data Guard, plus replication topologies. You will build a replica, break a primary, and fail over — in the lab, where breaking things is the point.

Objectives

  • Compare failover clustering, synchronous replicas, and asynchronous replication in plain language.
  • Explain the difference between high availability and disaster recovery.
  • Describe Always On availability concepts and Data Guard concepts at the concept level.
  • Design an HA/DR topology for a given RPO/RTO on paper.

Key concepts

High availability (uptime) vs disaster recovery (survivability): different problems, different tools

High availability keeps the service running through component failures — measured in uptime, served by clustering and synchronous replicas. Disaster recovery brings the service back after a site-level catastrophe — measured in RPO/RTO, served by asynchronous copies in another location. One is about not falling over; the other is about getting back up. The tools overlap but the designs do not, and confusing them produces a system that does neither well.

Synchronous vs asynchronous replication and the durability/latency trade-off

Synchronous replication waits for the secondary to acknowledge before committing: zero data loss on failover, at the cost of latency on every write and fragility when the secondary lags. Asynchronous replication commits locally and ships changes after: fast writes, but a failure can lose whatever had not shipped yet. The checkpoint's one-paragraph exercise — why zero data loss costs latency — is the whole trade-off in miniature. There is no free choice here, only an informed one.

Failover vs switchover; automatic vs manual promotion

A switchover is planned: you promote the standby deliberately, usually for maintenance, with no data loss and a controlled cutover. A failover is unplanned: the primary died, and you promote under pressure with whatever data made it across. Automatic promotion is faster but risks split-brain if the old primary is actually alive; manual promotion is slower but lets a human confirm. The lab does a manual promotion and documents every decision, because the runbook you write calmly is the one you follow in panic.

Quorum and witness concepts for preventing split-brain

Split-brain — two nodes both believing they are primary and accepting writes — is the nightmare that quorum exists to prevent. A quorum rule says only the partition holding a majority of votes (plus a witness if needed) may promote itself. The minority partition stands down rather than diverging. Any automatic-failover design without quorum is a divergence machine wearing an HA costume.

Readable secondaries and offloading reporting workloads

Many replica technologies let secondaries serve read queries, which turns the HA investment into a performance asset: reporting and analytics move off the primary. The catch is replication lag — a report on a secondary can be minutes behind, and some secondaries only support snapshot isolation. Design the workload split knowing the lag exists, and monitor it as a first-class metric rather than discovering it in a confused stakeholder meeting.

Replication lag: how to measure it and when to alert on it

Lag is the distance, in time or log volume, between what the primary has committed and what the secondary has applied. The lab applies a write load and measures it directly. Alert thresholds should be tied to the RPO the topology was designed for: if the design promises one hour, alert well before one hour, not at it. Lag that grows unboundedly is not a metric anomaly; it is the DR plan silently expiring.

Failover drills: planned rehearsals vs real failures

A failover that has never been rehearsed is a plan, not a capability. Drills surface the undocumented steps — the DNS change, the connection-string update, the job that only exists on the primary — while the stakes are low. The lab's manual promotion is a drill, and its documentation is the artifact. Schedule drills the way you schedule backups: the disaster will not wait for a convenient quarter.

The cost/complexity ladder: single instance, log shipping, replicas, clusters

HA/DR options form a ladder of cost and complexity: a single well-backed-up instance, log shipping to a standby, synchronous replicas, full failover clustering. Each rung buys less data loss and faster recovery at the price of money, operational burden, and new failure modes. The honest engineering move is to climb only as high as the RPO/RTO demands — the lab's small-business topology exercise is practice in stopping at the right rung.

Hands-on labs

  1. Build log-shipping-style replication between two free-edition instances using scheduled backup/restore jobs (the concept behind asynchronous DR).
  2. Apply a write load to the primary and measure replication lag on the standby.
  3. Simulate a primary failure — promote the standby manually and document every step and decision.
  4. Research which HA features are unavailable in free editions and write a one-page brief on what would require a paid edition.
  5. Design an HA/DR topology on paper for a fictional small business with RPO 1 hour and RTO 4 hours, and defend it in writing.

Self-check

  1. Synchronous replication offers zero data loss but costs latency. Explain why in one paragraph.
  2. Your standby is 45 minutes behind when the primary dies. What is the business impact in RPO/RTO terms?
  3. Why must a failover be rehearsed before it is ever needed?

Module 4 of 8

Security Hardening

A database holds the organization's crown jewels. This module covers authentication, authorization, encryption (at rest and in transit), auditing, and the hardening checklists for both platforms. You will lock down a lab instance and then try to break in — from the outside, as an attacker would.

Objectives

  • Apply least privilege by creating logins and users with only the permissions their job requires.
  • Implement role-based access with custom database roles instead of built-in privileged roles.
  • Enable auditing of logins and sensitive actions and practice reading the audit trail.
  • Configure encryption at rest and in transit at the feature level on a lab instance.

Key concepts

Least privilege and separation of duties in database access

Least privilege means every login holds exactly the permissions its job requires — no more, no less — and separation of duties means no single account can both make and hide a change. The lab builds three personas (service account, analyst, administrator) and proves the boundaries hold: the analyst cannot write, the app account cannot read outside its schema. Privilege is a liability that happens to be necessary; minimize the liability.

Authentication modes: OS/integrated logins vs database-native logins

Integrated authentication delegates identity to the OS or directory — one credential store, centralized policy, no passwords in connection strings. Database-native logins are portable and simple but create a second credential lifecycle to manage. The right mix depends on the environment: domain-joined fleets favor integrated, heterogeneous or cloud workloads often need native. Know which mode each login uses, because the audit and rotation story differs completely.

Server roles vs database roles vs custom application roles

Built-in privileged roles are convenient and dangerous: they bundle far more power than any application needs. The discipline is custom database roles that grant exactly the application's required permissions, with server-level roles reserved for actual administrators. The lab replaces a db_owner-style grant with a tailored role. Roles are the unit of least privilege — design them before you need them, not after an incident.

Auditing: capturing logins, schema changes, and access to sensitive tables

Auditing answers who did what, when: successful and failed logins, schema changes, and access to sensitive tables are the baseline capture set. The lab enables auditing, performs suspicious actions, then finds them in the trail — because an audit log you cannot read is decoration. Size and retention are part of the design: audit data grows, and a full audit volume that halts the engine is its own incident. For personal-data stores, the audit trail is also a compliance artifact.

Encryption at rest (transparent data encryption concepts) and key management basics

Transparent data encryption encrypts data and log files on disk so stolen files are unreadable without the keys — it protects against media theft, not against a compromised running server. The lab enables it, then restores the backup elsewhere to meet the key and certificate dependency face to face: without the keys, the backup is a brick. Key management — creation, backup, rotation, escrow — is the actual discipline; the encryption checkbox is the easy part.

Encryption in transit (TLS) and certificate concepts

TLS encrypts the conversation between client and server so credentials and data cannot be sniffed or altered in flight. The lab enables TLS on a containerized instance and verifies the connection is actually encrypted — configured is not the same as working. Certificates need a trust chain the client accepts and a renewal plan before expiry. Encrypting the wire is table stakes on any untrusted network, which in practice means every network.

Surface-area reduction: disabling unused features and services

Every enabled feature is attack surface: unused services, extended procedures, and optional components are doors with no business purpose. Hardening starts with an inventory and proceeds by disabling — the lab's checklist pass remediates each finding and documents it. Defaults favor convenience, not security, so a fresh install is the most exposed it will ever be. Reduce first, then defend what remains.

Patching cadence and vulnerability scanning as ongoing hygiene

Patching is not an event; it is a cadence — test, schedule, apply, verify — because unpatched databases are the low-hanging fruit of every breach report. Vulnerability scanning finds the misconfigurations and missing patches between cycles. The lab treats both as hygiene: recurring, boring, and non-negotiable. The database holding the crown jewels cannot be the least-patched box in the fleet.

Hands-on labs

  1. Create three personas (application service account, analyst, administrator) with tailored roles; prove the analyst cannot write and the app account cannot read outside its schema.
  2. Enable auditing of logins and schema changes, perform suspicious actions, then find them in the audit trail.
  3. Enable TLS for client connections on a containerized instance and verify the connection is actually encrypted.
  4. Enable at-rest encryption on a lab database, then back it up and restore it elsewhere to observe the key/certificate dependency firsthand.
  5. Run a hardening checklist against your lab instance, remediate every finding, and document each remediation.

Self-check

  1. Why is a db_owner/DBA-level account for an application a finding, and what do you replace it with?
  2. You restore an encrypted backup to a new server and it fails. What is missing, and why?
  3. Which events belong in the audit trail for a database that holds personal data?
  4. Explain the difference between encrypting the disk and encrypting the database itself.

Module 5 of 8

Monitoring and Alerting

You cannot fix what you cannot see. This module covers the monitoring stack: wait statistics and dynamic management views on SQL Server, AWR and ADDM on Oracle, and the alerting discipline that separates signal from noise. You will build a monitoring baseline and a paging policy.

Objectives

  • Identify the five health signals that matter most: waits, locks, space, slow queries, and errors.
  • Build a performance baseline so that 'abnormal' has a concrete definition.
  • Configure alerts with thresholds tied to the baseline while avoiding alert fatigue.
  • Read an execution plan at a basic level and find the most expensive operator.

Key concepts

Wait statistics: learning what the server is actually waiting on

Wait statistics are the engine's own account of where time goes: CPU, I/O, locks, network — each wait type is a category of delay the server measured on itself. Reading them tells you what the server is actually waiting on instead of what you guessed. The lab captures a baseline of waits across runs so that a shift — say, from CPU to I/O overnight — is visible as a fact, not a feeling. Diagnose from waits outward; everything else is speculation.

Blocking and deadlocks: detection, victim selection, and resolution concepts

Blocking is one session holding a lock another needs — normal in small doses, a problem when chains form. A deadlock is a cycle: each session waits on the other, and the engine picks a victim and kills it to break the cycle. The lab creates both on purpose and reads the deadlock report, because the cycle diagram is the concept. Blocking is resolved by finding the head blocker; deadlocks are resolved by design — consistent access order, short transactions.

Space monitoring: data files, log files, temp/scratch space, and OS disk

Databases die of full disks more often than of exotic failures: data files grow, logs grow, temp space spikes, and the OS volume underneath it all fills. The lab fills a scratch volume inside a container on purpose and watches monitoring react, then documents remediation. Monitor each space consumer separately with its own threshold and runbook, because a data file at 95% and a log at 95% are different emergencies with different fixes.

Slow-query capture: finding top queries by duration and logical reads

You cannot tune what you cannot see, so capture the top queries by duration and logical reads over a representative window. Duration tells you what users feel; logical reads tell you what the engine does — a query can be slow from waiting or from working, and the fix differs. The lab builds its baseline from these captures. Start every performance conversation with the ranked list, not with a hunch about which query is guilty.

Baselines, trends, and seasonal patterns: defining abnormal before it happens

Abnormal has no meaning without normal: a baseline is the recorded behavior of waits, space, and top queries over time, including seasonal patterns like month-end load. The lab stores its baseline in a workbook and the checkpoint asks you to define normal in three sentences from your own data. Without a baseline, every spike is a mystery and every alert threshold is a guess.

Alert design: thresholds tied to baselines, severity levels, and runbooks

Good alerts fire on meaningful deviation from baseline, carry a severity, and link to a runbook that says what to do at 3 AM. Bad alerts fire on fixed thresholds nobody remembers choosing, at volumes nobody reads — alert fatigue, where the real page drowns in noise. The lab's space-alert exercise includes writing the runbook entry, because an alert without a runbook is just anxiety with a pager. Tune relentlessly; every false page is a withdrawal from the team's trust.

Error logs and job history as the first place to look when something breaks

When something breaks, start with the engine's own diary: the error log and the job history. They record what the server saw, in order, without interpretation — failed logins, corruption warnings, job failures, crash traces. The lab treats them as step one of triage for exactly that reason. Learn the rhythm of a healthy log so the unhealthy entries stand out; most incidents announce themselves here before anywhere else.

Dashboards vs alerts: observation vs notification are different jobs

Dashboards are for observation — the current state you glance at to build intuition. Alerts are for notification — the push that interrupts you because something needs action now. Mixing the jobs produces dashboards nobody watches and alerts nobody trusts. The lab builds a one-page dashboard from baseline metrics as a separate artifact from the alerting exercise. Observe continuously; notify sparingly.

Hands-on labs

  1. Capture a baseline of wait statistics, file sizes, and top queries over several runs and store it in a workbook.
  2. Generate blocking on purpose with two concurrent sessions; identify the blocker and the victim using system views.
  3. Create a deadlock in the lab, read the deadlock report, and explain the cycle in plain language.
  4. Fill a scratch volume safely inside a container and watch space monitoring react; document the remediation steps.
  5. Build a one-page dashboard (even a spreadsheet) from your baseline metrics.

Self-check

  1. Wait statistics shift overnight from CPU to I/O. What changed, and what do you check first?
  2. Your space alert fires at 3 AM for transaction-log growth. What does the runbook say?
  3. How do you tell blocking apart from a deadlock, and why does the distinction matter?
  4. Define 'normal' for your lab server in three sentences using your own baseline.

Module 6 of 8

Performance Troubleshooting Basics

Slow queries are where DBA theory meets reality. This module teaches a repeatable troubleshooting method: identify the bottleneck, read the execution plan, fix the statistics or the index or the query — in that order. You will work real slow-query scenarios and document each diagnosis.

Objectives

  • Follow a repeatable triage order: scope, measure, hypothesize, change one thing, verify.
  • Use wait statistics and query stats to find bottlenecks instead of guessing.
  • Recognize missing-index and stale-statistics symptoms in query plans.
  • Know when a problem belongs to the database and when it belongs to the app, network, or storage.

Key concepts

The triage method: scope, measure, hypothesize, change one thing, verify

Triage is a discipline, not a talent: scope the symptom (what, exactly, is slow, and for whom), measure it (waits, plans, stats), form one hypothesis, change one thing, and verify against the measurement. The method's power is in what it forbids — changing three things at once, or tuning without a baseline. The lab's incident report is the method written down: timeline, root cause, prevention. Follow the order especially when the pressure says skip it.

Reading execution plans: scans vs seeks, key lookups, sorts, and spills

The execution plan is the optimizer's confession: what it actually did with your query. A seek finds rows through an index; a scan reads everything — the most expensive operator in the plan is usually the story. Key lookups, sorts, and spills (tempdb overflow from underestimated memory) each have a characteristic signature and a characteristic fix. The lab's slow-query exercise is plan-reading practice: find the most expensive operator first, then ask why the optimizer chose it.

Parameter sniffing concepts: why the same query performs differently with different inputs

The optimizer builds a plan for the parameter values it sees first and reuses it for later values — great when data is uniform, catastrophic when it is skewed. One customer with 100,000 orders gets a plan built for a customer with five, or vice versa. The lab builds a skewed dataset to demonstrate the flip and documents mitigations at concept level. When the same code is fast for A and 50x slow for B, sniffing is the prime suspect.

Statistics: what the optimizer knows about your data and when it goes stale

Statistics are the optimizer's map of your data — row counts, value distributions — and plans are only as good as the map. Bulk loads, purges, and skewed growth make statistics stale, and stale statistics produce confident, wrong plans. The lab simulates staleness, watches the plan regress, then recovers by updating statistics. Automatic updates handle the common case; the DBA's job is knowing when the common case does not apply.

Indexing fundamentals: clustered vs nonclustered structures and covering concepts

A clustered index defines the table's physical order — one per table, and the choice of key shapes every query. Nonclustered indexes are separate lookup structures pointing back at the rows; a covering index includes all the columns a query needs, so the engine never touches the table at all. The lab creates the index a plan suggests and measures before and after with the same workload. Indexes are the highest-leverage performance tool and the easiest to overuse — which is why the next module measures their cost.

Temp/scratch space pressure and its symptoms

When temp or scratch space fills — from spills, sorts, version stores, or runaway temp tables — symptoms masquerade as everything else: slow queries, failed jobs, mysterious errors. The tell is correlation: many unrelated things degrade at once, and space metrics show the pressure. The lab's fill-the-volume exercise builds the pattern recognition. Temp pressure is an infrastructure symptom with an application cause; fix the cause, relieve the pressure, then ask why monitoring did not warn sooner.

Knowing when the problem is not the database: app, network, or storage

Not every slow query is a database problem. Chatty application code (thousands of round trips), saturated network, or degraded storage all present as database slowness to the frustrated user. The triage method earns its keep here: waits and measurements distinguish engine work from waiting on something else. The honest — and cheapest — outcome of a good investigation is sometimes a finding that the database is innocent. Blame the evidence, not the habit.

Incident documentation: timeline, root cause, and prevention

Every incident ends with a document: a timeline of what happened and when, the root cause with evidence, and the prevention — the monitoring, runbook, or design change that stops the sequel. The lab's one-page incident report practices exactly this shape. Documentation is how an incident pays for itself: without it, the same outage recurs with different people; with it, the organization gets smarter. Write it while the memory is fresh.

Hands-on labs

  1. Load a sample dataset, run a deliberately slow query, capture its plan, and identify the most expensive operator.
  2. Create the index the plan suggests and measure before/after performance with the same workload.
  3. Simulate stale statistics in a lab-only database, observe the plan regression, then recover by updating statistics.
  4. Build a skewed dataset to demonstrate parameter sniffing behavior and document two mitigations at the concept level.
  5. Write a one-page incident report for a lab slowdown you induced, including timeline and root cause.

Self-check

  1. A query is slow for one customer but fast for everyone else. What is your first hypothesis?
  2. You added an index and nothing improved. What do you check next?
  3. When is 'add more hardware' the wrong answer to a slow query?
  4. Explain the most expensive operator in a query plan to a non-DBA in plain language.

Module 7 of 8

Migration Planning and Execution

Databases outlive their versions. This module covers upgrade paths, compatibility levels, migration strategies (backup/restore, log shipping cutover, Data Migration Assistant), and rollback planning. You will rehearse a full migration in the lab, including the rollback nobody wants to need.

Objectives

  • Inventory a source database completely: size, features in use, and dependencies.
  • Run compatibility checks and classify findings as blockers vs warnings.
  • Choose a migration method and justify the choice against downtime constraints.
  • Execute a practice migration to a container and validate row counts and application connectivity.

Key concepts

Discovery: inventorying everything that moves (data, jobs, logins, linked servers, code)

A database is never just data: jobs, logins, linked servers, procedures, and application connection strings all have to move with it, and the forgotten ones are what fail at cutover. Discovery inventories everything — size, features in use, dependencies — before any method is chosen. The lab lists every non-data object in its database as practice. Migrations fail on the uninventoried, never on the inventoried.

Compatibility levels and deprecated features

Target platforms have compatibility levels that gate behavior, and deprecated features that may not survive the move. Assessment tooling flags them; the DBA triages each finding as blocker, warning, or noise. A deprecated feature in active use is a decision, not a surprise — the checkpoint asks for your options, which range from rewriting to deferring the migration. Run the assessment early, because blockers found late become schedule slips.

Downtime windows and cutover planning

Every migration method implies a downtime window — the span during which the application is stopped and the final data movement happens. The window must fit the business's tolerance, which is why the method follows the constraint, not the reverse. Cutover planning sequences every step with owners and timings; the lab's timed dry run exists to find the steps that do not fit. A cutover without a rehearsed plan is a hope with a maintenance window.

Migration methods (backup/restore, detach/attach, export/import, replication) and their trade-offs

Backup/restore is simple and proven but needs downtime proportional to size. Detach/attach is fast but moves files, not safety — there is no fallback copy. Export/import is flexible across versions but slow and lossy on exotic objects. Replication-based moves minimize downtime at maximum complexity. The lab performs backup/restore and fixes the resulting orphaned users, feeling one method's trade-off directly. Choose by downtime budget, size, and version distance — in that order.

Login and user mapping: fixing orphaned users after a move

Logins live at the server level; users live inside the database — restore a database to a new server and the users point at logins that do not exist. These orphaned users are the classic post-migration authentication failure, and the lab creates and fixes them deliberately. Migrate logins separately, then remap. It is a five-minute fix when planned and a cutover-night mystery when not.

Validation: row counts, checksums, and application smoke tests

A migration is not done when the data arrives; it is done when the data is proven correct. Row counts catch gross loss, checksums catch silent corruption, and application smoke tests catch the semantic breakage counts miss — the report that returns wrong results after a successful-looking move. The checkpoint's wrong-report scenario points at statistics, compatibility, or collation first. Define success in measurable terms before cutover, then measure it.

Rollback planning: deciding in advance when and how you go back

Every migration needs a rollback plan with a marked point of no return — the moment after which going back costs more than going forward. The lab writes the rollback plan before the practice cutover, not during it. Decide the abort criteria while calm: which failures trigger rollback, who calls it, and how long it takes. A migration without a rollback plan is a commitment made before the evidence is in.

Post-migration steps: refreshing statistics and re-establishing baselines

After the move, refresh statistics (the optimizer's map is stale on new hardware), rebuild or verify indexes, and re-establish performance baselines — the old normal no longer applies. Re-point jobs, alerts, and monitoring at the new home. The lab's practice migration ends with validation, but the real job ends when the new environment is monitored, documented, and boring. Migrations conclude with operations, not with applause.

Hands-on labs

  1. Inventory your lab database — list every non-data object (jobs, logins, procedures, linked references) that must migrate with it.
  2. Run the platform's compatibility assessment tooling against the lab database and triage each finding as blocker, warning, or noise.
  3. Perform a backup/restore migration to a fresh container and fix the orphaned users/logins that result.
  4. Run a timed dry-run cutover from a checklist, then hold a retrospective on what slipped.
  5. Write a rollback plan for your migration and mark the point of no return.

Self-check

  1. The assessment flags a deprecated feature that is actively used. What are your options?
  2. After migration the app connects, but one report returns wrong results. Where do you look first?
  3. Why must logins be migrated separately from the database backup?
  4. Define 'migration success' in measurable terms before the cutover begins.

Module 8 of 8

Capacity Planning and Maintenance

The DBA's job ends where the platform engineer's begins: forecasting growth, automating the routine, and making yourself unnecessary for daily operations. This closing module covers capacity models, trend analysis, and the automation — jobs, scripts, runbooks — that turns administration into engineering.

Objectives

  • Build a maintenance plan covering integrity checks, index maintenance, and statistics updates.
  • Explain fragmentation and when rebuild vs reorganize (or the platform equivalent) applies.
  • Forecast storage and compute growth from trend data.
  • Schedule maintenance to minimize impact on production workloads.

Key concepts

The maintenance triad: integrity checks, index maintenance, statistics updates

Three jobs recur forever: integrity checks prove the data is not corrupt, index maintenance keeps access structures efficient, and statistics updates keep the optimizer's map current. The lab builds one weekly script covering all three plus history cleanup, and runs it end to end. Skip any leg of the triad long enough and it becomes an incident with a different name. Maintenance is not overhead; it is the job.

Fragmentation: what it is, how it is measured, and when it actually matters

Fragmentation is disorder in index pages from random inserts, updates, and deletes — measured as a percentage, felt as extra I/O. The lab fragments an index deliberately, measures it, then compares remedies. But fragmentation only matters when it measurably hurts: 5% on a large index is usually not worth a rebuild's cost, while high fragmentation on a hot range-scan index is. Measure first, act on evidence, and remember that some fragmentation is the normal cost of doing business.

Rebuild vs reorganize trade-offs: offline vs online, log impact, duration

Rebuild creates the index fresh — thorough, but heavy on logging, duration, and (in some editions) locking. Reorganize compacts in place — lighter and online-friendly, but less thorough. The lab compares both outcomes on the same fragmented index. The choice is situational: reorganize for routine tidying, rebuild for real disorder, and always weigh the maintenance window. On editions without online rebuild, the trade-off bites hardest.

Statistics maintenance strategies: automatic vs scheduled manual updates

Automatic statistics updates handle steady-state change well, but bulk operations and skewed tables outrun them — the optimizer plans against a stale map and performance falls off a cliff. Scheduled manual updates after known data events (nightly loads, purges) close the gap. The checkpoint's skipped-a-month scenario is the cautionary tale: plans degrade gradually, then suddenly. Know your data's change pattern and maintain statistics to match it.

History cleanup: job history, backup history, and audit retention

The msdb-style system tables that record job history, backup history, and audit trails grow without bound unless pruned. Unchecked growth slows the very tooling you rely on and can fill system databases. The lab's maintenance script includes history cleanup with a retention policy — because retention is a decision (compliance, forensics) before it is a purge. Keep what the business needs; delete the rest on schedule.

Capacity forecasting from trend data with headroom targets

Capacity planning is trend math: collect repeated samples of file growth, chart the line, and project when each volume hits the headroom target (the lab uses 80%). The forecast turns a surprise outage into a scheduled procurement. Recompute regularly, because growth is rarely linear for long — the business launches features. A forecast is a living document, not a one-time spreadsheet.

Maintenance windows and minimizing production impact

Maintenance consumes resources — I/O, locks, log space — so schedule it where it hurts least, and measure the impact when it overlaps live load anyway. The lab runs maintenance during a simulated business-hours load to feel the contention. Online-capable operations, smaller batches, and throttling are the tools when no true window exists. The goal is a system that stays healthy without ever making users notice the doctor visits.

Runbook documentation that your future on-call self will thank you for

The runbook records what runs, when, how long it takes, and how to back out — written for the tired, stressed reader at 3 AM, who is you. The lab's final artifact is exactly this document. Undocumented maintenance is a personal habit; documented maintenance is an organizational capability. Your future on-call self is the most important reader you will ever write for.

Hands-on labs

  1. Fragment a lab index with random updates, measure fragmentation, then compare rebuild vs reorganize outcomes.
  2. Build a weekly maintenance script (integrity check, index maintenance, statistics update, history cleanup) and run it end to end.
  3. Collect repeated file-growth samples, chart the trend, and project when each volume reaches 80% full.
  4. Run maintenance during a simulated business-hours load and measure the impact on concurrent user queries.
  5. Write the maintenance runbook — what runs, when, expected duration, and how to back out.

Self-check

  1. Fragmentation measures 5% on a large index. Do you rebuild? Justify with the trade-offs.
  2. Your forecast shows the log volume hitting 80% full in 60 days. What are your options?
  3. A maintenance job overlaps business hours and blocks users. How do you reschedule it safely?
  4. What breaks if statistics updates are skipped for a month?
