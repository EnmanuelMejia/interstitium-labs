Overview

Eight modules of core SQL taught on SQLite: DDL and DML fundamentals, filtering and aggregation, joins, subqueries and CTEs, window functions, set operations, transactions and isolation, and indexes with normalization. Dialect notes throughout translate each concept to SQL Server, Oracle, and Postgres. SQLite is the teaching engine — and it is never confused with the others: every dialect difference is called out explicitly.

It is for developers, analysts, and engineers who need working SQL fluency. No prior SQL is assumed; programmers will move faster, but the sequence starts at zero.

Every module is lab-driven: build the tables, run the queries, break things, fix them. The dialect notes are for reading, not memorizing — learn SQLite deeply, and treat the translations as a map for later. Do the self-checks from memory; the sequence's checkpoint questions are designed to be answerable without notes once the concept lands.

Module 1 of 8

Module 1 — DDL and DML Fundamentals

The foundation: creating tables, inserting rows, updating and deleting data. This module covers CREATE TABLE with constraints, the INSERT/UPDATE/DELETE statements, and the data types SQLite offers. You will build your first database from scratch — a small company schema you will extend all sequence long.

Objectives

  • Create, alter, and drop tables using standard DDL with constraints
  • Insert, update, and delete rows safely with WHERE clauses and transactions
  • Describe how SQLite's type affinity differs from strict-typed engines
  • Recover from a schema-migration mistake using the rebuild pattern

Key concepts

Schemas, databases, and tables: organizing containers for rows

Databases contain schemas, schemas contain tables, tables contain rows — the nesting that organizes everything. SQLite collapses the hierarchy (one file, effectively one schema), while server engines use it for security and organization. The lab's company.db with departments and employees is the hierarchy in miniature. Name things deliberately at each level; you will live with those names for years.

Column data types and why SQLite type affinity matters

Every column has a declared type, but what the engine enforces varies: strict-typed engines reject a string in an integer column, while SQLite's type affinity system nudges values toward the column's preferred type instead of rejecting them. Affinity is flexible — usually convenient, occasionally surprising when a value lands in a form you did not expect. The module's labs surface the difference deliberately. Know your engine's strictness before you trust its types.

Primary keys, foreign keys, UNIQUE, NOT NULL, CHECK, DEFAULT constraints

Constraints are the database enforcing your rules: PRIMARY KEY uniquely identifies each row, FOREIGN KEY ties rows to a parent table, UNIQUE forbids duplicates, NOT NULL forbids missing values, CHECK enforces a condition, DEFAULT supplies a value when none is given. The lab's departments table uses four of them at once. Constraints move data-quality enforcement from application hope to database guarantee — declare them at creation, not after the bad data arrives.

CREATE/ALTER/DROP TABLE as schema-change tools

CREATE TABLE defines structure, ALTER TABLE modifies it (with SQLite's historically limited ALTER — no dropping columns or changing types), and DROP TABLE removes it entirely. The lab's rebuild pattern — create new, copy with INSERT INTO ... SELECT, drop old, rename — is the portable answer to ALTER's limits. Schema changes are the dangerous half of database work: they affect every query, so practice them on scratch data first.

INSERT, UPDATE, DELETE as row-change tools

INSERT adds rows, UPDATE modifies rows matching a WHERE clause, DELETE removes them — and the WHERE clause is the difference between a targeted change and a catastrophe. The lab wraps the three operations in a transaction, runs them, rolls back, and watches the changes vanish: the safety net made visible. Always SELECT with the same WHERE first, so you see what you are about to change before you change it.

The full read-modify cycle: SELECT it, UPDATE it, DELETE it, re-verify

The disciplined change pattern is read-modify-verify: SELECT the rows you intend to touch, make the change, then re-run the SELECT to confirm exactly what happened. The lab practices the full cycle on employees — raise, rename, delete, count. Verification is not paranoia; it is how you catch the WHERE clause that matched zero rows or ten thousand. Every DML statement ends with a confirming read.

Hands-on labs

  1. Lab 1.1 — Create company.db and build a departments table: CREATE TABLE departments (dept_id INTEGER PRIMARY KEY, dept_name TEXT NOT NULL UNIQUE, budget INTEGER CHECK (budget >= 0)). Insert 4 departments. Dialect note: SQLite's INTEGER PRIMARY KEY auto-increments without the AUTOINCREMENT keyword; SQL Server uses IDENTITY(1,1), Oracle uses sequences. AUTOINCREMENT in SQLite is optional and adds a bookkeeping table.
  2. Lab 1.2 — Build employees (emp_id INTEGER PRIMARY KEY, name TEXT NOT NULL, dept_id INTEGER REFERENCES departments(dept_id), salary INTEGER, hire_date TEXT). Insert 8 employees, two per department. Dialect note: store dates as TEXT in ISO 'YYYY-MM-DD' form in SQLite; SQL Server has a real DATE type and Oracle uses DATE; comparisons on ISO text sort correctly.
  3. Lab 1.3 — Practice DML: give every employee in one department a 5% raise (UPDATE with WHERE), fix a misspelled name, delete one employee row, then re-run SELECT COUNT(*) to verify. Wrap the three changes in BEGIN; ... COMMIT; and re-run with ROLLBACK first to see changes vanish.
  4. Lab 1.4 — Alter the schema without losing data: ALTER TABLE employees ADD COLUMN email TEXT UNIQUE; update rows to fill it in. Dialect note: SQLite ALTER TABLE cannot drop a column (historically) or modify a type — the standard workaround is CREATE new table, INSERT INTO ... SELECT, DROP old, RENAME. SQL Server supports ALTER TABLE ... DROP COLUMN directly.
  5. Lab 1.5 — Explore the schema: run .schema employees and PRAGMA table_info(employees); in the sqlite3 CLI. Note what sqlite3 prints for the primary key and foreign key, and which of those it enforces by default.

Self-check

  1. Given an existing table customers with a UNIQUE email column, which single statement raises its balance column by 100 for every row where balance is negative?
    Answer key
    The single statement: UPDATE customers SET balance = balance + 100 WHERE balance < 0; — the WHERE is the entire safety mechanism. Without it you raise every balance; with the wrong predicate you raise the wrong ones. Discipline: run the SELECT with the same WHERE first, eyeball the rows, then run the UPDATE.
  2. Explain the difference between TRUNCATE TABLE (where supported) and DELETE FROM with no WHERE clause, in terms of what is logged and what can be rolled back.
    Answer key
    TRUNCATE TABLE (where supported) deallocates whole data pages with minimal logging — fast, but usually non-transactional: you cannot roll it back and it does not fire DELETE triggers. DELETE FROM with no WHERE logs every row deletion, fires triggers, and rolls back cleanly — slow, but recoverable. SQLite has no TRUNCATE; DELETE without WHERE is the portable equivalent.
  3. Describe, in your own words, what happens if an UPDATE statement matches zero rows.
    Answer key
    Nothing is changed and no error is raised: the statement succeeds with zero rows affected. This is by design — UPDATE is a set operation over the matching rows, and the empty set is a valid set. Always check the affected-row count; 'matched zero rows' is the most common silent surprise in DML, and it usually means your WHERE predicate is wrong.
  4. Write the SQLite pragma that lists the columns of a table, and state what a T-SQL equivalent would be (hint: information_schema or sp_help).
    Answer key
    SQLite: PRAGMA table_info(customers); — lists columns, types, nullability, defaults, and key positions. T-SQL equivalents: SELECT * FROM information_schema.columns WHERE table_name = 'customers'; or the sp_help 'customers' procedure. Same question, different catalogs — learn your engine's introspection early.

Module 2 — Filtering and Aggregation

WHERE clauses and aggregate functions turn tables into answers. This module covers comparison and logical operators, GROUP BY and HAVING, and the aggregate functions — plus the NULL-handling rules that trip up every beginner. Labs build the filtering reflex.

Objectives

  • Filter rows precisely with WHERE predicates including NULL semantics
  • Aggregate with GROUP BY and separate row filters from group filters (WHERE vs HAVING)
  • Page and sort result sets portably across dialects
  • Translate basic date/string functions between SQLite and T-SQL

Key concepts

SELECT column list, DISTINCT, and column aliases

The SELECT list names exactly which columns return — never SELECT * in production code, because schema changes then silently change your output. DISTINCT deduplicates the returned rows. Aliases (AS) rename columns for readability. The lab's queries practice all three deliberately. Explicit column lists are documentation, performance (less data moved), and safety in one habit.

WHERE predicates: comparisons, BETWEEN, IN, LIKE, IS NULL

WHERE filters rows with predicates: comparisons (=, <>, >, <), BETWEEN for ranges, IN for sets, LIKE for patterns (% and _ wildcards), and IS NULL — never = NULL — for missing values. The lab's NULL comparison is the lesson that sticks: NULL never equals anything, not even itself. Precise filtering is the foundation everything else builds on; get the predicate right before reaching for anything fancier.

Logical evaluation order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

SQL is written SELECT-first but executed FROM-first: the engine finds the tables, filters rows, groups, filters groups, then computes the SELECT list, sorts, and pages. The checkpoint asks you to write this order from memory because half of all SQL confusion is clause-order confusion — why WHERE cannot use a SELECT alias, why HAVING cannot precede GROUP BY. Memorize the pipeline and the language stops being mysterious.

Aggregate functions: COUNT, SUM, AVG, MIN, MAX and NULL handling

Aggregates collapse rows into summaries: COUNT tallies, SUM and AVG total and average numerics, MIN and MAX find extremes. The NULL rule is the subtle part — aggregates ignore NULLs, except COUNT(*), which counts rows. The lab inserts a NULL customer and watches COUNT(customer) diverge from COUNT(*): the difference is the concept. When a summary looks wrong, check the NULLs first.

GROUP BY buckets and HAVING post-aggregation filters

GROUP BY sorts rows into buckets by shared values, and aggregates then compute per bucket — sales per region, headcount per department. HAVING filters the buckets after aggregation, which is why the lab's attempt to move a SUM condition into WHERE fails: WHERE runs before grouping and cannot see aggregates. The mental model is pipeline order — filter rows, group, filter groups. WHERE versus HAVING is the most-tested distinction in the module for a reason.

ORDER BY, LIMIT, OFFSET for paging

ORDER BY sorts the result, LIMIT caps how many rows return, OFFSET skips the first N — the paging trio. The lab pages rows 6–10 by amount. The dialect note matters: LIMIT is SQLite/Postgres/MySQL, SQL Server uses TOP and OFFSET/FETCH, Oracle 12c+ uses FETCH FIRST. Paging without ORDER BY is not paging — it is a random sample wearing a LIMIT clause. Always sort before you page.

Hands-on labs

  1. Lab 2.1 — Seed an orders table (order_id, customer, amount, region, order_date). Write queries: all orders from 'West' over 500; customers whose names start with 'A' (LIKE 'A%'); all rows where shipped is NULL vs IS NULL. Observe that NULL never equals anything.
  2. Lab 2.2 — Aggregation: compute COUNT(*), COUNT(customer), SUM(amount), AVG(amount), MIN/MAX(amount) over orders. Run COUNT(customer) after inserting a row with NULL customer and note the difference from COUNT(*) — aggregates ignore NULLs except COUNT(*).
  3. Lab 2.3 — Group and filter groups: SELECT region, COUNT(*), SUM(amount) FROM orders GROUP BY region HAVING SUM(amount) > 5000. Then try moving the SUM condition into WHERE and record the error — WHERE cannot see aggregates because it runs before grouping.
  4. Lab 2.4 — Paging drill: ORDER BY amount DESC LIMIT 5 OFFSET 5 returns rows 6–10 by amount. Dialect note: SQL Server uses SELECT TOP 5 ... (no OFFSET equivalent without ORDER BY + OFFSET/FETCH), Oracle 12c+ uses FETCH FIRST 5 ROWS ONLY (older Oracle: WHERE ROWNUM <= 5). LIMIT is SQLite/Postgres/MySQL.
  5. Lab 2.5 — String/date practice: concatenate first and last name with || (SQLite/Postgres/Oracle; SQL Server uses +). Extract the order year with strftime('%Y', order_date) — dialect note: SQL Server uses YEAR() or DATEPART, Postgres EXTRACT(YEAR FROM ...).

Self-check

  1. Predict the result of WHERE salary = NULL versus WHERE salary IS NULL — and explain why.
    Answer key
    WHERE salary = NULL returns zero rows, always — any comparison with NULL yields UNKNOWN, and WHERE keeps only TRUE. WHERE salary IS NULL is the correct null test. This is three-valued logic, not a bug: NULL means 'unknown', and 'unknown = unknown' is unknown, not true.
  2. Rewrite a HAVING clause as a WHERE clause in a query where it is valid to do so, and state where the rewrite breaks.
    Answer key
    A HAVING clause can be rewritten as WHERE only when it filters on non-aggregated columns — i.e. when it is really a row filter wearing a HAVING costume. The rewrite breaks the moment the predicate uses an aggregate (HAVING COUNT(*) > 5 has no WHERE equivalent) because aggregates do not exist until after grouping.
  3. Given daily sales rows, which clause filters individual sales above 1000 and which filters stores whose total sales are below 10000?
    Answer key
    WHERE amount > 1000 filters individual sales rows before grouping; HAVING SUM(amount) < 1000 filters stores after aggregation. Mixing them up is the classic aggregation bug: the row filter shrinks the input, the group filter judges the output. Read the execution order (Module 2's figure) and the placement becomes obvious.
  4. Write the logical execution order of SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT from memory.
    Answer key
    Logical execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Memorize it, because it explains three mysteries at once: why WHERE cannot see SELECT aliases, why HAVING can use aggregates, and why ORDER BY is the only clause that may reference output aliases.

Module 3 — Joins: Inner, Outer, Self, Cross

Relational data lives across tables; joins put it back together. This module covers INNER, LEFT, RIGHT, and FULL joins, self-joins, and the join-condition discipline that prevents accidental Cartesian products. Labs drill the join patterns until they are reflex.

Objectives

  • Write inner and outer joins with correct ON conditions and aliases
  • Model a hierarchy with a self-join and keep the root rows
  • Predict and verify cross-join row counts
  • Simulate FULL OUTER JOIN in SQLite with UNION

Key concepts

INNER JOIN: matching rows only, the default workhorse

An INNER JOIN returns only rows with a match on both sides — employees whose dept_id exists in departments. It is the default mental model and the most common join in practice. The lab joins employees to departments, then switches to LEFT JOIN to show exactly which rows the inner join was hiding. When rows go missing unexpectedly, the join type is the first suspect.

LEFT/RIGHT/FULL OUTER JOIN: preserving unmatched rows from one or both sides

Outer joins preserve unmatched rows: LEFT keeps everything from the left table (NULLs where no match), RIGHT mirrors it, FULL keeps both sides' orphans. The lab adds an employee with NULL dept_id and watches the LEFT JOIN surface what the inner join dropped. SQLite lacks FULL OUTER JOIN, so the lab builds it from a UNION of LEFT JOINs — the same result, assembled manually. Choose the side whose orphans matter.

Table aliases and why join queries need them

Aliases (e, d, m) shorten table references and are mandatory when a table appears twice — without them, the engine cannot tell the two instances apart. In join queries they also document intent: e.name versus m.name reads as employee versus manager. The lab aliases every join from the start. Consistent, meaningful aliases are the cheapest readability investment in SQL.

Self-joins: a table joined to itself for hierarchies

A self-join treats one table as two by aliasing it twice — employees e joined to employees m on manager_id — which models hierarchies like org charts. The lab keeps the CEO by using LEFT JOIN: the root has no manager, and an inner join would erase it. The duplicate-pair checkpoint (A-B and B-A) is the classic self-join trap, fixed with one inequality predicate. Whenever a table references itself, the self-join is the tool.

CROSS JOIN: the cartesian product and its row-count math

A CROSS JOIN pairs every row of one table with every row of the other — the cartesian product, with row count equal to rows-A times rows-B. The lab verifies the math on small tables and shows the comma-style equivalence. Deliberate uses exist (generating combinations, test data), but an accidental cross join — a missing ON condition — is the classic runaway query. Know the formula so you recognize the explosion.

Multi-table join chains and join-order readability

Real queries chain several joins, and readability comes from ordering them as a narrative: start from the driving table, join outward, alias everything. The ON conditions should read as the relationships they are. Long chains deserve formatting — one join per line, consistent aliases. The optimizer reorders freely; you order for the human who debugs this at midnight.

Hands-on labs

  1. Lab 3.1 — INNER JOIN employees to departments on dept_id; select employee name, department name, salary. Then change INNER to LEFT JOIN and add an employee with a NULL dept_id — observe the new row with a NULL department name. Dialect note: join syntax is identical across SQLite, SQL Server, Postgres, Oracle.
  2. Lab 3.2 — Self-join hierarchy: ALTER TABLE employees ADD COLUMN manager_id INTEGER REFERENCES employees(emp_id). Set managers, then SELECT e.name, m.name AS manager FROM employees e LEFT JOIN employees m ON e.manager_id = m.emp_id. LEFT JOIN keeps the CEO (no manager).
  3. Lab 3.3 — CROSS JOIN experiment: SELECT d.dept_name, p.proj_name FROM departments d CROSS JOIN (small projects table) — count the rows and verify it equals departments × projects. Then rewrite the same query with a comma-style join and an explicit ON 1=1 to see the equivalence.
  4. Lab 3.4 — FULL OUTER JOIN in SQLite: SQLite has no FULL OUTER JOIN keyword (Postgres and SQL Server do). Simulate it: LEFT JOIN query UNION RIGHT-equivalent (swap table order) LEFT JOIN. Compare the result to the INNER JOIN row count and account for every extra row.

Self-check

  1. Draw the Venn-diagram overlap for INNER vs LEFT JOIN on employees ⋈ departments and state which side keeps its unmatched rows.
    Answer key
    INNER keeps only matched pairs; LEFT JOIN keeps every row from the left table, filling unmatched right-side columns with NULL. On employees LEFT JOIN departments, employees without a department survive (with NULL department columns); departments without employees do not. The kept side is the one named by the join type.
  2. A self-join query returns each pair twice (A-B and B-A). What single predicate removes the duplicates?
    Answer key
    Add WHERE a.id < b.id (or >). The strict inequality keeps exactly one ordering of each unordered pair and also excludes self-pairs (a.id = b.id). != alone is not enough — it keeps both (A,B) and (B,A).
  3. State the row-count formula for a CROSS JOIN and explain when you would actually want one.
    Answer key
    Row count = m × n (every row of A paired with every row of B). You actually want one when generating combinations deliberately: test matrices, calendar scaffolds (dates × shifts), or pairwise comparisons. Anywhere else, an unexpected CROSS JOIN is a missing join condition — and a very large surprise.
  4. Explain what happens to columns when a FULL OUTER JOIN is simulated in SQLite with a UNION of LEFT and RIGHT joins.
    Answer key
    SQLite has no native FULL OUTER JOIN; the UNION of LEFT and RIGHT joins simulates it. What happens to columns: each side contributes its own columns, unmatched sides become NULL, and the UNION (not UNION ALL) dedupes the matched rows that appear in both halves. Column order and types must align across the two branches.

Module 4 — Subqueries and CTEs

Queries inside queries: subqueries and common table expressions. This module covers correlated and uncorrelated subqueries, EXISTS versus IN, and the CTE patterns that make complex queries readable. Labs build multi-step analytical queries.

Objectives

  • Choose between scalar, correlated, and EXISTS subqueries for a task
  • Avoid the NOT IN / NULL trap with NOT EXISTS
  • Refactor nested subqueries into readable chained CTEs
  • Traverse a hierarchy with a recursive CTE

Key concepts

Scalar, row, and table subqueries in SELECT, WHERE, and FROM

Subqueries come in shapes: scalar (one value, usable in the SELECT list), row/table (usable in FROM as a derived table), and predicates (IN, EXISTS in WHERE). The lab's scalar subquery broadcasts one average per row; the derived-table form appears in the set-operations module. A scalar subquery must return at most one row — more is an error, which is the engine enforcing your assumption. Match the shape to the clause.

Correlated vs uncorrelated subqueries and how the engine evaluates them

An uncorrelated subquery runs once, independently; a correlated subquery references the outer query and re-evaluates per outer row — conceptually a nested loop. The lab correlates an average-salary subquery per department, then rewrites it as a CTE join. Correlation is expressive but can be slow on large data; the rewrite pattern (CTE plus join) is the standard escape. Know which kind you wrote before you worry about performance.

EXISTS vs IN: semantics and NULL pitfalls

EXISTS asks whether the subquery returns any row — true or false, immune to NULLs. IN compares against a list — and a single NULL in the list makes NOT IN return nothing at all, silently. The lab demonstrates the trap: insert a NULL dept_id, watch NOT IN go empty, then fix it with NOT EXISTS. The rule is absolute: for negative membership tests, use NOT EXISTS. IN is fine for positive tests on clean data; NOT IN is a loaded gun.

Common Table Expressions (WITH) for readability and reuse

A CTE (WITH name AS (SELECT ...)) names a subquery so the main query reads as prose instead of nesting. The same CTE can be referenced multiple times in the query. The lab's refactor turns a nested correlated query into a named dept_avg step joined cleanly. CTEs are primarily a readability tool — the engine may or may not materialize them — so use them wherever a query's logic deserves names.

Chained CTEs: building a query in named steps

CTEs chain: WITH a AS (...), b AS (SELECT ... FROM a) — each named step building on the last. The lab rewrites a correlated query as a two-CTE chain and the readability difference is the lesson. Named steps are self-documenting; nesting is not. When a query needs three levels of nesting, it needs CTEs instead.

Recursive CTEs: traversing hierarchies and sequences

A recursive CTE (WITH RECURSIVE) defines a base case and a recursive step that joins back to itself — the lab walks the employee-manager hierarchy printing indentation by level. It is the SQL answer to tree traversal and sequence generation, which plain subqueries cannot express. Every recursive CTE needs a termination condition, or it recurses until the engine stops it. Hierarchies, bills of materials, org charts: this is their query.

Hands-on labs

  1. Lab 4.1 — Scalar subquery: SELECT name, salary, (SELECT AVG(salary) FROM employees) AS avg_sal FROM employees — one value broadcast per row. Then correlate it: employees earning more than the average of THEIR department, with the inner query referencing the outer alias.
  2. Lab 4.2 — EXISTS vs IN: find departments with no employees using NOT EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.dept_id). Insert a NULL dept_id employee and show that NOT IN (SELECT dept_id FROM employees) silently returns nothing — the classic NULL trap; NOT EXISTS is immune.
  3. Lab 4.3 — CTE readability: rewrite Lab 4.1's correlated query as WITH dept_avg AS (SELECT dept_id, AVG(salary) a FROM employees GROUP BY dept_id) SELECT e.name FROM employees e JOIN dept_avg d ON ... WHERE e.salary > d.a. Chain a second CTE that ranks the result.
  4. Lab 4.4 — Recursive CTE: WITH RECURSIVE reports(emp_id, name, lvl) AS (SELECT emp_id, name, 0 FROM employees WHERE manager_id IS NULL UNION ALL SELECT e.emp_id, e.name, r.lvl+1 FROM employees e JOIN reports r ON e.manager_id = r.emp_id) SELECT * FROM reports. Print the org chart with indentation via lvl.

Self-check

  1. Convert a correlated subquery to an equivalent JOIN and state which reads more clearly for 'employees earning above their department average'.
    Answer key
    For 'employees earning above their department average', the JOIN version (aggregate per department in a derived table, join back) usually reads more clearly than the correlated subquery — the aggregation step is named and visible. Correlated subqueries hide the per-row re-evaluation; the join makes the data flow explicit. Prefer the form where the next reader sees the shape of the computation.
  2. Explain why a scalar subquery must return at most one row, and what error you get otherwise.
    Answer key
    A scalar subquery sits where a single value is expected (=, SELECT list) — two rows cannot fit in one value slot. Exceeding one row raises a runtime error ('subquery returns more than one row' / 'single-row subquery returns more than one row'). The query compiles fine; it dies on the data that violates the assumption. Guard with aggregation or LIMIT 1 when the data cannot guarantee uniqueness.
  3. Rewrite a three-level nested subquery as a chain of two CTEs and compare readability.
    Answer key
    Three nested levels become: WITH step1 AS (...), step2 AS (SELECT ... FROM step1 ...) SELECT ... FROM step2. Readability wins twice: each step gets a name documenting its intent, and the final SELECT reads top-down instead of inside-out. Nesting depth is a readability tax; CTEs pay it down.
  4. State one thing a recursive CTE can do that a plain subquery cannot.
    Answer key
    A recursive CTE can iterate: walk org-chart hierarchies, bill-of-materials explosions, or graph traversals to arbitrary depth with a base case plus a recursive step. A plain subquery is a fixed-depth lookup — it cannot loop. Recursion in SQL is bounded by the engine's iteration limit, not by how many levels you were willing to nest by hand.

Module 5 — Window Functions

Window functions compute across rows without collapsing them: rankings, running totals, moving averages. This module covers ROW_NUMBER, RANK, LAG/LEAD, and frame clauses — the most powerful analytical tool in modern SQL. Labs build reports that GROUP BY alone cannot express.

Objectives

  • Compute rankings, running totals, and moving aggregates without collapsing rows
  • Choose correctly between ROW_NUMBER, RANK, and DENSE_RANK
  • Use LAG/LEAD and frames for period-over-period analysis
  • Solve top-N-per-group problems with window functions

Key concepts

OVER() clause: computing across rows without collapsing them

The OVER clause defines the window — the set of rows a function sees — and the revolutionary property is that rows survive: unlike GROUP BY, the result keeps every input row with the computed value attached. SUM(amount) OVER () totals without collapsing; add PARTITION BY and it totals per group. The lab's running-total query shows the shape. Windows answer questions about rows in context; aggregates answer questions about groups.

PARTITION BY: independent calculations per group

PARTITION BY divides the rows into independent groups — per department, per year — and the window function restarts in each. The lab ranks salaries partitioned by department; removing PARTITION BY ranks across the whole table, which the checkpoint asks you to predict. Think of it as GROUP BY that does not collapse: grouping for calculation, not for output. Every per-group analytic starts here.

ORDER BY inside OVER and frame boundaries

ORDER BY inside OVER orders rows within each partition, and the frame clause (ROWS BETWEEN ... AND ...) selects which of those ordered rows the function sees — the running total versus the moving average differ only in frame. The lab changes the frame from unbounded to 2 PRECEDING and watches the total become a 3-month moving average. Default frames vary subtly by function, so specify the frame when it matters. Frames turn ordering into arithmetic.

Ranking: ROW_NUMBER, RANK, DENSE_RANK

The three rankings differ on ties: ROW_NUMBER assigns unique sequential numbers (ties broken arbitrarily), RANK gives tied rows the same rank and skips the next numbers, DENSE_RANK gives tied rows the same rank without skipping. The lab inserts tied salaries and compares all three side by side. Top-N-per-group queries filter on ROW_NUMBER in an outer query — the standard pattern the lab demonstrates. Choose the function whose tie behavior matches the business rule.

Running totals and moving averages with ROWS frames

A running total is SUM(x) OVER (ORDER BY d) — cumulative from the partition start to the current row. A moving average narrows the frame: ROWS BETWEEN 2 PRECEDING AND CURRENT ROW averages the current and two prior rows. The lab builds both on monthly sales. Frames make time-series math declarative: describe the window, and the engine does the arithmetic. This is the reporting workhorse of window functions.

LAG/LEAD: reaching into neighboring rows

LAG reaches backward and LEAD forward — previous or next row's value within the partition — which makes period-over-period math trivial: amount minus LAG(amount) is month-over-month change. The lab handles the first row's NULL with COALESCE. FIRST_VALUE and LAST_VALUE extend the idea to partition edges. Before window functions, this required self-joins; now it is one expression.

Insert two employees with identical salaries and compare the three columns on the tie.
  2. Lab 5.2 — Running totals: monthly sales table; SELECT month, amount, SUM(amount) OVER (ORDER BY month) AS running FROM sales.   3. Lab 5.3 — LAG/LEAD deltas: SELECT month, amount, amount - LAG(amount) OVER (ORDER BY month) AS mom_change FROM sales. Handle the first row's NULL with COALESCE(..., 0). Note FIRST_VALUE/LAST_VALUE exist too — try FIRST_VALUE(amount) OVER (PARTITION BY year ORDER BY month).

Self-check

  1. State the difference between ROW_NUMBER, RANK, and DENSE_RANK on tied values.
    Answer key
    ROW_NUMBER never ties: 1, 2, 3, 4 even on equal values (order among ties is arbitrary but distinct). RANK ties share a rank and the next rank skips: 1, 2, 2, 4. DENSE_RANK ties share a rank and the next rank does not skip: 1, 2, 2, 3. Pick by the reporting rule: competition ranking → RANK; continuous numbering → DENSE_RANK; unique row ids → ROW_NUMBER.
  2. Explain what happens to a window function's result when the PARTITION BY is removed.
    Answer key
    Without PARTITION BY there is exactly one partition: the entire result set. ROW_NUMBER() OVER (ORDER BY salary DESC) numbers every row in the table; SUM(x) OVER () is the grand total on every row. The window did not disappear — it expanded to everything.
  3. Predict the output of SUM(x) OVER (ORDER BY d ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING) on five rows.
    Answer key
    Five rows, values say 10, 20, 30, 40, 50 with SUM(x) OVER (ORDER BY d ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING): row 1 sees rows 1–2 (30), row 2 sees 1–3 (60), row 3 sees 2–4 (90), row 4 sees 3–5 (120), row 5 sees 4–5 (90). Edge rows get smaller frames — the frame slides, it does not pad. This is the moving-average pattern.
  4. Name two reporting questions that are painful without window functions but trivial with them.
    Answer key
    Two classics: (1) 'top-N per group' (highest-paid employee per department) — trivial with ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC), painful with self-joins or correlated subqueries; (2) 'period-over-period change' — LAG(revenue) OVER (ORDER BY month) puts last month on every row, making the delta a subtraction instead of a join.

Module 6 — Set Operations

UNION, INTERSECT, and EXCEPT combine result sets the way joins combine tables. This module covers set semantics, the duplicate-handling rules, and the practical patterns — change detection, reconciliation — where set operations shine.

Objectives

  • Combine result sets with UNION/UNION ALL and explain the cost difference
  • Answer membership questions with INTERSECT and EXCEPT
  • Enforce column alignment with explicit CASTs for portability
  • Translate EXCEPT to Oracle's MINUS

Key concepts

UNION vs UNION ALL: deduplicated vs raw appends

UNION concatenates result sets and removes duplicates; UNION ALL concatenates without the dedupe pass — cheaper, because dedupe requires sorting or hashing. The lab counts rows both ways on regional sales tables and the duplicate rows' disappearance is the lesson. Default to UNION ALL unless you need dedupe: paying for sorting you did not ask for is the common waste. When the inputs cannot contain duplicates, ALL is pure win.

Column alignment rules across set-operation branches

Every branch of a UNION, INTERSECT, or EXCEPT must return the same number of columns with compatible types, matched positionally — the first column of each branch aligns. The lab hits SQLite's lenient coercion versus SQL Server's strictness and fixes it with explicit CASTs. Name columns in the first branch; later branches' names are ignored. Alignment is positional, not nominal — count carefully.

INTERSECT: rows present in both sets

INTERSECT returns only rows appearing in both queries — customers who ordered in both Q1 and Q2. The lab rewrites it as an inner join of DISTINCT subqueries and compares plans, showing two routes to the same answer. INTERSECT reads as the question asked; the join reads as the mechanism. Duplicates are eliminated by definition — it is set semantics, not bag semantics.

EXCEPT: rows in the first set but not the second

EXCEPT returns rows present in the first query but absent from the second — Engineering employees not on Project X, in the lab. It answers membership negatively where INTERSECT answers positively. The checkpoint contrasts it with LEFT JOIN ... WHERE right IS NULL: equivalent results, but EXCEPT states the intent directly. For set-difference questions, reach for the operator before the join.

Set operations as an alternative to joins for membership questions

Membership questions — in both sets, in one but not the other — can be answered with set operators or with joins, and the operator usually states intent more directly. The lab demonstrates both forms for INTERSECT so you can compare. Prefer the form whose reading matches the question: future readers (including you) will thank you. Performance differences are engine-specific; clarity is universal.

Dialect note: Oracle calls EXCEPT 'MINUS'

The set-difference operator is spelled EXCEPT in Postgres, SQL Server, and SQLite, but MINUS in Oracle — same semantics, different keyword. The lab translates deliberately. Portable SQL avoids the operator or abstracts it; dialect-aware SQL just spells it right. Small differences like this are why the dialect notes run through the whole sequence.

Hands-on labs

  1. Lab 6.1 — UNION ALL drill: two regional sales tables with identical schemas; SELECT region, amount FROM sales_east UNION ALL SELECT region, amount FROM sales_west.   3. Lab 6.3 — INTERSECT: customers who ordered in both Q1 and Q2: SELECT customer FROM orders WHERE quarter='Q1' INTERSECT SELECT customer FROM orders WHERE quarter='Q2'. Rewrite with an INNER JOIN of two DISTINCT subqueries and compare plans with EXPLAIN QUERY PLAN.
  4. Lab 6.4 — EXCEPT and the Oracle name: employees in Engineering EXCEPT employees assigned to Project X. Dialect note: Oracle spells this operator MINUS; Postgres, SQL Server, and SQLite use EXCEPT.

Self-check

  1. State the column-count and type-compatibility rules that UNION enforces.
    Answer key
    UNION requires the same column count and compatible types positionally — names do not have to match (the first branch's names win). Violate either and the statement is rejected at parse/prepare time. This is set algebra: you cannot union a 3-column set with a 4-column set, any more than you can add vectors of different dimensions.
  2. Explain the practical difference between UNION and UNION ALL on a 10-million-row append.
    Answer key
    UNION dedupes, which means sorting (or hashing) all 10M rows — the sort is the cost, often dwarfing the reads. UNION ALL skips dedup entirely: it just concatenates. If you know the inputs are disjoint (or duplicates are acceptable), UNION ALL can be an order of magnitude faster. Default to UNION ALL; pay for dedup only when you need it.
  3. Show how INTERSECT answers 'customers who bought in BOTH January and February'.
    Answer key

    Answer key
    A LEFT JOIN ... WHERE right.id IS NULL finds the same rows, but the EXCEPT version declares intent: 'rows in A not in B' as set difference. Module 7 — Transactions and Isolation

ACID is the promise databases make. This module covers transactions, the isolation levels, and what actually happens when two sessions touch the same row. You will run concurrent sessions against SQLite and observe locking and serialization firsthand.

Objectives

  • Wrap multi-statement changes in atomic transactions with savepoints
  • Demonstrate and fix a lost update with proper locking
  • Explain the four isolation levels and the anomalies each prevents
  • Contrast SQLite's locking model with SQL Server/Postgres isolation settings

Key concepts

ACID: atomicity, consistency, isolation, durability

ACID is the transaction contract: atomicity (all or nothing), consistency (valid state to valid state), isolation (concurrent transactions do not see each other's partial work), durability (committed means surviving crashes). The lab's atomic transfer — debit one account, credit another, verify the total — is atomicity made tangible. Every checkpoint scenario in the module maps to one letter. ACID is why databases exist instead of files.

BEGIN / COMMIT / ROLLBACK and savepoints

BEGIN opens a transaction, COMMIT makes its changes permanent, ROLLBACK discards them — the three verbs of atomic work. Savepoints mark positions inside a transaction so ROLLBACK TO can undo part without abandoning all: the lab rolls back to a savepoint and shows only the pre-savepoint change surviving. T-SQL spells the savepoint SAVE TRANSACTION; the semantics match. Transactions are the unit of correctness: group statements that must succeed or fail together.

SQLite locking: DEFERRED, IMMEDIATE, EXCLUSIVE

SQLite transactions begin in DEFERRED mode (locks acquired lazily, upgraded as needed), IMMEDIATE (reserved write lock at BEGIN — other writers wait), or EXCLUSIVE (no other access at all). The lab's lost-update fix uses BEGIN IMMEDIATE deliberately. Coarse locking is SQLite's simplicity trade: one writer at a time, but SERIALIZABLE behavior by default. Choose the mode that matches the transaction's intent; the default defers the decision until contention decides it.

The four standard isolation levels: READ UNCOMMITTED → SERIALIZABLE

The standard levels trade correctness for concurrency: READ UNCOMMITTED (sees everything, guarantees little), READ COMMITTED (no dirty reads), REPEATABLE READ (no non-repeatable reads), SERIALIZABLE (no phantoms — transactions behave as if sequential). Higher levels mean more locking and more waiting. SQL Server and Postgres default to READ COMMITTED; SQLite's locking gives SERIALIZABLE-like behavior without the setting. The lab contrasts the defaults so the difference is explicit rather than assumed.

Dirty reads, non-repeatable reads, phantom reads

The three classic anomalies: a dirty read sees uncommitted data (permitted only at READ UNCOMMITTED), a non-repeatable read sees a row change between two reads in one transaction, a phantom read sees new rows appear in a repeated range query. Isolation levels are defined by which anomalies they forbid. The lab's vocabulary exercise makes the distinctions writable from memory. Name the anomaly before choosing the level.

Lost updates and why read-modify-write needs a transaction

Read-modify-write without protection loses updates: two sessions read 5, both add 1, both write 6 — one increment vanishes. The lab demonstrates it with a counter, then fixes it with BEGIN IMMEDIATE so the second session waits. The pattern is everywhere (balances, inventory, counters) and the fix is always the same: make the read and the write one atomic unit. Concurrency bugs are logic bugs that only appear under load.

Self-check

  1. List the four ACID properties and give a one-sentence failure scenario each prevents.
    Answer key
    Atomicity — all-or-nothing (a transfer debits and credits, never one alone); Consistency — transactions move the DB between valid states (constraints hold after commit); Isolation — concurrent transactions do not see each other's partial work; Durability — committed means surviving a crash (write-ahead log). Each property answers one failure: partial writes, broken invariants, dirty reads, lost commits.
  2. Explain the difference between BEGIN DEFERRED and BEGIN IMMEDIATE in SQLite locking terms.
    Answer key
    BEGIN DEFERRED takes no locks up front — locks are acquired lazily as statements need them, so two connections can both begin and read. BEGIN IMMEDIATE takes a reserved write lock immediately, so a second writer's BEGIN IMMEDIATE fails fast instead of deadlocking mid-transaction. Use IMMEDIATE when you know you will write; it converts a mid-transaction deadlock into an instant, retryable error.
  3. Describe a dirty read in plain language and name the isolation level that permits it.
    Answer key
    A dirty read is seeing uncommitted data: transaction A updates a row but has not committed; transaction B reads the new value; then A rolls back — B acted on data that never officially existed. Permitted only by READ UNCOMMITTED, the lowest isolation level. Every higher level forbids it; that is the first rung of the ladder.
  4. State what happens to an uncommitted transaction when the sqlite3 CLI exits.
    Answer key
    An uncommitted transaction is rolled back — the sqlite3 CLI rolls back any open transaction on exit (there is no implicit commit). This is the safe default: half-finished work must not survive. If you want the work, COMMIT explicitly before quitting; the CLI will not guess for you.

Module 8 — Indexes, Query Plans, and Normalization

The final module covers the two topics that make databases scale: indexes (what they are, when they help, when they hurt) and normalization (1NF through 3NF and when to denormalize). You will read query plans, add indexes, measure, and design a normalized schema from scratch.

Objectives

  • Create and evaluate indexes with EXPLAIN QUERY PLAN
  • Apply the composite-index leftmost-prefix rule
  • Quantify the write cost of over-indexing
  • Normalize to 3NF and justify deliberate denormalization

Key concepts

B-tree indexes: ordered lookups, range scans, sorting

A B-tree index keeps keys in sorted order, which serves three query shapes: point lookups (find this key), range scans (keys between A and B), and ordered output (no separate sort). The lab creates an index on customer and watches the plan change from SCAN to SEARCH — the visible payoff. Indexes are sorted copies of key columns plus row pointers; every query shape they serve is a consequence of sortedness.

When indexes help: selective WHERE, JOIN keys, ORDER BY

Indexes pay off on selective WHERE clauses (few rows out of many), join keys (the engine looks up matches repeatedly), and ORDER BY (sorted output without sorting). The lab's 100,000-row timing makes the speedup concrete. Selectivity is the key word: an index on a yes/no column helps nobody. Index the predicates and joins your workload actually runs, not the columns that look indexable.

When indexes hurt: write amplification and storage

Every index is a second structure to maintain: each INSERT, UPDATE, and DELETE does extra work per index, and each index consumes storage. The lab times 10,000 inserts with five indexes versus none and records the slowdown percentage — write amplification made measurable. On write-heavy tables, each index must earn its keep in read performance. Indexing everything is worse than indexing nothing when the workload writes more than it reads.

Reading EXPLAIN QUERY PLAN: SCAN vs SEARCH, covering indexes

EXPLAIN QUERY PLAN reveals the access path: SCAN means the engine read the whole table, SEARCH means it used an index to find rows. A covering index goes further — the plan touches only the index, never the table. The lab points at the SEARCH line naming its index. Read the plan before tuning and after; the plan is the ground truth of what the engine did, and the checkpoint asks you to identify SCAN versus SEARCH on sight.

Composite indexes and leftmost-prefix rule

A composite index on (region, amount) serves queries filtering on region, or on region and amount — but not on amount alone. The leftmost-prefix rule: the engine uses the index from the left until the WHERE clause stops matching. The lab tries both column orders against a real query and explains which prefix the WHERE clause can use. Order composite columns by how queries filter: equality columns first, then ranges, then sorting.

Normalization forms 1NF–3NF vs deliberate denormalization trade-offs

Normalization removes redundancy: 1NF demands atomic values, 2NF removes partial dependencies on part of a key, 3NF removes transitive dependencies (the address depends on the customer, not on the sale). The lab normalizes a flat sales table, then deliberately denormalizes a total_spent column maintained by a trigger — and argues in writing when each shape wins. Normalize for integrity; denormalize for measured performance, with the maintenance cost acknowledged. 3NF is the default; denormalization is the documented exception.

Self-check

  1. State the two questions an index answers faster, and the two costs every index charges.
    Answer key
    An index answers two questions faster: finding rows by key (WHERE, joins) and ordering rows (ORDER BY without a sort). It charges two costs on every write: the index itself must be maintained (write amplification — each INSERT writes the table and each index), and it consumes disk space. Read the workload before indexing: indexes are a bet that reads outnumber writes.
  2. Read an EXPLAIN QUERY PLAN line and identify SCAN vs SEARCH and which index was used.
    Answer key
    In EXPLAIN QUERY PLAN, SCAN orders means a full table scan — every row visited, O(n). SEARCH orders USING INDEX idx_orders_customer (customer_id=?) means an index seek — O(log n) to the matching entries. The parenthesized predicate shows the seek key. If you expected a SEARCH and see a SCAN, the index is missing, unusable (function on the column, type mismatch), or the planner judged the table too small to bother.
  3. Explain why indexing every column is worse than indexing none on a write-heavy table.
    Answer key
    Every index is a second data structure to maintain: on a write-heavy table, each INSERT/UPDATE/DELETE pays per index, and the write path — your bottleneck — gets slower with each one you add. Indexing every column can make writes several times slower while helping no query (most indexes never get used). Measure: index the predicates your slow queries actually use, drop the rest.
  4. Give a real example of a query that got slower after denormalization, or explain why that can happen.
    Answer key
    Denormalization pre-joins data for read speed, but it can slow queries when: the wider rows bloat the table so full scans read more pages; duplicated columns must be kept consistent (triggers or app logic add write cost); or the query's filter no longer matches any index because the predicate moved to a denormalized column. Denormalization is a trade, not a win — it buys specific reads at the price of writes, space, and consistency risk.
