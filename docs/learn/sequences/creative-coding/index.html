Creative Coding: Generative Art with JavaScript and CSS

Drawing machines: how code becomes a visual medium — the canvas as paint, motion as material, simple rules blooming into lifelike behavior, and shipping work that respects the viewer.

Start the sequence All sequences

SCIENTIA OMNIA VINCIT

The sequence

What you will learn, and how.

Generative art is art made with autonomous systems: you write the rules, and the rules make the piece. A 14-second clip of spider-like "web crawlers" skittering across a screen — built by a systems artist in plain JavaScript and CSS — can stop millions of thumbs mid-scroll, because the motion reads as alive. That aliveness is not magic; it is technique. This sequence teaches the technique class behind it, from first principles: drawing to the canvas, driving motion with time, growing complexity from tiny rules, composing for the screen, and shipping pieces that run well and treat viewers kindly.

An explicit boundary: the crawler artwork referenced above is someone else's work, and this sequence does not reproduce it. It teaches the underlying craft — noise-driven motion, agent rules, connection-drawing — in original words, so you can build your own creatures, not imitate theirs. This is also not security content; "crawler" here is an animated creature, not a scraping tool, and nothing here touches web scraping, automation, or tooling of any kind.

Your tools are open and free: the browser's Canvas 2D API, CSS animations, p5.js and three.js for higher-level drawing, and the open tutorial literature of the generative-art community. This page is the study guide; the linked references are the manuals.

Who this sequence is for

  • Developers who want to make art with code — and artists who want to add code to their practice.
  • Web engineers who already know JavaScript and CSS and want a second use for those skills.
  • Portfolio-builders: this sequence ends with a real, shippable animation piece of your own.

Prerequisites

  • Basic JavaScript (functions, objects, loops, arrays) and basic CSS (selectors, transforms, keyframes).
  • A browser and a text editor. No build tools, no accounts, no budget — everything here runs from a single HTML file.
  • Patience with iteration: generative art is a conversation with randomness, and the first runs are always ugly.

How to use it

  • Work the modules in order — canvas drawing, then motion, then emergence, then composition, then shipping. Each is the vocabulary of the next.
  • Every module ends with labs. Do them in a single local HTML file and watch your sketch evolve across the sequence.
  • Keep one running sketchbook file and save a version after each module — your own gallery of experiments is the real curriculum artifact.
  • When a guide concept appears in a reference below, read it there: MDN and the community tutorials are the authority on exact API semantics.

The curriculum

5 modules plus a build lab, in order.

Module 1

The Canvas as a Medium: 2D Immediate-Mode Drawing

Learning objectives

  • Set up a canvas, get its 2D context, and draw basic shapes from code
  • Explain immediate-mode drawing: pixels, not objects, and what that costs and buys you
  • Work with paths, strokes, fills, transforms, and the drawing state stack
  • Compare raw Canvas 2D with p5.js's artist-oriented wrapper

Key concepts, explained

The canvas is a bitmap you paint on, not a document you describe

The <canvas> element is a grid of pixels; once you draw a line, the canvas remembers only colored pixels, not "a line object." There is nothing to move or restyle later — to change the picture you repaint it. This is called immediate-mode drawing, and it is the fundamental contract of the whole sequence: every frame, you redraw everything. The MDN Canvas API reference is the exact map of what you can paint.

This sounds wasteful, but it is liberating. Because there are no objects, there is no object model to fight; anything you can compute as pixels, you can draw. The cost is that animation, hit-testing, and persistence are all your job — which is exactly what modules 2 and 3 teach.

The 2D context: your brush, pen, and ruler

All drawing goes through the 2D rendering context, obtained once from the canvas element. It holds paths (the shapes you define with moveTo/lineTo/curves), strokes and fills (how paths become visible), transforms (translate, rotate, scale — moving the coordinate system rather than the drawing), and the state stack you push and pop so nested transformations do not leak. Generative art lives mostly in paths and transforms: a hundred lines drawn in a rotated coordinate system is one loop and one rotate() call.

Learn the state stack early. Every interesting sketch is a tree of transformed drawings, and push/pop discipline is what keeps that tree sane. p5.js makes the same idea friendlier with its own push/pop, translate, and rotate — same mental model, gentler syntax.

p5.js: the artist's friendly dialect of the same canvas

p5.js is a free, open-source JavaScript library built for artists, designers, and beginners, descended from the Processing tradition. It wraps the canvas in an artist's vocabulary — ellipse(), stroke(), noise() — and gives you a sketch lifecycle of setup() (runs once) and draw() (runs every frame). The official p5.js reference documents every function; the library is the fastest on-ramp in this sequence.

Nothing in p5.js is capability you lack in raw canvas — it is ergonomics and community. Many artists prototype in p5.js, then port to raw canvas or WebGL when they need the last drop of performance. Knowing both, and when to switch, is a professional skill.

Resolution, pixel density, and why your lines look blurry

A canvas element has two sizes: its CSS display size and its internal pixel grid. On high-density displays the internal grid must be scaled up or drawings blur. This is a two-line fix once you know it exists, but it is the single most common visual bug in first sketches. Fix it before you judge any aesthetic.

Related: the canvas does not scale its pixels when zoomed, and its contents are invisible to accessibility tools — MDN notes both explicitly. Generative pieces are art, so provide a textual description alongside them for screen-reader users.

Hands-on labs

  1. Draw a static composition: one hundred lines radiating from a circle's edge, in a rotated coordinate system
    Set up a canvas and a 2D context, then draw the composition using translate and rotate inside a loop rather than computing coordinates by hand. The transform should do the geometry for you.
  2. Rebuild the same composition in p5.js using setup() and draw()
    Load the p5.js library in a second file and express the same piece with its vocabulary. Compare the two programs line by line and note what p5.js removed.
  3. Fix the blur: handle device pixel ratio and compare before/after screenshots
    Scale the canvas backing store by the display's pixel ratio, keep the CSS size fixed, and screenshot both versions at 200% zoom. The difference is the lesson.
  4. Write a one-paragraph alt-text description of your composition, then implement describe()-style text output
    Describe what a sighted viewer sees — structure, motion, palette — in plain words, and put it where assistive technology can reach it. This habit ships with every piece you make from now on.

Self-check

  • Why can you not "move" a shape on a canvas without redrawing it?
  • What goes wrong in a sketch that rotates and translates without push/pop discipline?
  • When would you reach for raw Canvas 2D instead of p5.js, and vice versa?

Module 2

Motion and Time: requestAnimationFrame, Easing, Noise

Learning objectives

  • Drive a draw loop with requestAnimationFrame and explain why it beats setInterval
  • Use elapsed-time deltas so motion runs at the same speed on any display
  • Apply easing curves and noise to turn linear motion into organic motion
  • Animate declaratively with CSS @keyframes alongside imperative canvas animation

Key concepts, explained

requestAnimationFrame: the heartbeat of web animation

The browser offers requestAnimationFrame() as the sanctioned way to animate: you register a callback, and the browser calls it before the next repaint, typically once per display refresh. MDN's reference is explicit about the two rules that matter — the callback is one-shot (you must re-request each frame to keep animating), and you must use the callback's timestamp to compute progress, because on a 120 Hz or 144 Hz display a per-frame step would run twice as fast as on 60 Hz.

It also pauses in background tabs, which is both a battery gift and a trap: if your simulation depends on wall-clock time across tab switches, elapsed-time accounting (next concept) is what keeps it coherent. Timers like setInterval cannot match this — they fire off the paint cycle and drift.

Delta time: decouple motion from frame rate

Time-driven animation computes delta = now - lastFrame and multiplies every speed by it, so a circle crosses the screen in the same seconds on any display. The alternative — fixed per-frame steps — is frame-rate-dependent motion, and it is the classic bug of first animation code: smooth on your laptop, frantic on a gaming monitor, sluggish when the tab throttles.

This is a small habit with outsized payoff: it makes your pieces behave identically everywhere, and it is the foundation for the fixed-timestep physics some artists add later for determinism. Learn delta time before you need it.

Easing and noise: the two ingredients of aliveness

Real motion is rarely linear. Easing curves — smoothstep, cubic, sine-based ease-in-out — remap a linear progress value (0 to 1) into a motion that accelerates and decelerates, which is why a CSS ease-in-out feels natural while linear feels robotic. Noise — smooth pseudo-random fields such as the Perlin-style noise that p5.js exposes as noise() — gives motion that wanders without repeating: not random jitter, but continuous, unpredictable drift, the way a dust mote or an insect path actually moves.

The classic combination: a creature's heading is steered by a noise field sampled at its position, while individual limb twitches follow an eased oscillation. Linearity plus noise reads as organic to human perception; that sentence is worth more than most tutorials. The Nature of Code, a Creative Commons book on exactly these forces-and-noise techniques, is the deep reference.

CSS animation: the declarative half of the craft

Not all motion needs JavaScript. CSS @keyframes plus the animation shorthand describe declarative animation: the browser owns the timeline, composites it on the GPU, and often beats hand-rolled JS on efficiency for simple transforms. MDN's "Using CSS animations" guide is the canonical walkthrough of timing, iteration, direction, and fill modes.

The viral crawler piece was tagged #js #css, and this duality is part of the craft: JavaScript for simulation logic (where bodies go), CSS for presentation flourishes (how limbs twitch, how layers parallax). A common architecture in this genre is canvas-simulated agents rendered as DOM elements animated by CSS — or the reverse. Learn to reach for each layer for what it does best.

Hands-on labs

  1. Convert a setInterval-driven sketch to requestAnimationFrame with timestamp deltas
    Take any frame-stepped animation, rewire it to the callback's timestamp, and test it on two different refresh-rate displays (or emulate by capping the frame rate). The motion should be identical.
  2. Build an easing visualizer: one dot per easing curve, racing across the screen
    Animate a row of dots with linear, ease-in, ease-out, and ease-in-out mappings of the same progress value. Watching the race teaches what the math feels like.
  3. Steer a wanderer with noise instead of random(): a dot that drifts organically for 60 seconds
    Sample a noise field for the heading each frame and compare the trail to a purely random walk. The random one jitters; the noise one wanders. Keep the sketch.
  4. Recreate the wanderer's trail with pure CSS: a div that traces a path via @keyframes
    Hand-author keyframes approximating an organic path (or generate them with JS once and paste the result). Note where CSS stops being expressive — that boundary is the next module's starting line.

Self-check

  • What breaks if you re-request the animation callback unconditionally but never use the timestamp?
  • Why does noise-driven motion read as organic where random() reads as jittery?
  • Name one job best left to CSS animation and one that demands canvas + JS.

Module 3

Emergence: Simple Rules, Complex Behavior

Learning objectives

  • Explain emergence: why tiny local rules produce global lifelike structure
  • Build a small agent system: bodies, steering, and local interaction rules
  • Implement connection-drawing: proximity-triggered lines with distance-based alpha
  • Design readable creature motion from layered simple mechanisms

Key concepts, explained

Emergence is the whole genre: nobody animates the spider

The most arresting generative pieces are never keyframed. Instead, each "creature" follows a handful of local rules — keep moving, steer a little toward neighbors, avoid the edges — and the audience perceives intention, flocking, even personality. Nobody choreographed the spider; the spider is what the rules look like when they run. This is emergence: global structure nobody explicitly programmed, arising from local interactions repeated thousands of times.

The design skill is rule selection, not animation craft. You tune three numbers — separation radius, steering strength, noise scale — and watch the system's character change. The Nature of Code teaches this family of systems (autonomous agents, flocking, forces) as its core subject; read its agent chapters as this module's companion.

A crawler, decomposed: bodies, legs, webs — our own exposition

Consider the anatomy of a spider-like crawler as a design exercise, built from scratch in our own terms. The body is a point with position and velocity, steered by a noise field so it wanders organically. The legs are line segments: each leg has a fixed anchor angle around the body and a foot target that alternates between "planted" and "stepping" — when the body has moved far enough from a planted foot, the foot lifts and arcs to a new forward position. Drawn as two segments with a knee joint, they read as legs. The web is a connection rule: whenever two bodies come within a threshold distance, draw a line between them with opacity falling off as distance grows, and let those lines fade over frames. No spider was modeled; only points, segments, and proximity rules.

Each layer is trivial alone; together they read as a creature spinning a web. That ratio — trivial parts, rich whole — is the signature of the technique class. Your build lab (below) walks this construction step by step.

Connection-drawing: the signature look of the genre

The visual language of node-and-line generative art — particles drifting, lines blooming between near neighbors — is one rule: for each pair of agents closer than R pixels, draw a line whose alpha is proportional to 1 - distance/R. Add a slow background fade (repaint with a translucent dark rect instead of clearing fully) and lines leave trails; the screen becomes a living web.

The naive version is O(n²) pair checks per frame, which is fine for a few dozen agents and educational at any scale. When you want hundreds, spatial hashing (bucketing agents into grid cells and checking only neighbors) is the standard fix — a data-structure upgrade, not a conceptual one.

Seeds, parameters, and the curator's eye

Generative systems are seeded random processes: the same seed replays the same piece, which turns exploration into a practice — you scrub parameters (noise scale, leg count, connection radius, fade rate) and seeds until something beautiful emerges, then freeze the winner. The artist's job migrates from drawing to curating: choosing which of a hundred generated moments deserves to exist.

Keep a parameter log next to your sketchbook. Six months later, "the good one" is useless without the seed and the six numbers that made it. Reproducibility is part of the craft.

Hands-on labs

  1. Build five wandering agents with noise steering and edge wrapping
    Each agent is a position and velocity, steered by a noise field. No legs, no connections — just wander. This is the organism's nervous system; everything else attaches to it.
  2. Add the connection rule: lines between agents within R pixels, alpha by proximity
    Implement the O(n²) pair check, tune R until the web breathes — dense but not solid. Then add translucent background fades and watch trails appear.
  3. Give one agent legs: six anchored segments with plant-and-step foot logic
    Implement the foot alternation described above in your own code. It will look wrong for a while; tune the step threshold and arc height until it skitters.
  4. Run a parameter sweep: 20 seeds × 3 noise scales, and curate the best three
    Capture a still from each run, log seed + parameters, and pick three keepers. Write one sentence for each about why it works. That is the curation habit.

Self-check

  • Why does adding more agents sometimes make the web look worse, not richer?
  • What is the plant-and-step foot rule actually optimizing for, visually?
  • At what agent count does the O(n²) pair check start hurting, and what is the standard fix?

Module 4

Color and Composition for Screens

Learning objectives

  • Choose limited palettes and map data (speed, age, distance) to color
  • Compose generative frames: negative space, focal weight, motion balance
  • Use glow, additive blending, and background fades deliberately rather than by accident
  • Read a generated frame like a critic: what the eye does first, second, third

Key concepts, explained

Constraint is the palette: two or three colors beat fifty

Generative art's signature looks come from restraint. The web-crawler aesthetic — near-black ground, pale filaments, one accent — works because the eye has nowhere to hide; every line carries meaning. A disciplined palette (one background, one primary, one accent) makes randomness readable: when color varies, the viewer trusts it encodes something.

Map color to the simulation's state and the piece explains itself: line alpha by proximity, body color by speed, trail warmth by age. Color becomes a legend for the system's inner life rather than decoration.

Additive light, trails, and the glow that is not an accident

Many glowing generative looks come from two cheap techniques: drawing with low-alpha strokes so overlaps brighten additively, and never fully clearing the frame so each frame's faint residue becomes a motion trail. These are techniques, not filters — and they have failure modes. Unbounded additive drawing saturates to white mush; too-slow fades turn the canvas to mud. The fade rate is a compositional parameter: fast fades read as crisp and mechanical, slow fades as dreamy and biological.

Learn to set these numbers with intent. A screenshot series at five fade rates, compared side by side, teaches more than any paragraph about "mood."

Composition in a system that never sits still

A generative piece composes itself thousands of times a second, so you compose statistically: seed the initial agent positions for balance rather than uniformity, leave generous negative space at the edges (the frame's quiet zone), and give the motion a center of visual gravity — one slow, bright element the eye can rest on while the system churns around it.

Record short clips and scrub them. A piece that looks balanced at second 3 and chaotic at second 30 has a composition bug; constraining agent wander or adding a gentle centering force fixes whole classes of them. Composition is curation extended to time.

Shaders: the deep end of per-pixel craft

When the craft outgrows per-shape drawing, shaders take over: small programs that run per pixel (fragment shaders) and can produce flowing noise fields, ray-marched depth, and plasma-like fields at full frame rate on the GPU. The Book of Shaders, by Patricio Gonzalez Vivo and Jen Lowe, is the canonical gentle on-ramp — a step-by-step guide from "what is a shader" through shaping functions, noise, and cellular patterns. three.js's ShaderMaterial is the natural place to run what you learn there.

Shaders are optional for this sequence's build lab, but they are the horizon: the most virtuosic web-art pieces of the genre live in fragment shaders. Bookmark the book now; return when canvas starts feeling small.

Hands-on labs

  1. Restrict your lab-3 sketch to a three-color palette mapped to agent state
    Background, filament, accent — no more. Map one state variable (speed, age, or proximity count) to the accent and describe the mapping in a comment. The piece should read better, not duller.
  2. Shoot a fade-rate contact sheet: the same seed at five background-fade alphas
    Capture stills, line them up, and pick the fade that matches the mood you want. Write down why — this is your compositional vocabulary forming.
  3. Rebalance a chaotic run: add a gentle centering force and compare clips
    Take a run that wanders into the corners and dies, add the weakest centering force that keeps agents in frame, and compare 30-second clips. Notice how little force it takes.
  4. Complete one Book of Shaders chapter (shaping functions) and port one pattern to your sketch
    Work through the chapter in the book's own editor, then reproduce one shaping function as a canvas-drawn element. Feel the jump from shapes to fields.

Self-check

  • Why does mapping color to simulation state make randomness readable?
  • What is the visible difference between a fast-fade and a slow-fade piece, and when would you want each?
  • What can a fragment shader do per pixel that canvas path drawing cannot do practically?

Module 5

Shipping It: Performance Budgets and Respecting the Viewer

Learning objectives

  • Measure frame time and set a performance budget your piece must hold
  • Apply the standard optimizations: batching, offscreen caching, particle caps
  • Honor prefers-reduced-motion: still or gentle alternatives for motion-sensitive viewers
  • Publish the piece with credits, description, and a licensing choice

Key concepts, explained

The performance budget: know your frame cost

A piece that runs at 20 frames per second is not art, it is a slideshow of intentions. Measure: wrap your draw loop with a frame-time average and watch it as agent counts grow. The standard budget is to hold 60 fps on a mid-range laptop with headroom — and the standard levers are particle caps (hard limits on agent and line counts), batching (fewer state changes, fewer beginPath calls), and offscreen caching (pre-render static layers to a second canvas and composite).

Profile before optimizing. Most canvas sketches are dominated by one or two surprises — an accidental per-frame gradient creation, a shadowBlur left on — and the frame-time readout finds them in minutes. three.js's documentation covers the WebGL-side equivalents when your work graduates to the GPU.

Reduced motion is not optional polish

Motion can cause real harm: vestibular disorders make scaling, spinning, and full-screen movement physically nauseating for some viewers. The platform's answer is the prefers-reduced-motion media query, which detects the viewer's system-level setting — MDN documents it thoroughly, including the settings location on every major OS. The professional practice: query it before starting your animation, and when it is set to reduce, offer a still frame, a gentle fade, or a paused first frame with a play control — never the full-motion piece by default.

This is also where the CSS/JS duality pays off: the same media query can swap an aggressive @keyframes animation for a muted one in pure CSS. Build the reduced-motion variant as part of the piece, not as an afterthought — accessibility is a design constraint that improves the work.

Pause when hidden, degrade gracefully, credit openly

requestAnimationFrame already pauses in background tabs; add a visibility-change handler so your simulation state stays coherent when the tab returns. For older or weaker devices, consider a quality ladder — fewer agents, no trails — rather than one fixed configuration. And publish like an artist: title, one-line description, the tools used, and a license choice for the code. The generative-art community runs on shared technique; Generative Artistry's tutorial library is a model of that open teaching culture.

None of this is glamorous, and all of it is what separates a demo from a work. The viral pieces you admire all shipped these details — or wish they had.

Hands-on labs

  1. Instrument your sketch: live frame-time readout and an agent-count stress test
    Add a rolling average frame-time display, then raise the agent count until the frame rate breaks. Record the breaking point — that number is your piece's documented capacity.
  2. Implement the reduced-motion branch: still frame + play control when reduce is set
    Query the media setting on load, render one composed still frame for reduced-motion viewers, and provide an explicit opt-in control to start motion. Test it by toggling the OS setting.
  3. Add a quality ladder: two agent budgets chosen by a quick device heuristic
    Ship a full and a lite configuration, chosen at load. Verify the lite version holds the frame budget on the weakest machine you can borrow.
  4. Publish the piece: single HTML file, title, description, tools, license, and credits
    Put it online (any static host), write the one-paragraph artist statement, and link it from your portfolio. This is the sequence's graduation deliverable.

Self-check

  • What is the first thing you check when a sketch drops frames, and why measure before optimizing?
  • What should a reduced-motion viewer get instead of the animated piece, and why is opt-in the right default?
  • What belongs in a published piece's credits besides your name?

The build lab

Build a crawler study, from first principles.

This is the capstone: a crawler-like animation built from the techniques in this sequence, described in your own words and implemented in your own code. It is a study — an exercise in the technique class — not a reproduction of any artist's work. Each step builds on the last; resist the urge to skip ahead.

Step 1 — The wanderer

One agent on a dark canvas. Position, velocity, and a noise-sampled heading that updates every frame with delta-time scaling. Leave a faint trail by repainting the background at low alpha instead of clearing. You are done when a single dot moves like something small and alive, not like a screensaver.

Step 2 — The colony and the web

Grow to a dozen wanderers. Add the connection rule: agents within R pixels get a line whose alpha scales with closeness. Tune R until the web forms and dissolves as bodies cross — the screen should read as a net being woven and unwoven, which is the signature image of the genre.

Step 3 — Legs

Give each body jointed legs using the plant-and-step rule from Module 3: feet planted in world space, lifted and arced forward when the body outruns them, drawn as two-segment limbs. Start with four legs; tune the step threshold until the motion skitters instead of gliding. It will look wrong before it looks right — that gap is the actual work.

Step 4 — The CSS half

Pick one presentational flourish and implement it declaratively: a subtle leg-twitch via @keyframes on rendered elements, or a parallax glow layer drifting on a slow CSS loop behind the canvas. This is the #js #css duality in miniature — simulation in JavaScript, ornament in CSS — and it is how the pieces that inspired this sequence are architected.

Step 5 — Ship it like a professional

Apply Module 5 end to end: frame-time instrumentation, a reduced-motion still-frame branch, a pause on tab-hide, a three-color palette, and publication as a single HTML file with a title, description, and license. Then pick one parameter you never tuned — noise scale, fade rate, leg count — change it, and see what creature you get. That moment of surprise is the entire point of the genre.
