Ansible Configuration Management

Agentless automation from control node to fleet: inventory, playbooks, roles, vault, and the discipline of idempotent change.

Start the sequence All sequences

The sequence

What you will learn, and how.

Ansible is an automation platform for configuring systems, deploying software, and orchestrating complex tasks across a fleet of machines. Its defining design decision is that it is agentless: the machine you drive everything from, the control node, reaches each managed node over SSH (or WinRM for Windows) and runs ordinary commands there. There is nothing to install, patch, or license on the machines you manage, which means Ansible works on anything you can log into — including network devices, appliances, and legacy systems that will never run an agent.

This sequence walks the full path from first principles to production practice. You start with the agentless execution model and the control-node/managed-node relationship, then learn inventory — how Ansible knows which machines exist and how to address subsets of them. Playbooks follow: the YAML documents that declare what should be true on each group of hosts. From there you add variables and Jinja2 templating, package reusable logic into roles, internalize idempotence as the core contract of every task, protect secrets with ansible-vault, and finish with a troubleshooting discipline for when playbooks fail in production.

Everything here is keyed to the official Ansible documentation, which is the authoritative reference for exact syntax and behavior. This page teaches the concepts and the habits; the docs supply the canonical syntax.

Who this sequence is for

  • System administrators and SREs who need to manage fleets of Linux servers reproducibly.
  • DevOps engineers building configuration management into CI/CD pipelines.
  • Engineers who know basic SSH and YAML and want a vendor-neutral automation foundation before specializing in tools like Terraform or Puppet.

Prerequisites

  • Comfortable with the Linux command line and SSH key authentication.
  • Basic YAML literacy (indentation, mappings, lists).
  • Two disposable lab VMs or containers you can SSH into — nothing in this sequence should be run against production infrastructure while learning.

How to use it

  • Work the modules in order: each one assumes the vocabulary of the previous one.
  • Do every lab on a real lab host. Ansible is learned by watching runs succeed, fail, and converge — reading alone will not stick.
  • Answer every self-check in writing before moving on. If you cannot answer, re-read the concept — that is the point of the check.
  • Keep the official documentation open beside you; when this guide describes a behavior, verify the current syntax there.

Module 1

Agentless Architecture, Control Node, and SSH Transport

Learning objectives

  • Explain how Ansible operates without managed-node agents and why that shapes its trust model
  • Stand up a control node and establish key-based SSH to two target hosts
  • Configure privilege escalation (become) safely across mixed-privilege fleets

Key concepts, explained

Push-based, agentless execution over SSH (WinRM for Windows)

Ansible inverts the usual agent-based model: instead of every managed machine running a daemon that phones home, a single control node pushes work out to the fleet. For each task, Ansible opens an SSH connection to the target, transfers a small module payload, executes it, collects the result, and closes the connection.

Because nothing persistent runs on the managed node, there is no agent to upgrade, no agent certificate lifecycle, and no pull schedule to reason about. The cost is that every action depends on working SSH access — credential rotation, bastion hosts, and SSH tuning are operational concerns you inherit directly.

Windows hosts cannot be reached over SSH in the classic model, so Ansible uses WinRM (and increasingly SSH on modern Windows) for them; the agentless principle is the same, only the transport changes.

Control node vs managed node roles

The control node is the machine where Ansible is installed and where you run playbooks — typically a workstation, a CI runner, or a dedicated automation host. It holds the inventory, the playbooks, the vault passwords, and the credentials, so it is the crown jewel of your automation security posture.

Managed nodes are the targets: servers, network devices, cloud instances. They need no Ansible installation — just a reachable SSH port, a user account, and (for most modules) a Python interpreter so the module payloads can execute.

This asymmetry matters for network design: the control node needs outbound reachability to every managed node, while managed nodes need no inbound access beyond SSH. Firewall rules and bastion architecture follow from that one fact.

Python on the control node; minimal Python on managed nodes

Ansible itself is a Python application, so the control node needs Python 3 installed along with the ansible-core package. Managed nodes do not need Ansible, but most modules are small Python programs that get copied over and executed — so they need a Python interpreter too.

The interpreter on the managed side can be modest; Ansible will even auto-discover it. A handful of modules (notably the raw module) work without Python, which is exactly what you use to bootstrap Python onto a fresh host before anything else can run.

ansible.cfg scoping (global, user, project) and inventory defaults

Ansible reads its configuration from the first ansible.cfg it finds in a defined search order: an ANSIBLE_CONFIG environment variable wins, then a file named ansible.cfg in the current project directory, then ~/.ansible.cfg, then /etc/ansible/ansible.cfg.

This precedence is what makes project-local configuration work: each automation project can carry its own ansible.cfg pinning its inventory path, role locations, and defaults, without affecting other projects or the system. In practice, keep one ansible.cfg per project, versioned with the project, and treat the global file as a fallback.

become/become_user/become_method privilege escalation semantics

Ansible connects as an ordinary user and escalates only where needed, which mirrors good operational hygiene. The become directive on a play or task requests privilege escalation; become_user names the target identity (root by default); become_method selects the mechanism (sudo by default, with su, pbrun, and others available).

Escalation is explicit and auditable per task rather than a blanket "run everything as root." When become is requested but sudo is misconfigured on the target — wrong NOPASSWD entry, missing sudo package — the task fails with a permission error rather than silently running unprivileged, which is the safe failure mode.

SSH key authentication, ControlPersist, pipelining

Key-based SSH authentication is the foundation: the control node holds a private key whose public half is installed on every managed node, so automation never types passwords. Passphrase-protected keys are unlocked once via ssh-agent rather than embedded in files.

Two performance knobs matter at fleet scale. ControlPersist keeps SSH connections open and reuses them across tasks, eliminating per-task connection setup cost. Pipelining streams the module payload through the SSH channel instead of writing a temporary file on the target via sftp/scp, which is faster and avoids touching the filesystem — at the cost of requiring slightly different sudo configuration.

Connection plugins and local execution

Ansible abstracts the transport behind connection plugins: ssh is the default, but local runs tasks on the control node itself, and there are plugins for containers, network devices over API, and cloud CLIs. The same playbook can target heterogeneous infrastructure because the connection detail lives in inventory, not in the tasks.

Local execution deserves special attention: running Ansible against localhost turns it into a configuration tool for the control node itself, and delegate_to lets you run a single task on a different host (for example, updating a load balancer from the web-server play) while the rest of the play targets the fleet.

Hands-on labs

  1. Install ansible-core in a venv and run ansible --version from a project directory
    Installing into a virtual environment keeps Ansible isolated from system Python and lets different projects pin different versions. Running ansible --version from the project directory also confirms which ansible.cfg and inventory Ansible would pick up there.
  2. Generate an SSH keypair, distribute via ssh-copy-id to two lab VMs, and confirm passwordless access
    ssh-copy-id appends your public key to the target authorized_keys in one step. Confirm with a plain ssh command before involving Ansible — if raw SSH fails, Ansible will fail for the same reason and the error will be harder to read.
  3. Ping the fleet with an ad-hoc command and observe connection failures under a misconfigured key
    The ping module is the canonical connectivity test. Deliberately breaking the key first teaches you what an authentication failure looks like, so you recognize it instantly in production output.
  4. Write a project-local ansible.cfg and demonstrate config precedence against the global file
    Set a distinguishing option — like a different default inventory path — in the project file and show ansible picking it up. Then set ANSIBLE_CONFIG to a third file and watch the environment variable win; the precedence ladder is now something you have felt, not just read.
  5. Run a privileged ad-hoc task with become and contrast it against a run without become
    A package-install or file-write to a protected path makes the difference visible: without become it fails with permission denied, with become it succeeds. This is the mental model you will reuse for every playbook.

Self-check

  • Which side of the connection requires an installed agent, and why does that matter for network design?
  • Describe what happens when become is requested but sudo is misconfigured on the target
  • Given two conflicting ansible.cfg files, which wins and why?

Module 2

Inventory: Static Files, Groups, and Dynamic Sources

Learning objectives

  • Author a static INI/YAML inventory with groups, children, and variables
  • Query hosts by pattern and predict group membership
  • Describe how dynamic inventories source truth from external systems

Key concepts, explained

INI vs YAML inventory formats

Inventory is simply the list of machines Ansible manages, and it can be written in INI or YAML. INI is compact for small fleets — a group header in brackets followed by hostnames — while YAML expresses the same structure as nested mappings and scales better to complex groupings with variables attached.

Both formats describe the same underlying model: hosts organized into groups, groups containing other groups, and variables attached at any level. Choose one format per project and stay consistent; mixed-format projects confuse future readers.

Groups, group children, and the all group

Groups are the unit of targeting: you run plays against webservers, dbservers, or prod, not against individual hostnames. Groups can contain child groups, so prod can include web-prod and db-prod, letting you address the whole environment or one tier with a single name.

Every inventory has an implicit all group containing every host, and a special localhost. Well-designed group trees mirror your real topology — by role, by environment, by datacenter — because the group tree becomes the language you use to aim changes.

Host patterns: wildcards, ranges, unions, intersections

Host patterns are the query language for inventory: web* matches names by prefix, web[01:10] expands numeric ranges, and the set operators & (intersection), ! (exclusion), and , or : (union) combine groups. The pattern web:&prod:!db means "hosts in both web and prod, excluding db."

Patterns are evaluated fresh on every run, so they are the safe way to aim a change at exactly the right hosts. Always preview with ansible-inventory --graph or --list before running a destructive play against a pattern you composed by hand.

host_vars/ and group_vars/ directories

Variables can live in files beside the inventory: host_vars/<hostname>.yml for one machine, group_vars/<groupname>.yml for a whole group. This keeps the inventory file itself clean and gives each variable a single, discoverable home.

The resolution rule is specificity wins: a value in host_vars overrides the same variable in group_vars for that host, which is how you express "everyone gets the default, this one machine is special." Version these directories with the inventory so variable changes are reviewed like code.

Inventory precedence across multiple sources

Ansible accepts multiple inventory sources at once — a static file plus a dynamic script, for example — and merges them. When sources disagree about a host's variables, the last-loaded source wins, which is deterministic but easy to misread.

The discipline is to give each source a clear jurisdiction: static files for the long-lived topology, dynamic sources for cloud fleets that change hourly, and never two sources both claiming authority over the same variable.

Dynamic inventory plugin concept (cloud, virtualization, CMDB)

Static files rot when infrastructure is created and destroyed by APIs. Dynamic inventory plugins query the source of truth — a cloud provider, a virtualization platform, a CMDB — at the start of each run and build the group tree from live data, often grouping by tags or regions automatically.

The inventory becomes a view over the infrastructure rather than a separate record of it, which eliminates the "forgot to add the new server" failure class. The trade is that runs now depend on the API being reachable, so inventory caching and refresh behavior become part of your design.

Inventory caching and refresh behavior

Querying a cloud API on every playbook run is slow and risks rate limits, so Ansible can cache dynamic inventory results and refresh them on a schedule. Cached inventory is fast but potentially stale; uncached inventory is fresh but slow and API-dependent.

Choose deliberately: caching with a short TTL suits large fleets, while a forced refresh suits the playbook that provisions brand-new machines and must see them immediately.

Hands-on labs

  1. Build a static YAML inventory: web, db, and prod groups with group children
    Model a small realistic topology: web and db groups, each with prod and staging children, and a top-level prod group containing both prod children. This single exercise teaches the whole group-membership model.
  2. Target subsets with patterns (web:&prod, !db) using ansible-inventory --graph
    The --graph output renders the group tree and shows exactly which hosts each pattern selects. Practice predicting the set before you run the command; the intersection and exclusion operators are where mistakes happen.
  3. Place variables in host_vars/group_vars and verify resolution with ansible-inventory --host
    Set the same variable at group and host level with different values, then ask Ansible what one host sees. The --host view shows the merged result and makes precedence concrete.
  4. Combine two inventory files and observe merge precedence
    Pass two -i sources and watch how groups and variables merge. Then create a deliberate conflict and confirm which source wins, so the rule is earned rather than memorized.
  5. Configure a cloud inventory plugin against a free-tier account or mock, and list returned hosts
    Point the plugin at a real (free-tier) or mocked cloud account and list the hosts it discovers. Seeing groups form from cloud tags is the moment dynamic inventory clicks.

Self-check

  • Predict the host set for pattern 'web:&prod:!db' before running it
  • Where must a variable live so that one host overrides its group's value?
  • What goes wrong when two inventory sources disagree about a host's group membership?

Module 3

Playbooks: Plays, Tasks, Handlers, Conditionals, and Loops

Learning objectives

  • Write a multi-play playbook with distinct host targets
  • Trigger handlers on change and control execution with conditionals
  • Replace repetitive tasks with loops and structured iteration

Key concepts, explained

Plays, tasks, and modules as the execution unit

A playbook is a YAML list of plays; each play maps a set of tasks onto a set of hosts. A task names one module — the unit of work, like package, copy, or service — with its arguments, and Ansible executes tasks in order against every targeted host.

This structure is what makes playbooks readable as policy: the play says "on the webservers," the tasks say "ensure these things are true," and the modules are the verbs. Thinking in desired state rather than in shell commands is the single biggest mindset shift in this module.

Task ordering and play-level vs task-level scope

Tasks within a play run top to bottom, and each task completes on all hosts before the next begins (by default). Directives can be set at play level — applying to every task — or overridden per task, which is how you express "this whole play escalates, except this one diagnostic task."

Ordering matters because later tasks may depend on earlier ones having converged. When you need a strict sequence across hosts rather than per-task batching, that is what serial and strategy settings are for — but the default ordering covers the vast majority of cases.

Handlers: notify, change-triggered runs, flush_handlers

Handlers are tasks that run only when notified, and only if the notifying task actually reported a change. The classic pattern: a task writes a configuration file and notifies a "restart service" handler, so the service restarts only when its config really changed.

Notified handlers do not run immediately — they run once each at the end of the play, in the order they are defined, no matter how many tasks notified them. If you need the restart to happen mid-play before later tasks proceed, flush_handlers forces the queued handlers to run at that point.

when conditionals with facts, variables, and registered results

The when clause gates a task on a Jinja2 expression: it runs only when the expression is true. Conditions can test gathered facts (like the OS family), inventory variables, or the registered result of an earlier task, which is how playbooks adapt to heterogeneous fleets.

A when referencing an undefined variable fails the task, so conditions on possibly-absent variables should use the default filter or is defined tests. Defensive conditionals are a production habit, not paranoia.

loop keyword and loop_control (label, loop_var, pause)

The loop keyword replaces N near-identical tasks with one task iterated over a list — creating five users becomes one task looping over five names. Each iteration sees the current item as the item variable, and can use per-item dictionaries for structured data.

loop_control fine-tunes the loop: label controls what the output shows per iteration (vital for readable logs), loop_var renames item to avoid collisions in nested loops, and pause inserts a delay between iterations for rate-sensitive operations.

block/rescue/always for error handling structure

Blocks group tasks so error handling applies to the group: if any task in the block fails, the rescue section runs (rollback, cleanup, alerting), and the always section runs no matter what (restoring state, removing temp files). It is the playbook equivalent of try/catch/finally.

Use blocks to make failure behavior explicit and reviewable. A playbook that aborts halfway through a database migration is a liability; the same playbook with a rescue path is an engineering artifact.

tags and task selection at runtime

Tags label tasks so a run can select a subset: --tags deploys only the tagged tasks, --skip-tags excludes them. This is how you build a playbook that does everything but can be run surgically — "just the app deploy, not the OS hardening."

Tag discipline matters: tag by function (deploy, configure, restart) and document the supported tag sets, because untagged tasks run by default and a forgotten tag silently includes work you meant to skip.

Hands-on labs

  1. Write a playbook that installs a package, writes a config file, and notifies a restart handler
    This is the canonical playbook shape: package task, template/copy task with notify, handler that restarts the service. Build it once and you have the template for half of all configuration work.
  2. Run the playbook twice and confirm the handler fires only on the first run
    The second run should report zero changes and no handler execution. Watching idempotence and change-triggered handlers work together is the core Ansible experience.
  3. Gate tasks with when clauses on distribution and on a registered command result
    Write one task that runs only on Debian-family hosts and another that runs only if a registered command found a marker file. Conditionals on facts and on prior results cover nearly every real gating need.
  4. Convert three near-identical user-creation tasks into one looped task with per-item variables
    Start with the repetitive version, then collapse it into a single looped task with a list of dictionaries. The diff between the two versions teaches why loops exist.
  5. Structure a failing task with block/rescue so the playbook reports cleanly instead of aborting
    Make a task fail deliberately inside a block, handle it in rescue with a clear message, and use always for cleanup. The playbook should finish with a controlled, informative outcome.

Self-check

  • When does a notified handler actually run relative to the task that notified it?
  • Rewrite a three-task sequence as a loop without changing its observable effect
  • What is the failure mode of a when clause referencing an undefined variable, and how do you guard it?

Module 4

Variables, Facts, and Jinja2 Templating

Learning objectives

  • Navigate the variable precedence chain from defaults to extra vars
  • Gather and consume facts to drive OS-conditional logic
  • Author Jinja2 templates and test them before deployment

Key concepts, explained

Variable precedence chain (role defaults up through extra vars)

Ansible has over twenty levels of variable precedence, but the shape is simple: broad defaults lose to specific overrides, and explicit runtime input beats everything. Role defaults sit at the bottom as the documented "sane default"; inventory group_vars and host_vars sit in the middle; extra vars passed with -e sit at the absolute top and cannot be overridden.

The practical rule: define defaults where the role lives, tune per environment in group_vars, handle snowflakes in host_vars, and reserve -e extra vars for one-off operator overrides. If you cannot predict which value wins, your variable layout is too clever — simplify it.

Magic variables: hostvars, inventory_hostname, groups, group_names

Magic variables are populated by Ansible itself: inventory_hostname is the current host's name, groups is the whole group tree, group_names lists the groups the current host belongs to, and hostvars gives access to every host's variables — letting a webserver template reference the database hosts' addresses.

hostvars is the key to multi-tier configuration: a load balancer config rendered on the web tier can loop over groups['db'] and pull each database host's address from its hostvars. This is how one playbook configures cooperating tiers without hardcoding addresses.

Gathered facts (ansible_facts) and fact caching

At the start of each play, Ansible gathers facts about every host — OS distribution, network interfaces, memory, disks — into the ansible_facts dictionary. Facts are what let one playbook handle Ubuntu and RHEL correctly: the package task branches on ansible_facts['os_family'].

Fact gathering costs an SSH round trip per host, so large fleets cache facts (in Redis, JSON files, or a database) and refresh them on a schedule. Cached facts trade freshness for speed; disable gathering entirely (gather_facts: false) for plays that provably need no host data.

Registered task results and set_fact

Any task can register its result into a variable, capturing return code, stdout, and the changed flag for later tasks to test in when clauses. Registered variables are the playbook's short-term memory — the bridge between "do something" and "decide based on what happened."

set_fact creates a persistent fact for the host that lasts the rest of the play (or longer, with caching), computed from Jinja2 expressions. Use it to derive values once — like a computed port or a normalized hostname — rather than recomputing them in every template.

Jinja2 expressions, filters, and lookups in templates

Jinja2 is the templating language: {{ variable }} interpolates, {% if %} and {% for %} add logic, and filters transform values — {{ name | upper }}, {{ ports | join(",") }}, {{ config | default({}) }}. Filters are where most real template work happens: defaults for missing values, type conversions, list manipulation.

Lookups fetch data from outside the playbook at template time (a file, an environment variable, a password store). Keep template logic simple — templates that need complex control flow are a sign the logic belongs in a variable or a role default instead.

template module vs copy module with content

The template module renders a Jinja2 file through the engine and deploys the result, which is the right choice for any file containing variables or logic. The copy module transfers files verbatim; its content parameter can inline small static content without a source file.

Rule of thumb: if the file has even one variable in it, use template; if it is byte-identical everywhere, use copy. Mixing them up either leaks unrendered {{ }} braces into production configs or wastes a template render on a static file.

Variable typing pitfalls (strings vs booleans vs numbers)

YAML's loose typing is a classic trap: yes, on, and no are parsed as booleans in YAML 1.1, so a variable meant to hold the string "yes" can silently become True. Quote anything that must stay a string, and be explicit about types at role boundaries.

Jinja2 renders everything as strings inside templates, so a port number becomes "8080" unless filtered back with | int. Test templates with --check --diff and eyeball the rendered output before deploying — type surprises are cheapest to catch in preview.

Hands-on labs

  1. Set the same variable at five precedence levels and observe which value wins
    Define one variable in role defaults, group_vars, host_vars, the play, and -e extra vars, then print it with the debug module. The winning value demonstrates the precedence ladder more convincingly than any diagram.
  2. Run the setup module on one host and extract one fact to drive a when condition
    Call the setup module directly, find the OS family fact in its output, then write a task whose when clause keys off that exact fact path. This is the pattern behind every cross-distribution playbook.
  3. Write a Jinja2 template for a service config with conditionals and loops, rendered via the template module
    Build a realistic config — say, a web server vhost file — with an if block for TLS and a for loop over backend servers. Render it and diff the output against a hand-written reference.
  4. Break a template intentionally, read the Jinja2 error, and fix it
    Introduce an undefined variable and a syntax error separately, and read both error messages carefully. Jinja2 errors point at the template line; learning to read them now saves hours later.
  5. Pass -e extra_vars at runtime to override a template parameter and re-render
    Override one parameter from the command line and confirm the rendered file changes while the committed variables stay untouched. This is how operators tune a run without editing versioned files.

Self-check

  • Rank these from lowest to highest precedence: group_vars, extra vars, role defaults, host_vars
  • Given a host's facts, write the when expression that selects only Debian-family hosts
  • Why does a bare 'yes' in YAML break a boolean test, and what is the fix?

Module 5

Roles: Structure, Dependencies, and Galaxy

Learning objectives

  • Scaffold a role and explain the purpose of each directory
  • Compose playbooks from roles with variables and dependencies
  • Evaluate and pin third-party roles from Galaxy

Key concepts, explained

Role directory layout: tasks, handlers, defaults, vars, files, templates, meta

A role is a directory with a conventional layout that Ansible understands: tasks/main.yml holds the task list, handlers/main.yml the handlers, defaults/main.yml the overridable defaults, vars/main.yml the non-overridable variables, files/ the static payloads, templates/ the Jinja2 templates, and meta/main.yml the metadata.

The layout is the documentation: anyone who knows the convention can open an unfamiliar role and know exactly where to look. Roles turn playbooks from scripts into packages with a predictable internal geography.

defaults vs vars precedence within a role

defaults/main.yml is the lowest-precedence variable source in all of Ansible — deliberately so, because role defaults are meant to be overridden by the playbook author. vars/main.yml sits much higher and cannot be overridden by inventory, which makes it the place for values the role itself must control.

The design rule: put anything a user might reasonably change in defaults, with a comment explaining it; put internal constants the role depends on in vars. A role whose defaults are empty or undocumented is a role nobody can safely reuse.

meta/main.yml: dependencies, argument specs, platform support

meta/main.yml declares the role's relationships: dependencies lists other roles that must run first, and the argument spec validates the variables callers pass in — failing fast with a clear message instead of mid-run with a Jinja2 error.

It also declares supported platforms, so automation can refuse to run a Debian-only role on RHEL rather than failing obscurely. Metadata is what separates a folder of tasks from a distributable, trustworthy role.

requirements.yml for pinning collections and roles

requirements.yml pins every external dependency — Galaxy roles and collections with exact versions — so a playbook run today and a run in six months install the same code. Without pinning, a fresh install silently pulls the newest upstream release and your automation drifts.

Commit requirements.yml with the project and install from it in CI. Version pins are reviewed and bumped deliberately, exactly like a lockfile in application development.

Galaxy as a distribution registry; collection vs role granularity

Ansible Galaxy is the public registry where the community publishes reusable automation. The older unit is the role; the modern unit is the collection, which bundles roles, modules, plugins, and documentation under one namespace and version.

Prefer collections for new work — they carry their own modules and are versioned as a unit — and treat Galaxy content as third-party code: read it before you run it, pin it, and prefer well-maintained, widely-used projects.

Role inclusion order and dependency execution

Roles listed on a play run in order, and each role's dependencies run before the role itself, recursively. This gives a deterministic execution sequence you can reason about: dependencies first, then the role's own tasks.

Because dependencies always run first, deep dependency chains can surprise — a role you included for one task may drag in three others. Keep dependency trees shallow and prefer explicit role lists in the play over hidden transitive dependencies.

Idiomatic role naming and versioning

Role names are lowercase with underscores, namespaced by collection or author, and describe what the role manages — not who wrote it or which project first needed it. Versions follow semantic versioning so consumers can reason about upgrades.

Good naming is a reuse strategy: a role named webserver_tls is discoverable and self-describing; a role named johns_stuff is not. Name for the next team, not the current sprint.

Hands-on labs

  1. Scaffold a role with ansible-galaxy init and map each directory to its runtime function
    The scaffolding generates every conventional directory with placeholder files. Walk each one and state what Ansible loads from it and when — the layout becomes a mental map rather than a mystery.
  2. Refactor an earlier playbook into two roles (common, webserver) wired by a site playbook
    Split a working playbook along responsibility lines: common for baseline configuration, webserver for the application tier. The site playbook becomes a short, readable composition of roles.
  3. Declare a dependency in meta/main.yml and observe dependency execution order
    Make webserver depend on common and watch the run order: common's tasks execute before webserver's, even though the play lists only webserver. Dependencies are execution order made declarative.
  4. Pin a Galaxy role version in requirements.yml and install it into a local roles path
    Write the requirements file, install with ansible-galaxy, and confirm the exact pinned version landed in your roles path. Then bump the pin and reinstall to feel the upgrade path.
  5. Diff defaults/main.yml against vars/main.yml overrides to demonstrate precedence
    Set the same variable in both files plus an inventory override, and show which value wins at runtime. Watch role defaults lose to inventory, and role vars beat inventory — seeing the three tiers resolve once makes the precedence chain real.

Self-check

  • Which role directory's variables can a playbook override, and which cannot?
  • When do role dependencies execute relative to the role that declares them?
  • What breaks if requirements.yml pins a collection version your roles don't support?

Module 6

Idempotence: Check Mode, Diff, and Change Semantics

Learning objectives

  • Design tasks that converge to desired state without side effects on rerun
  • Use check mode and diff to preview changes before applying them
  • Interpret changed/failed/ok/unreachable task outcomes in run output

Key concepts, explained

Idempotence as the contract: describe state, not steps

Idempotence is the promise that running the same automation twice produces the same end state, with the second run reporting no changes. Every Ansible module is designed around this: you declare the desired state ("this package installed, this line present in this file"), and the module checks current state before acting.

This contract is what makes automation safe to re-run — after failures, on schedules, across fleets. A playbook that is not idempotent is a script with YAML syntax; a playbook that is idempotent is infrastructure as code.

Changed vs failed vs ok vs unreachable vs skipped outcomes

Every task ends in one of a small set of states: ok means the desired state already held; changed means the task altered something; failed means the task errored; unreachable means Ansible could not even reach the host; skipped means a when condition excluded it. The recap at the end of a run tallies these per host.

Reading the recap is a core skill: a run with zero changed is a converged fleet; changed on every run for the same task is a broken idempotence promise; unreachable points at SSH and network, not at your tasks. The outcome vocabulary tells you where to look.

check_mode (--check) and per-task check_mode overrides

Check mode (--check) is the dry run: Ansible runs through the playbook and reports what would change, without changing anything. It is the last review gate before a production run — the equivalent of reading the diff before merging.

Individual tasks can opt out or force check-mode behavior, because some modules cannot predict their effect without executing. Treat check mode as a preview, not a proof: it shows intent, but only the real run shows reality.

--diff rendering of file-level changes

Combined with check mode, --diff shows the actual file-level differences a run would produce — added and removed lines in configs, exactly like a code diff. For file-managing tasks this turns a dry run into a precise, reviewable change proposal.

Make --check --diff the default way you review any playbook that touches configuration files. It catches the "I didn't expect it to rewrite that whole file" surprises before they reach production.

changed_when and failed_when for non-idempotent commands

The shell and command modules cannot know whether they changed anything, so they report changed on every run — breaking the idempotence contract. changed_when lets you define the condition (for example, a string in stdout) that actually means "something changed," restoring honest reporting.

failed_when is the mirror: it defines what failure means for commands whose exit codes lie — a nonzero exit that is actually the expected "not found" signal, for instance. Together they let raw commands participate honestly in the changed/failed/ok vocabulary.

Why shell/command modules break idempotence and how to guard them (creates, removes)

Shell tasks are imperative steps in a declarative system: Ansible cannot diff "the state after running this script" against anything. The creates and removes arguments are the standard guards — the task is skipped if a marker file already exists (creates) or is missing (removes).

Prefer a purpose-built module over shell whenever one exists; modules encode idempotence, while shell tasks make you encode it by hand. Every shell task in a playbook should make a reviewer ask "why isn't this a module?" — and have a good answer.

Dry-run limits: modules that cannot support check mode

Some modules cannot predict their outcome without executing — anything involving external side effects, generated secrets, or API calls with non-idempotent semantics. These modules skip or approximate check mode, and the run will tell you so.

Know which of your modules these are before you trust a dry run. A clean --check on a playbook whose critical tasks all skipped prediction is a false sense of security; pair it with a staging run for those tasks.

Hands-on labs

  1. Write a raw shell task that reports changed every run, then make it idempotent with changed_when
    Watch the task report changed on three consecutive runs — the visible symptom of broken idempotence. Then add a changed_when condition tied to real output, and watch the second and third runs go green.
  2. Run a file-management playbook with --check --diff and reconcile the preview with the real run
    Preview first, note every predicted change, then run for real and compare. The preview and the reality should match exactly; any divergence is a lesson about check-mode limits.
  3. Compare three runs of the same playbook and record the changed-count decay to zero
    Run the playbook three times and record the changed tally each time: N, then smaller, then zero. That decay curve is the signature of a healthy idempotent playbook.
  4. Use failed_when to treat a nonzero exit code as success for an idempotence probe
    Write a probe command whose nonzero exit means "already in desired state" and teach the task to interpret it correctly. Exit codes are data; failed_when is how you decode them.
  5. Identify one module in your playbook that ignores check mode and add a guard task
    Find a task whose check-mode output is uninformative, and add a preceding guard — a stat check or a when condition — so the dry run stays meaningful. Not every module cooperates; your playbook design must compensate.

Self-check

  • Your playbook reports changed on every run for one task — list three candidate causes in order of likelihood
  • What does --diff show for a task that changed nothing, and why?
  • When is failed_when preferable to ignore_errors?

Module 7

ansible-vault and Secrets Handling

Learning objectives

  • Encrypt sensitive variables with ansible-vault and use them in playbooks
  • Design a vault password workflow that keeps secrets out of version control
  • Audit a playbook for secret leakage in logs and output

Key concepts, explained

ansible-vault encrypt/decrypt/view/edit/rekey operations

ansible-vault encrypts files and strings with AES, turning secrets into ciphertext that is safe to store alongside code. The subcommands cover the lifecycle: encrypt and decrypt for whole files, view for reading without decrypting to disk, edit for in-place editing through a decrypted temp file, and rekey for rotating the password.

Encrypted files remain usable by Ansible directly — playbooks reference them like any vars file, and Ansible decrypts in memory at runtime. The workflow never requires plaintext secrets to rest on disk outside the editor's temp file.

Encrypting whole files vs encrypt_string for single values

Whole-file encryption suits files that are mostly secrets — a group_vars file holding database passwords, for example. encrypt_string encrypts a single value inline in an otherwise readable playbook, keeping the surrounding structure visible for review.

Prefer whole files when most of the file is sensitive, and encrypt_string when one value in a readable file needs protection. Either way, the ciphertext is committed and the password never is.

Vault password sources: prompt, password files, vault-id labels

Ansible needs the vault password at runtime, and there are three honest ways to supply it: an interactive prompt (--ask-vault-pass) for human runs, a password file (--vault-password-file) for automation — ideally an executable script that fetches the password from a real secret store — and vault-id labels that map different passwords to different vault identities.

The password file is the sharp edge: if it holds the plaintext password and gets committed, the encryption is theater. Treat the vault password with the same care as the secrets it protects.

no_log to suppress sensitive task output

Tasks that handle secrets — registering a password, templating a config — can leak values into logs and console output. no_log: true on a task suppresses its arguments and results from all output, closing that leak.

Apply no_log to any task that touches secret values, and verify with -v output that nothing sensitive appears. Logging is a secret-handling surface; treat it as one.

Separation of secrets from code in version control

The vault model's whole point is that ciphertext can live in git while the password lives elsewhere. Secrets are versioned (so changes are reviewed and auditable) without being exposed (because the password is not in the repo).

This separation must be total: no plaintext secrets in playbooks, no password files committed, no secrets in CI logs. Audit regularly — a single committed password file voids the entire scheme.

Multi-vault-id setups for per-environment secrets

Vault IDs let different environments use different passwords: the production vault is encrypted with the production password, staging with staging's. A playbook run supplies the relevant --vault-id, and Ansible decrypts only what that identity can open.

This limits blast radius: a compromised staging password does not decrypt production secrets. It also models real organizational boundaries — the people who can read production secrets are not everyone with repo access.

Rotation practice: rekeying and updating dependent vars

Rotation means generating a new secret, updating every place that consumes it, and rekeying the vault files to a new password. Because vault files are versioned, the rotation itself is a reviewed change with a clear before and after.

Practice rotation on a schedule, not just after incidents: scheduled rotations prove the procedure works when nothing is on fire, which is exactly when you want to discover that a consumer was missed.

Hands-on labs

  1. Create an encrypted group_vars file holding a service password and consume it in a task
    Encrypt a vars file with ansible-vault create, reference the variable in a task, and run the playbook with the password prompt. The task should succeed while the committed file stays ciphertext.
  2. Convert a plaintext password in a playbook to an inline vault-encrypted string
    Take a working playbook with a plaintext secret, replace the value with ansible-vault encrypt_string output, and re-run. The playbook stays readable; only the value becomes opaque.
  3. Run a playbook with a vault password file and confirm no secret appears in -v output
    Supply the password via a file, run with verbose output, and grep the output for the secret value. The absence of the value is the test — and add no_log where the test fails.
  4. Mark a secret-registering task no_log: true and verify redaction
    Register a task result containing a secret, first without no_log to see the leak, then with it to see the redaction. The contrast makes the setting unforgettable.
  5. Rekey a vault file with a new password and re-run the playbook end to end
    Rotate the vault password with rekey, confirm the old password no longer works and the new one does, and run the full playbook. Rotation is a procedure; rehearse it.

Self-check

  • A colleague commits the vault password file — what is the blast radius and the recovery plan?
  • When should a value be encrypt_string in the playbook vs a separate encrypted vars file?
  • How do you prove a run did not leak a secret into the log?

Module 8

Troubleshooting Playbooks in Production

Learning objectives

  • Diagnose failed runs from output, verbosity levels, and return data
  • Isolate faults to inventory, connectivity, privilege, or task logic
  • Build repeatable debugging habits for fleet-wide changes

Key concepts, explained

Reading task results: msg, rc, stdout/stderr, changed

Every task result is a small data structure: msg carries the human-readable error, rc the return code, stdout and stderr the command output, changed whether anything was altered. The habit is to read the result bottom-up — the msg first, then the output that explains it.

Most Ansible errors are precise if you read them fully: the failing task name, the host, and the module's own error message usually name the cause. Skimming to the recap and guessing wastes the information Ansible already gave you.

Verbosity ladder (-v to -vvvv) and what each level reveals

Verbosity is a ladder: -v shows task results and basic facts, -vv adds more detail, -vvv exposes the SSH connection layer — the exact command Ansible ran to connect — and -vvvv adds connection-level debugging including SSH's own verbose output.

Climb one rung at a time. Connection failures want -vvv; task-logic failures rarely need more than -v. Reaching for -vvvv first buries the signal in SSH internals.

Common failure classes: unreachable (SSH), permission (become), undefined variable, Jinja2 syntax

Production failures fall into a small taxonomy. Unreachable means SSH failed — keys, network, host keys. Permission errors after become mean sudo is misconfigured. Undefined variable means a name was misspelled or never defined at that precedence level. Jinja2 syntax errors mean the template is malformed.

Classify first, then investigate: each class has a different fix location (inventory, target sudoers, variable layout, template file). Misclassifying an SSH failure as a playbook bug sends you debugging the wrong layer.

debug module and strategic task isolation (--start-at-task, --step)

The debug module prints variable values mid-run — the fastest way to answer "what does Ansible think this variable is right now?" Add debug tasks temporarily, run, read, and remove them; they are scaffolding, not permanent fixtures.

For long playbooks, --start-at-task resumes from a named task instead of re-running everything, and --step pauses before each task for confirmation. Together they turn a 200-task run into a debuggable sequence.

Retrying failed hosts with --limit @retry-files

When a run fails on some hosts, Ansible writes a retry file listing them. Re-running with --limit @<retryfile> targets exactly those hosts, so the fix run is surgical rather than fleet-wide.

This pairs with idempotence: the retry re-runs the playbook, and already-converged hosts report no changes. Retries are safe precisely because the playbook is idempotent — another reason the contract matters.

Idempotent re-runs as the safe retry strategy

The safest response to a half-failed run is usually to fix the root cause and re-run the whole playbook: converged hosts stay converged, failed hosts get another chance, and no manual per-host surgery diverges the fleet.

Manual fixes on individual hosts are the enemy of this model — they create snowflakes that the next playbook run may or may not reconcile. Prefer the re-run; reserve manual intervention for the cases automation genuinely cannot express.

Callback plugins and structured output for post-mortems

Callback plugins control how Ansible presents results: the default is human-readable, but JSON or YAML callbacks emit structured output for machines. A JSON callback report from a failed run gives per-host, per-task failure data you can query programmatically.

For post-mortems and fleet-wide analysis, structured output beats scrolling terminal history. Generate it for significant runs, extract the failure counts, and file it with the incident record.

Hands-on labs

  1. Inject four faults (bad key, bad sudo, undefined var, Jinja2 typo) and classify each from its error alone
    Break one thing at a time and read only the error output to name the failure class. This builds the pattern-matching reflex that makes production debugging fast.
  2. Use -vvv to trace an SSH connection failure to its root cause
    Break SSH access deliberately, then climb the verbosity ladder until the output shows the exact failing step — key rejection, host key mismatch, or network timeout. The -vvv output is the map.
  3. Resume a half-failed run with the generated retry file limited to failed hosts
    Run a playbook that fails on a subset of hosts, then re-run with --limit @retryfile after fixing the cause. Watch the previously-failed hosts converge while the healthy ones report no changes.
  4. Add debug tasks that dump the three variables most likely to be wrong, then remove them
    When a task misbehaves, the fastest diagnosis is printing the variables it consumes. Practice the add-run-read-remove cycle until it is muscle memory.
  5. Produce a JSON callback report for a run and extract per-host failure counts
    Run with a JSON callback, then query the output for per-host failed-task counts. Structured post-mortem data is a professional habit worth building early.

Self-check

  • Distinguish an unreachable host from a failed task in the recap output — what differs?
  • A run fails on 2 of 20 hosts with a permission error — what is your isolation sequence?
  • Why is re-running an idempotent playbook usually safer than targeted manual fixes?
