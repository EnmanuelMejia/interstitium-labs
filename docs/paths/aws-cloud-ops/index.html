Role loop

Think like the engineer who owns the cloud bill and the pager: design → deploy → monitor → respond → optimize. Every phase trains that loop: architect it, ship it, watch it, fix it when it wakes you, and make it cheaper next quarter.

Gamified mastery modules — four phases

Sixteen modules in four gated phases — what you learn, and why it matters in production or in an interview. Each phase ends with a gate: quiz, hands-on lab, timed sim, and oral defense.

  1. Phase 1

    Foundations — think in cloud

    • Cloud mental model

      Regions, availability zones, and the shared-responsibility model. Why it matters: every AWS decision is a region decision first, and every outage postmortem starts with “which AZ?”

    • IAM

      Users, roles, policies, and least privilege. Why it matters: IAM mistakes are how breaches happen and how surprise bills are born.

    • CLI & console fluency

      Profiles, pagination, and reading the docs like a map. Why it matters: speed in the console and the terminal is operational competence.

    • Cost awareness

      Budgets, Cost Explorer, and tagging discipline. Why it matters: the cloud bill is an ops metric — nobody respects an admin who can't explain it.

  2. Phase 2

    Core — the services you will actually run

    • VPC networking

      Subnets, route tables, NACLs, and security groups. Why it matters: the network is the application boundary, and misconfigured security groups are the classic outage.

    • EC2 & compute

      Instances, AMIs, user data, and key pairs. Why it matters: EC2 remains the workhorse of cloud ops — know it cold.

    • S3 & storage

      Buckets, versioning, lifecycle rules, and encryption. Why it matters: S3 holds half the internet's data; versioning is your undo button.

    • RDS & managed data

      Managed databases, backups, and restore drills. Why it matters: data loss is the unforgivable failure — backups you have tested are the only backups that count.

  3. Phase 3

    Advanced — scale and defend

    • Load balancing & autoscaling

      ALB target groups and autoscaling policies. Why it matters: elasticity is the entire point of cloud — manual scaling is a failure mode.

    • Monitoring

      CloudWatch metrics, alarms, and log insights. Why it matters: you cannot operate what you cannot see, and alarms are how systems tap you on the shoulder.

    • Security services

      KMS, WAF, and GuardDuty literacy. Why it matters: defense in depth is an ops job, and auditors love evidence.

    • Delivery pipelines

      How code reaches the cloud through CI/CD. Why it matters: ops owns the path to production — map this to the DevSecOps pipeline sequence.

  4. Phase 4

    Proof — operate like it's production

    • Incident drill

      A degraded app traced through metrics to logs to fix. Why it matters: on-call is diagnosis under pressure, and pressure is trainable.

    • Cost optimization

      Find the waste, rightsize the fleet, propose the savings. Why it matters: FinOps is an ops skill now, and it gets noticed by leadership.

    • HA design review

      Redesign a single-AZ app for multi-AZ resilience. Why it matters: resilience is designed, not hoped for.

    • Evidence portfolio

      Architecture write-ups with tradeoff notes. Why it matters: interviews are won with stories, and stories need artifacts.

Module → lesson map

There is no single AWS lesson sequence on this site, so the map is honest about where each module lives: SuperLab scenarios, your own account, vendor Skill Builder, and the DevSecOps pipeline sequence for delivery topics.

  • Foundations

    Cloud concepts, IAM, and CLI fluency — practiced in SuperLab and your own AWS account; vendor Skill Builder for guided console labs

  • Core services

    VPC, EC2, S3, and RDS — hands-on in SuperLab with architecture notes you write yourself

  • Advanced

    Load balancing, monitoring, and security — SuperLab labs; delivery pipelines → DevSecOps pipeline sequence

  • Proof

    Incident drills, cost optimization, and HA design — SuperLab scenarios plus your portfolio write-ups

Assessments

Assessment here is evidence, not watch-time. Each phase ends with a gate: a short adaptive quiz that finds your weak spots, a SuperLab task lab graded on outcome (did the thing actually work?), and a timed troubleshooting sim where you diagnose a broken system against the clock. Missed concepts remediate into /adapt/ fringe sessions. Cloud incident sims live in the drill library. Oral defense matters too: after every phase you explain a past failure out loud in STAR format, because interviews are oral exams.

Capstone

Capstone: “Launch weekend.” Design and deploy a multi-AZ web stack from your own notes: VPC with public and private subnets, an application load balancer, an autoscaling group, a managed database with tested backups, and static assets on S3. Add CloudWatch alarms, a cost report with a monthly estimate, and an incident runbook for the two most likely failures. Tear it down cleanly afterward — no orphaned resources left behind.

FAQ

What should I know before starting?

Basic Linux shell comfort and general networking ideas (what an IP address and a firewall do). No prior AWS needed.

How long does it take?

Self-paced. The four phases are sequential and gated — advance when you clear each gate.

Is this an AWS certification?

No. This is independent preparation built by Interstitium Labs — not affiliated with or endorsed by Amazon Web Services, and it confers no certificate. It builds real operational skill so vendor credentials, if you pursue them, rest on something solid.

Are these real exam questions?

No. All quizzes, drills, and sims are original practice material. We never reproduce exam questions.

Do I need to pay for AWS?

Console labs can be done on the free tier with strict budget alarms, or in guided vendor Skill Builder labs.
