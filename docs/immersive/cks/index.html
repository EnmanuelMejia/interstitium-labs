CKS paper — secure it by typing.

The real CKS is a performance-based exam: task statements, a terminal, a clock. This paper works the same way across all six CNCF CKS domains. You run the CIS benchmark and fix what it flags, lock down RBAC and NetworkPolicy, confine with AppArmor, enforce Pod Security, sandbox with gVisor, gate images with admission policy, Trivy, an SBOM, cosign, kubesec and KubeLinter, and turn on audit logging and Falco. Each task gets its authored 3D scene and a shell already in the task’s starting state. Partial credit per verified checkpoint, scored by the published CKS domain weights. It is a simulated shell over an in-browser rules engine: not a live cluster, not killer.sh, not the CNCF exam, and none of those tools really run here.

Start a paper

  • Bank: ? typed CKS tasks across the 6 domains: Cluster Setup 15 · Cluster Hardening 15 · System Hardening 10 · Minimize Microservice Vulnerabilities 20 · Supply Chain Security 20 · Monitoring, Logging & Runtime Security 20. Domains are drawn heaviest first, so a 6-task paper covers every domain and a 3-task paper covers the three 20% domains.
  • Seeded variants: every paper re-draws each task’s names: namespace, user, ServiceAccount, Secret, AppArmor profile, service port, registry host and image tags. So a paper is not a replay of the free-play drills. The shell speaks the paper’s names, and a drill-replay name simply does not exist in that paper. For 21 tasks these are surface variants over the same staged fault.
  • Seeded fault variants + two nodes: the three kube-bench tasks also draw which fault is staged and where: the controlplane kubelet, or the kubelet on node01 (a worker you reach with ssh node01, with its own config file and no API server or etcd), anonymous access vs a ServiceAccount token under AlwaysAllow, or one finding per node. kube-bench audits only the node it runs on, so you have to work on the right host. The worker’s name is drawn per paper too. That is 7 authored faults over 3 tasks, not procedurally generated faults. CIS check ids, kubelet ports and system paths stay real.
  • Cluster contexts: each scene on a paper is its own cluster with its own kubectl context, and the task panel names the context for every task. The first task starts on a context no task uses, and every later task starts wherever you left the shell. kubectl config get-contexts, current-context and use-context work. Any kubectl command typed on another context goes to an empty stand-in cluster and verifies nothing, as forgetting the switch costs you the task on the real exam. The 3D scene is the task’s cluster, so it renders dimmed until kubectl points at it (a study cue the exam does not give). Only kubectl depends on the context: ssh, kube-bench and lab files do not.
  • Every paper gives 6 minutes per task, the pace of the real exam (15–20 tasks in 2 hours, per the Linux Foundation’s CKS instructions).
  • Each task gives you the statement only, with no step list. check counts verified checkpoints. hint gives the next one at half credit. solution stays off until the results screen.
  • The score is weighted by the CKS domain weights over the domains this paper tested, and the domains it did not test are listed, never counted as passed. The weakest domain is the one with the most points at stake. The 67% pass bar mirrors the published CKS passing score as a study bar. It is not a CNCF result.
