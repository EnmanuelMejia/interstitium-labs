--- NOTE: Roles, Linux, Git: the foundation
The **seven roles** (build, release, operate, observe, secure, automate, collaborate — boundaries vary by org) give the path its sequence. **Linux/shell/Git for DevOps**: administration fluency, scripting, and **branching strategies** (trunk-based vs GitFlow — know the trade-offs), PR review discipline, GitHub Actions basics, monorepo vs polyrepo.

- Golang/Python for tooling: glue languages for operators — CLIs, controllers, automation scripts
- Branching: trunk-based (small teams, fast) vs GitFlow (release trains, overhead) — match the strategy to the release cadence
- PR review: small diffs, automated checks first, human review for design — review latency is a DORA metric in disguise
- Actions basics: workflows, jobs, runners, secrets — CI as code, versioned with the repo

--- NOTE: Docker and CI/CD: build and ship
**Docker**: images and **layers** (each instruction a cached layer — order Dockerfile for cache hits), the Dockerfile (multi-stage builds: compile in one stage, ship a slim runtime), registries (tagging discipline: immutable tags for releases).

**CI/CD with Jenkins**: pipeline as code (Jenkinsfile), agents and stages, artifact management (immutable artifacts, SBOMs), **security scanning gates** (SAST/dependency scan in the pipeline — fail the build, not the audit).

- Multi-stage: `FROM golang:1.22 AS build` → `FROM gcr.io/distroless/static` — 800MB becomes 15MB
- Layer caching: put slow-changing instructions (deps) early, fast-changing (source) late
- Pipeline stages: lint → test → build → scan → push → deploy — gates between each, not after all

--- NOTE: Kubernetes, Ansible, observability: run it
**Kubernetes foundations**: pods, services, deployments (rolling updates), ConfigMaps/secrets, ingress, Helm basics (charts as packages).

**Ansible**: playbooks for fleet state, roles, Vault for secrets, idempotent operations (cross-link: IL-04 Module 4 is the deep dive).

**Observability**: metrics and **PromQL** (`rate(http_requests_total[5m])`), alerting (alert on symptoms, not causes), Grafana dashboards (RED/USE methods), Loki for log aggregation.

- Deployment strategy: rolling update with readiness probes — zero-downtime is a probe configuration
- ConfigMaps vs secrets: secrets are base64, not encrypted — know the actual security boundary (etcd encryption, RBAC)
- Alerting: page on user-facing symptoms (latency, error rate); ticket on causes (disk filling)
- The milestone arc: containerize → pipeline → deploy → observe — each tool proven by a running system

--- NOTE: KCNA + CKA: architecture and administration
**KCNA**: Kubernetes architecture (control plane vs nodes), cloud-native principles (microservices, immutable infra), GitOps concepts, observability basics — the vocabulary exam.

**CKA**: **etcd** (the cluster's brain — backup/restore it), workloads and scheduling (taints/tolerations, affinity, resource requests/limits), services and networking (ClusterIP/NodePort/LoadBalancer, DNS, CNI at concept level), storage (PV/PVC, StorageClasses), and **troubleshooting** (the largest hidden domain — broken clusters, fix them live).

- etcd backup: `etcdctl snapshot save` — know the flags; restore is the tested skill
- Requests vs limits: requests schedule, limits throttle/kill — set requests honestly, limits defensively
- Troubleshooting method: `kubectl describe` → `kubectl logs` → events → kubelet — the same order every time
- CKA is 2 hours, performance-based, with docs allowed — speed with kubectl (`-o yaml --dry-run=client`, aliases) is the exam skill

--- NOTE: CKAD: the developer's exam
**CKAD**: application design (multi-container pods, init containers), deployment configuration (probes, rolling updates, rollbacks), observability for developers (logs, metrics endpoints), services and networking for apps.

- Imperative speed: `kubectl run/create/expose` with `--dry-run=client -o yaml > pod.yaml` — generate, don't hand-write
- Probes: liveness (restart me) vs readiness (don't send traffic) vs startup (slow starters) — misconfigured probes are the #1 self-inflicted outage
- ConfigMaps/secrets as env vs volumes: env for simple, volumes for files and rotation
- 2 hours, performance-based — the fastest typists with the best aliases win; it's a feature, not a bug

--- NOTE: CKS + KCSA: the security tier
**CKS** (requires CKA): cluster hardening (API server flags, etcd TLS, kubelet auth), system hardening (least-privilege OS), **supply-chain security** (image scanning, ImagePolicyWebhook, signed images with cosign), runtime security (**Falco** rules, seccomp profiles, AppArmor).

**KCSA**: cloud-native security overview and Kubernetes security fundamentals — the associate on-ramp.

- Pod Security Standards: privileged → baseline → restricted — know what each forbids
- Falco: runtime threat detection on syscalls — write a rule that alerts on unexpected shell in a container
- seccomp/AppArmor: constrain what a compromised container can *do* — defense in depth past the image
- Admission control: the policy enforcement point — where supply-chain rules actually bite

MODULE il05-zero-trust | Zero-Trust Platform Architecture
SUMMARY: NIST SP 800-207 as the blueprint: the seven tenets, the policy engine / policy administrator / policy enforcement point, control plane vs data plane, the trust algorithm; identity as the perimeter (phishing-resistant MFA, device posture, continuous authentication, privileged access); microsegmentation and the network pillar; deployment models (device agent/gateway, enclave, resource portal) and migration from perimeter security.

OBJECTIVES:
- State the seven zero-trust tenets and map them to controls.
- Design identity-first access: phishing-resistant MFA, device posture, continuous auth.
- Plan microsegmentation: east-west inspection, software-defined perimeters, encrypted everything.
- Choose a deployment model and sequence migration from perimeter security.

--- NOTE: SP 800-207: tenets and components
The **seven tenets**: (1) all data sources/services are resources; (2) all communication secured regardless of location; (3) per-session access grants; (4) dynamic policy (identity + device + behavior); (5) enterprise monitors all asset integrity; (6) auth is dynamic and strictly enforced; (7) maximum enterprise-collected info improves posture.

**Components**: **Policy Engine** (decides), **Policy Administrator** (executes: provisions credentials/config), **Policy Enforcement Point** (the gate). **Control plane** (decisions) vs **data plane** (traffic) — separate them.

**Trust algorithm**: the PE's logic — static rules vs dynamic behavioral scoring; know that 'algorithm' here means policy logic, not ML magic

- 'Never trust, always verify' is the slogan; per-session least-privilege grants are the mechanism
- The PEP is wherever the decision is enforced: gateway, agent, or enclave — placement follows the deployment model

--- NOTE: Identity as the perimeter
When the network perimeter dissolves, **identity becomes the boundary**: **phishing-resistant MFA** (FIDO2/WebAuthn — not SMS), **device posture** (managed, patched, encrypted, EDR-healthy), **continuous authentication** (re-verify on risk signals, not just at login), **privileged access** (just-in-time elevation, session recording, vaulted credentials).

- MFA strength ladder: FIDO2 > TOTP app > SMS (SIM-swap) > none — phishing resistance is the criterion
- Device posture as a policy input: unhealthy device = reduced access, automatically
- Privileged access workstations (PAWs) and tiering: don't administer the kingdom from a browsing laptop
- Cross-link: IL-11's identity defense modules go deeper — this is the platform-architecture lens

--- NOTE: Microsegmentation, models, migration
**Microsegmentation**: workload-to-workload policy (east-west), **software-defined perimeters** (authenticate first, connect second — the network is dark until verified), **east-west inspection**, **encrypted everything** (mTLS between services).

**Deployment models** (SP 800-207): device **agent/gateway**, **enclave** (per-resource PEPs), **resource portal** (gateway to legacy).

**Migration**: inventory → classify → pilot high-value resources → expand; **maturity steps** (CISA's model: traditional → advanced → optimal); **measuring**: policy coverage %, MFA enrollment, mean time to grant/revoke.

- Start where the crown jewels are — migrate the highest-value resources first
- Measure the migration: % of access decisions via PE/PEP, % phishing-resistant MFA, lateral-movement test results
- Zero trust is a strategy executed over years — the exam tests the models, the job tests the patience

CARDS:

Microsegmentation secures which traffic? => East-west (workload-to-workload) — the lateral-movement surface.
Migration first step? => Inventory and classify — then pilot on the highest-value resources.

MODULE il05-terraform | Terraform: Infrastructure as Code
SUMMARY: HashiCorp Terraform through the Associate (003) exam: HCL and the core workflow (resources, providers, variables, outputs, plan/apply), state fundamentals then remote state with locking, module composition, workspaces, import and refactoring — plus IaC concepts and exam-day logistics.

OBJECTIVES:
- Write HCL: resources, data sources, variables, outputs, locals.
- Run the workflow: init → validate → plan → apply → destroy.
- Manage state: remote backends, locking, import, refactoring moves.
- Compose modules; use workspaces; pass the Terraform Associate exam.

--- NOTE: HCL and the core workflow
**Resources** (`resource "aws_instance" "web"`) declare desired state; **providers** talk to APIs; **data sources** read existing infra; **variables/outputs/locals** parameterize.

**Workflow**: `init` (providers/modules) → `validate` (syntax) → `plan` (the diff — READ IT) → `apply` (execute) → `destroy` (teardown). The plan is the code review of infrastructure — never auto-apply blind in production.

- `terraform plan -out=tfplan` then `apply tfplan`: the saved plan is the auditable artifact
- Data sources bridge the brownfield: read the existing VPC instead of importing everything day one
- `count` vs `for_each`: for_each for named instances (stable keys); count for identical counts (fragile on removal)

--- NOTE: State: the crown jewels
**State** maps config to real resources — lose it and Terraform forgets your infrastructure. **Remote state** (S3 + DynamoDB lock, Terraform Cloud, GCS): shared, **locked** (no concurrent applies corrupting state), versioned.

**Import**: `terraform import aws_instance.web i-12345` brings brownfield under management (then write the config to match). **Refactoring**: `moved` blocks rename without destroy/recreate.

- State locking: DynamoDB (or native S3 locking now) — concurrent applies without locking corrupt state
- Never hand-edit state except via `terraform state mv/rm` — and back it up first
- Workspaces: `terraform workspace new prod` — same config, separate states (fine for small setups; separate configs for serious multi-env)

--- NOTE: Modules and the Associate exam
**Module composition**: root module calls child modules (`source = "./modules/vpc"` or registry); inputs via variables, outputs bubble up. Registry modules: vet them like dependencies.

**Terraform Associate (003) domains**: IaC concepts, Terraform basics, workflow (the largest), state, modules — plus exam-day logistics.

- Module design: thin root, composable children; outputs for everything the next module needs
- `terraform fmt` and `validate` in CI — IaC gets the same hygiene as app code
- Exam tip: the test loves 'what happens when' — drift (config ≠ real), taint/replace, lock contention. Reason from the state model, not memorization

CARDS:
plan → apply discipline? => Read the plan like a code review. Save it (-out) for the auditable artifact. Never blind-apply in prod.
State locking prevents? => Concurrent applies corrupting the state file — DynamoDB/S3-native locks serialize runs.
count vs for_each? => for_each: named instances, stable on removal. count: fragile index shifts when one is removed.
import then what? => Write matching config immediately — import only binds state; the config must describe it.
moved block? => Refactor resources (rename/module-shift) without destroy/recreate.
Associate exam's largest area? => The workflow (init/plan/apply) + state — reason from the state model.

MODULE il05-aws-architect | AWS Solutions Architecture: SAA-C03
SUMMARY: The Solutions Architect Associate: resilient architectures (multi-AZ, decoupling, backup/DR), high-performing (compute/storage/database selection, caching, elasticity), secure applications (IAM, KMS, security groups/NACLs, WAF/Shield), cost-optimized (pricing models, S3 tiers, right-sizing) — plus Terraform reference stacks and exam prep.

OBJECTIVES:
- Design multi-AZ resilient architectures with decoupled components.
- Select compute/storage/database services by workload requirements.
- Apply IAM, encryption, and network security to architectures.
- Optimize cost: pricing models, storage tiers, and right-sizing.

--- NOTE: Resilient: design for failure
**Multi-AZ** (not just multi-instance): ALB across AZs, RDS Multi-AZ, S3's 11-9s. **Decouple**: SQS/SNS/EventBridge between tiers — a failed consumer retries instead of a failed request erroring. **Backup/DR**: RTO/RPO drive the choice (backup-restore → pilot light → warm standby → multi-site active).

- AZs are isolated failure domains — single-AZ is a hope, not a design
- Decoupling turns cascading failures into queue depth — monitor the queue, not just the app
- RTO/RPO first, then pick the DR pattern — the business numbers choose the architecture

--- NOTE: Performant + secure: choose and protect
**High-performing**: compute (EC2 vs Lambda vs Fargate vs ECS — by workload shape), storage (EBS gp3/io2, EFS, S3, instance store — by access pattern), databases (RDS vs Aurora vs DynamoDB — by query pattern), **caching** (CloudFront, ElastiCache — cache at every layer), **elasticity** (Auto Scaling on the right metric).

**Secure**: IAM (least privilege, roles not users for apps, permission boundaries), **KMS** (envelope encryption, CMKs), security groups (stateful) vs NACLs (stateless), WAF/Shield.

- Database choice is query-pattern choice: relational+complex joins → Aurora; key-value at scale → DynamoDB
- SGs are stateful (return traffic allowed); NACLs stateless (explicit both directions) — the classic exam trap
- Cache invalidation: TTLs + versioned keys — there are only two hard problems

--- NOTE: Cost-optimized + exam prep
**Cost**: pricing models (On-Demand vs Reserved vs Spot vs Savings Plans — by steadiness), **S3 tiers** (Standard → Intelligent-Tiering → Glacier — by access recency), right-sizing (Compute Optimizer), data transfer awareness (same-AZ free, cross-region metered).

**Terraform reference stacks**: the module's IaC patterns for each architecture — VPC, ALB+ASG, RDS, S3+CloudFront as composable modules.

**SAA-C03 prep**: scenario questions with 2 plausible answers — eliminate by constraint (cost? resilience? ops overhead?). Domain mapping: resilient (Modules: resilient), performant, secure, cost-optimized — the exam mirrors these four pillars.

CARDS:
Multi-AZ vs multi-instance? => Instances in one AZ share a failure domain. Multi-AZ is the resilience unit.
Decoupling benefit? => Failures become queue depth, not errors — consumers retry instead of requests failing.
SG vs NACL? => Security groups: stateful, instance-level. NACLs: stateless, subnet-level, explicit both directions.
DynamoDB vs Aurora? => Key-value at scale → DynamoDB. Complex relational joins → Aurora. Query pattern decides.
S3 Intelligent-Tiering? => Auto-moves objects between access tiers — for unpredictable access patterns.
Spot vs Reserved? => Spot: interruptible, cheapest — batch/fault-tolerant. Reserved/SP: steady-state commitment discount.

MODULE il05-hashicorp-vault | Vault & Consul: Secrets and Service Networking
SUMMARY: HashiCorp Vault (secrets engines: KV, dynamic database/AWS creds, PKI, transit; auth methods: userpass/LDAP/OIDC/Kubernetes/AWS; policies; operations: unseal, raft, DR replication) and Consul (service discovery: catalog, DNS/HTTP, health checks; service mesh: Connect, intentions, gateways) — through the Vault Associate and Consul Associate exams.

OBJECTIVES:
- Run Vault: engines, auth, policies, unseal/raft operations.
- Issue dynamic secrets and manage PKI/transit engines.
- Discover services with Consul: catalog, DNS, health checks.
- Mesh services: Connect intentions, gateways, mTLS.

--- NOTE: Vault: engines and auth
**Secrets engines**: **KV v2** (versioned static secrets), **dynamic** (database creds, AWS STS — leased, auto-revoked), **PKI** (internal CA — short-lived certs), **transit** (encryption-as-a-service — data never leaves your app).

**Auth methods**: userpass/LDAP (humans), **OIDC** (SSO), **Kubernetes** (pod service accounts), **AWS** (IAM-based) — machines authenticate as themselves.

**Policies**: HCL paths with capabilities (`read`, `list`, `create`, `update`, `delete`, `sudo`) — least privilege for secrets.

- Dynamic secrets: credentials that expire — the leaked-credential problem solved structurally
- Transit engine: Vault encrypts/decrypts without storing data — crypto without key-management pain
- Policies are deny-by-default — nothing is readable until a policy allows it

--- NOTE: Vault operations reality
**Unseal**: Shamir keys or **auto-unseal** (KMS) — plan this before production. **Raft** integrated storage (no Consul needed anymore). **DR replication** (disaster recovery clusters), **performance replication** (read scaling).

- Auto-unseal via cloud KMS: operators never handle key shards — the sane default
- Raft snapshots: `vault operator raft snapshot save` — back up the encrypted store
- Seal migration and rekey: practice in staging — unseal ceremonies fail at 3 AM otherwise
- Monitoring: seal status, leader changes, token expiry storms — Vault is critical path, watch it like one

--- NOTE: Consul: discovery to mesh
**Service discovery**: **catalog** (registered services), **DNS** (`web.service.consul`) and **HTTP** APIs, **health checks** (only healthy instances get traffic).

**Service mesh (Connect)**: **mTLS** between services (automatic, rotated), **intentions** (allow/deny service-to-service — microsegmentation for east-west), **gateways** (mesh/ingress/terminating).

**Associate exams**: Vault Associate (engines, auth, policies, tokens/leases) and Consul Associate (discovery, mesh concepts) — concept + CLI, hands-on flavored.

- Intentions: `consul intention create -allow web api` — the firewall rule for services
- Health checks gate discovery — unhealthy never receives traffic, no LB config needed
- KV in Consul vs Vault: Consul KV is config (not encrypted by default) — secrets go in Vault

CARDS:
Dynamic secrets solve? => Leaked credentials — short-lived, auto-revoked, per-request. No long-lived passwords.
Transit engine? => Encryption-as-a-service: Vault encrypts/decrypts; your data never lands in Vault.
Vault policy default? => Deny — nothing readable until a policy explicitly allows.
Consul DNS name? => web.service.consul — DNS interface to the service catalog.
Intentions? => Allow/deny rules for service-to-service traffic — microsegmentation for the mesh.
Consul KV vs Vault for secrets? => Consul KV is config (plaintext default) — secrets belong in Vault.
